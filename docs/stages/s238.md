# s238: the compile gates change at runtime, from the monitors and the CLI, and are kept

Summary: The compile CPU gate, settle time, job count, idle-kill time, stall limit and the memory and disk floors can now be changed while masond runs (`mason resources gate`, `POST /resources/gate`, WS `SetGate`, steppers in both monitors) and are kept across restarts in `gates.kv`.

**Problem.** On 2026-11-13 the owner wanted `compile_cpu_max` at 70 "now"; `resources.toml` is read once, so it took a restart, which kills every step host (#267).

**Change.**
- `Broker::set_gate(name, Some(v) | None)` (`sched.rs`) checks the value with the bounds `parse_resource_cfg` holds (`compile_cpu_max` 1–100; the others whole numbers, 0 or more, and the three u32 ones no larger than u32), applies it to `State` and runs a `pass`. `None` returns to resources.toml or the default. Overrides are written to `gates.kv` beside `limits.kv` and read after `resources.toml` at start, so a runtime change wins. A saved `compile` limit in `limits.kv` still wins over `compile_jobs`.
- `Broker::gates()` and the `gates` array of `GET /resources` give each gate's value, source (`default`, `resources.toml`, `runtime`), default and file value. `mason resources` prints them with how to reset.
- `POST /resources/gate {name, value}` (`value: null` resets), owner only (`x-mason-as`), recorded as an owner override of kind `gate`. WS `Cmd::SetGate` (`SetGate {name, value, reset}`, additive in `mason.proto`) maps onto it. CLI: `mason resources gate <name> <value>` / `--reset`, in `mason help`.
- masond starts the disk-stall prober even when `stall_ms = 0`, so the owner can turn that gate on at runtime (0 still means off).
- Monitors (Swift and Compose): in the Compilation section a CPU-gate stepper (steps of 5, 10–100) and a settle stepper (steps of 5, 0–600), and a daemon refusal (`lastResult`) shown beside them. `clients/features.toml` has `runtime-gates`, done in both.

**Not done.** The "More limits" list of the other gates in the monitors (optional in the ticket): they are settable through the CLI and API only. `order.max_wait_s` (#287) does not exist on this base; when it lands it should be added to `GATES`.

**Trust.** `sched.rs` and `clients/features.toml` are in `PROTECTED`. Existing gates become adjustable by the owner at runtime; no default (CPU gate stays 50), bound or meaning changes, and nothing is loosened.

**Verified.** `run_check` scoped to `gate` (new broker, persistence and HTTP tests), and the swift-clients and compose-clients suites passed in the check.
