# Stage 234: monitor views read the broker's wait reasons from a snapshot

Summary: The broker publishes every waiting task's explanation after each pass, and `explain_task` and the monitor views read that snapshot instead of taking the broker lock once per row.

See decision 0229. `Broker::pass` ends by calling `publish_waits`, the single place the snapshot (`RwLock<Arc<BTreeMap<TaskId, String>>>`, swapped, never held during work) is written; `Broker::waits_snapshot()` returns the `Arc`, `Ctx::new` takes it once per build, and `why_waiting` is a map lookup. Tests: `explain_task_reads_the_snapshot_without_the_broker_lock` (sched.rs) and `tests/waits_snapshot.rs` (21 tasks, 20 waiting, at most one broker lock per sidebar + task-detail build). Exit script: `scripts/exit/s234.sh`.

Not verified: the live WebSocket behaviour with 36 jobs (the exit script runs the tests, not a socket client), and the cost of the extra `waits_gated` per pass (the companion task reduces passes).
