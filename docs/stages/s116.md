# Stage 116: the disk-full alert works when the store cannot be written

Summary: When the store refuses writes, alerts are served and delivered from memory (once per channel), and the table catches up, without repeats, when writes work again.

## What changed
- `notify::sync_table` (called by `attention::sync_alerts`) writes the alert table; if that fails it keeps what `alerts_now` said in memory, preserving each alert's `since`/ack.
- `notify::live_alerts` is what `GET /alerts` and `tick` read: the table's cleared rows plus memory's live list while the store is unwritable. `GET /alerts` adds `store_writable: false` and a `note`; `mason alerts` prints the note.
- `record` keeps a delivery in memory if it cannot be stored; `tick` counts those when deciding what is due, and writes them to the store when it can.
- `Store::sync_alerts_since` lets a held alert keep its `since` when the table catches up, so deliveries stay tied to the same alert.
- Injection: `notify::refuse_writes` and `POST /debug/store-writes?refuse=1|0` (only with `--debug`).
- Trust: `attention.rs` changed only in `sync_alerts` (it now calls `sync_table`); nothing about who may answer.

## Tests
`the_disk_alert_survives_a_store_that_refuses_writes_and_is_delivered_once` (daemon/tests/notify.rs); `scripts/exit/s116.sh`.

## Not verified / known limits
- Sound and speech go through the store's announcement queue; while writes are refused they are not said (not recorded as sent either), and are queued once when writes work. Only remote channels (webhook, push, email) are sent from memory.
- Acknowledging an alert needs a store write and still fails while it is refused.
- The injection switch covers the alert table, deliveries and the announcement queue; I did not test a genuinely full disk.
- Not rebased onto #65's thread move; `sync_table` and `live_alerts` are plain functions and should move with it.
