# s691: landing lints first, blames a lint red by file, and the test step has an fmt suite

Summary: Landing now runs the lint tier before the batch suites and parks the tasks whose diff touches a file the lint (or a red `ci_gates` fmt test) names, instead of bisecting the whole suite; the test step gains a fast `fmt` suite.

**Cause.** `verify` ran `run_local` (15-25 min) and linted only when it was green; a red `workspace_is_fmt_clean` then went through rerun and whole-suite bisect (batch #421: 148 min for a 3 s check).

**Change.** (1) `verify` runs `lint_checks` first and returns at once on a red, so no suite starts (also in each split run, which calls `verify`). (2) `lint_checks` records the files named by `Diff in` / `-->`; the red ladder, before its rungs, parks every active task whose footprint contains one (`blame_by_files`) and keeps the rest. When no task touches a named file the old ladder runs unchanged. (3) A batch red whose failed tests are all `ci_gates` fmt/SPDX tests runs the lint tier once to get the files and is blamed the same way. (4) `[suite.fmt]` in `.mason/mason.toml`: `cargo fmt --all -- --check`, level unit, no build, `uses = {}`, in `step.test.suites`, selected by `crates/**`. A skip of `cargo-workspace` does not cover it (skips are per suite; a skip of the whole step or of all testing still does).

**Not verified.** The ci_gates path (3) has no integration test. SPDX failures are recognised by a test name containing `spdx`, but the lint tier runs no SPDX check, so such a red falls through to the old ladder (#660 adds repository checks to the lint command). The #628 case (every task red alone, so the base's) is unchanged. The exit script runs the two integration tests, not a real scratch repository, and I did not run `fmt` against a real unformatted worktree through a test step. Trust files (`landing.rs`, `.mason/mason.toml`) change and need the owner's approval.
