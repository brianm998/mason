# s757: rank GitHub runner waiters and count other workflows' jobs (#766)

Summary: The `gha` pool now counts other workflows' running jobs (read from the Actions API with an ETag) and an account-wide `gha_ceiling` against MASON's units, landing batches wait for pool units at their landing rank, and idle debt payments wait while anything waits for a runner.

- `sched.rs`: `set_other_workflows` and the ceiling put two held entries (`Meta::Other`) in the ledger: the other workflows' jobs and the part of the `gha` limit above what the ceiling leaves. `mason resources limit gha_ceiling N` sets it (saved in limits.kv, default 20). The snapshot gains `gha` (MASON, other, ceiling) and `mason resources` prints it under the `gha` line.
- `remote.rs`/`github.rs`: `OtherWorkflows::poll` lists in-progress runs (conditional on the last ETag; a 304 changes nothing and makes no job lookups), skips `mason-run.yml`, counts `in_progress` jobs per workflow. `spawn_other_workflows` polls every 30 s.
- `landing.rs`: a batch's hold goes through `pool_needs`, so on a GitHub project it queues for runner units ranked as its first task (landing rank), as test steps (#761) and agent checks already did.
- `suites.rs`: `run_idle_debts` returns while any request waits for `gha`/`gha-macos`.

The broker already ordered `gha` waiters by rank with the passing rule, so a higher-ranked waiter is not passed by a lower one; the new test confirms it.

Not done / not verified: `debt_max` is not a setting: idle debts already run one at a time, each taking one lease unit, and I did not change how many jobs a sharded run uses. Nothing was run against the real GitHub API; the poller is tested with a fake. Task priority within a rank is the existing rank order and was not re-tested. The ceiling is applied to `gha` only, not `gha-macos`. Tests were run through `run_check` only.
