# Stage 15: GitHub, CI and PR landing

## Built
- **`adapter-api`**: the three service traits (git host, issue tracker, build system) with declared capabilities, classified errors (`classify`: 404/422/401/403 permanent; 429, rate-limit 403 and 5xx not), the conditional-polling state machine (`Poller`: ETag, doubling capped backoff, a rate limit waits as long as it said, a permanent error stops the poll until a refresh), the HTTP seam (`Curl`, `Recorded`), conformance kits for each trait, and webhook signature verification (SHA-256 and HMAC written and tested against NIST and RFC 4231 vectors).
- **`adapters`**: `GitHub` as host (PRs, check runs, reviews, merge, the merge queue's GraphQL mutation), tracker (Issues, with ETags) and build system (Actions, found by commit), `FakeHost` and the generic `CommandCi` (the fake host and CI of the exit test, and Part 11's no-code adapter), `workflow_problems` / `workflow_problems_at`.
- **The landing engine, all seven modes.** `direct-ci` and `local-only-ci` push `mason/ci/<project>-b<batch>-<n>`, run CI on it, delete it; `pr-each`, `pr-batch` and `host-queue` open a PR from `mason/pr/...`, wait for its checks, any required review, and the host's merge (or its queue). A CI or PR red goes to the same ladder, with each probe of a bisection a candidate ref or PR; a moved base folds in the new tip and runs CI again; everything put outside is recorded the moment it is pushed and removed on restart if a crash left it. `[host]`, `[ci]` and `[tracker]` are sections of the project file; a mode that lacks what it needs is refused with a sentence naming it.
- **The tracker as a signal**: conditional polling thread, `POST /hooks/github` (signed), `mason task refresh`, import rules (outside issues ignored until labeled, kept untrusted, PRs never tasks), the tracker's authority over title, body, priority and closure (new event `TrackerEdited`), best-effort mirroring out.
- **`mason doctor`** checks a project's landing mode, its services, and that a workflow can run on a candidate ref.
- Store migration 8 (`landing_refs`, `tracker_items`); `docs/decisions/0012-ci-hosts-readings.md`; `scripts/exit/s15.sh` and the manual `scripts/exit/s15-real.sh`.

## Exit test
`bash scripts/exit/s15.sh` passes: each of the seven modes lands a clean batch and parks only the culprit of a red (`direct`, `local-only`, `direct-ci`, `local-only-ci`, `pr-each`, `pr-batch`, `host-queue`); `direct`, `direct-ci` and both local-only modes also fold in a moved base (and `direct-ci` shows CI ran a second time); `pr-batch` waits for a required approval and shows the alert; kill -9 at `ci_pushed`, `ci_finished`, `pr_pushed`, `pr_opened`, `pr_checked` and around promotion in `direct-ci`, `pr-batch` and `host-queue` leaves no ref and no open PR on the host and lands the clean task once.

### `s15-real.sh` was not run
It needs a scratch GitHub repository you have approved, a token, and `MASON_REAL_APPROVED=yes`; it refuses without them, and I have none. It is written completely (workflow, landing config, scripted agent, a clean task and a culprit in `direct-ci` and then `pr-batch`, then `mason landing`, `gh pr list` and the remote's `mason/*` branches) and passes `bash -n`, but **it has never been executed**, so nothing in this stage has touched real GitHub. There is therefore no real output to include, and the GitHub adapters' behaviour against the real API (pagination, the merge-queue mutation, how `mergeable_state` reads on your branch protection, Actions' timing) is unverified.

## What testing found
- **A race in the fake host, found by CI on both platforms (first push).** The reviewer's `approve` rewrote the PR's JSON while the host was also writing it, so an approval could put a merged PR back to open. An approval is now a file of its own. A second failure on CI, the same test: the kit's reviewer thread approved "soon", and a fast runner merged first; the kit now calls a `reviewer` hook between opening and merging, so it is deterministic.
- **The macOS job hit its 10-minute budget** once the seven-mode matrix was added to the workspace tests, because the exit scripts then ran the same tests a second time. `s14.sh` and `s15.sh` now skip re-running what `cargo test --workspace` just ran (as earlier scripts do), and the budget is unchanged.
- **A parked task waited for the end of its batch**, so a culprit's verdict sat behind a review the clean tasks needed for hours. Parked tasks now go back at once.
- **A first draft of the recorded script matched the wrong URL**: the substring matcher is order-sensitive (`/pulls/7` also matches `/pulls/7/reviews`), so the fixtures list the longer paths first. Noted in the fixture format, since a wrong match fails loudly rather than quietly.
- The existing `modes_after_this_stage...` test from Stage 14 had to change: a mode that lacks a service is now refused for that reason, not for "arrives in Stage 15".

## Not done or not run
- **Real GitHub**, as above. Everything GitHub-shaped is against responses I wrote from the documentation.
- **Asana** (not in the first release), **Jenkins**, GitLab CI and the other build systems; the plugin protocol is Stage 28's.
- **Pagination**: issues and check runs read the first 100 only.
- **Webhooks need a route**: a desktop behind a router has none by itself; `gh webhook forward` to `http://127.0.0.1:<port>/hooks/github` is the intended way and was not tried.
- **Notifications of an approval wanted** are an alert (monitors show it); no email or ntfy (a later stage).
- **Review state in the fake host is one flag**; the real rules (several reviewers, dismissed reviews, required checks by name) are only as faithful as the GitHub adapter's reading of them.
- A batch whose service fails permanently ends with every task *failed* (not sent back), and needs a retry from you once the cause is fixed.
