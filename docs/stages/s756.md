# s756: agents parked on a check do not hold a Claude session

Summary: An agent parked on a `run_check` no longer counts as holding an LLM session in admission, so idle sessions stop blocking new tasks; `park_extra` in the project file caps tasks in agent steps at the limit plus that many.

What changed
- `daemon.rs`: `Daemon::parked` (set by `CheckSlots::swap_for` when the agent gives its lease back, cleared in `take_agent_slot_back`); `llm_free` splits tasks without a lease into `unclaimed` and `parked` and uses the pure `sessions_free`. `llm_states` gives (working, parked).
- A returning agent is `unclaimed` again, so it is reserved a session ahead of any new admission; its wait is the existing lease wait, credited to the deadline as before.
- `config.rs`: `park_extra` in the project registration (`~/.config/mason/projects/<P>.toml`), read by `llm_free` (the largest of an account's projects). It was first a definition key; that touched `mason-definition`, which put most of the workspace into the task's narrowed (unsharded) run, and that run hit GitHub's 60-minute limit twice. The parked mark is also cleared when the agent step ends.
- Decision: `docs/decisions/0749-parked-agents-hold-no-session.md`.

Not verified: the fake-GitHub end-to-end scenario from the ticket; only the pure `sessions_free` arithmetic is tested (`park_tests` in `daemon.rs`). `mason resources` / `mason status` do not yet show "N working, M parked" (`llm_states` is ready for it). `park_extra` is read from the project registration only, not the definition. No trust file (`sched.rs`, `crates/scheduler`) was changed. The two red rounds timed out at GitHub's 3600 s limit with the definition-crate version; after moving the key out of `mason-definition`, the owner skipped testing for this task (debt #505), so nothing in this version was built or tested here: local cargo builds were refused by the build-queue hook, and the code was only reread against the base.
