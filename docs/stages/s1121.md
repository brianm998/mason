# s1121: a remote run GitHub does not take keeps its place in line

Summary: A remote run that no runner picks up, or that GitHub fails for the environment, now gives back its runner units and waits again at its original place in line instead of going to the back; an agent's check and a landing check give up after three such failures in a row.

**Cause.** A cancelled run was an environmental failure: the test step slept the backoff while still holding its runner units and pushed again; an agent's check and a landing check made two tries at once and then got the error.

**Change.**

- `remote.rs`: `wait_again` gives back every runner unit of a grant, waits `env_backoff` (from the second failure in a row on, base `env_retry`) holding nothing, then asks the broker for the units at the request's original rank and wait start. `run_retrying` (agent checks, landing checks, the red-develop check) uses it between tries.
- Without `fallback = "local"`, a check ends after 3 environmental failures in a row (was 2 tries). Unchanged: with the fallback, two misses then this Mac; a run cut off at the runner limit is tried once more, not twice; a favor-remote spill and a too-short grant behave as before.
- `suites.rs`: the test step's retry loop uses `wait_again` (no limit, as before, charged to no task) in place of sleeping with the lease held. The first retry no longer sleeps 30 s. A run that gives a result resets the count. A skip ends the backoff. Debt payments and landing batch suites now give their runs the lease's giver, so they do the same, and give a unit back per finished job (#820).
- `remote.rs`: `Grant::regain` asks again when the lease holds no runner unit, not only when the lease is gone.
- `landing.rs`: the error of a run that already waited in place three times is not waited out again; it ends the batch (a floor build is first built on this Mac, #962). A push or dispatch GitHub refuses every time keeps #772's 30 minute wait.
- `jobs.rs`: a passing check's line says how often its run waited again; the two build runs of a check are credited to the agent's deadline like its test runs.
- `sched.rs`: `Giver::held`, the runner units a lease holds now.
- Merged with develop's "wait on GitHub for a bigger grant": a run that waited for more runners is pushed on that grant without a second wait.

**Tests.** `remote.rs`: a run nobody picks up (units freed, granted ahead of a younger waiter; the same at landing rank), the backoff holding nothing, three misses, a push refused every time. `landing.rs`: no second wait. `jobs.rs`: the note. `two_misses_are_no_result_not_a_failure` is now `two_misses_go_on_and_three_are_no_result_not_a_failure`, because the limit moved from 2 to 3. Exit test `scripts/exit/s1121.sh`. Decision 1110.

**Not verified.**

- No test drives a whole test step, a whole `run_check` or a whole landing batch against a fake GitHub: the wiring in `suites.rs`, `jobs.rs` and `landing.rs` is covered only through the functions above. The landing floor-build test uses a landing-ranked lease with `run_retrying`.
- Nothing ran against real GitHub.
- A lease that also holds something other than runner units (a device, a batch's local slots) keeps that while its run waits; only the runner units go back.
- A check that attached to a run already out holds no broker lease, so its retries are pushed without asking.
- The hold file for restarts is written for a check's first run only, as before, so a retry run is not counted after a restart.
