# s784: the base's own cargo-workspace red in batch #491

Summary: Batch #491's three base reds are traced to their panics; `mason remote <word>` now rejects an unknown subcommand before it needs masond, and the unmapped-file test ignores the three files a remote run's snapshot adds; the third red (landing_yield) was the test counting a run's immediate rerun as a second run, and now allows for it.

Source: the batch's stored logs, `t/batches/491/b491-r1-bis2-2-n-cargo-workspace.log` (the alone
run; the same three panics are in `b491-r1-0-u-cargo-workspace.log`), base `56b70881`. The
daemon's `batch_runs` row names the same three tests as "still red on its own".

First `panicked at` line, in log order:

1. `landing_yield::a_draining_update_stops_a_red_batch_between_runs_and_the_next_batch_reuses_its_results`
   at `crates/daemon/tests/it/landing_yield.rs:65:5`: `no run after the first one`, left 2, right 1.
2. `definition::tests::no_tracked_file_but_the_definition_is_unmapped` at
   `crates/cli/src/definition.rs:252:9`: `unmapped  .mason: 3 file(s) ...: .mason/base-sha,
   .mason/changed-files.txt, .mason/run.json`.
3. `bogus_remote_command_names_all_four` at `crates/cli/tests/remote_dispatch.rs:31:9`:
   `setup missing: error: masond is not running`.

Causes and fixes:

- (3) `crates/cli/src/main.rs` found the daemon (`client::find`, line 583) before it rejected an
  unknown `remote` word (line 673 on origin/develop), so on a runner with no masond the error
  was "masond is not running". It passed on the owner's Mac only because a daemon was up. The
  word is now checked before the daemon is looked for.
- (2) `crates/daemon/src/remote.rs:517,530` (and `run.json`) put three files into the snapshot
  commit a remote run tests; `git ls-files` there lists them and no `[impact]` glob maps them.
  `unmapped_report` now leaves them out, as it already did `.mason/mason.toml`. No glob was added,
  because that would have made a run-only file select suites.
- (1) The red run is followed at once, in the same run, by a rerun of its failing tests
  (`rerun_failing`, `crates/daemon/src/suites.rs` ~2105; this suite has no `rerun` template, so
  the whole suite runs again). The script logged both, so `reds` held 2 (`left: 2`) while the
  batch had made one run. The test now accepts one red line or two (run plus its rerun); a later
  run of the batch adds its own red and rerun. No ignore, skip, quarantine or removed assertion.
  The failing message also lists the red runs. The earlier exit-scripts timeout (1800 s) fits
  other scripts waiting out this test's 900 s `wait_for`; that was not run locally.

Run: fmt and the three tests through `run_check` on GitHub (2 and 3 green; 1 green alone twice
and red once as above). cargo test was not run locally.
