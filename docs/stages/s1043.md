# s1043: alert when a batch's CI run stops changing

Summary: a pending CI run whose job states do not change for `[ci] stuck_after` (default 30 minutes, 0 = off) raises a `landing` alert naming the batch, run and jobs, cleared when the run moves or ends.

## Cause

On 2026-11-23 a batch's GitHub run hung for over an hour (one job stuck in `cargo test`, two never got a runner) and nothing told the owner; only `[ci] timeout_s` (7200 s) ended it.

## Change

- `crates/core/src/ci_stuck.rs`: pure `stuck_for(looks, after_s)` over (time, signature, unfinished) looks.
- `landing.rs`: `ci_verify` feeds each pending poll to `watch_stuck`, which raises `ci-stuck:b<batch>` (kind `landing`) and pokes; the key is cleared when the signature changes and after `ask` returns, however it ends. `ask` is unchanged. Nothing is cancelled and no verdict changes.
- `config.rs`: `[ci] stuck_after` (`"30m"`, seconds, or 0). Documented in `docs/examples/star.project.toml`.
- `fakehost.rs`: the command CI's pending answer may list `running: a, b` and `queued: N`, so a scripted CI can have jobs.
- The alert text rounds the quiet time down to multiples of `stuck_after` so it holds still between polls.

## Not verified

- The exit script runs the unit and in-process daemon tests, not a separate masond process with `mason alerts`.
- Against real GitHub only counts and running job names exist, so queued jobs are not named, and there is no "running since HH:MM". The run URL is shown only when `progress` supplies one; otherwise the text points to `mason landing`.
- Nothing was built or run in my shell (builds are refused there); `run_check` built it and was green but, with testing skipped for this task (debt #623), ran only the tests this change adds.
