# s325: pick a priority when approving, and Defer into a new Deferred state

Summary: the owner can choose a priority when approving a proposed task and can put it aside with Defer into a new Deferred state, from the CLI, the daemon and both monitors.

## What changed

- `State::Deferred` (core, engine, store codec): events `Deferred` (Proposed to Deferred) and `Undeferred` (back). From Deferred the owner can approve, reject, cancel or undefer; nothing admits it, it raises no alert or reminder, and it has a collapsed "Deferred" sidebar section and count tile. Old logs replay unchanged: both event kinds are new and no existing payload changed.
- Approve takes an optional `priority`. The daemon emits `Approved`, then the same edit `task priority` makes, so the log shows both.
- CLI: `mason task defer <id>`, `mason task undefer <id>`, `mason task approve <id> [--priority P]`. `POST /tasks/{id}/defer`, `/undefer`, and `priority` in the approve body. Proposal routes accept Deferred tasks.
- Both monitors: the approval card has a priority picker (default normal) and a Defer button; rows offer `defer` and `undefer`.
- The tracker importer treats a deferred task as filed, so it is not proposed again.

## Not verified

- Nothing was compiled or run in this session (the build queue and run_check were unavailable). Swift and Compose were edited but not built, and no Swift/Compose test for the picker default or the Defer command was added.
- `clients/features.toml` is in `PROTECTED`: the feature row (swift and compose "done") waits for the owner's approval and is not added.
