# s43: MASON hands out the numbers

Summary: MASON reserves each task's stage note, exit script and decision numbers when it is claimed, tells the task in its prompt, sends back a task that uses another number, and builds the README status block itself.

Task #9. Parallel tasks used to pick the same "next number" and conflict when the second one landed (task #2 and task #1 both took `s20`, `0017`, and the README `Status:` line). Now MASON owns the counters.

## Built
- **Store**: migration 11, `number_reservations` (`UNIQUE(kind, number)`, one row per task and kind, released rows kept). `Store::reserve_number` (one writer transaction; idempotent per task), `reservations`, `all_reservations`, `release_numbers`.
- **`crates/daemon/src/numbers.rs`**: the pure logic (parse numbered names, `Stage NN` in a title, `check_added`, the prompt text) and the I/O half (`base_paths` by `git ls-tree`, `ensure_numbers`, `number_lines`). Reserved when a task is claimed (`admit`) and re-checked before every explore and develop prompt (so tasks claimed before the upgrade get numbers). Released on `Canceled` (in `Daemon::emit`).
- **Prompts**: explore and develop (default or pack) end with the three reserved paths, "do not look for the next number yourself; do not take another number", and "do not edit the README status block; put `Summary: <sentence>` in your stage note".
- **Landing check**: `landing::check_numbers` before a task joins the queue; a numbered file the task adds under a number that is not its own, or that the base already uses, is a send-back naming the file and the one to use.
- **Status block**: `scripts/gen-status.sh`, `scripts/check-status.sh`; `Batch::regenerate_status` / `drop_status_commit` in `crates/landing/src/batch.rs`, called after assembly and after a fold of a moved base. README's `Status:` paragraph is now the generated block.
- **Filing** refuses with "used up" when the ad-hoc range (`MASON_ADHOC_EXIT_START`, default 40, to 99) has no number left.
- **Views**: `NumberLine` and `TaskDetailView.numbers` in the proto, `mason task show` / `--json`, both monitors (detail page), `clients/features.toml` `reserved-numbers`. `mason.pb.swift` regenerated.
- **fake-claude**: `sh` actions get the prompt in `$FAKE_PROMPT`, so the scripted agent can read its numbers like a real one.
- Decision record: `docs/decisions/0021-numbers-readings.md` (status-line format and the other open choices).

## Exit test
`bash scripts/exit/s43.sh` (a real masond, fake-claude, a bare origin holding Stage 20 and s42):
```
alpha #0: s43, decision 21; beta #1: s44, 22; gamma #2: s45, 23
   every explore and develop prompt states its own stage note, decision record and exit script, and no one else's
   gamma #2 took s41 and 0020 first, then landed after feedback
   uses numbers that are not its own: docs/decisions/0020-2.md: number 20 is already used on the base branch; your decision record number is 23, so name it docs/decisions/0023-2.md; docs/stages/s41.md: number 41 is not yours; MASON reserved 45 ... so name it docs/stages/s45.md; ...
   after a daemon restart it still holds s45 and 23
   alpha, beta, gamma, delta and epsilon all landed; the README status block lists them and check-status.sh passes
   it keeps s21 (with decision 26) and landed docs/stages/s21.md
   #6 held s48 and 27, released on cancel; the next task #7 got s49 and 28
   refused: error: the range of stage and exit-script numbers for ad-hoc tasks (from 99 to 99) is used up; ...
s43 OK
```
Landing order in the run was not the numbering order (alpha and delta, the lowest of their pairs, landed after the others).

## What testing found
- A scripted agent that moved `docs/stages/s20.md` (the base's own Stage 20 note) corrupted the scenario; the wrong-number task now takes s41. The check judges added files only, so editing an existing note is never a violation.
- The landing step needs `on_red` and `max_rounds` for a send-back to go back to development; a pipeline without them fails the task (existing behaviour, unchanged).

## Not done, not run
- **The Swift and Compose monitors were not built or run here**: the Swift code was added next to the regenerated `mason.pb.swift` and the Compose code uses Wire's generated `numbers`; neither toolchain was run in this session, so the detail-page lines are unverified. Parity is by `clients/features.toml` only.
- The pull-request and merge-queue landing modes use the same batch runner and so the same status regeneration; only `direct` mode was exercised by the exit test.
- No check that two live tasks naming the same stage collide before landing; the landing check catches it when the second adds its file.
- `check-status.sh` is not in CI (a task branch alone holds a stale block until it lands).
