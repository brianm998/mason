# s105: a wait that stops moving is an alert, and a request that can never fit is one at once

Summary: The broker raises one `long-wait:<resource>` alert when a resource with waiters has granted nothing for `[stall] long_wait` (default 60 min, 0 = off), a `never-fits:<resource>` alert at once for a request over its limit or naming an undeclared resource, and a grant stuck on a kernel lock says so in the task's wait after 60 s.

- `Ledger` records when each resource last had a grant (`adopt` counts) and `Ledger::stalls(now, ..., long_after_ms)` reports, from the plan's waits: `TooBig`/`Unknown` always; any other wait whose resource has granted nothing for the limit, measured from the later of the last grant and the request's arrival (so a new arrival after a quiet spell is not "long", and a long queue that keeps moving is not a stall). Grouped per resource; the CPU gate and settle wait count as waits on `compile`; the disk cause is left out (it has its own alert). The clock is a parameter.
- `Broker::wait_alerts` turns those into alert text (the existing `explain` sentence, who holds it, the `mason resources limit` fix) and adds grants stuck on kernel locks. `attention::alerts_now` gets one line, `wait_alerts(d)`, which reads `long_wait` from notify.toml each time.
- `Broker::acquire`'s kernel-lock loop: after 60 s it says what it waits for through `on_wait` (the task row), and from then counts as a long wait on `kernel-lock:<classes>`; an `Io` error is logged once per distinct message, not every 25 ms.
- `[stall] long_wait` in notify.toml: a span (`"15m"`) or seconds; `0` turns the long-wait alert off. `never-fits` is not governed by it.
- Nothing here changes who is granted what.

Tests: scheduler `ledger.rs` (long, moving, new arrival, TooBig/Unknown at once, CPU, disk left out); `sched.rs` (kernel lock held outside the broker; a limit of 0); `notify.rs` (the setting); `scripts/exit/s105.sh` against a real daemon.

Not verified: the real 60 s kernel-lock threshold (tests inject zero); the 60-minute default on a live system; how the new kinds route on push/email (they use the default routing: monitor only). A `long_wait` alert with several causes on one resource shows the cause of the first in line.
