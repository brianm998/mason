# s989: a fixed red develop moves the tasks it held up

Summary: a background watch reruns a stale red baseline's tests narrowed at develop's tip and records a partial baseline, so a fixed test stops being "red on develop"; it folds develop into the developing tasks that failed those tests and tells their agents on the next `run_check`, alerts the owner when a branch stays behind 30 minutes, and checks a test that fails unexplained in three tasks at the tip (red there: recorded and one urgent task; green: the tasks are behind).

Decision record: docs/decisions/0982-red-develop-fixed-moves-held-tasks.md.

## What changed

- `crates/core/src/red_base.rs`, `crates/daemon/src/rerun.rs`: libtest's `--report-time` FAILED lines are read (already on develop).
- `crates/store`: a migration (`baselines.partial`, `red_sightings`, `red_notes`, `red_folds`, `red_fix_pending`); `put_partial_baseline`, partial-aware `latest_baseline`. A partial row is never read as a whole-suite baseline or cache.
- `crates/daemon/src/redwatch.rs` (new): the pass (probe, fold, notes), suspects, alerts, and `held`, the developing tasks whose last check failed only tests that are red on develop.
- The probe is placed as any run is: `hostedcheck::pool_units` decides GitHub or here, and it takes its runner units (or the suite's slots) from the broker through `remote::fallback_lease`, ranked as owed work, before anything is pushed or started.
- `jobs.rs`: sightings after each suite check, notes before the result, the fold count in the "tree changed while waiting" test, and the stop hook of a check also fires once develop was folded in under it; the check is then made again on the folded tree and the agent sees one result.
- `views.rs`: a developing task held by a red develop has the wait class `base-red` (`TaskRow.wait`, `why_waiting`), with the test names and the fix task.
- `daemon.rs`, `attention.rs`, `lib.rs`: the loop, and the Home alert "N tasks held by a red develop (tests)".
- No protected file is touched (`suites.rs`, `suites/base_red.rs`).

## Tests

- Store: partial rows (green, still red, new red, not a cache, not replacing a whole row) and the sightings/notes/folds/pending tables.
- `redwatch::tests`: fixed set, note wording, the three-task window, known/baseline exclusion, the 30-minute delay, the Home line.
- `tests/it/red_develop.rs` (real daemon, scratch repository, real worktrees, sleeping agents, the pass driven on a given clock): the fix folds into two clean branches and each is told once; the conflicting one gets the conflict note and the owner alert at exactly 30 minutes on the test clock, which goes once it has the base; `known_header`'s "red on develop" goes when a partial baseline is green; a task shows `base-red` while held; three tasks failing an unknown test that fails at the tip file one urgent task, and none when it passes there (the tasks are folded); a known-red test is never counted; a `run_check` running on the old tree is stopped when develop is folded in and made again, and the agent sees one result with the note.
- No test asserts timing.

## Not verified

- Nothing ran against GitHub: the probe's placement (runner units from the broker before a push) is the same call the landing batch and `run_check` use, but no fake-GitHub test of `redwatch::probe` exists.
- The exit script is these tests, not a separate masond process with its own scripted agent.
- A note reaches the agent only on a `run_check` result, not on other tool results.
- The probe needs the project's `rerun_filter`; without it nothing is narrowed and nothing is probed.
- The `base-red` wait is shown by the task and sidebar views only; no wait event is recorded for it, so the wait totals (introspection) do not count it.
- The urgent task is filed by this watch with the base-red gate's title format; the gate itself (`suites/base_red.rs`) is untouched and does not know about it beyond the title.
