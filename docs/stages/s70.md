# s70: Test, command, script and plugin steps report real progress

Summary: Test steps count passed tests as the output arrives (against the last green run's count, else the suite's minimum), suites and script steps can append JSON progress lines (`progress`, `MASON_PROGRESS_FILE`), plugins on protocol 2 send `step.progress`, and approval steps say what they wait on.

Task #41, the third of four on live step progress (after s45/s49). It feeds the record that s45 built; showing it is ticket 4.

## What was built

- **Live test counts** (`crates/testing/src/live.rs`, `parse.rs`): `LiveCount` cuts output into lines and counts passed, failed and skipped with the per-line functions the full parse now shares. TAP, nextest, pytest, xctest, Swift Testing, Gradle and regex. The verdict is still the full parse.
- **Daemon** (`suites.rs`): one sub-count per selected suite (`tests`, done = passed, total = last green count for this base as `expected`, else `min_tests` as `minimum`); the step's count is their sum. The count is rebuilt from the log after a restart. A suite's `progress` file is tailed (`progress.rs` `FileTail`). The store keeps `suite_green` (migration 20).
- **Script steps** (`jobs.rs`): `MASON_PROGRESS_FILE`, same format. Approval steps set the message "waiting for the owner".
- **Plugins**: protocol 2, `step.progress` notification; protocol 1 plugins keep working. The conformance kit checks a plugin's notifications; the example plugin (`docs/examples/plugins/migration-check`) sends them.
- **CI and PR checks** (`adapter-api` `CheckCounts`, `PrStatus.counts`; `github.rs`, `fakehost.rs`; `landing.rs`): a host that lists its checks gives "N of M" and the name of a running one; the batch shows it as a `checks` sub-count on every member's landing run. A host that lists none shows the message "waiting for the pull request's checks" (or "waiting for CI on <ref>") whose time is the wait's start. The fake host reads `prs/N.counts` (`{"done","total","running"}`) because its checks are one command.
- **Landing** (`landing.rs`): each member's landing run counts the batch's phases (forming, integrating, running suites, landing; `unit` "phases", done of 4) with the phase's name as the message; the batch's suites report into the first member's run (`run_over`'s `sink`) and are copied to the others, as sub-counts.
- **Demo** (`demo.rs`): two more checkpoints file and admit six tasks with one record of each kind (tests, script, plugin, batch, PR checks, approval). Existing checkpoint items are unchanged.
- **Protocol**: `SOURCE_EXPECTED`, `SOURCE_MINIMUM`; Swift regenerated.
- Docs: `docs/step-progress.md`, `docs/plugin-protocol.md`; decision 0055.

## What was not done or not run

- **Not in the exit test:** the protocol 2 / protocol 1 plugin run and the fake-host CI count. Plugins are covered by unit tests in `crates/plugins`; the PR checks and the batch phases and suite sub-counts by `a_pr_wait_shows_the_hosts_checks_and_the_batch_phases_on_each_member` in `crates/daemon/tests/landing_modes.rs`, which runs the real daemon against the fake host. No daemon-level test runs a protocol 2 plugin that sends `step.progress`.
- **CI (build system) waits** show a message only: no adapter reports run-level counts for `trigger`/`status`; only PR checks have counts. Gate steps have no job, so nothing was added.
- Playwright and Cucumber have no live count (whole JSON documents; the ticket listed them).
- Not run: the Compose client build; the Swift generated file was regenerated with the installed `protoc`.
- Not run through MASON's own pipeline.
