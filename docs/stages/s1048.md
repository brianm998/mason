# s1048: a diagnosis ends in a decision card (#1044)

Summary: a diagnosis of any failed task ends in a decision card of 2 to 4 options with one recommended, stored on the diagnosis row, with one diagnosis per failure (six per task) and `POST /v1/tasks/{id}/diagnose` / `mason task diagnose` to ask for one.

## What changed

- `crates/adapter-api/src/contract.rs` (protected): `submit_diagnosis` takes `{summary, options: [{label, recommended, action, step?, note?, reason?, kind?, duplicate_of?, evidence?}], no_code_change?, evidence_lines?}`. 2 to 4 options, exactly one recommended, labels at most `card::OPTION_MAX`, `action` one of retry, explore, close, cancel with the arguments each needs. The single-`verdict` shape is no longer accepted from a session; it is a stricter shape and no existing check is loosened.
- `crates/store`: migration adds `diagnoses.card` and `diagnoses.failed_at`; `add_diagnosis` takes `failed_at`, `set_diagnosis_card` is new. Older rows (verdict shape, empty card) read as before.
- `crates/daemon/src/diagnose.rs`: `recommended` picks the recommended option; `decide` runs on its action (unchanged rules; cancel and explore are never applied by themselves); `build_card` stores `Card::to_json` with each option's action arguments under `options[i].action`, key `diagnosis:<id>`; `row_text` (alerts, CLI) reads from the card. `apply` carries out the recommended option, and `cancel` is a new action. Budget: `budget` allows one diagnosis per `state_entered_at` and `MAX_PER_TASK = 6`, a session with no verdict counted. `start` is the one entry (automatic or owner), refusing while one runs. The trigger is every entry into Failed unless `autoretry::pending`.
- `http.rs`: `POST /tasks/{id}/diagnose` (owner only, 409 for not Failed, budget or running), `diagnosis_running {started_ms, ran_on}` in the task JSON of a failed task, `card` and `failed_at` in `/tasks/{id}/diagnoses`. CLI: `mason task diagnose <id>`, and the task view prints the running line. The health action `rerun_diagnosis` uses `start`.

## Not verified

- No real model was run; the prompt wording is untested against one. The model and effort are the ones #1043's setting gives (`session_spec`, unchanged).
- The CLI command was compiled but not run against a daemon; the daemon test calls the same route.
- The owner choosing a non-recommended option is the answer task's work; `mason task diagnosis apply` carries out the recommended one.
