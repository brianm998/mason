# s700: the thermal gate reads the die temperature and SMC power limiting, not only pmset

Summary: The thermal gate now also holds new compiles and tests when the CPU die reads `[cpu] thermal_max_c` (default 97 °C) or more, or the SMC has power-limited the package for 30 s, read from `AppleSMC` without root, because `pmset`'s speed limit stayed at 100 through 647 minutes at 90 °C or more.

**What changed.**
- `crates/daemon/src/thermal.rs`: `AppleSMC` read through IOKit (`IOConnectCallStructMethod`, selector 2, request/reply built by byte offset in `thermal::wire`); decoders for `sp78`, `fpe2`, `flt`; die = `TCXc`, else the hottest of `TC0c`..`TC9c`; power limiting from `PZ1E`/`PZ1F`; a pure `Tracker` that holds the hottest die reading and the power-limit episode for `HOLD_MS`; the pure decision `hot()`. If `AppleSMC` or a key is missing (other models, Linux) the extra readings are `None` and the gate is the old `pmset` gate.
- `crates/daemon/src/sched.rs`: new `thermal_max_c` (default 97, 0 turns the die and power-limit checks off; `resources.toml` `[cpu]`, `mason resources gate thermal_max_c N`, kept across restarts). The scheduler's `ThermalGate` is unchanged: a die or power-limit reading is carried as a minimum one above the speed, and the reason ("thermal: die 97 °C", "thermal: power limited") is kept in the broker and shown on the home page's compile waits.
- Shown: `mason resources` has a `thermal` line (speed limit, die, power-limit time, why work is held); the `cpu` object of the snapshot has `thermal_speed_pct`, `thermal_die_c`, `thermal_max_c`, `thermal_power_limited_ms`, `thermal_why`.

**Not verified.**
- No real SMC read was run by this session (interactive cargo is not available in it); the test `the_real_smc_can_be_read` (kept out of normal runs, macOS only) is for the owner to run on the iMac Pro.
- Which of `PZ1E`/`PZ1F` tracks powermetrics' `CPU Plimit` was not confirmed against `powermetrics --samplers smc` output; `is_power_limited(limit, nominal)` assumes `PZ1E` falls below `PZ1F` when limited. If it is the other way round the power-limit condition never fires or fires too often; the die check does not depend on it.
- The scheduler's own wait sentences (`mason resources` waiting list, `explain`) still read "CPU held to N% ... work starts at N+1%" for a die or power-limit hold; only the home page reason names it. Fixing that needs a field on `ThermalGate` (protected).
- The monitor app's Swift model does not show the new fields yet; they are in the JSON snapshot.
- The exit test on the owner's machine (die matches `~/CPU_USAGE`, leases wait at 97 °C) was not run.
