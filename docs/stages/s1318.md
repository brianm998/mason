# s1318: update health rows say what was tried and why it failed

Summary: `update_failed` health rows now carry the target, the phase and the error, `update_ok` carries the target, and `mason health history` shows both.

## Cause

`note_update` in `crates/daemon/src/health.rs` wrote both rows with an empty detail, and `history_json` filtered them out.

## Change

- `update_failed` detail: `{"target", "phase", "error"}`, the error cut to 500 characters.
- `update_ok` detail: `{"target"}`. After a takeover the new daemon's status names no target, so it is the commit that is running.
- `history_json` lists both kinds; the CLI already prints the detail.
- Still one `update_failed` row per check (decision 1308).

## Phase

`update::Status` holds only `failed` once an update fails, and `update.rs` is protected, so the phase is read from the milestone lines in the status log: `fetching`, `building`, `testing`, `taking over`, or `unknown` for an empty log. A reworded log line there would make the phase less exact. A failure while waiting for landing batches cannot happen on its own; one after the wait is a takeover failure.

## Not verified

- No real self-update was made to fail. The test sets the status by hand.
- Only the `testing` phase is covered by a test.
- `update_ok` after a real takeover (the running-commit fallback) is not tested.
- As before, a check that runs while a retry is under way writes `update_ok` and ends the streak. Its target is then the retry's, which has not taken over yet. This change does not alter that.
