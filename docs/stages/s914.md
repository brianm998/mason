# s914: exit-scripts shard 3 on ubuntu was red for six scripts

Summary: Two of the six red shard-3 scripts had Linux-independent causes and are fixed (s669's fixture lacked the files the lint now reads; s546's affected-test fixture never registered its `tpl` target); s777 passed on Linux, and s09, s40 and s422 were not reproduced.

Each script, from a run_check on ubuntu-latest (run 45025395118 on the first attempt) running s914.sh, which runs the six and prints each failure:

- s546: failed in `cargo test -p mason-daemon --lib affected`. `affected::tests::a_mason_file_selects_only_the_targets_that_read_the_repository_copy` asserted `--test tpl` at affected.rs:961, but the test added `tpl.rs` to the file map and never to the package's test targets. Fix: the test now registers the target. No assertion changed.
- s669: `bash: scripts/check-workflows.sh: No such file or directory`, then `FAIL clean tree refused`. The lint command in `.mason/mason.toml` gained `check-workflows.sh` and the `-p` name guard, and the script's temp repo had neither the script, workflow files, nor `crates/*/Cargo.toml`. Fix: the fixture copies the script and adds one workflow file of each kind and a one-package `crates/x`, each with its SPDX line. Every assertion is kept; it passes locally.
- s777: passed on Linux on that run; left unchanged.
- s09, s40, s422: the output was cut off by the check's tail limit and later runs of the exit-scripts check returned "no result.json" (a runner problem), so their Linux failure line was not seen. They are unchanged. s422 runs two scheduler tests and `suite_builds::`, which passed in cargo-workspace; s09 and s40 start a real masond. If they stay red on the next full run, the failing lines will be in s914's end-of-run report.

s914.sh runs the six scripts and, if any fail, prints the last 12 lines of each together. It has no timing assertion (only a 1200 s kill limit).
