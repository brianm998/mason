# s416: the repeat check runs a test at the base before calling it known red

Summary: the test step's repeat check (s282) counts the tests that fail on every run of a task's test step. When a test not yet known red has done so in 3 or more different tasks within 7 days, it is now run at the merge base, the same way as the last-round check: up to 3 targeted runs, with the suite's device and environment brought up when it has them. It goes into the known-red ledger, with a fix task, only if it is red there. Green at the base, or no result, leaves no entry, and the reason is logged. Either way, the task's own step goes on as before.

## Why

On 2026-11-15, `workspace_is_fmt_clean` was made known red and quarantined for 29 days as `mason:exhausted`, and #421 was filed to fix it. `origin/develop` was `cargo fmt --all --check` clean. Three tasks had each failed it on their own unformatted code (#363's in `crates/conformance/src/tokens.rs`). Until the owner lifted the quarantine, tasks with unformatted code were excused and could land. A test that checks the task's own diff fails in many tasks without being red at the base.

## What changed

- `crates/daemon/src/exhausted.rs`:
  - `record_persistent` records, and returns the tests that crossed the threshold; it no longer adds them.
  - `repeated_at_base` checks those tests at the base.
  - `on_last_round` and `repeated_at_base` share `check_at_base`. The fix task's text says which check filed it.
- `crates/daemon/src/suites.rs`: the device and environment wrapping for base runs became the `at_base` closure, used by both checks.
- `crates/daemon/src/jobs.rs`: the command path calls `repeated_at_base` on rounds before the last.
- Test: `a_test_red_in_three_tasks_but_green_at_the_base_is_not_made_known_red` (`crates/daemon/tests/testing.rs`).

## Cost

A base run happens only on the round where a test crosses the threshold. A test that keeps failing in tasks and keeps passing at the base is run at the base again each time.
