# s475: the daemon's integration tests are one executable plus eight that need a process of their own

Summary: 81 of the 89 files in `crates/daemon/tests` are now modules of one test executable (`tests/it/main.rs`), so a `-p mason-daemon --no-run` build links 11 executables (lib, bin, `it` and eight separate tests) instead of 91, with the same 931 tests.

## What changed

- `crates/daemon/tests/it/main.rs` declares the 81 files (moved with `git mv` into `tests/it/`) as modules. Cargo finds it by itself (`tests/*/main.rs`), so `autotests = false` is not needed. `tests/support/` stays where it is and is mounted with `#[path]`; each moved file's `mod support;` became `use crate::support;`. The one `include_str!` (in `targets.rs`) got one more `../`.
- Eight files stay separate targets: `git_blips` and `ssh_keys` (they set `PATH` and `MASON_*` variables for the whole process), `fetch_deadline` (it sets the process-wide git deadline to 5 s; merged, it made other modules' git calls time out and failed the `notify::` and `landing_split::` tests in the full run) and the five in `.mason/serial-tests.txt` (`scheduling`, `holds`, `wait_classes`, `stallwatch`, `taskcache_own`). Their target names did not change, so `.mason/serial-tests.txt`, `scripts/test-parallel.py` and `.mason/mason.toml` (the impact map names no test file) needed no edit.
- Test names are now `module::test_name` in target `it`. The 84 exit scripts that ran `--test <file>` now run `--test it` and, where they ran a whole file, filter on `<file>::`; helpers that pass an exact name pass `<file>::<name>`. A positional filter such as `conflict` now matches in every module, so it can run more tests than before; none of them is expected to fail.
- `scripts/exit/s475.sh` is the exit test.

## Shared state in the merged process

libtest runs the 81 modules on several threads in one process. Checked: no merged file sets an environment variable or the working directory (the two that set environment variables stayed out, and `fetch_deadline`, which sets a process-wide git deadline); `support::Slot::take` is a counting limit on running worlds (`MASON_TEST_WORLDS`) and is the same across the process on purpose; `BUILT` in support is a mutex around building binaries; every test builds its own temp dirs and its own world. Ports are chosen by binding to port 0 in the tests that open one. A signal helper in `stop.rs` signals its own child only.

## Numbers (same commit, `-p mason-daemon`, load average about 100 during both, so read them as rough)

| | before | after |
|---|---|---|
| test executables for the daemon (`--no-run` JSON) | 91 (89 tests + lib + bin) | 11 (`it`, 8 separate, lib, bin) |
| tests listed (`--list` over all of them) | 931 | 931, each name identical module for file |
| `--no-run` after touching `src/lib.rs` | 3m36 wall, 13m CPU | 1m38 wall, 1m49 CPU |

Cold build (dependencies included) before: 5m50 wall. The full test run time before and after was **not** measured by me; the whole-workspace run is the pipeline's test step. The before and after lists of test names were compared and match one to one.

## Not verified

- The full run time. A merged process runs its tests on libtest threads; I did not check that against a run on a quiet machine.
- The 84 rewritten exit scripts were checked with `bash -n` and by reading the diff; I ran `s475.sh` only. A script that filtered by a bare word now matches more tests, so it may run longer.
- The quarantine list lives in the daemon's store, not the repository; I could not read it. Any entry that names a moved test as `test_name` still matches by substring, but an entry written as an exact `file::name` of the old target needs a look with `mason quarantine list` after this lands.

## Run results

The merged `it` binary run alone: 514 passed, 0 failed (1505 s on a loaded machine). One earlier run of the pipeline's test step had `it` failing (eight `notify::` tests) while another copy of the binary was running beside it; the notify tests pass alone (19 of 19) and in the full run, and the cause was `fetch_deadline`, which set the process-wide git deadline to 5 s for every other module; it is a separate target again. The last unscoped `run_check`: cargo-workspace passed; exit-scripts timed out as a whole, and `s11` failed on its own 100 ms admission timing check (it printed 118 to 120 ms on every run under load, before and after this change).
