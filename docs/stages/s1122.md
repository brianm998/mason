# s1122: "Update masond" updates the nodes too

Summary: `mason update` now builds the nodes' runtimes beside the coordinator's own, sends each reachable node its runtime after the coordinator's self-test and before the takeover (also to a node on another protocol), shows each node's update state in `mason update status`, `mason node list`, the alerts and the monitor model, and `mason node update NAME|--all` sends now.

## Already there (origin/develop)

`nodes.rs` `poll_once` pushed the coordinator's runtime to each node that lacked it after every poll, cross-built under a compile lease, and the node verified it, installed it and took over when its jobs ended (`node_serve.rs`). It sent only to a node on the same `node_proto`, started the cross-build only after the coordinator had taken over, and showed nothing but a log line.

## Change

- `node_fleet.rs` (new): the per-node state (`Fleet`, a pure function of the node's status and the last try), `begin` (starts the cross-builds when the update starts building), `deliver` (sends, bounded by `update_wait_max_s`, never fails the update), `start_push` (one send on a thread, with `force`), the alert for a failed send, and `FleetIo`, the seam tests replace.
- `nodes.rs`: `needs_runtime` no longer compares `node_proto`; `push_runtimes` uses `node_fleet`, skips nodes that did not answer their last poll and any poll during an update; `POST /nodes/update`; `GET /nodes` rows carry `update`, `update_state`, `runtime_sha`, `node_proto`; the failed-send alert joins `nodes::alerts`.
- `node_serve.rs`: `RUNTIME_ROUTE` and `RUNTIME_STATUS_KEYS` name the contract that holds across protocols; the status adds `pending_runtime` (a display only).
- `node_runtime.rs`: `runtime_of` and `package_of` take the commit (an update that has not taken over yet runs on another one).
- `update.rs` (protected): `run` calls `begin` before the build and `deliver` after the self-test and the `--check` return, before "taking over".
- `http.rs`: `GET /update` has `nodes`; route `/nodes/update`. CLI: `mason node update`, node lines in `mason update status`, `[runtime: ...]` in `mason node list`.
- Swift MonitorCore (`NodesModel.swift`, `Model.swift`): `NodeRow.update`, `updateState`, `canUpdateNow`, `NodesSnapshot.updateSummary`, `updateNode(_:)`. No view changes.
- `docs/nodes.md` section 1.3 describes what happens, what the owner sees and what to do.

## Tests

`needs_runtime` for a node on an older protocol (unit); the state machine and its words (unit); in `tests/nodes.rs` (`fleet::`), with a fake node and `FakeIo` instead of a Developer ID: the route and status keys on a node of another protocol, an update across a protocol bump (building, sent, installed), up to date in the node list and the update status, a failed send as an alert and `node update --all` inside the retry window, an off node that is pending and is sent the runtime by the next poll, and `update::run` with a real build and self-test that sends before "taking over" and is not stopped by a refusing node. `scripts/exit/s1122.sh` runs them.

## Not verified

- A real cross-build and a real signed `PUT /node/runtime` to Marmot: the tests use ad-hoc copies and a fake send, because nothing here may touch the node or sign with the owner's identity. The node's own takeover (the exec) after its jobs end is not run, so "up to date" after the node's restart is shown by a unit test of the state function and by a node that already runs the commit.
- Sending to two nodes of one architecture at once, and a cross-build that outlasts `update_wait_max_s`.
- The monitor's views: only the model compiles (`swift build`) and passes its unit tests; no row or banner shows the new text, nor a button.
- The `release` channel, which has no source to cross-build from.
