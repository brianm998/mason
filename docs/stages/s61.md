# s61: Tracker setup: MASON says when issues are not imported, and the tracker is easy to turn on

Summary: A project with a GitHub remote and no `[tracker]` section is now noted by `mason doctor`, `mason task refresh` and the monitors' landing page, instead of silently importing nothing; the example project file has a ready-to-fill tracker block, and the poll's last result, counts, stop reason and the issues waiting for a `[self]` slot are shown.

## What was wrong

MASON's own project is set up from `docs/examples/mason-self.project.toml`, which had no tracker section. The poller then never runs for the project, issues filed on GitHub never become tasks, and `mason doctor` reported all ok. Only noticing that nothing happened told the owner. Items refused by a `[self]` limit were skipped in a bare `continue`, so nothing counted or named them either.

## What was built

- **Example and docs.** A commented `[tracker]` block at the end of the example (kind, repo, token as `env:`/`file:` reference, label, interval, optional webhook secret reference). `docs/self-hosting.md` has "Importing issues": how to turn it on, the token scope (issues read; write only for mirroring comments and closes back), that outside issues need the label, what the first poll does, and what a stop means. A daemon unit test parses the example with the block uncommented, and refuses a literal token.
- **Daemon.** `Hub` keeps a `PollRecord` per project (time, counts, error); `Summary` gains `unchanged` and `waiting_slot`. An issue refused by `check_filing_as` is collected once in a map, whatever the number of passes, and the `tracker-slots` alert names them and the limit that refused them (cleared when none waits). A failed look or an unmodified listing keeps the previous counts. `/status` gains a `trackers` array (state off, polling or stopped; config path; record).
- **`mason doctor`.** A new `note` level (never a failure). A GitHub remote (https, scp-like or ssh form; the project's `remote`, else `origin`) with no `[tracker]` prints `issues on <owner/repo> are not imported; see docs/self-hosting.md`. With a tracker, doctor reads the running daemon's `/status`: last poll time, imported, ignored, unchanged, waiting for a slot, the last error, and a warning with the reason when the poll stopped. Without a running daemon it says the poll state is unknown.
- **`mason task refresh`.** With no tracker it says so, names the config path, and says nothing is imported until `[tracker]` is added. With one it prints the new counts.
- **Monitors.** `LandingView.trackers = 9` (additive) carries one line per in-scope project: off (with the config path), polling (with counts), or stopped (with the reason). Swift and Compose render it on the landing page; `clients/features.toml` has a `tracker-state` row, done in both; both core test suites assert the lines arrive.
- **`fake-github`** answers the issue listing with a status from a `listing-status` file, to show a stopped poll.

## What testing found

- The first version of the script raced: the first poll imported and claimed two tasks before claims were paused, and they failed for want of an agent, which freed their slots and made the limit counts wrong. The script now starts with an empty listing, pauses claims, and only then serves the issues.
- An existing test asserted that a second look at an unchanged listing returned an all-zero summary. It now asserts `unchanged: 3` (the three imported issues), which is what the field means. Nothing in it was loosened.

## Not done, not verified

- **GitHub itself was never called.** Everything ran against `fake-github`. The recorded fixtures are in the shape of GitHub's issue listing but were written for this test; a real token's scope was not tried. The scope advice in `docs/self-hosting.md` (issues read; write for mirroring) follows from which requests the adapter makes (listing and blocked-by reads; comments and PATCH for mirroring), not from a try against GitHub.
- **Nothing was turned on for MASON's own project.** Registering the tracker is the owner's act. "Every open owner issue is imported in one batch on first turning it on" is what the existing import does, and the script shows it with a fake listing; it was not run against the real `brianm998/mason` issues.
- The doctor note reads `git remote get-url` only; a repository whose GitHub remote has another name than the project's `remote` or `origin` is not noticed.
- Doctor learns the poll state only from a running `masond` that has the config loaded; a config edited after start shows as "restart masond".
- Per-poll counts are of the last full listing; a poll answered "not modified" refreshes the time and keeps the counts.
- `protoc` and `protoc-gen-swift` were available: `mason.pb.swift` was regenerated with `scripts/gen-clients.sh`. `swift test` passed (39 tests). Gradle `:core:test` and `:app:compileKotlin` ran offline and passed. The monitors' apps were not launched, so the rendered line was not seen on screen.
- `clients/features.toml` is a gate (docs/self-hosting.md). The change only adds one row; owner approval for that line is needed.
- `scripts/run-exit-scripts.sh` as a whole was started but cut off at 590 s, so it did not finish. Only `s61.sh` and `s42.sh` (the neighbouring tracker script, which passed) ran to the end. `cargo test --workspace` (through `run_check`), `cargo fmt`, `clippy -D warnings`, `check-spdx.sh` and `check-pure.sh` passed.
- During that run the worktree was left in the middle of a merge of `origin/develop` that this change did not start (an unrelated exit script or process). It was aborted with `git merge --abort`; the commit was intact and the tree clean afterwards.
