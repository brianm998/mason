# s61: A test step judges the change, not the machine

Summary: A test step folds the base in before it runs, so fixes that reached the base while a task waited count. A red test command can be run again (`test_reruns`), so a flaky test is a recorded flake, not a red round. A step is told what it holds (`MASON_HELD`).

Done by hand on the owner's request, after s60, outside the pipeline. On 2026-11-07, tasks #12, #14, #15 and #16 kept going red on a different load-sensitive test each round, and fixes on `develop` never reached them.

## Why

- **One flaky test anywhere was a red round.** MASON's own test step is one `cargo test --workspace` over about 83 test binaries, many of them starting real daemons. A single red test anywhere sent the task back to develop: an agent session for a change that had nothing wrong with it, and after three rounds the task failed.
- **Fixes on the base never reached a task in testing.** Only agent steps brought a branch up to date with the base. A test step tested the branch as it was, so a task kept running tests that had already been fixed on `develop`.
- **A command could not tell that its step already held a class.** With the owner's queue wrapper (`mason run --needs compile`) and a definition `uses = { compile = 1 }` together, a step would hold a slot and then wait for another, and with two slots two steps would wait on each other.

## What changed

- `command_job` (`crates/daemon/src/jobs.rs`) and `suites::run`: a test step first runs `prepare`, which fetches and merges the base.
  - A conflict there is a red round. Its feedback is s60's conflict note, and the develop step that follows meets the same conflict and gets the note too.
  - Command steps that are not tests are unchanged.
- `test_reruns` in a project's local overlay (0 to 3, default 0):
  - A test command that is red by its exit status alone is run again, up to that many times, each run on a fresh step host (`t<task>r<run>-test-again<k>`, with its own log and exit files).
  - Green on a rerun is green. The earlier red runs are written to `test-r<run>.flaky` and logged as a warning.
  - Red on every run is red, and the reason says how many runs it took ("2 runs, red every time").
  - Not run again: a timeout or a signal (a rerun would only double the wait), and a script's own `passed: false` verdict.
  - A restarted daemon finds each run's host and collects it, as before.
- `mason logs` labels a rerun ("test, run again (1)") and renders it as test output.
- `MASON_HELD` in every step's environment: the classes the step's `uses` names, comma-separated. `~/.config/mason/bin/mason-queued` runs its command directly when the class is already held.
- MASON's project overlay sets `test_reruns = 1` (owner configuration, not in the repository).

## Tests

- `e2e.rs`:
  - `a_red_test_that_is_green_when_run_again_is_a_flake_not_a_red_round`: one develop round, one test round, the command ran twice, the flake is recorded, and the log shows the rerun.
  - `a_test_that_is_red_every_time_is_still_red_with_reruns`: two rounds, four runs, the task fails "red every time", and nothing lands.
  - `the_test_step_folds_in_the_base_so_a_fix_that_landed_meanwhile_counts`: the tests need a file that reaches the base during develop; the task lands with one develop round.
- `scheduling.rs`: `a_step_is_told_what_it_holds_so_its_command_need_not_queue_for_it`.
- `definitions.rs`: `an_invalid_definition_edit_is_refused_and_the_old_one_keeps_running` waits for the landing job, whose own reload raced the explicit one, and keeps the watcher out of the way.

## Exit test

`scripts/exit/s61.sh` runs the four new tests and the definitions one.

## Not done, not verified

- A suite step (`suites = [...]`) gets the base merge but not reruns. Suites already have per-test results and quarantine; reruns there would belong in the suite runner.
- `test_reruns` reruns the whole command. For cargo, rerunning only the failed test binaries would be faster; it needs the command to be cargo, which a test step does not know.
- A flake is recorded but not raised as an alert or counted anywhere. The `.flaky` files are the record, and it is up to the owner to go through them.
- Not run through MASON's own pipeline.
