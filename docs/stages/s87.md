# s87: a stale pid cannot block the daemon, and a refusal is not a crash

Summary: The one-daemon-per-data-directory guard is now a kernel `flock` on `daemon.lock`, and a start that declines to run (a daemon already there, a port taken) is logged as `refused` in `boots.log` and not counted as a crash by the rollback logic.

`ensure_single` used to refuse when the pid in `daemon.json` was alive, which after a reboot could be any process. It now takes an exclusive non-blocking `flock` on `<data-dir>/daemon.lock`, held in a static for the life of the process. The file is close-on-exec, so the managed loader (which never takes it) and `take_over` pass through `exec` cleanly; the new image retries for 5 s while the lock is busy. A repeat call by the holder (`serve`) does nothing. The message still names the holder's pid (written into the lock file, falling back to `daemon.json`).

`masond` writes `refused` to `boots.log` (when it has a `--runtime-sha`) and exits 1 on a lock refusal or a taken port; `crashes_in` lets `refused` cancel the `start` the loader recorded. Store-open and migration failures are not refused and still count. `update.rs` is a guard file: the only change is that `crashes_in` ignores refused starts; a crashing build is still rolled back (tested).

Tests: `crates/daemon/tests/single.rs`, `refused_starts_are_not_crashes` in `update.rs`, `scripts/exit/s87.sh`.

Not verified: behaviour across an actual reboot; `take_over` end to end with the new lock (relies on the existing update tests passing); lock semantics on network filesystems.
