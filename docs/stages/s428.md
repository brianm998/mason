# s428: a build that already passed on an unchanged tree takes no compile slot

Summary: A test step or run_check skips the build, and its `compile` slot, when the same build already passed on this exact tree in this worktree; the wait_share finding now names the longest wait and the compile count in force.

## Why

Over 7 days tasks spent 675.7 h waiting for `compile` and 397.5 h for `test-suite`. Whole test steps were already reused on an unchanged tree, but a build was not, so a retry of a step whose tests did not pass queued for `compile` again.

## What changed

- `crates/daemon/src/cmdreuse.rs`: `build_key`, `build_green_for`, `record_build_green`, `record_build_red`. A hit needs the same tree, build command and worktree (the build's output lives there).
- `crates/daemon/src/jobs.rs`: the test step and `run_check` consult the memo before queueing for `compile`, and record the build's result. The restart-attach path is unchanged.
- `crates/core/src/introspect.rs`, `crates/daemon/src/introspect.rs`, `sched.rs`: the wait_share evidence names the longest wait and the `compile` count in force.

## Not changed

The cap itself (`compile_jobs`, `limits.kv`, `compile_cpu_max`) is an owner decision and is not changed here. Defaults, the CPU gate and settle values are as before. Most of the wait is capacity, so this alone is not expected to move wait_share much.
