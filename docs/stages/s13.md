# Stage 13: Compose monitor (completes M3)

## Built
`clients/compose/`: a Gradle project with a `core` module and an `app` module, in Kotlin with Compose Multiplatform for desktop. It has the same layout, behaviour and design tokens as the approved SwiftUI client:
- **Top bar** with back, forward and home, the attention indicator (only while something needs a look), the project filter, usage lines, fixed-size count tiles (a dash while disconnected, tinted when a state wants the owner, a click expands and scrolls to its section), add task, mute; **banners** only while true; **sidebar** with a Home row, search with name, title and body checkboxes, a collapsible section per state, page links; **main view** exactly one of Home, task detail or another page.
- **Home** (status, attention queue with answerable decision cards, active models, the session stepper, landing queue, per-stage detail, no counts), **task detail** (progress, why it waits, the daemon's allowed actions, copy buttons, why exploring was skipped, the decision card, steps, tests, debts, plan, log), and the **Landing, LLM usage, Health and Pipeline pages** with the same content as the SwiftUI client.
- **Progress cells**, browser-style navigation, `mason://` deep links (parsed and tested), text scale (⌘/Ctrl +, −, 0), the owner's identity on every command, reconnect with the last sequence number.
- **`monitor-tool`**: `conformance`, `snapshot`, `answer`, `cancel`, `skip`. The SwiftUI tool gained `cancel` and `skip` so both can be driven the same way.
- `docs/decisions/0010-compose-monitor-readings.md`, `scripts/exit/s13.sh`, a `monitor-compose` CI job on Ubuntu and macOS, `clients/features.toml` with every feature done in both clients, and Wire-generated Kotlin messages from the one schema.

### Tests
- **Kotlin core (14)**: browser-style history, deep links, tiles and the attention indicator while disconnected, collapse choices remembered, tile click reveals its section, search with each checkbox, text-scale range and memory, views and sequence numbers from the daemon, Wire's JSON mapping against what the daemon sends (camelCase, enum names, 64-bit strings, an unknown field), commands carrying the owner's identity and the card hash, the conformance items and the collapse state, durations, the Health report.
- The Rust side is unchanged except the token path; all exit scripts s00 to s13 pass.

## What testing found
- **Landing re-ran the project's test command after folding in a moved base**, and my exit script's scratch project had `test = "false"` (copied from earlier scripts where nothing landed concurrently), so one skipped task failed to land with "tests are red after folding in the new base". Not a bug in the pipeline (a red base is a red base), but worth knowing when several tasks land at once. The script now uses a passing command.
- Wire renames a field called `header` to `header_` in Kotlin (it clashes with a reserved name), which the model had to account for; the JSON name is unchanged.

## Not done or not run
- **Windows**: Compose Desktop supports it and nothing in the client is Windows-specific, but I ran it on macOS only here; CI has Ubuntu and macOS. Linux ran only in CI (see below).
- **Neither client was clicked through by a person.** The click paths are covered by the shared model code the buttons call, the tool commands that do what the buttons do against a real daemon, and a launch check that the real window connects.
- **Conformance reads the model in both clients**, not the real accessibility tree (decision 0009); every element carries its id as a test tag, so a harness can read it later.
- The same known gaps as the SwiftUI client (usage lines squeezed at 1440 points, no diff or token sections in the task detail, the log refreshing only on change, the Pipeline page a placeholder).
