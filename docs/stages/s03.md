# Stage 3: Event store

## Built
`crates/store` (`mason-store`):
- SQLite via `rusqlite` (bundled), WAL mode, `synchronous=FULL`, one **writer thread** that owns the write connection; a separate read-only connection for readers. The API is blocking (async callers will use a bounded worker pool).
- **Append-only log** (`events`: `seq`, `at`, `kind`, `payload`), with triggers that abort any UPDATE or DELETE.
- **Append = reduce + log row + projection rows + `projected_seq`, in one transaction.** A refused event (reducer error) writes nothing.
- **Projections** (`projects`, `tasks`, `decisions`) written incrementally and rebuildable from the log (`rebuild_projections`); rebuilt automatically on open if `projected_seq` lags the log.
- **Migrations** by `PRAGMA user_version` (v1 log, v2 projections), one transaction per step.
- **Resume:** `read_since(seq, limit)`; `last_seq()`.
- `verify()`: log contiguous, replays cleanly, projections identical to a replay (the "nothing half-applied" check; also useful for `mason doctor` later).
- A hand-written text codec for events (`src/codec.rs`), so `mason-core` stays dependency-free as `s02.sh` requires. A unit test pins every event kind round-tripping, including tabs, newlines, backslashes and non-ASCII.
- `crates/store/examples/crash_tool.rs` and `scripts/exit/s03.sh`.

## Exit test
`bash scripts/exit/s03.sh` passes locally: runs the store tests, then six rounds of: start a separate writer process appending (and printing `ACK <seq>` after each commit), `kill -9` it at a different point, reopen the store, and require `last_seq >= last acknowledged` and a clean `verify()`.
```
round 1: killed writer after ack 95    -> OK last_seq=95 (acknowledged 95)
round 3: killed writer after ack 405   -> OK last_seq=406 (acknowledged 405)
round 6: killed writer after ack 1173  -> OK last_seq=1174 (acknowledged 1173)
s03 OK
```
(Rounds 3 and 6 show an event committed but not yet acknowledged when the kill landed: kept, not lost, not half-applied.)

Store tests (10 integration + 2 codec): contiguous sequence numbers and resume; refused events write nothing; live projections == rebuilt == reopened over a 1,500-attempt scenario; append-only triggers; an uncommitted transaction vanishes after reopen; damaged projections detected and repaired; stale projections rebuilt on open; **an older (v1) database copy migrates** while the original stays at v1; concurrent reader sees no gaps.

## Not run
- Power-loss durability (only process kill was exercised; `synchronous=FULL` is set for it but untested).
- Linux run of `s03.sh` until CI reports.
- A kill landing inside a single commit is covered by SQLite's WAL guarantees plus the repeated random kill points, not by deterministic fault injection (that is the Stage 6 crash-injection harness).
