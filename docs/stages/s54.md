# s54: Self-hosting max_open: tasks held behind a blocker do not count as open

Summary: the `max_open` self-hosting limit now counts only tasks doing or about to do work (running, queued and claimable, paused, waiting on the owner). Tasks held behind unlanded blockers, and proposed tasks, are not counted; `mason self` shows the held count.

Task #20 (the tracker import of the owner's chain under `max_open = 3` left every other issue unimported although only #9 ran).

## Built
- **`crates/daemon/src/selfguard.rs`** (trust file, waits for the owner): `Status.held`; `open_counts` (activity neither idle nor held); refusal message names what was counted and the held count. `max_steps`, `per_week`, cooldown untouched.
- **`GET /self`** carries `held`; **`mason self`** prints "N/M open (K held behind others, not counted)".
- Decision record: `docs/decisions/0032-self-open-readings.md`. `docs/self-hosting.md` Limits updated.

## Tests
- Unit (`selfguard.rs`): running and queued count, held and proposed do not, a released task counts, ten held plus one running do not refuse, three counted do with the new text.
- `crates/daemon/tests/selfguard.rs`: ten held behind a blocker do not block a filing, three counted ones do. Three older tests now file queued rather than proposed tasks, because proposed no longer counts.
- `crates/daemon/tests/scheduling.rs`: five held tasks released at once never run more than `max_concurrent` agent steps at once.
- `bash scripts/exit/s54.sh` (a real masond, command-step pipeline gated by files): five chained tasks accepted, `1/3 open (4 held behind others, not counted)`; two more running tasks make 3/3 and the next filing is refused with the new message; landing the first releases each next one in order.
