# Stage 22: Introspection and recurring jobs

Summary: MASON now notices its own problems and checks its own fixes: daily rule-based detectors file findings as proposals with evidence and a named metric, the next cycle after a fix lands reports "this fix worked" or "this fix didn't help" with before and after values, a digest and a Health page show only recorded data, recurring jobs (including base-health that files only new failures) run from the local overlay, and an optional triage records suggestions for the owner's review without ever answering.

## Built
- `crates/core/src/introspect.rs` (pure): failure signatures, permanent or transient classification, the detectors for every Part 14 example (no-result rate, time waiting, same signature three times, retry loop on a permanent error, landing queue idle with ready tasks, frequent force-skips of one suite, expired switches), metrics as rates with counts, the verdict rule, median and ratio helpers for the digest, new-failure diff against a baseline, schedule parsing, the checks on the analyst's output, and the triage sampler. Unit tests for each.
- Migration 16 (`step_attempts`, `findings`, `schedules`, `triage_samples`) and `crates/store/src/introspect.rs`; `jobs.rs` writes one `step_attempts` row when each step attempt ends. `crates/store/examples/plant.rs` writes planted history for the exit test.
- `crates/daemon/src/introspect.rs`: the detector cycle, findings filed through `proposals::file` (so duplicates, evidence and caps apply), closing the loop, the analyst task and ingest of its JSON file, triage recording, the digest and the Health report. `crates/daemon/src/schedule.rs`: `[schedule.<name>]` in the overlay, kinds `task`, `base-health`, `mutants`, `live`. Options `--introspect-ms`, `--analyst-ms`, `--schedule-ms` for `masond`; `[introspect]` and `[triage]` in the project file.
- API: `GET /health`, `GET /digest`, `GET /schedules`, `POST /schedules/run`, `GET /triage`, `POST /triage/{id}/review`. CLI: `mason health`, `digest`, `schedule list|run`, `triage list|review`.
- Health page in SwiftUI and Compose: findings with their verdicts, recurring jobs, the digest, triage state. Row `health-introspection` in `clients/features.toml`.
- `scripts/exit/s22.sh`, `s22-real.sh`, `s22-manual.sh`, decision 0048.

## Exit test
`bash scripts/exit/s22.sh` ends with `s22 OK` (about 30 seconds). With a real `masond`, fake agents and local repositories it shows:
1. A retry loop on a permanent error is planted into `step_attempts` (5 attempts of one step failing with the same reason, plus two timeouts beside it). The detector files one proposal, routed to MASON's repository, with evidence from the recorded rows and the metric `retry_loop_rate` (4 of 7 when found); the timeouts are not a finding; three more cycles do not file it again. The owner approves, a scripted fix lands on MASON's main, nothing is concluded before data exists, and after 8 planted attempts without retries the next cycle says `this fix worked: retry_loop_rate went from 0.571 to 0.000`, in `mason health` and in the digest.
2. A second planted problem (a different permanent error) is found; its fix (a doc note) lands; the same failures planted again are reported as `this fix didn't help: retry_loop_rate went from 0.400 to 0.500`. The first verdict stands, and the detector does not file the failed fix's problem again.
3. The analyst's file has three findings: one is filed, one without evidence and one naming an unknown metric are refused (with the reasons in `analyst-refused.txt`).
4. Triage, with `sample_percent = 100`: a question is still the owner's (the task waits), the suggestion sits in the review queue, and the owner's review changes nothing about the task. Off by default.
5. The digest shows the landed count, median claim-to-land, interventions per landed task, time by state and wait reason, exploring skips by route with how many came back, a forced landing with its reason, and "Tokens per landed task: not recorded". `digest.trace` gives the row and event counts behind it.
6. Base health: the first run only records the baseline (one known failure); after a new failing test is pushed, the next run files one task for it, and a third run files nothing.
7. After a restart with a `[schedule.logs] every = "2s"` job, one Low-priority task appears and is not filed again while it is open.

## What testing found
- The first detector run over a closed finding re-filed the same loop on the next cycle, because the old rows were still in the 24-hour window. The detector now judges a finding that had a fix only by history since the fix landed, and does not file a fix that did not help again (reverting is the owner's decision from the digest).
- A task with `--explored` showed route `explore` in the digest: the test definition had no `explored_entry`. The script's definition now has one, which is what makes skips by route appear.
- A tick that re-wrote every schedule row could overwrite a job's own update; rows are now written only when new or changed.
- `cargo clippy` flagged one boolean expression in the detector; it is split into a named condition.

## Not done, and not verified
- **No real agent** ran. The analyst, the triage agent and every fix were scripted (`fake-claude` and a shell command). Whether a real analyst writes useful findings is untested.
- **No live adapter run and no `cargo-mutants` run.** `cargo-mutants` is not installed here. `s22-real.sh` runs both as scheduled jobs and needs `MASON_REAL_APPROVED=yes` (and `MASON_REAL_LIVE=yes` for the live adapter, which spends tokens). It has not been run. The `mutants` kind's defaults (`cargo mutants --no-shuffle`, survivors read from `mutants.out/missed.txt`) are untested against the real tool's output.
- **The owner's Health check is not done.** I built the SwiftUI app (`swift build`) and compiled the Compose modules (`gradle --offline :core:compileKotlin :app:compileKotlin`), and `conformance features` reports parity, but nothing was opened and looked at. `s22-manual.sh` plants a loop and lists what to check in each monitor.
- Base-health, `mutants` and `live` run their command directly on a worker thread, not through the resource scheduler; the tasks they file do. A job that needs a shared resource (a device, a port) must say so by being a `task` schedule instead.
- Thresholds and the permanent or transient phrase lists are readings (decision 0048), chosen without real-world history to tune against.
- The analyst's file is read when an agent step of a task titled "Analyse recent pipeline behaviour" ends. If the owner renames the task, nothing is read.
- Tokens per landed task are not shown because the daemon does not record tokens per task; the digest says so rather than estimate.
- The digest replays the whole event log on each request. Fine for this size; it will need a cache before the log is large.
- No protobuf `HealthView`: the page uses the raw JSON GET it already used for resources (decision 0048).
- `bash scripts/run-exit-scripts.sh` exits 1. The failures, none of which touches introspection:
  - `s20.sh` and `s53.sh` fail as noted in the Stage 21 note; I did not look into them.
  - `s49.sh` dies with status 137 after its first demo: its `stop_demo` does `kill -9` then `wait`, and `wait` returns 137 under `set -e` in this shell (reproduced with a four-line script that has nothing of MASON in it). I did not change the script.
  - `s06.sh` and `s07.sh` failed in the full run on `explore_anyway_before_a_task_starts_and_after_it_skipped_exploring` (`definitions` tests): the scripted agent's `git commit` met an `index.lock` in its worktree. The test passes alone and mostly in the whole binary; across 16 runs of the `definitions` binary the base commit failed 0 times and this branch twice, so I cannot rule out that this stage made a latent race in that test more likely. I found no code of this stage on that path (it writes one row when a step ends and starts one idle thread). `s06.sh` passed when run again; `s07.sh` failed again.
  - All other scripts, including `s21.sh` and `s22.sh`, print OK.
- No test was removed, ignored or loosened and no limit changed.
