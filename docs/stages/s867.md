# s867: favor-remote spills to this machine when GitHub is overloaded

Summary: `favor-remote` now places a run here, under local slots, when GitHub is overloaded (the pool is full with waiters, the account queue is over `remote_queue_max`, or recent pickups are slower than `spill_after`) and this machine has room; a run unpicked on GitHub for `spill_after` is cancelled and runs here instead of waiting out `pickup_timeout`. Decision 0860.

## Built
- `place.rs`: `RemoteLoad`, `RemoteSpill`, `LocalLoad::has_room`, `local_needs`, favor-remote branch of `balance`, `remote_spill_for`.
- `remote.rs`: `Site::spill_after` / `local_room`, `spill_due`, `site_for_task`, `site_for_run`, recent pickup median; plain `remote` no longer spills.
- `config.rs`: `[remote_runs] remote_queue_max` (default 4).
- Tests: table test and reason test in `place.rs`, `an_unpicked_favor_remote_run_comes_back_early_when_this_machine_has_room` (fake GitHub, fake clock, three cases incl. plain `remote`), daemon test `favor_remote_runs_here_only_while_github_is_full_and_this_machine_has_room`. Exit script `scripts/exit/s867.sh`.

## Not verified
- Nothing was compiled or run (builds are refused in the session and the test check was skipped by the owner); expect compile fixes at landing.
- `account_queued` is always `None`: #819's account job count had not landed, so the queue rule is tested only through the pure table.
- Recent pickup times are kept in memory (last five runs this daemon saw), not re-read from run records, so a restart clears them.
- The exit script runs the unit and daemon tests; it does not start a real masond with a fake GitHub as the ticket described.
