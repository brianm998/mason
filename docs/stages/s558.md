# s558: a developing task shows its checks, live counts and what the agent is doing

Summary: A develop step's `run_check` calls now show their phase (waiting, building, running, done), live test counts as a `check <suite>` sub-progress, a per-call history (scope, wait, run time, result) and the agent's latest tool call with its age; rows carry the short form and the home page sums developing tasks by phase.

`crates/core/src/checks.rs` (pure) holds `CheckEntry`/`CheckPhase` and the wording: `check_line`, `check_short`, `doing_text` (open check first, then the tool call with age, or "idle, no check running"), `phase_summary` ("31 developing: 23 waiting for a test slot, 6 running checks, 2 editing"). `Progress` gains `checks`, `tool`, `tool_ms` (in memory; not stored, so the history of a round is lost on a daemon restart).

`hostedcheck::run_with` takes a `CheckProgress` and feeds the same `mason_testing::LiveCount` the test step uses, plus the test executable from cargo's `Running` line; the verdict is unchanged. `jobs.rs` opens one entry per `run_check` call, moves it through the phases around `swap_for` (the wait text is the broker's `wait_text`, as the task shows it; #512's richer data shape had not landed, so this is plain text for it to replace), and closes it green, red (with the failing names) or ended. `rollup` no longer sums sub-counts into an agent step's own figure, so the check's counts do not replace the tool-call count.

Wire: `ProgressCell.checks/tool/tool_ms/doing`, `TaskRow.check/doing`, `HomeView.developing` (all additive). Counts come in steps with the parallel runner (it prints a block when an executable ends); that is accepted.

Tests: core `checks::tests` (phases and times, idle, summary); `tests/hosted_check.rs::a_check_feeds_the_develop_runs_counts_and_phases` (scripted TAP output: the count ends at the parsed 2 passed, the executable is named, the entry ends red with 1 failed). No timing assertions.

Test isolation: `DaemonConfig.launch_frozen_alert` (default on) gates the frozen-launch alert. The launches it counts are process-wide (`mason_step_host::launcher::launching`), so in the `it` test binary one test's step host that took over two minutes to come up raised an alert in every other test's daemon, and the `notify::` tests, which count alerts and announcements exactly, went red in full runs while passing alone. The test support turns it off; the real daemon and `scripts/exit/s108.sh` (a separate `masond`) keep it. This cause was inferred from the code (the failure output gave only test names), not reproduced.

Not verified / not done: the desktop monitors, phone screens and `clients/features.toml` (protected, needs owner approval) were not changed, so clients do not yet show the new fields; `mason task show` / `mason status` text was not extended; the "usually up to" length is the single recorded maximum, not a range; there is no end-to-end run with a fake agent calling `run_check` twice (the exit script covers the core and hosted-check pieces only); I did not run the full workspace.
