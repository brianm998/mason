# s197: retry is idempotent

Summary: A retry may carry `seen` (the run the client was showing) and is refused with 409 "already retried (run R is running)" when the task has a newer run, and a retry of a task whose step is running is refused unless `restart` is given, so two retries sent a second apart no longer restart the step twice.

**Built.**
- `http.rs`: `latest_run`, `last_run` in the task JSON, and `retry` checks `seen` and the running state under a lock (`RETRY_GATE`) so concurrent requests cannot both pass. Failed and needs-attention tasks are still retried without `seen`.
- CLI: `mason task retry` sends the `last_run` it read, and has `--restart`.
- Protocol (additive): `Retry.seen = 3`, `Retry.restart = 4`, `TaskRow.last_run = 25`; `ws.rs` passes them on. The Swift (regenerated `mason.pb.swift`) and Compose monitors send `seen` from the row.

**Tests.** `crates/daemon/tests/retry_idempotent.rs`: the same `seen` twice gives 200 then 409 and one new run; a running task without `restart` gets 409, with it 200; a failed task without `seen` gets 200. `scripts/exit/s197.sh` runs them.

**Not verified.**
- The exit script drives the HTTP router in-process, not a real `masond`; it does not check that the step's command runs once.
- The Swift and Compose changes were not built or run (Compose is generated by Wire in Gradle). The blocker-link "retry" buttons in both monitors send no `seen`.
- A retry of a task in `needs_attention` without `restart` is still allowed.
