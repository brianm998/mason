# s100: tell the owner when a full disk has stopped the pipeline, and why

Summary: When free disk is below the floor, `mason status` prints a STUCK line (and `--json` a `stuck` object), every request the disk holds says so in `mason resources` and `mason task show`, and `disk` is a routed condition (monitor, sound, speech, push after 10 minutes) whose alert counts the tasks held.

What changed:

- `disk` is in `CONDITIONS` and `Routing::defaults()` with the channels of `failed` and `landing`, so `mason notify status` lists it and it can be rerouted. The spoken line is "MASON is stopped: disk is nearly full, 9 tasks waiting."
- Scheduler `plan`: a request the disk gate holds now gets `WaitCause::Disk` whether or not another request is ahead of it (the arm moved before `Behind`/`Exclusive`). The request is still queued the same way, so grants, line order and `position` are unchanged.
- `Broker::disk_held()` counts the requests waiting on the disk. The `disk` alert text ends "; N tasks waiting".
- `/status` carries `stuck: {cause, free_mb, floor_mb, tasks_waiting}` only while free disk is below the floor; `mason status` prints `STUCK: no new compile or agent session can start: disk has 18 GB free, floor 20 GB; 9 tasks waiting` near the top.

Tests: scheduler (`every_request_in_line_behind_the_disk_gate_...`), core (`a_full_disk_is_a_condition_...`), daemon `tests/disk.rs` (alert counts tasks) and `tests/stuck.rs` (a real `masond` and the CLI). Exit script: `scripts/exit/s100.sh`.

Not verified: delivery to push/email was not tried (only the announcement the monitor speaks is checked); no real full volume; `mason task show` was checked through the shared `explain_task` path, not by running the CLI on it; the full workspace suite was run only through the MASON check.
