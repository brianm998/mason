# Stage 12: SwiftUI monitor (owner checkpoint)

## Built
`clients/swift/`: a Swift package with a `MonitorCore` library, a `MonitorUI` library and a macOS app, laid out as Part 17 asks.
- **Top bar on every page**: back (⌘[), forward (⌘]), home; the attention indicator, only while something needs a look; the project filter; LLM usage lines; one fixed-size count tile per state (a large count over a one-line label, tinted when the state wants the owner, with a tooltip, a dash while disconnected, a click expands and scrolls to its sidebar section); add task; mute.
- **Banners** under it, only while true (connection lost, pauses, a refused definition).
- **Sidebar on every page**: a Home row; search with name, title and body checkboxes; a collapsible section per state in the design's order with its count (failed, landed and canceled start collapsed; choices remembered per device); then Landing, LLM usage, Pipeline and Health. Rows show key and title, project, activity, time in state, progress cells, the model while one runs, and a link for each blocker.
- **Main view**: exactly one of Home, task detail or another page; selecting a row replaces Home while the bars stay. **Home** has the status, the attention queue (decision cards you can answer there), active models with task and step, the session-limit stepper, the landing queue and per-stage detail, and **no counts**. **Task detail** has progress, activity and why it waits, the actions the daemon allows, copy buttons (key, branch, worktree), why exploring was skipped with "Explore anyway", the decision card (options, "Other" with a text box, evidence), steps, tests, debts, plan, task text and the log.
- **Progress cells** as the legend says (filled, part, hatched with a label, empty), no percentages, amber and never red when slow, ranges only with enough history.
- **Browser-style navigation** (back, forward, home) and `mason://task/12`-style deep links (parsed and tested; `scripts/bundle-monitor.sh` builds the app bundle that registers the scheme). **Text scale** with ⌘+ ⌘− ⌘0 reflows real text.
- **`monitor-tool`**: `conformance` (dump what the client shows at every demo checkpoint), `snapshot` (render screenshots), `answer` (answer a question exactly as the card's buttons do).
- `docs/decisions/0009-swiftui-monitor-readings.md`, `scripts/exit/s12.sh`, `scripts/exit/s12-real.sh`, a `monitor-swift` CI job.
- Server additions the client needed: `TaskRow.body`, and `route`, `started_at`, `explore_returns` on the task detail.

## Exit test
`bash scripts/exit/s12.sh` passes: the package builds and its 12 tests pass; the monitor's visible items match the daemon's views at all 8 `--demo` checkpoints through the same `conformance check` the other client will use; a planted difference (a wrong count and a missing button) is caught; the app bundle with the `mason://` scheme builds; and the real app launches and holds a connection to the daemon.

### Manual run on a real daemon
`bash scripts/exit/s12-real.sh` (the scripted agent stands in for the model): a task in a scratch repository asks a question; `monitor-tool answer` does what clicking an option on the decision card does (finds the card in the Home view, sends the answer with the card's hash and the owner's identity):
```
task #0 is waiting for the owner
card: Should the token expire after one hour or one day?
options: One hour, with refresh tokens (recommended) | One day, without refresh tokens
answered task #0 with option 1; it is no longer waiting for the owner
task #0 resumed after the monitor's answer and landed
  state     landed       failures  0
1 intervention(s) for 1 landed task(s): 1.00 per landed task
```
**What I saw and did not see.** The first attempt was refused with "'' is not the owner's identity": the monitor did not say who it was. It now sends its identity with every command, and the second run landed the task. I did not click through the real window myself (I cannot drive the app's controls here), so the click path is covered by the same model code the buttons call, plus a launch check, not by a person using the window.

## Things to judge and known gaps
- **Usage lines are squeezed out of the top bar at 1440 points**: eleven fixed-size tiles take the width, so "claude: n of m sessions" shows as an ellipsis until the window is wider. The design says narrow windows squeeze text, never the tiles; if you want the usage lines to keep room, the tiles can be narrower or wrap to a second row.
- **Tile labels read "needs attention"** (the state's name); the sidebar section says "Needs you". Say if the tile should too.
- **The live log is the daemon's last 40 lines, refreshed when something changes.** A step that is silent for a while does not tick. A streamed log is a later change.
- **Not in the task detail yet because the daemon does not have the data**: code changed (a diff), per-check results, token counts. The sections will appear when the server supplies them.
- **The conformance run reads the model, not the real accessibility tree** (see decision 0009).
- **Demo data shows "0 s" in state** for most rows because the demo plays in a few seconds.
- **Deep links** are parsed and tested, and the bundle script builds the app that registers `mason://`; I did not register it with LaunchServices and open a link from outside, which needs the app installed.
- **No signing or notarization**, and no Xcode project; the package builds the app with `swift build`.
- **CI**: the new `monitor-swift` job has not yet run on GitHub (it will on this push).
