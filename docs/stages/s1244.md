# s1244: a taken-over check no longer orphans its run (#1253)

`take_over_remote_where` released an earlier run's ledger entry and broker meta but left its
hold file, `.remote` record and ref, and `reap_adopted` only walked the broker's adopted list,
so nothing ever cancelled or reaped them.

The broker now keeps each taken-over `(key, record)` in `taken_over`. `reap_adopted` merges
them into the adopted list (still not counted: "counted once" of #818 holds), so `judge` and
`reap_pass` decide as before: a finished run is reaped, an unwanted one is cancelled, one the new
call attaches to (not superseded, newest) is kept. An entry is forgotten once its record and hold
are gone. `holder_views` now says `being cancelled` only for runs the reaper acts on.

Not verified: no run of the tests or an exit script by me; the exit script is not written (the
unit tests cover the reap pass with a fake GitHub). The in-memory list is lost on restart, where
adoption rebuilds it from the hold files.
