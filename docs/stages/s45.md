# s45: Live step progress, the daemon's record and the push

Summary: every running step keeps a live progress record in the daemon (what it counts, done, total, last output, when it last moved), fed from its step host's output as it arrives, pushed to monitors as `StepProgress` (at most once a second for output alone) and carried by the views.

Task #13 (GitHub #18), the first of four tickets on live step progress. #19 adds real counts for agent steps, #20 for the other step kinds, #21 shows it in the monitors and the CLI.

## Built
- **`crates/core/src/progress.rs`** (pure): `Progress` (run, step, unit, `done`/`total` as `Figure { value, source }` with `Source` none/reported/counted/history, `message`, `Output { lines, bytes, last_output_ms }`, `started_ms`, `updated_at_ms`, `subs`, and a per-stream high-water mark). `output(stream, offset, bytes, at)` counts only bytes beyond the mark, so a re-read adds nothing and `updated_at` moves only on new bytes. `middle_half` is the rule `typical()` in views.rs now shares (at least five samples); `history_total` is its high end. `Throttle` (`note`, `take_due`) is the one-a-second coalescing.
- **Store, migration 12**: `step_progress` (one row per open run, columns), `step_progress_subs`, `step_history` (successful runs only). `put_progress`, `progress_rows`, `drop_progress`, `drop_progress_except`, `record_history`, `history_samples`.
- **Step host / adapters**: `collect_to_file_observed` (every chunk, live and from disk; `collect_to_file` unchanged). `SessionSpec.progress` (a `ProgressSink` of host id, offset, bytes) is called by `hosted::follow` and `drain_disk`.
- **Daemon `progress.rs`**: the `Book` of live records, `progress_begin/observe/catch_up/report/subs/finish`, a 250 ms ticker that flushes due sends and writes records every 3 s, and `progress_bus`. `start_job` opens the record before the job and closes it after (also after a panic). `command_job`, suite steps (`run_hosted`) and `agent_job` feed it.
- **Views**: a running step's `ProgressCell` carries the live record (`done` = lines so far, unit `lines`, source `counted`, lines, bytes, last output, times, run); the label stays "running"; a finished step's cell is as before. No `ViewUpdate` is sent for output.
- **Protocol (additive, PROTOCOL stays 1)**: `ProgressCell` 6 to 15, `ProgressSource`, `ServerMessage.step_progress = 8` (`StepProgress { seq, task, run, step, progress, now_ms }`), `Welcome.now_ms = 9`. `mason.pb.swift` regenerated with `scripts/gen-clients.sh`; the Compose client is generated by Wire at Gradle build time (not run here).
- **`GET /tasks/{id}/progress`** (and the `Raw` command) and **`mason task progress <id> [--watch] [--json]`**.
- Decision record: `docs/decisions/0023-step-progress-readings.md` (throttle, ticker, persistence, history total, label, restart rule).

## Tests
- core: line and byte counts, dedupe by offset and stream, `updated_at` unmoved without output, reported figures win over counted, middle half with 4 samples (none) and 5, a history total is never real, a burst of 10,000 lines gives one scheduled send and none at once, urgent changes go at once.
- store: migration 12 on an existing database, put/replace/drop of records with marks and sub-counts, rows of runs that are not open removed, history per project and step.

## What testing found
- Run ids and task ids start at 0, so "a cell has a run" cannot be told from `run != 0` (proto3 omits 0); the exit client recognises a running cell by its state and lines instead.
- The first version of the exit script evaluated its wait condition once, not on each poll; the view snapshot then waited out the whole step. Fixed by polling a function.
