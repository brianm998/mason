# s851: the Compose conformance dump no longer lags the daemon by a step

Summary: The Compose conformance tool now waits for the views of each step (a new `lastViewSeq` that only applied views move) and a 1.5 s quiet window, instead of treating the events message's seq as proof the views had landed.

**Cause (hypothesis from the failing job's dump diff, not reproduced locally).** The harness decided a step was done when `lastSeq` reached the daemon's status seq, but `Model.apply` advances `lastSeq` on the events message, which the daemon sends before the views of the same rebuild (crates/daemon/src/ws.rs). A 300 ms quiet window then passed on a loaded runner, so the dump held rows the server had already removed.

**Change.** `Model.lastViewSeq` (views only, never moved back by a stale view); `Tool.kt` `step` waits for it, bounded by 60 s, with a quiet-window fallback for steps whose views did not change; `settle` uses 30 x 50 ms. The check, expected side and item lists are unchanged.

**Follow-up.** The Swift monitor's conformance path was not checked here.
