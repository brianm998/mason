# s119: a brief git failure decides nothing

Summary: A failed fetch no longer fails a step (it goes on from the last-known base), a lock error or git deadline in `prepare` is waited out for up to 15 minutes instead of failing the task, and an unreadable `landing.toml`, `mason.toml` or base listing now holds (queue untouched, error reported, alert after 5 minutes) instead of silently becoming the defaults, the built-in pipeline or an empty number list.

## What changed

- `jobs::prepare`: a failing fetch is logged and the step goes on if the base ref exists. The locked part (worktree, status, catch-up) runs under `wait_out_environment`: timeouts and lock errors (`index.lock`, `packed-refs.lock`, "another git process") emit `WaitStarted`, back off 1 s doubling to 30 s, retry for 15 minutes, then fail naming what failed. Real errors fail at once. `prepare_worktree_only` does the same.
- `landing::read_config` separates "no such file at that commit" (defaults) from "git failed" (`ConfigError::Unread`). `form_and_start` then starts nothing, fails nobody, looks again in 2 s, and raises the `landing-config-unread` alert after 5 minutes. `load_config` keeps its signature for the views.
- `defs::read_definition`: only "no such base commit" (rev-parse exit 1) or "the base has no `.mason/mason.toml`" give the built-in definition. Any other git failure is returned as an error, which goes through `definition_error`; the definition in force stays.
- `numbers::base_paths` and `added_files` return `Result`. `ensure_numbers` fails (it no longer reserves against an empty list); the agent step waits out environmental failures first; `check_numbers` in landing waits, and a real error is a `Failed` verdict, never a pass.

## Not verified

- I could not run cargo in this session (the shell hook sends every cargo command to the shared queue), so everything here was checked only by `run_check`.
- `scripts/exit/s119.sh` assumes landing holds (does not fail) while the remote is gone; it has not been run by me.
- The lock-error classification is by git's message text; other git versions may word it differently.

The fetch_stall test no longer expects the stuck task to fail with "timed out" (the old behavior this task removes). It now asserts the task is not failed and reaches development only after the 8 s git deadline, so a skipped fetch is still caught.
