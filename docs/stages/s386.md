# s386: a task's test step runs only the tests its change needs, when the suite says how

Summary: a suite may say how to run only some of its tests with six `narrow_*` keys. In a task's test step, such a suite runs only the test units the change needs:
- units in a test file the change edits (for a file split into classes, the classes holding an added line), and
- units whose text names a file the change edits, by its stem as a whole word.

It runs whole when a changed path matches `narrow_never`, when nothing is picked, or when more than half would be. A narrowed run records no evidence, no "green at base" and no run time, and its baseline at the base is not cached. The closing note says what it ran. The landing batch always runs the suite whole.

## Keys

- `narrow_command`: the command, with `{tests}`.
- `narrow_tests`: a glob for the test files.
- `narrow_each`: one unit's part of `{tests}`. `{}` is its name (default `{}`); `{file}` its file under `narrow_root` (`tests/test_engine.py`); `{path}` its file from the repository root (#924). For a `narrow_split` unit `{file}` is the file holding the class, so `"{file}::{}"` gives `tests/test_x.py::TestA`. pytest needs paths, so use `{file}`: `mason definition check` warns when a pytest `narrow_command` uses `{}` alone.
- `narrow_root`: for a file that is one unit, the path prefix dropped before the rest becomes its name (`/` to `.`, extension dropped).
- `narrow_split`: for a file holding many units, a regex whose matches start one each, named by its first group.
- `narrow_never`: globs of changed paths that make the suite run whole.

## Why

On 2026-11-14 star #216, a 48-line drop-zone change in both clients, ran all 808 desktop tests and all 374 gui tests in its test step, and the owner asked for lighter tests for changes like it. Star's t1 suites also run in the landing batch, over the batch's combined change, so the full run still happens before anything lands. Per task it duplicated that, and `test-gui` needs the whole machine. The cost #209 showed, a skipped desktop run letting a red reach develop, does not arise: nothing is skipped, and the batch runs everything.

## What changed

- `crates/testing/src/model.rs`: `Narrow`, plus `Suite::narrow` and `Suite::narrowed`.
- `crates/testing/src/narrow.rs`: `units`, `select` and `command`.
- `crates/definition/src/testing_parse.rs`: the `narrow_*` keys and their checks.
- `crates/daemon/src/suites.rs`:
  - `narrow_for_step` in the test step's loop.
  - `added_lines` reads `git diff -U0`.
  - No evidence or "green at base" for a narrowed green, its baseline uncached, its time not recorded.
  - Its note goes into the closing note.
- Tests:
  - `narrow::tests` (unit).
  - `the_narrow_keys_parse_into_one_narrow_and_their_mistakes_are_named` (`crates/definition/tests/testing_tables.rs`).
  - `a_task_test_step_runs_only_the_tests_its_change_needs_and_proves_nothing_for_the_tree` (`crates/daemon/tests/testing.rs`).

## Not verified

Star's suites gain the keys in a separate commit to star's `.mason/mason.toml`. The heuristic (a test that names a changed file) misses a test that depends on a change without naming it. The landing batch's whole run is what catches that.
