# s460: APNs push channel from the daemon to paired iPhones and iPads

Summary: The daemon can now push alerts straight to paired iPhones and iPads through Apple's push service with the owner's own key (new `apns` channel, per-device tokens a device registers for itself, dead tokens cleared), on by default for needs-attention, failed, landing, stalled and daemon-down once `[apns]` is set up.

## What changed

- `crates/store`: migration 41 adds `devices.push_token` and `push_env`; `set_push`, `clear_push`, `clear_push_token`, `push_targets`, `push_of`; `revoke_device` clears the token.
- `crates/core`: `POST` and `DELETE /devices/self/push` are allowed for viewers too (why it is safe: decision 0453). `Channel::Apns`, and `apns` at 0 minutes in the default routes of `needs_you`, `failed`, `landing`, `stalled`, `daemon_down`.
- `crates/adapter-api/src/apns.rs`: key parsing, ES256 JWT cached 50 minutes, payload (`aps` alert, `thread-id` = project, `mason` = kind, key, task), one POST per device, answer classification. `Curl` gains `http2` and `config()` so a test can check what is on stdin.
- `crates/daemon`: `[apns]` in `notify.toml`; `/devices/self/push` handlers in `lan.rs`; `send_apns` in the dispatcher; `mason notify test apns`; `reaches_without_monitor` counts `apns` with a key and at least one device token; `mason notify status` shows `apns` and the device count.
- Docs: `docs/DESIGN.md` Part 19 note. A daemon that is down cannot send its own "daemon down" push, and that stays.
- Tests: adapter-api (JWT header, claims and signature against the public key, payload, host choice, the curl config carries the JWT and nothing else does, answer kinds), core (access rules, routing defaults), `crates/store/tests/devices.rs`, `crates/daemon/tests/apns.rs` (a fake APNs on loopback: owner-only, viewers option, 410 clears the token, readable key refused, reaches-without-monitor, test command, self-only registration); exit script `scripts/exit/s460.sh` (ran green here against a real masond, curl and openssl).

## Config

```toml
[apns]
key_file = "/path/AuthKey_ABC123DEFG.p8"   # mode 0600
key_id   = "ABC123DEFG"
team_id  = "TEAM123456"
topic    = "com.example.mason"             # the app's bundle id
viewers  = false                           # true: viewer devices get pushes too
# endpoint = "http://127.0.0.1:9999"       # tests only
```

## Not verified

- A real push to a real phone, and a real `.p8` from Apple (it may be PKCS#8 without the public key; `ring` is expected to accept that, but only generated keys were used). Owner check.
- Real HTTP/2 over TLS to `api.push.apple.com`: the tests and exit script use cleartext through the endpoint override, so curl's `http2` option was exercised only as an h2c upgrade against an HTTP/1.1 server.
- The task spoke of "update/daemon-restart conditions that already alert"; no alert kind with that name exists, so `daemon_down` is the one routed.
- `mason devices list` does not show which devices have a token.
- `cargo test -p mason-store --lib` has one failure, `codec::tests::every_event_kind_round_trips` (28 samples against 26 kinds); it fails the same without this change.
- The full workspace test and `run-exit-scripts.sh` were not run (the test step was skipped for this task); only the touched packages, `s460.sh` and `cargo fmt` were. `cargo clippy -D warnings` was clean for the workspace before the last test additions; a final run was blocked by the build queue.
- Nothing runs XCUITests or shows anything on the Mac's screen.
