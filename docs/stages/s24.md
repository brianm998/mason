# Stage 24: Discovery, pairing and mobile

Summary: A phone can now be paired with MASON over the LAN: an explicit `[lan]` setting (off by default, loopback unchanged) starts a separate TLS listener that serves only paired devices, with single-use 120 s pairing codes, per-device hashed tokens, owner and viewer roles, immediate revocation, a pinned self-signed certificate and an `_mason._tcp` mDNS record; the Swift and Compose cores gain pairing, pinning, discovery parsing and the phone layout rules, and `s24.sh` checks the daemon side end to end with a fake phone. No real phone, simulator, emulator or Wi-Fi was used.

## Built
- `crates/core/src/access.rs` (pure): `Role`, `decide(role, method, path)` and the pairing-code state machine (`Pairing`: issue, attempt, 120 s expiry, lock after 5 wrong tries). Unit tests for each rule.
- Migration 19 and `crates/store/src/devices.rs`: `devices` (name, role, SHA-256 of the token, created, last seen, revoked). Tests in `crates/store/tests/devices.rs`.
- `crates/daemon/src/lan.rs`: the self-signed certificate (rcgen, kept in `<data dir>/lan/`, key `0600`), the TLS listener (rustls with the `ring` provider, served with hyper-util), the token guard (Bearer on every route including the WebSocket upgrade; `x-mason-as` replaced), `POST /pair`, `POST /pair/codes`, `GET /devices`, `POST /devices/{id}/revoke`, `GET /lan`, mDNS through `mdns-sd`. `config.rs` reads `[lan]` strictly; `masond --lan` and `--lan-port`. `daemon.json` gains `lan_port` and `lan_fingerprint` only when LAN is on. `ws.rs`: the peer's role gates typed commands, `Welcome.role` (protocol field 10, additive), and a revoked device's open sockets close.
- CLI: `mason lan status`, `mason pair [--viewer]`, `mason devices list|revoke ID`.
- Swift: `Pairing.swift` (pair URL, pin, token store keyed by fingerprint with a Keychain implementation, a pinning `URLSessionDelegate`, `Pairing.pair`, `PinnedSocket`), `PhoneLayout.swift`, a Bonjour `NWBrowser` and `ServiceRecord` in `Discovery.swift`, a `MonitorPhone` target (`Phone.swift`: tiles, Home row, sections, task detail with decision options, cancel, skip, land now, mute, landing and usage lists), iOS added to `Package.swift`, and `ios/MasonIOS` (app entry and an `Info.plist` with `NSLocalNetworkUsageDescription` and `NSBonjourServices`). Regenerated `mason.pb.swift`.
- Compose: `Pairing.kt` (pair URL, pin, `PinningTrustManager`, token store keyed by fingerprint, `ServiceRecord`) and `PhoneLayout.kt` in the core; `clients/compose/android` with an NSD browser.
- `clients/features.toml`: three `[phone.*]` deliberate differences, in their own commit (see below).
- `scripts/exit/s24.sh`, `s24-real.sh`, `s24-manual.sh`, `scripts/exit/fixtures/s24/fake_client.py`, decision 0051.

## Exit test
`bash scripts/exit/s24.sh` ends with `s24: all checks passed` (46 PASS lines). A real `masond` with `[lan]` on a random port beside loopback, and a fake phone over TLS (Python `ssl`, pinning by SHA-256, the s45 WebSocket framing):
- Default: no `lan_port` in `daemon.json`, `mason lan status` says off, `mason pair` says LAN is off. A `[lan] enabled = "yes"` file stops `masond` naming `daemon.toml: lan.enabled`.
- Unpaired: `GET /status`, `GET /tasks`, `POST /tasks/1/cancel`, `GET /devices` and the WebSocket upgrade all return 401; a made-up token and an `x-mason-as: <owner>` header do not help.
- Pin: a client pinning a different fingerprint refuses the connection; `GET /lan` (what the mDNS record is built from) has `proto`, `fp`, `version`, service `_mason._tcp.local.` and an instance `MASON on <host>`, and `fp` equals the served certificate's SHA-256.
- Codes: `1234`, `abcdefgh`, a nine-digit code and an empty one are refused (400); a code pairs an owner, a second use is refused, another pairs a viewer.
- Owner: `GET /status` 200; a command is answered by its handler (not refused); an owner token can issue a code; the WebSocket Welcome says `role: owner`; a typed command with a forged actor is allowed.
- Viewer: `GET /status` 200; `POST /tasks`, `POST /tasks/999/cancel`, `POST /pair/codes` and `GET /devices` are 403 even with `x-mason-as` set to the owner; subscribe gives a snapshot; a typed command gets 403; Welcome says `role: viewer`, `owner` false.
- Revocation: `mason devices revoke` makes the token 401 at once and closes the open socket; the owner device is unaffected.
- Lockout: five wrong codes lock; the right code is then refused (429); a newly issued code works after a lockout.
- The key file is mode 0600, and no `mt_` token or 8-digit code is in `masond.log`.

Also: `cargo test` (core access tests, store device tests, daemon config and lan unit tests); `gradle --offline :core:test` (PairingTest, 8 tests) passes; the Swift pairing, pin, discovery and phone-layout tests (`PairingTests`, 8 tests) pass.

## What testing found
- The first `s24.sh` run found the `mason lan status` subcommand word was not consumed, so the CLI printed help; fixed.
- `protocol` has a hand-built `Welcome` in a unit test that needed the new field.
- The owner "command" check first assumed a missing task gives 404; the handler gives 409 or 404 depending on the path, so the check says "answered by the handler, not refused".
- `mdns-sd` logs an error for each virtual IPv6 interface it cannot send on (`awdl0`, `utun*`). It still registers; it is noise, not a failure, and is left as is.

## Not done, and not verified
- **No real phone, no Wi-Fi.** Pairing a real phone over Wi-Fi (`s24-real.sh`) was not run, and real mDNS discovery by another device was not verified: `s24.sh` checks the record the daemon hands to the advertiser, not what appears on the network. This is left for the owner.
- **No simulators or emulators.** `s24-manual.sh` was not run. Conformance on iOS simulators and Android emulators was not run.
- **The Swift package could not be built in full here**, because `swift-protobuf` could not be fetched with no network. `Pairing.swift`, `PhoneLayout.swift` and `Discovery.swift` were compiled and their 8 tests run in a scratch package with only the files they need. `Phone.swift`, `PinnedSocket`/`Pairing.pair` (which are under `canImport(CryptoKit)` and use `MonitorSocket`) and the iOS app source are written but were not compiled against the real `MonitorCore`, and nothing was built for iOS. There is no Xcode project for `ios/MasonIOS`; making one is left.
- **The Android module was not built.** `clients/compose/android` is not in `settings.gradle.kts`, because the Android Gradle plugin was not resolved here. No Android UI exists beyond the NSD browser; the Compose phone screens, QR scanning on either phone, the Keychain/Keystore-backed store for Android, and the code-entry screen are not built. The Swift app has no QR scanner or code-entry screen either (the pair URL can be handled by a `mason://` link). The pure parts are tested.
- **Phone features are partial.** The Swift `Phone.swift` covers home, task lists and detail, decision options, cancel, skip, land now, mute, landing queue and usage as simple lists; the session limit control and speech on the phone are not built, and the catch-up from the last event on opening is the existing resume logic, untested on a phone. Background alerts through ntfy are the Stage 23 channel (the phone subscribes with the ntfy app); nothing new was built for them.
- **`Hello.token` is not used.** The token is checked on the upgrade request, so an unpaired WebSocket never reaches a Hello (decision 0051).
- **Features parity.** Three `[phone.*]` tables are recorded in `clients/features.toml` as data the parity gate does not read. Adding `ios` and `android` to `CLIENTS` in `crates/conformance/src/features.rs` would change a gate, and was not done; it waits for the owner. The `features.toml` edit is in its own commit and also waits for approval.
- **`scripts/run-exit-scripts.sh`**: `s20`, `s42`, `s44`, `s49`, `s52` and `s53` were already failing on the base before this stage (per the s23 notes). They are not fixed here and may still fail.
- The whole-process Rust tests (`cargo test --workspace`) and the exit scripts are run by the pipeline's tests check, not repeated in this note.
