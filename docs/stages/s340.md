# s340: a test step holds the whole machine only while an exclusive suite runs

Summary: a test step queues suite by suite when one of its selected suites needs `exclusive`, not only when one builds first. Each suite holds what its own run needs and gives it back, so `exclusive` is held only while an exclusive suite runs. Builds and other projects' work run between and beside the rest of the step. Base-red checks still go with suites that build, as before.

## Why

On 2026-11-14 the queue showed 27 tasks developing and 7 testing, with the CPU at 8–14%. A star test step (#293, then #197) held one lease of `compile + exclusive + test-suite` for its whole run, about 17 minutes. Only `test-StarCpp-qos` (about 2 minutes) needed `exclusive`; the rest were five builds and plain test suites. While it held `exclusive`, 26 compile requests waited (mason's `run_check`s and builds, star develop builds), and five more star test steps queued for `exclusive` behind it. Star's suites have no `build`, so the step never queued suite by suite (decision 0173): it took the union of every selected suite's needs at once.

## What changed

- `crates/daemon/src/suites.rs`: `builds_per_suite` is also true when a selected suite's run needs `exclusive`. In `run`, `per_suite` (which drives leasing, and the gates' lease) is set the same way, and a separate `builds` flag keeps base-red checks where they were.
- `crates/daemon/src/jobs.rs`: comment only. The step-wide acquire is skipped through `builds_per_suite`.
- Test: `a_step_with_an_exclusive_suite_holds_the_machine_only_for_that_suite` (`crates/daemon/tests/scheduling.rs`). Without the change, the plain suite runs holding `exclusive,test-suite`.

## Not verified

Throughput on the live queue. Watch `mason resources` the next time a star test step selects an exclusive suite: the holder should show `exclusive` only during `test-StarCpp-qos`, `test-gherkin`, `test-gui` or `test-desktop`.
