# s1059: MASON updates itself by priority

Summary: masond now starts its own updates, ranks each by what it brings (urgent, normal, off-peak, none), picks the moment by what a takeover would interrupt, and lets a newer build replace a waiting one.

## Change

- `crates/daemon/src/update_plan.rs` (new): pure rules (path classification, urgency, the cost of a takeover, the decision, merging) and the glue that reads the mirror, the store and the scheduler. A planner loop looks every 30 s; `check_once` files what it finds.
- `update.rs`: `[auto]` in `update.toml` (`enabled`, `normal_max_wait_s`, `offpeak`, `cost_max`, `none`, `low`); `Check.moved`; `Request.planned` (the planner has chosen the moment, so the s473 gap is skipped) and `Request.urgent` (the build is not held behind task work); the landing drain stops when a newer build replaces the waiting one; the banner and `mason update status` show the waiting update, why, what it waits for and the latest time.
- Cost counts: agent `run_check` calls without a `call_id` (guard in `TestChecks::run_scoped`), test steps mid-suite (guard in `suites::run`), running landing batches, and an exclusive holder (`Broker::exclusive_running`). A normal update never goes while an exclusive request runs.
- `mason task update-priority <id> urgent|normal` (owner only, `POST /tasks/{id}/update-priority`) is kept in `update-urgent.txt` in the data dir.
- Path rules: the owner's `update.toml` wins, then the repository's `.mason/update-priority.toml` (`none = [...]`, `low = [...]`), then defaults. Entries are `dir/` prefixes, `*.ext` top-level endings or exact paths.
- Nothing is scheduled while the channel is switched to an improvement's branch (the project's `switch` setting decides that takeover).
- Unchanged: rollback, the self-test, the no-downgrade rule, the landing drain and `takeover_wait_s`; `mason update` and "Update now" still go at once.

## Trust

`update.rs` is protected (updates and rollback guards). It needs these edits to carry the new request flags, the replace check inside the drain, the banner text and the trigger from `check_once`; none of the guards is loosened.

## Not verified

Tests ran only through run_check. The real-daemon tests in `crates/daemon/tests/it/update.rs` assume the scripted agent's `run_check` carries no call id. The off-peak window is only unit-tested with a fake minute of the day. A planned update replaced while it builds wastes that build. Release-channel installs are not scheduled automatically.
