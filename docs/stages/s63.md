# s63: Monitors show the tier and the real model in use: "deep (Opus medium)"

Summary: every place a model is shown (task row, home's active models, each run in the task detail, the editor's inspector, `mason task show` and `mason status`, with `--json`) now carries one daemon-made string such as `deep (Opus medium)`, built from what each step run actually launched, so a retry, an override and a restarted daemon all show the truth.

Task #31. Builds on s57 (task #26), whose `tiers::launch` and mapping this reads back.

## Built
- **Store**: migration 14 adds `step_launches` (PRIMARY KEY run, seq): kind (`launch`, `retry`, `resume`, `reattach`), tier, level, the mapped model and effort, the model and effort passed to the CLI, provider, where each came from, retry n of max, the model moved up from, whether the owner overrode it, and the model the CLI reported. `Store::record_launch`, `set_reported_model`, `launches(run)`, `launches_for_task(task)`. The daemon writes it, as it does `step_progress`; it is not rebuilt by event replay.
- **Pure core** (`tiers.rs`): `describe(tier, provider, model, effort, &Note)` replaces the old `describe` (which was only used by its own test), plus `describe_request` for the inspector (`deep at high → Opus max`). `Launch` gains `overridden` (a runtime or per-task override named the model or effort).
- **Daemon**: `jobs.rs` writes a row at every session start: first run, each ladder retry (with its retry number and the model it moved from), each resume after a provider hold. A session found again after a restart keeps the model and effort recorded for it, and a `reattach` row is written only if the run has no record at all. New `launchview.rs` turns rows into `ModelUse` (display plus parts), makes the expected use of a step that has not started, and builds the inspector line. `views.rs`, `http.rs` (`/tasks/{id}`, `/status`) use it.
- **CLI model name**: `AgentEvent::Model`, read from Claude's `system/init`, goes through the runner to `SessionSpec.on_model` and is stored as `reported_model`. `fake-claude` now reports the model it was given with `--model`.
- **Protocol** (additive): `ModelUse`; `TaskRow.display`/`model_use`, `ActiveModel.display`/`model_use`, `StepLine.launches`, `Inspector.launch`/`launch_from`. The old `model` strings are still filled. Swift protobuf regenerated with `scripts/gen-clients.sh`.
- **Monitors** (both, in parity): task row, home active models, task detail (every launch under each run), editor inspector. `clients/features.toml` has `model-display`; the conformance items (Rust, Swift, Kotlin) include the display string on rows, active models and steps.
- **CLI**: `mason task show` prints `model`, its why, and each run's launches; `mason status` prints `active:` lines; `--json` carries `model` (display, tier, level, model, effort, provider, why, kind, retry, expected, overridden...) and `steps[].launches`.

## Display forms
`deep (Opus medium)`, `light (Haiku)`, `deep (Codex default, high)`, `deep (Opus medium, retry 1 of 2)`, `deep (Opus medium, override)`, `Opus medium` (no tier), `deep (Opus medium, expected)` (not launched yet).

## What testing found
- A task in `queued` is waiting for its first session and has no step state, so it shows no model; the "expected" form appears only for a task already in a step state that has not launched (for example a later step waiting for a session). That window is too short to poll, so the exit script does not assert it.
- With one session allowed, a second task stays queued; the exit script therefore checks a changed provider file by what the second task launches once the first is done, while the first, still running, keeps its string.
