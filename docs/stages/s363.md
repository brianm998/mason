# s363: an agent's own `mason run` waits do not use up its budget

Summary: while an agent step runs, time its own `mason run` commands spend waiting in the resource queue is added to its deadline when they are granted, as a `run_check`'s wait already was. An agent that has to wait for compile slots or the whole machine keeps the working time its budget allows.

## Why

On 2026-11-14 star #242's develop step (budget 4 h) failed at exactly 4 h: "the step ran out of time". Its plan needed a release build of star's cli and a run over 19 frames at 4240 × 2832, each through `mason run` (the build for a compile slot, the run for the whole machine). As a develop-stage request it ranks behind every test step, review and landing (s349), and the queue held 40–50 requests that afternoon, so those commands waited a long time. Only `run_check`'s queue time was added to the deadline (`TestChecks`), so the waits counted as work. The agent left a draft script with its placeholders unfilled and no masters.

## What changed

- `crates/daemon/src/sched.rs`:
  - `Broker::credit_waits_to` and `stop_crediting_waits` keep a task's agent deadline (`DeadlineExtra`) while its agent step runs.
  - When an external (`mason run`) lease of that task is granted, the time since it was opened is added to that deadline.
- `crates/daemon/src/jobs.rs` (`agent_job`): registers the step's `DeadlineExtra` and unregisters it when the step ends (a drop guard).
- Test: `an_agents_mason_run_wait_is_added_to_its_deadline_when_granted` (unit, `sched.rs`). Without the change it fails.

## Not verified

A `mason run` the agent starts in the background and that is granted after its step ended adds nothing, which is intended. A daemon restart mid-step registers the restarted step's deadline afresh. Waits granted before the restart were added to the old daemon's copy of the deadline, so the restarted session gets only its remaining budget.
