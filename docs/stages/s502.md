# s502: further compiles wait while macOS's syspolicyd is overloaded

Summary: a new `compile` gate holds further compiles while `syspolicyd` uses 300% CPU or more (`[cpu] syspolicyd_max_pct`), so MASON's builds and test runs cannot swamp the Mac's code checks again.

## Why

On 2026-11-16 `syspolicyd` climbed to 640–770% CPU over the morning. At 09:55:36 WindowServer's watchdog killed the owner's session: its main thread had not answered for 40 seconds, while `syspolicyd` had 17 of its 40 threads running. Programs that need a code check waited on `syspolicyd`, so after logging back in nothing worked, and the owner rebooted.

Measured after the reboot on this Intel Mac (macOS 15.8.2):
- The first launch of each new 40 MB test binary cost `syspolicyd` about 0.3–0.8 CPU s. A 0.5 MB binary cost about 0.03 s.
- Ad-hoc signing made no difference: 40 unsigned and 40 signed first launches, interleaved, cost 33.0 s and 34.2 s.
- A repeat launch cost about nothing, and so did writing a binary without running it.
- One cold workspace build links about 180 executables over 1 MB, and every relink makes fresh ones. Ten tasks building and testing at once is the load that took the session down.

The CPU gate cannot see this. The scans run in Apple's process, and the compiles that cause them spend that time waiting on it.

## What changed

- `crates/daemon/src/policyd.rs` (new): reads `syspolicyd`'s CPU time every 5 s with `/bin/ps`. `ps` is set-uid root and can read a root process; `proc_pid_rusage` cannot. It reports the busiest 5-second interval of the last 30 s. A missing or restarted `syspolicyd`, or a failed `ps`, gives no reading, and no reading never holds anything.
- `crates/scheduler/src/plan.rs`: `PolicyGate` and `WaitCause::Policy`. As with the disk stall, the gate holds only a further compile while one is already running, so a busy `syspolicyd` that is not ours can never hold the queue for good. Agent sessions are not held.
- `crates/daemon/src/sched.rs`: `[cpu] syspolicyd_max_pct` in resources.toml (default 300; 0 turns the gate off). It is a live gate, settable while masond runs like the others, and the compile rules in `mason resources` name it.
- A held compile says `compile waiting: syspolicyd is at N% CPU checking new programs (limit M%)`; its class is `syspolicyd`.
- `crates/store/src/lib.rs`: an unnecessary cast that failed clippy on develop.

## Tests

- `crates/scheduler/tests/properties.rs` `a_busy_syspolicyd_holds_only_a_further_compile`.
- `crates/daemon/tests/limits.rs` `a_busy_syspolicyd_holds_further_compiles_but_never_the_first`: the config key, the wait text, turning the gate off and on at runtime, and the bound.
- `crates/daemon/src/policyd.rs` unit tests: `ps` time formats, finding the pid, the percent reading and its hold, a restarted process.

## Not verified

- The 300% default is a judgment from one morning's readings. No run has shown that it keeps WindowServer responsive.
- The sampler was not run end to end in a test, because that would read the real machine. Its two `ps` output formats were checked by hand on this Mac.
- What exactly blocked WindowServer's main thread is not known: the watchdog report has no symbols.
- The number of new binaries, which is the cause, is not reduced here; #461 and #474 do that.
