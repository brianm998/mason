# s540: the UI-thread watchdog runs in release builds and its numbers show on the Health page

Summary: Both monitors now run the UI-thread watchdog in every build (one ping per 250 ms, late over 100 ms; 20 ms / 50 ms kept for debug builds and `MASON_WATCHDOG=1`) and show "UI thread: worst N ms late in the last 10 minutes, M late pings" on the Health page.

**Change.** `LatenessStats` keeps the pings of the last 10 minutes beside the since-launch totals; the clock is passed in. Swift: `WatchdogConfig` (`release`, `debug`, `current()`), `MainThreadWatchdog.start(config:)` no longer returns early in release, `App.swift` starts it without `#if DEBUG`, `HealthPage` takes an injectable `lateness`. Compose: `WatchdogConfig`, `UiWatchdog` without the env guard (a minimum-priority daemon thread), `UiLateness.recent` set by `Main.kt`, `HealthPage(model, lateness)`. A ping more than 1 s late logs one line to stderr. Nothing is sent to the daemon.

**Tests.** Window drop-out with an injected clock, release config and `start` (Swift: the timer exists; Kotlin: the thread runs without the env var), the log threshold, the line text in both clients, and the Health page given fixed numbers (Swift offscreen; Compose UI test on the tagged line).

**Not verified.** The real cost of a 250 ms ping on a long-running release monitor was not measured, and no release build was started by hand. The Swift Health test checks the line text and that the page lays out; it does not read the drawn text back. The owner skipped testing for this task (debt #189), so the Swift and Compose tests were not built or run by the pipeline's check; the earlier green run_check was before the new tests existed.
