# s91: odd bytes in command output no longer empty a log or panic a session reader

Summary: Logs and results files are read lossily (invalid UTF-8 becomes U+FFFD), log tails read only the last megabyte, and the hosted adapter's stderr buffer is cut on a character boundary.

`jobs::read_lossy` and `jobs::read_tail_lossy` replace `read_to_string(..).unwrap_or_default()` at `suites.rs` (suite log and results file), `jobs.rs` (`run_shell`, the check-failure tail) and `schedule.rs`. Before, one bad byte made the whole text empty. `hosted.rs` `push_stderr` moves the cut forward to a char boundary instead of slicing at a raw offset, which panicked the reader thread. The other byte-offset slices in `crates/adapters` are on ASCII digits or already guarded (`clip` in `claude.rs`).

Verdict logic (`suites.rs`): reading lossily cannot turn a red into a green. The parser still needs real test lines, and `judge` still takes the exit status; a bad byte only becomes U+FFFD in text that was previously discarded whole. Tests cover a failing run with a bad byte staying red and an output with no test lines staying not-green.

Tests: `lossy_tests` in `suites.rs`, `run_shell`/tail tests in `jobs.rs`, a proptest on the cut in `hosted.rs`, `scripts/exit/s91.sh`.

Not verified: `xcodebuild` or `adb logcat` output in practice; lossy replacement of a byte inside a test name can change that name's text (it was previously lost entirely).
