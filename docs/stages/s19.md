# Stage 19: Plugins and extensions

## Built
- **`crates/plugins`** (`mason-plugins`): the manifest (strict keys; parser, environment and adapter refused as "not yet supported"), JSON-RPC 2.0 lines (`initialize`, `step.run`, `shutdown`), the subset of JSON Schema that settings use, SHA-256 and the folder hash, a process host with timeouts (a silent plugin is killed), and the **conformance kit** `plugin_kit`. Manifest, rpc, schema and hash do no I/O.
- **Definition**: `StepType::Plugin`, `Step::plugin` and `Step::config`, `parse_with`, `Capabilities::plugins`; validation checks a plugin step's category and settings against the manifest and its `config_schema`; `palette` appends one entry per plugin (with its categories, a starting set of fields and its form) and `plugin_schema` builds the inspector's form.
- **Daemon** (`plugins.rs`): reads `.mason/extensions/` from the base commit, hashes, keeps approvals in `<config dir>/trust/<project>.toml`, copies the hashed bytes to `<config dir>/extensions/<hash>/` and runs that copy. `plugin_job` fails the step with `needs approval: mason extension approve <name>` unless that exact hash is approved. `GET /projects/<p>/extensions`, `POST .../extensions/<name>/approve` (owner only).
- **CLI**: `mason extension list|show|approve`; `conformance plugin-kit <dir>`; `mason doctor` knows the base branch's plugin step types.
- **The four levels**: `extends` (Stage 18); script steps get `MASON_*` variables and may write a JSON result file (`passed`, `summary`); process plugins; prompt packs in `.mason/prompts/<kind>.md` read from the base commit.
- `docs/plugin-protocol.md`, `docs/examples/plugins/migration-check/` (a Python plugin), `docs/decisions/0016-plugins-readings.md`, `scripts/exit/s19.sh`.

### Tests
- **plugins (18)**: SHA-256 against the standard vectors (including a million `a`), the folder hash changing with any path, mode or byte, manifest mistakes, schema checks and samples, rpc framing; the **kit** passes the example and names a bad `initialize`, a schema mismatch, a plugin that accepts bad settings, a timeout, no shutdown, a missing program and a bad manifest.
- **definition `plugins` (3)**: a plugin type parses only when provided; settings and categories are checked; the palette entry and form.
- **daemon `plugins` (4)** and unit tests: extensions come from the commit (a worktree edit changes nothing), a name/folder mismatch is refused, approval is by hash and name and project, a tampered copy is replaced; prompt packs replace default text but keep the task fenced, are read from the base commit; the script result file.

## What testing found
- **The Python start-up is slow enough to matter**: kit tests with a 1 s timeout failed on a cold start; they use 3 s. A real project can raise a step's `budget`; `initialize` is allowed 30 s.
- **`wc -l` pads its output on macOS**, which made the first exit-script comparison fail silently; the script strips it.
- **A landing task could carry a changed extension to the base.** The exit script's "evil" task would land its rewritten `check.py` on `main` if it got to landing; the new hash then needs a new approval, which is the intended protection, so the script parks tasks at an approval step instead.

## Not done or not run
- **Parser, environment and adapter plugins** are refused ("not yet supported"); only step types run. Nothing in the testing system, scheduler or services can load them yet.
- **The monitors were not changed or run against a plugin step.** Both draw the palette and the inspector from the daemon's JSON and schema, and their step lists are not hard-coded, but I did not run SwiftUI or Compose on a palette with a plugin entry (`s19.sh` checks the daemon's JSON). The conformance comparison of the two clients (`s18.sh`) was not rerun.
- **`mason definition check FILE`** knows only built-in types; a definition with a plugin step needs the daemon (`mason doctor` and the editor do know them).
- **An outside PR's extension** is covered by the same rule as a task branch (only the base commit is read); no test opens a PR.
- **A plugin's sandbox**: an approved plugin runs with the daemon's authority, as the design says. No OS sandbox (Stage 20).
- **Definition validation changed** (`parse.rs`, `validate.rs`, `model.rs`, and the editor): docs/self-hosting.md lists definition validation as protected, so these changes wait for the owner's approval, and existing tests were not weakened (`parse` still rejects every unknown type).
- Plugins are not told when a task is cancelled during `step.run`; the host kills the process at the step's timeout only.
