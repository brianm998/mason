# s1251: an agent that cannot reach its API waits and resumes

Summary: an agent step whose run ended because its API could not be reached (ENOTFOUND, no route, connect timeout) waits on `network_backoff` and resumes the same session, uses up no round, failure or automatic retry, and is noted in the outage record; past `network_agent_hold` it fails as `Outside`.

## Cause

`FailReason::Crash` became `the agent failed: {detail}`, which `FailClass::classify` read as `Code`; #1185's outage record was fed by git calls and suites only.

## Change

- `net::agent_unreachable` (wording; the adapter already turns the result with `terminal_reason` `api_error` into a `Crash` whose text is the CLI's message) recognises it. A refused credential, 429 and request errors are not.
- `jobs.rs` `settle_all`: such a `Crash` notes the outage for the task, releases the lease, sleeps the next `network_backoff` (the last one repeated), resumes. After `network_agent_hold` (default 30 min) in all, the step ends `the agent could not reach its API after waiting N s: ...`.
- `AGENT_UNREACHABLE` in `crates/core/src/task.rs` makes that reason `Outside`, so auto-retry (10 and 60 min) and the one outage alert cover it. Diagnosis starts only for a repeated outside failure, so none starts while waiting.

## Trust

`crates/core/src/task.rs` is protected: `classify` lives there and is the only place that decides `Outside`; one marker line and a constant, and tests for auth/request errors staying `Code`.

## Not verified

The structured end reason was not added to the adapter API: the wording is used, as the text the CLI gives is the only thing the adapter keeps. Not run against a real network drop.
