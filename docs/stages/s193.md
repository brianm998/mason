# s193: the workspace builds for Windows

Summary: A new `mason-platform` crate holds every Unix/Windows difference, `nix` is `cfg(unix)` only, and the whole workspace type-checks for `x86_64-pc-windows-msvc`, with a `windows` CI job that builds and lints it.

What changed
- `crates/platform` (`mason-platform`): `process` (group leader, signal group/process, liveness, `exec` replacement, exit signal), `net` (unix sockets; stubs on Windows whose `bind`/`connect` fail `Unsupported`), `fs` (positioned reads, owner-only files, execute bit), `disk` (`statvfs` / `GetDiskFreeSpaceExW`), `host` (host name). Windows stubs for work owned by later port tasks return `Unsupported` naming the task.
- Seven crates lose `nix`; the daemon keeps it under `[target.'cfg(unix)'.dependencies]` (signal handler, rlimit, load average); step-host has it as a Unix-only dev-dependency. File locks (`resources`, `devices`, daemon `ensure_single`) use `std::fs::File::try_lock`.
- Daemon: `stopsig::install` is `Unsupported` on Windows, `fdlimit::raise` is a no-op, `cpu::read_loadavg` is `None`, `take_over` and the managed loader report that takeover is unsupported.
- Integration tests that use signals, unix sockets or permission bits are gated `cfg(unix)`.
- `rust-toolchain.toml` lists the Windows target; `.github/workflows/ci.yml` has a `windows` job; `docs/DESIGN.md` points at decision `docs/decisions/0188-windows-port.md`.

Tests: `mason-platform` unit tests (positioned reads, execute-bit round trip, wide-path encoding, Windows extension rule, `Unsupported` message, process group kill on Unix); `scripts/exit/s193.sh` (Windows `cargo check --all-targets`, no `nix` in the Windows tree).

Known to fail on Windows (not run there): everything needing a unix socket (step host, contract socket, MCP bridge), process groups, `sh`, signals, `exec` takeover. Those tests are gated or will fail at run time until the IPC, process-tree, takeover, shell and service port tasks.

Not verified
- The Windows check on a Mac compiles sqlite's C for the host through wrappers in `s193.sh` (no Windows C toolchain here); the object is never linked. Windows `cargo clippy -D warnings` was also run this way and is clean.
- The CI `windows` job was not run; the owner checks it after landing.
- Nothing was run on Windows. The Windows code (`GetDiskFreeSpaceExW`, `OpenProcess`) is only type-checked, and its runtime behaviour is untested.
- On Windows `is_executable` goes by file extension, so a plugin folder's recorded execute bits will not match the on-disk hash for scripts; the plugin port work must settle that.
- Protected files touched (owner approval): `ci.yml`, `scripts/exit/s193.sh`, `contract.rs` (one `use` line), `update.rs`, `crates/landing/**`, `crates/resources/**`. `deny.toml` was not changed (`windows-sys` is MIT OR Apache-2.0 and already in `Cargo.lock`).
