# s361: back and forward restore each page's scroll position in the monitors

Summary: both desktop monitors remember where each history entry was scrolled when it was left, and back or forward puts the page there; a new selection starts at the top.

## What changed

- `NavHistory` (Swift `Navigation.swift`, Compose `Navigation.kt`) keeps saved positions in step with `back` and `forward`, plus `restore` (where the current entry opens) and `visit` (counts arrivals). `go`, `goBack`, `goForward`, `goHome` take the current page's position and save it on the entry being left.
- The models hold the live position unpublished (`liveScroll`, `reportScroll`), since it changes every frame, and pass it to the history when navigating.
- Swift: `RestoringScroll` (`MonitorUI/ScrollRestore.swift`) wraps the pages' `ScrollView`s. It reads the offset with a `GeometryReader` preference and scrolls to a marker placed `restore` down the content, once, after the content is ready and only if the owner has not scrolled. `MainPane` gives each visit a fresh identity.
- Compose: `Scrolling` hoists a `ScrollState` per visit and does the same with `scrollTo`.
- `clients/features.toml`: `back-restores-scroll`, done in both (a protected file; the owner must approve the entry).

## Not verified

The Swift and Compose view behaviour was not run on screen (nothing may appear on screen); only the pure history and model are unit-tested. The Swift marker trick and its 60 ms layout wait are untested against a real layout. The pipeline editor canvas and the phone screen are unchanged.
