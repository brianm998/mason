# Stage 16: Self-reload and updates

## Built
- **`update.rs`** (library): channels (`stable`, `main`, `branch:<name>`) resolved against a mirror of the source; the **no-downgrade rule** (an ancestor of the running version needs `--rollback`; an unknown running version cannot be compared); **immutable runtimes** in `runtimes/<sha>/` (built in a `git archive` copy, copied in complete with a `READY` mark last, never from a checkout that can move); the **boot record and crash rule** (three starts that never became healthy within five minutes roll back to the previous runtime); the update pipeline (resolve, check direction, build, back up the database, self-test, take over) and **takeover by `exec`** (same pid, same port).
- **`masond selftest --db COPY`**: in the *new* build, migrations on a copy of the real database, the five golden event logs replayed, and a scripted task landed in a sandbox with the stand-in agent.
- **`masond --managed`**: the entry point for a service manager. It picks the current runtime, counts crashes, rolls back by itself and leaves an alert until `mason update ack`.
- **`mason update`** (`--channel`, `--sha`, `--rollback`, `--check`), **`mason update status`**, **`mason update ack`**; `GET/POST /update`; the rollback alert in `mason alerts`.
- **The wire**: `Welcome` carries the daemon's build and the oldest protocol it serves (`min_protocol`), `Hello` the monitor's build; the daemon serves current and previous; a client outside the range gets a readable `Welcome`, then the reason.
- **Both monitors**: an update banner with a button (build from a source checkout and relaunch, or open an install page), read-only with the reason when the protocol is too old; a `monitor-update` feature in the parity file, done in both.
- Store: `backup_to` (`VACUUM INTO`). `docs/decisions/0013-updates-readings.md`, `scripts/exit/s16.sh`.

## Exit test
`bash scripts/exit/s16.sh` passes (real `masond`, real `mason`):
```
== 1. an update while an agent session runs
   same pid after exec, same step host, one attempt, landed once, database backed up
== 2. a build that crashes is rolled back by itself
   three crashes in five minutes: back on the previous runtime, an alert, the bad build refused
== 3. a build that fails its self-test never takes over
== 4. no accidental downgrades
== 5. the self-test
== 6. versions on the wire, and the monitors
```
In (1) a 25-second agent session is running when `mason update` builds, proves and takes over; afterwards the daemon has the same pid, the agent's step host is the same process, the task lands once with one attempt at developing, and the database backup exists. In (2) the new build passes its self-test and then exits at start; the loader (restarted by the test as launchd or systemd would) rolls back on the third crash, marks the build bad, and the alert shows in `mason alerts` until acknowledged. In (4) `--sha <older>` is refused ("an ancestor of the running ... would drop 1 commit(s). Use --rollback"), and goes with `--rollback`.

## What testing found
- **The command line waited forever for a daemon that never came back** (a build that crashes at start). It now gives up after 30 seconds (`MASON_UPDATE_WAIT_S`) and says what happened and that the rollback is automatic.
- **A restarted daemon has forgotten the target it was building**, so `mason update` could not tell it was done; it now remembers the target from earlier polls and compares it with what runs.
- **A build that dies at once never records its own start**, so crash counting would never have seen it. Starts are recorded by the loader and the takeover.
- **A stale `-wal` file made a garbage "database" pass the self-test** in my test (the copy had left sidecar files); the pipeline now removes them and the test does too.

## Not done or not run
- **No service manager is installed.** `masond --managed` is what launchd or systemd should run (with restart on exit), but the units are not written (a later stage), so today a crash after a takeover leaves no daemon until someone starts `masond --managed` again. The automatic rollback has only been exercised with the test acting as the service manager.
- **Signed builds are not fetched**: there is no signing or publishing. The monitor's Update button builds from a source checkout (`MASON_SOURCE_DIR`) or opens an install page (`MASON_INSTALL_URL`); the building and relaunching path was not clicked, and was not run by a test (the plan that chooses it is tested).
- **The protocol range is one version wide** (both are 1), so "current and previous" is in the code and its tests but has not been exercised by a real bump. The step hosts' range predates this stage.
- **The `mason` command line is not switched with the daemon** (it is a binary in the runtime but you run whichever is on your PATH).
- **A downgrade of the database is not handled**: migrations only go forward; rolling back to an older build after a newer one migrated relies on the backup (`runtimes/backups/`), restored by hand.
- The golden replay is of recorded logs and a scripted task, not of a larger corpus; the sandbox task needs about 7 seconds.
