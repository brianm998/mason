# Stage 1287: An agent CLI that cannot start holds the project

Summary: A project whose `claude` (or `codex`) masond cannot run is held with one needs-you notice; its tasks wait instead of failing, and `mason doctor` reports what the daemon resolves.

**What changed.**
- New `crates/daemon/src/agentbin.rs`. The binary is looked for as the launch would: `claude_bin` / `codex_bin`, else the CLI's name on the `PATH` of the project's `agent_env`, else the daemon's. It must be an executable file, and a script's absolute interpreter must be one too. Looked at at start, register, reload, before each agent launch and on every pass of the definition watcher.
- While held (and only if the current definition has an agent step): queued tasks are not claimed and say why; a claimed step waits before its launch, holding no lease and no session reservation; no diagnosis or cause diagnosis starts; the health check and the stall alert skip the waiting tasks. One alert, `agent-bin:<project>`, kind `needs_you`.
- A launch that ends in the step host's `failed to start` holds the project. The step concludes nothing and is run again from a new context when the hold lifts. A restarted daemon does not adopt such an invocation as a session. That hold lifts on a reload or when the file has changed.
- The hosted adapter shortens the host's message to program and error: it quotes every argument, and the 4000-byte output cut would drop its start.
- A diagnosis (or cause diagnosis) that could not start writes no row. A `none` row reads "Diagnosis #N: the session ended without a verdict".
- `GET /agents` reports each project's resolution; `mason doctor` uses it, and says it checked the shell's `PATH` only when there is none.

**Not changed.** `autoretry.rs`, `contract.rs`, `sched.rs`. Task 1111's recovery handoff after a verdict-less session is as it was.

**Not verified.**
- No real `claude` or `codex` was run; the tests use `fake-claude` and scripts with a missing interpreter.
- Tests ran through `run_check` on GitHub, not on this Mac; Windows was not tried.
- A sandboxed project (`sandbox-exec`, `bubblewrap`) gets the checks before launch only: the step host starts the wrapper, so a CLI that fails inside it is not recognised.
- A script run through `/usr/bin/env` whose program is missing exits 127 with `env`'s message, which is still an ordinary crash.
- `failed to start` for another reason (a missing worktree) holds the project too, until a reload; the notice carries the host's message.
- Health sessions and owner sessions that fail to start do not set the hold.
- The monitors were not built or looked at; the notice is an ordinary alert.
