# s1118: the coordinator runs masond from one stable app bundle

Summary: On macOS the coordinator now execs masond from one signed bundle on the internal disk (`~/Applications/MASON Coordinator.app`) whose path never changes, so a Local Network rule can apply, and a rule macOS cannot apply is named as such.

## Change

- `crates/daemon/src/stable_app.rs` (new): chooses the bundle directory (`app_dir` in `update.toml`, else `~/Applications` for the signed coordinator with the default data directory), installs a runtime's Mach-O files into it, signs and verifies it, swaps it in by rename, and reverts if the exec fails. It also asks `df`/`diskutil info` whether a volume is internal and warns at start-up when `masond`'s executable is not.
- `update.rs`: `app_dir` setting, `sign_as` (a named signing identifier), and `take_over` stages the bundle, swaps it just before the exec and reverts on failure.
- `main.rs`: the managed loader execs the bundle too (also after a rollback).
- `node_client.rs`, `nodes.rs`: "no route to host" to a LAN node that answers ping, from an executable on an external disk, is `LocalNetworkUnapplied` with its own words. The older denial text now adds "if it is already on, see docs/nodes.md".
- `docs/nodes.md` section 1.9: the failure, the `nehelper` log line, the bundle, the loopback relay.

All binaries go into the bundle, so `step-host` and `mason-mcp` are found beside `masond` as before. The runtimes stay in the data directory.

## Tests

Unit tests for the volume check (stubbed `df`/`diskutil` text), the choice of directory, the error classifier, and (macOS) install, re-install, revert and refusal with ad-hoc signed copies of system binaries. Integration (macOS, `crates/daemon/tests/stable_bundle.rs`): `two_takeovers_run_masond_from_the_same_stable_bundle_path` runs `stable_app::stage` and `executable`, the two calls `take_over` makes before its exec (the exec itself would replace the test process), twice with two fake runtimes and a scratch `app_dir`; the path is the same both times, under `app_dir`, and `codesign --verify --strict` passes. `scripts/exit/s1118.sh` runs it with the unit tests.

Protected: `update.rs` (`app_dir`, `sign_as`, the staging and revert in `take_over`) changes with the owner's approval. Rollback, the self-test, the no-downgrade rule and the landing drain are unchanged.

## Not verified

- That macOS then applies the Local Network rule: nothing here was run on the real coordinator. Existing rules for the same identifier may keep macOS from prompting or from finding the new UUID; registering with `lsregister` is done for the default directory but its effect is untested.
- That `/sbin/ping` run by an affected `masond` gets through. If it is blocked too, the older "denied" message (with the pointer to the docs) is shown instead of the new one.
- mDNS send failures are not classified: `mdns-sd` 0.11 only logs them. The node poll and `node add` meet the same condition.
- The loopback relay in the docs is a rewrite; the owner's `~/mason-node-relay.py` was not read, and this one was not run.
- Signing the bundle with a real identity (tests sign ad hoc).
- Privacy grants given to the old runtime path (Full Disk Access and the like) follow the signature, so they are expected to hold; not checked.
- A packaged (`release` channel) install with `sign_identity` set would have its binaries re-signed with that identity.
