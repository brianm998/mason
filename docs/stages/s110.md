# s110: a frozen base raises an alert

Summary: While a project's landing is frozen (its post-land tier went red), `alerts_now` raises `frozen:<project>` of kind `landing` naming the reason, how long, and the fix task with its state, and says the freeze will not lift by itself, with `mason task retry`/`force`, when that fix task failed or was canceled.

`freeze_alerts` in `attention.rs` only reads the `freezes` table and the world; `landing.rs` is unchanged. The alert exists exactly as long as the row, so it clears when the post-land tier goes green or the freeze is cleared.

Tests: `a_frozen_base_raises_an_alert_naming_the_fix_task_until_the_freeze_clears` (attention.rs, a freeze row, fix task running then failed, then cleared); the existing `a_red_post_land_tier_freezes_landing_until_the_fix_lands` now also asserts the alert appears and clears. `scripts/exit/s110.sh` runs both.

Not verified: the exit script drives an in-process daemon (the test harness), not a separate `masond` process with `mason alerts`; the canceled-fix wording is the same code path as failed but only failed is tested; the `mason task force` command named in the text was not run against a frozen base.
