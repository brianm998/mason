# s982: daemon endpoints to add a project (candidates, plan, apply)

Summary: the daemon serves `GET /onboarding/candidates`, `POST /onboarding/plan` and `POST /onboarding/apply` (owner only) over the `mason-onboard` crate, with `[onboarding] roots` (default `["~/git"]`), so a desktop monitor can add a local repository and answer the same questions as `mason init`; see decision 0975.

Task #885, after the mason-onboard extraction. No protected file is changed (`crates/landing/**`
and `landing.rs` are called, not edited).

## JSON (field names are stable; the Swift and Compose monitors depend on them)
All three need the owner identity (`x-mason-as`, which the LAN guard sets for an owner device);
anyone else gets 403.

- `GET /onboarding/candidates` -> `{"candidates": [{"path", "name", "has_mason", "remote"}], "errors": [{"path", "error"}]}`.
  Sorted by `name`. `remote` is `origin`'s URL or null. A root that cannot be read goes to
  `errors`; the call still succeeds.
- `POST /onboarding/plan {"path", "answers"}` -> `{"detected", "kind": "init"|"adopt", "next": {"id","text","options","default","flag"} | null, "errors": [string], "files": [{"path","contents"}]}`.
  Writes nothing. `answers` is the flag set of `mason init` by field name: `id, tracker, agent,
  agent_bin, sessions, workflow, suites, base, landing, alerts, ci_workflow, land (no|merge|push|pr),
  no_prove, force, test` (all optional strings, except the booleans). A path inside a registered project: 409 `{"error"}`.
- `POST /onboarding/apply {"path", "answers"}` -> `{"id", "registered", "landed": {"merged","published","refused"}, "proof_task": N|null, "base", "kind", "report", "notes", "progress": [string], "error"?, "proof_error"?}`.
  The call is synchronous (as the editor's apply is): progress lines come back in `progress`.
  Refusals write nothing and return `{"error": reason}`: 400 (not a git repository, an answer that
  does not parse), 409 (path inside or equal to a registered project, id taken, dirty tree for
  `land = merge`). The proof task is filed unless `answers.no_prove` is true.

## Built
- `config.rs`/`main.rs`: `[onboarding] roots`, `~` expanded; unknown keys refused; documented in
  `docs/install.md`.
- `onboarding.rs`: candidates, plan, apply. `Daemon::repo_lock_at(path)` takes the repository
  lock (same map and key as a project's) around `mason_onboard::apply_validated`; registration
  runs after it is released because reading the definition takes that lock. Git work runs on the
  daemon's blocking pool.
- `http.rs`: the three handlers and routes; the proof task is filed through the `POST /tasks` handler.
- `mason-onboard` now owns `PROOF_TITLE`/`PROOF_BODY`; the CLI re-exports them. The CLI still
  calls `POST /projects/{name}/register` itself.
- Tests: `it/onboarding.rs` (candidates, plan, apply, viewer 403, path inside a project) and the
  config parse test.

## Not verified
- Nothing was run on this machine (tests run on GitHub through `run_check`).
- `land = push` and `pr` were not exercised through HTTP (they need a remote).
- With `land = no` the proof task is filed although the base has no `.mason/` yet, as the task
  asks; the CLI instead refuses to file it until the setup branch is merged.
