# s349: an aged request never passes work further along

Summary: the scheduler's order is now, without exception for pipeline work: landing first, then progress (how far along the task is, as a share of its route), then aged requests, then issue priority, then arrival. A request that has waited past `order.max_wait_s` keeps its progress and goes first only among requests as far along as it, oldest first. It no longer jumps ahead of work further along. Interactive callers and landings keep their places.

## Why

On 2026-11-14 the owner asked that pipeline priority be followed in all cases: tickets further along first, then other precedence such as issue priority. An audit of the live queue (47 waiting requests) found the broker following that order. The one exception in the rule itself was aging (decision 0231): an aged request went to band 1, ahead of every non-landing request, with progress ignored. With 40–50 requests queuing for compile slots, early-stage requests that had waited 30 minutes would pass test steps and reviews that were closer to landing.

Aging still does what decision 0231 needed it for. Among requests as far along, such as star's exclusive test step against mason's `run_check`s, which rank as a test step, it puts the one that has waited longest first, whatever their priority or task age. An exclusive request still drains the machine of everything ranked behind it, aged or not.

## What changed

- `crates/scheduler/src/rank.rs`: aged keeps `remaining` and band 2. A new field `not_aged`, after `remaining`, puts aged requests first among equal progress. The rule's doc comment is updated.
- `crates/scheduler/tests/properties.rs`:
  - The starvation property now asserts that nothing ranked behind an aged exclusive request is granted the machine.
  - The exclusive-at-the-back test loses on issue priority instead of progress.
  - The aging-off test expects work further along to go first.
- Tests: `rank::tests::an_aged_request_goes_ahead_of_pipeline_work_oldest_first_but_not_ahead_of_a_landing` (new assertions: an aged request goes ahead at equal progress, and never passes work further along).
