# s174: a red batch gets the failed job's log, and is not blamed for a job red on the base too

Summary: A landing batch red in CI now gives its tasks the end of each failed job's log, and is not blamed (the batch waits, and an alert is raised when the assertion text differs) when every failing test also fails in the base branch's latest run of the same workflow.

**Built.**
- `JobFailure.log` (adapter-api): the last 400 lines of a failed job's log. The GitHub adapter now reads it for every failed job, whether or not `infra_judge` is on; with the judge off nothing is judged (`infra` stays `None`) and landing adds no judge notes, as before.
- `mason_core::red_base` (pure): `failing_tests` reads pytest (`FAILED id - text`) and cargo (`test x ... FAILED`) failures; `judge` returns `Blame`, `RedOnBase` or `Differs`.
- `ci_watch::assess` reads the base's latest finished run of the same workflow through the watch's `Source` (the #164 reading), and the base job's log.
- `landing.rs` `red_notes` (protected file): about 60 log lines in all go into the batch notes, so into the task's feedback and `mason task show`; then the verdict. `RedOnBase` and `Differs` hold the batch through the existing service-error path (nobody parked, tasks stay queued); `Differs` also raises a `landing` alert naming both texts. Where #164's freeze is configured, landing is frozen by it as before.

**Still blamed.** A batch is blamed, as today, for any failure that is green on the base: a job green or missing on the base, a failing test that does not fail in the base's log, a failure with no readable test names, a base run or log that cannot be read, a CI that is not GitHub Actions.

**Changed test.** `with_the_judge_off_no_log_is_requested_and_no_job_is_reported` asserted the old behaviour (no log fetched, no job reported with the judge off); it is now `with_the_judge_off_nothing_is_judged_but_the_log_is_kept_for_the_task`.

**Tests.** Core unit tests, `crates/daemon/tests/red_base.rs` (same test red on both, green on base, new failing test, other text, other workflow), the adapter test above. No timing assertions.

**Not verified.** The workspace tests passed through `run_check`; I did not run `scripts/exit/s174.sh` or `scripts/run-exit-scripts.sh` or clippy myself. A non-GitHub CI (command, Jenkins) is judged as before; GitHub Actions is judged only with `infra_judge` on. The exit script runs the tests above; it does not start a masond or a fake GitHub, so the landing wiring (`red_notes`, the hold, the alert) has no end-to-end test. Logs are read as GitHub serves them (timestamped); cargo's failure text is read from its `---- name stdout ----` block only when that block is inside the kept log tail (4000 lines for the base, 400 for the batch).
