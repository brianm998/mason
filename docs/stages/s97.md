# s97: views index step runs once, and history sections are capped

Summary: Building the monitors' views no longer scans every step run per row (runs are indexed by task and typical spans by step once per view), a history section sends at most its newest 500 rows with the true `count`, and the task page reuses its log tail until the task's journals change.

`Ctx::new` builds a `RunIndex` (runs by task sorted by id, each task's latest start, typical `(low, high)` per step name from one suffix-minimum pass per task) and a blocker-to-blocked map. `typical`, `state_since`, `progress`, the task page's step list and `blocks` read them. The typical figures are the same as the old code's (a run ends at the earliest later start of the task); a unit test compares them with a copy of the old nested loop on generated data.

`section_of` sends at most `HISTORY_ROW_CAP` (500) rows for failed, landed and canceled; `count` is the true total. A task outside the cap opens by id (`task_detail` takes no section). Both monitors show "500 of 2000" in the section header (`countText`; "features.toml": `history-cap`). Their search runs over the rows they were sent, so **search does not find tasks older than the newest 500 in a capped section**; while searching a capped header reads "3 in newest 500". Searching on the daemon is not part of this stage.

`task_detail` keeps the last 40 log lines per task in a small in-process cache (64 tasks) keyed by each journal's host id, size and modified time (`http::log_signature`), so an event that changed no journal does not re-read them. The signature still lists the hosts directory and stats the journals.

Tests: `views::index_tests` (matches the old figures; the index visits each run twice at any size, asserted by count, not time), `tests/history_cap.rs` (520 canceled tasks: count 520, 500 rows, the newest kept, an old one opens by id), Swift and Compose `countText` tests, `scripts/exit/s97.sh` (real masond, 520 tasks, websocket client).

Not verified: the Swift and Compose tests and UI were not built or run here; no timing of a large sidebar; the log cache against a journal rewritten in place with the same size and mtime; non-history sections are not capped, and a history section is still filtered and sorted in full (only the row building is capped).
