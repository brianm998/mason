# s84: step time limits survive a daemon restart

Summary: A step's time limit now counts from when its host started (`started_ms` in `host.kv`), so re-attaching after a daemon restart gives a run only what is left of its limit, and a limit already past stops it at once as a timeout.

Before, `attach_as` (agent steps) and the two test-run watchers (`jobs.rs`, `suites.rs`) each started their deadline at `Instant::now() + limit` on every attach, so every restart began the count again. All three now call `mason_step_host::registry::remaining_limit(limit, host_dir)`, built on the pure `remaining_at(limit, started_ms, now_ms)`. A host whose `host.kv` cannot be read gets the whole limit.

Unchanged: a nudge, an answer or a resume after a hold starts a new invocation (a new host) with its own limit; whether a budget should span invocations is left alone. No verdict changes: a test that runs out of time is still red (`suites.rs` only has its start point changed).

Tests: unit test of the helper (`registry.rs`); `crates/daemon/tests/restart_limit.rs` (agent step with a 3 s `budget`, and a test step with `test_timeout_s = 3`, daemon killed 2 s in and restarted; the host ends 2.9–4.8 s after it started — without the fix the agent case ended at 5.9 s); `scripts/exit/s84.sh` (real daemon, 6 s budget, killed at 3 s, ended at 6.1 s, task shows "the step ran out of time").

Not verified: the codex adapter's re-attach (it shares `attach_as`, but no test restarts a codex run); a real provider CLI; a restart in which the daemon is down past the whole limit (covered only by the unit test of the helper, not by a daemon test).
