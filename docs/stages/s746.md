# s746: the cargo-workspace suite green on ubuntu-latest

Summary: Nine tests that were red only in the first remote whole-suite run are fixed or classified (a CLI that asked for a daemon before refusing an unknown `remote` word, a runner-only `.mason/run.json`, a core-count-dependent slot, a timing-sensitive message check); the draining-update test is not reproduced and not fixed.

How each was classified. Nothing here was run on this Mac: `cargo test` is refused in this shell, so every "red here" below is from reading the code. The only run evidence is the narrowed GitHub run 44853985824, which I did not re-read in this retry; I have no per-test run URL for the others.

Classified from code reading only:
- `remote::tests::iso_times_and_ref_names`: test bug on any machine (2026 is not a leap year). Fixed on `origin/develop` (the test uses 2028); this branch takes that version.
- `remote::tests::a_skip_while_queued_or_running_...`: simulated-time race on any machine. `origin/develop` changed the test to a simulated-clock skip; this branch takes that version.
- `reuse::tests::a_second_task_changing_only_crate_b_...`: test bug (the note prints twelve tree characters). Fixed on `origin/develop`; taken.
- `cli remote::tests::a_swiftpm_project_...`: the template mentions `rust-cache` in a comment. Fixed on `origin/develop` (looks for `- uses: Swatinem`); taken.
- `landing_modes::a_pr_wait_shows_...`: the member message is the batch's last word, either its phase or the running check; the test now accepts both (phase unit and count still asserted). Mine.
- `limits::a_hot_die_holds_...`: depends on core count; the compile limit follows the cores, so on a small runner the fourth lease waited for a slot, not for power limiting. The test closes the first two leases first. Mine.
- `definition::tests::no_tracked_file_but_the_definition_is_unmapped`: `.mason/run.json` is written by MASON into a runner's snapshot and is not a repository file; the test skips it. (`scripts/test-shard.py` is already mapped on `origin/develop`, so this branch no longer edits `.mason/mason.toml`.) Mine.
- `remote_dispatch::bogus_remote_command_names_all_four`: real CLI bug, not Linux-specific: `mason remote <word>` looked for a daemon before rejecting an unknown word. Fixed in `crates/cli/src/main.rs`. Mine.

Not reproduced, not fixed:
- `landing_yield::a_draining_update_stops_a_red_batch_...` ("no run after the first one", 2 vs 1). I found no cause. The assertion is unchanged and no timing assertion was added. A guess: a red run may be repeated (a test rerun) inside the same run, which would write a second line to `reds`; unconfirmed. It needs a whole-suite rerun on GitHub.
