# s108: an alert while a step host is frozen at launch

Summary: A step host launch that has waited more than two minutes now raises one `launch-frozen` environment alert (count, longest wait, tasks, and on macOS whether `syspolicyd` is running), which clears when the launches end.

`launcher::launching()` lists the launches in progress (host id, start time); an entry is removed by a drop guard however `spawn_host_within` ends. `alerts_now` adds one line calling `launch_frozen_alert(list, now, threshold, syspolicyd)`, a pure function; `syspolicyd_running` runs `/usr/bin/pgrep -x syspolicyd` with a 2 s limit, only when a frozen launch exists (it is passed as a closure). The task comes from the host id prefix `t<task>r<run>`. `START_LIMIT` is unchanged. The threshold is 120 s; `MASON_LAUNCH_FROZEN_MS` overrides it (used by the exit test). `attention.rs` is a trust file: only an alert was added; nothing about who may answer changed. #74/#75 code is untouched.

Tests: `crates/step-host/tests/host.rs` (listed while waiting, gone after success and after timeout, with a sleeping `--host-bin`), `launch_frozen_tests` in `attention.rs` (pure; pgrep result injected), `scripts/exit/s108.sh`.

Not verified: the real `pgrep` path against a real `syspolicyd` outage; behaviour on non-macOS (the text omits the syspolicyd clause).
