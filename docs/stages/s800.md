# s800: Develop CI on push is the fast jobs; the full matrix runs from the full-test schedule

Summary: a push to develop runs only `lint` and `windows`; the rest of `ci.yml` runs on `workflow_dispatch` (run-name `CI: full`, input `macos`, default true) from MASON's full-test schedule, there is no GitHub cron, and the base-branch CI watch judges each job by the latest run that ran it, so a job missing from a push run is neither stale nor "waiting for a newer run".

Task #784. Decision 0793.

## Built

- **`.github/workflows/ci.yml`** (protected, owner approval): triggers are `push` (develop,
  `stage/**`, README ignored), `pull_request` and `workflow_dispatch` (input `macos`); the cron is
  gone. `run-name` is `CI: full` for a dispatch. `lint`, `windows` and `dco` are unchanged. `test`,
  `exit-scripts`, `monitor-swift`, `monitor-compose` and both device samples have
  `if: github.event_name != 'push'` (so pull requests behave as before); the two macOS legs run
  only on a dispatch with `macos`. The full run's own concurrency group is `full`, and the long
  repeat counts and 3600 s script limit now follow `workflow_dispatch`, not `schedule`.
- **Where `windows` went:** it stays in the fast set (the only Windows signal on push). To move it
  to the full set, add `if: github.event_name != 'push'` to it and to the fast list in the text check.
- **The schedule** is a commented example in `docs/examples/mason-self.project.toml`
  (`[schedule.full-ci]`, kind `ci`, `run_name = "CI: full"`, `at = "01:00"`, `when_quiet = "30m"`,
  `max_tickets = 6`). The owner adds it to `~/.config/mason/projects/mason.toml`; this task does not.
- **CI watch** (`crates/core/src/ci_watch.rs`, `crates/daemon/src/ci_watch.rs`): `RunRec.full`
  (a `workflow_dispatch` run, read from the new `ActionsRun.event`) and `JobState.full` (the kind
  of run the job last appeared in, saved). A job counts as absent only from a run of its own kind,
  so push runs never age out the full-only jobs and a full run never ages out `lint`/`windows`.
  A job's state comes from the latest run that has it. A full-only job whose fix landed shows
  "not yet confirmed ... next full run" until the next full run, with no repeat filing.
- **Tests** (no timing assertions): core `push_runs_without_the_full_jobs_leave_them_alone` and
  `a_red_full_job_is_reported_and_a_fix_waits_for_the_next_full_run`; conformance
  `push_runs_only_the_fast_jobs_and_the_full_matrix_is_dispatched` (the concurrency check was
  renamed from `schedule`/`nightly` to `workflow_dispatch`/`full`).
- **Exit**: `scripts/exit/s800.sh`.

## Not verified / limits

- Nothing was compiled or run in this session (the shell refuses local cargo); the tests are
  written and only `run_check` / CI will execute them.
- The workflow was not run on GitHub: the dispatch with the `macos` input and the `run-name`
  expression are untested there. The schedule's `run_name` must equal what GitHub shows.
- Task item 5 (README status block showing the last full CI run): `mason status` already prints
  the last full test per schedule (s782); the README block is built from stage notes by
  `gen-status.sh` and holds no live data, so it was not changed.
- A job saved before this change has `full = false`; a full-only job that was red then is
  forgotten after `agreement + 2` push runs and returns with the next full run's result.
- Pull requests still run the whole matrix, as before.
