# s525: merge the base into idle develop worktrees when it fixes a red they hit

Summary: while a develop agent's `run_check` is queued, a known-red test its last check failed that leaves the ledger (the base fixed it) gets the base merged into its clean worktree, signed off, before the check runs, and the agent is told on the result; a dirty, mid-merge or conflicting worktree is left as it was.

## Why

On 2026-11-16 develop's matrix red was fixed at 16:01, but 10 of 15 develop worktrees still had the bug: an agent picks the base up only when it merges by itself. The four whose agents were blocked in a queued `run_check` with a clean tree were merged by hand, and all merged cleanly.

## What changed

- `crates/daemon/src/fixsync.rs` (new): `Reds` remembers, per worktree, the known-red tests (by ledger scope) the last check failed. `Reds::sync` sees which of them have left the ledger and calls `merge_clean`, which merges the base with `git merge --no-edit --signoff` only when there is no merge in progress, no uncommitted change to a tracked file, and `git merge-tree` finds the merge clean. Anything else changes nothing, and the agent is told why it was not merged.
- `crates/daemon/src/jobs.rs`: `TestChecks::queued` wraps each slot wait of a check (build and run, both paths). It credits the wait as before and polls the ledger every 2 s on a second thread, which has ended before the check runs. A failed check records its known-red failures from the whole log; a pass clears them. Specs and the content tree are taken after the wait, so a merged tree is what is recorded as green. What was merged is put before the check's result, after the existing base-fold note.
- `crates/daemon/src/basefold.rs`: `would_conflict` is `pub(crate)`.

## Tests

`fixsync::tests` (real git repositories): an idle clean worktree is merged, signed off, and its next tree has the fix; a test still known red merges nothing; a dirty worktree, a merge in progress and a conflicting merge are left exactly as they were; a failure that was not known red is never watched. No test asserts timing.

## Not verified

- Nothing ran a whole daemon with a real queued `run_check` and a landing: the poller and `queued` are covered by compiling and by the unit tests of what they call, not end to end.
- Only tests already in the known-red ledger are watched. A red on the base that the ledger does not hold yet (the `run_check` "red on develop too" ticket detects those) is not synced until it is there and then leaves it.
- Failing names are read from the check's log with `rerun::failing_names` and matched to ledger names by text, so a runner whose log names differ from its results' names is not matched.
- A merge during a wait leaves a suite selection made before it (`plan_for`) as it was.
- State is in memory: a daemon restart forgets what was watched.
