# s430: a Settings page for proposal policy, notification routes, schedules and the tracker

Summary: Both monitors have a Settings page (`mason://settings`) and masond has owner-only endpoints (`GET/POST /projects/{name}/settings`, `GET/POST /notify/settings`) that change proposal policy, schedule cadence, tracker settings and notification routes in the config files, validated by the loaders' own parsers, comments kept, applied without a restart.

**Problem.** The graph editor covers the definition, but where each alert goes, the proposal rules, the schedule cadence and the tracker settings could only be changed by editing TOML.

**Change.**
- `crates/daemon/src/settings.rs`: reads and writes with `toml_edit` so comments and layout survive. Only listed keys can change: `[proposals]` (the four dispositions, `per_task`, `per_day`, `[proposals.introspection]`), `every` and `title` of an existing `[schedule.<name>]`, `[tracker]` `interval_s`, `label`, `import_as`, `require_label` (and `token`/`webhook_secret` only as `env:`/`file:` references), and in `notify.toml` `[routing.<condition>]`, `[quiet]`, `[reminder]`, `[speech]` `daemon`/`stale`/`preferred_client`, `[stall]`. A change is rendered, parsed by `config::parse_project` (or `notify::parse`), written to a temporary file and renamed, then `reload_registration` applies it; if that refuses, the old text is written back. One edit at a time (a process-wide lock). A literal secret in a request, or an unlisted key, is a 400 and the file is not touched. GET reports a literal secret already in a file only as "set in file, not shown".
- `http.rs`: the four routes; the writes are owner only (`x-mason-as`). `notify.toml` is read on every notify tick, so a route change is used by the next tick.
- `tracker.rs`/`daemon.rs`: a reload sets the running poller's `interval_s` (`Hub::set_interval`), so a new interval needs no restart.
- Swift and Compose: `Page.settings` / `Page.Settings` (`mason://settings`), a Settings sidebar link, `SettingsModel` (parses the two GETs, builds one-key request bodies), and a page with proposal pickers, notification route checkboxes with a Test button (`POST /notify/test`), schedule cadence with Run now (`POST /schedules/run`), and tracker controls. The runtime gates and limits keep their existing Compilation steppers and endpoints.

**Not done.** Adding or removing a schedule; `[self]`, tracker kind/repo, the email/ntfy/webhook endpoints and the speech command (the last runs a program); a "More limits" list on the page (limits and gates stay on the CLI and the Compilation section).

**Trust.** `scripts/exit/s430.sh` is a protected path and waits for the owner. `clients/features.toml` was not touched: no feature rows were added, so parity is unchanged and the owner approves rows separately. `/resources/limit` was left as it is (it has no owner check; adding one could break monitors that send no identity).

The Rust code, the Swift and Kotlin sources and the exit script have been read, not compiled, so expect compile fixes. In particular: the Moshi null-writing for "remove a route" in Compose, the Swift `Binding` closures in `SettingsPage`, and `scripts/exit/s430.sh`'s plain HTTP calls to the loopback port. The refused-reload rollback has no test (no allowed key can make `reload_registration` refuse). No UI test ran and nothing appeared on screen.
