# s103: a watchdog outside masond

Summary: `scripts/mason-watchdog.sh`, run every minute by a launchd agent, asks `GET /status` and says (with `say` and `[ntfy]`) when the daemon is down, hung or crash-looping, and once when it is back; `mason doctor` notes when it is not installed.

Only an open monitor could raise `daemon_down`, and `KeepAlive` restarts a dead `masond` but not a hung one. The script uses only `/bin/bash`, `/usr/bin/curl`, `/usr/bin/say` and `/bin/date`, so it runs while `syspolicyd` is down. It reads the port from `daemon.json`, asks `/status` with a 20 s limit, and keeps `key=value` state in `mason-watchdog.state` beside the data directory. Two failures in a row is down (repeated every 30 minutes; one "back"); a changed `pid` or `uptime_s` under 60 on three runs in a row is crash-looping. State path, `daemon.json`, `notify.toml`, the speech command, curl, the timeout and the clock come from `MASON_*` variables so the tests can use a fake server and call it once per simulated minute.

Files: `scripts/mason-watchdog.sh`, `scripts/tests/watchdog.sh` (up, down, hung, recovered, restart, both crash-loop forms, no `say`), `scripts/exit/s103.sh` (real daemon, `kill -9`, a listener that never answers, restart), `docs/examples/com.example.mason-watchdog.plist`, "The watchdog" in `docs/self-hosting.md`, `check_watchdog` in `mason doctor`. No protected or guard file is touched.

Not verified: the plist under a real launchd (only `plutil -lint`); behaviour on Linux or with `syspolicyd` actually down; `[ntfy]` against a real server (a fake one only); `token_env` is read from the agent's environment, which is not the daemon's. A single pid change is treated as an ordinary restart, not a crash loop (my reading of "three runs in a row").
