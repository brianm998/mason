# s68: A conflict with the base is not a red round, and a retry gets its rounds back

Summary: A send-back for a conflict with the base (at the test step, a suite step, or landing's batch) no longer spends one of a step's `max_rounds`; it has its own limit of five. Rounds count from the owner's last retry, so a retried task gets them again.

Done by hand on the owner's request, outside the pipeline. The numbers 68 and 0053 were reserved in the store first (task 900068 stands in for the owner), so no task's reservation collides with them. s61 was not reserved this way, and task #27, reserved 61/0041, is waiting on the owner over it.

## Why

- **The base moving was charged to the change.** s61 made the test step merge the base before it runs, and a conflict there was a red round. On 2026-11-07/08 MASON landed about thirty tasks in a day, and many of them added a migration to `crates/store/src/migrations.rs`. A task whose develop round resolved its conflicts met a new one at its test step ten minutes later, when another task had landed. #23, #17 and #40 each used up their three test rounds this way and failed, without a red test in the last round. #40's last round: develop merged `develop` at 01:11, #30's migration 16 landed after that, and the test step at 01:21 conflicted in `migrations.rs`.
- **A retry did not give the rounds back.** A step's round was its attempt number, counted over the task's whole life. A task that failed after three red rounds and was retried by the owner was on its fourth round, so any red failed it again at once. #17 failed again that way after it was retried yesterday.

## What changed

- `Ctx::conflict` (`crates/daemon/src/jobs.rs`) sends the task back to the step's `on_red` with the conflict note, without a round check, and records the run in the task's `conflicts.txt` (`<run>\t<reason>`). The sixth conflict fails the task: "... ; still conflicting with the base after 5 merges" (`CONFLICT_ROUNDS`).
  - Used by the test step's base merge (`command_job`), a suite step's (`suites::run`), and landing when a task is ejected from its batch for a conflict (`landing::Verdict::Conflict`, from `Parked { conflict: true }`).
  - Not a conflict: a red batch, a pull request that was turned down, a self-hold, numbers that are not the task's own. These are red rounds as before.
- `Ctx::round` is what `max_rounds` now counts: the step's runs since the task's last restart, leaving out the runs that ended in a conflict. A restart is a run that ended `Failed`, `Superseded` or `Canceled`, which only the owner's retry or explore-anyway follows.
- The engine's attempt numbers are unchanged (`MASON_ATTEMPT`, `retry_n` in the history, the monitors' attempt counts).

## Tests

- `e2e.rs`:
  - `a_conflict_with_the_base_at_the_test_step_is_not_a_red_round`: with `max_test_rounds = 1`, the base moves during develop, the test step conflicts, develop merges and the task lands. Fails without the change ("still red after 1 round").
  - `a_base_the_agent_never_catches_up_with_still_fails_the_task`: the base moves every round; six test runs, five recorded conflicts, then the task fails.
  - `a_retried_task_gets_its_test_rounds_again`: red twice with `max_test_rounds = 2` fails it; after a retry from test, one more red goes back to develop, and the task lands. Fails without the change.

## Exit test

`scripts/exit/s68.sh` runs the three tests and the s60 and s61 conflict tests.

## Not done, not verified

- `migrations.rs` is still where parallel tasks collide: each new migration is appended to one list with the next number. This change only stops those collisions from failing tasks. Numbering migrations the way MASON numbers stage notes would remove the conflicts.
- `conflicts.txt` lives in the task directory, as `feedback.txt` does, not in the event log. It is lost if the task directory is, and the conflict runs then count as rounds again.
- Approval steps still count their attempts (`conclude_approval`).
- Not run through MASON's own pipeline.
