# s816: one placement mode (local, remote, favor-local, favor-remote) at three levels

Summary: where runs go is now one placement mode, `local`, `remote`, `favor-local` or `favor-remote`, set for all of MASON (`remote.toml` `mode`), per project (`[remote_runs] mode`) and per task (`run_on`), the most specific set level winning; the old `default`, `fallback` and `github`/`local` values still read, and `mason remote mode`, `mason remote status` and `mason task run-on` show and set it. Decision 0809.

## Built
- `place::Mode` replaces `Global` and `Choice`; `Facts` carries task, project and global modes and `decide` resolves them (task, then project, then global). A project with no `[remote_runs]` is always local.
- `place::balance(mode, facts, runs_on, from)` is the one function the two favor modes call. In this stage `favor-local` is local and `favor-remote` is GitHub, with the s812 bounded fallback (`remote::fallback_lease`) after `pickup_timeout`. A project whose effective mode is `favor-remote` gets that fallback even without `fallback = "local"`. The follow-up tickets replace its body.
- `config.rs`: `[remote_runs] mode`; without it `fallback = "local"` reads as `favor-remote`, `fallback = "none"` as `remote`.
- `remote.toml` `mode = "<mode>"`; the old `default` is read when `mode` is absent and dropped when the file is next written.
- CLI: `mason remote mode <mode> [--project P]` (the project form writes the registration file with `toml_edit` and re-reads it), `mason remote on|off` as aliases, `mason remote status` shows the mode per project and its source, `mason task run-on <id> <mode>|default`, `mason task add --run-on <mode>`.
- HTTP: `POST /remote` takes `{"mode", "project"?}` (owner only); `GET /remote` and the task view's `run_on` carry `mode` and `from` (`task`, `project`, `global`).
- `remote::executor_task` (new) gives `pool_needs` the whole-step choice from the effective mode.
- Each decision's text says why ("favor-remote, GitHub had room", "favor-local, this machine had room").
- Tests: `place::tests` (every combination of the three levels, old values, reasons), `definitions::the_project_mode_sits_between_the_task_and_the_global_mode`. Exit test `scripts/exit/s816.sh`; `s722.sh` and `s727.sh` updated for `mode` in place of `default` and for `--run-on remote` now being valid.

## Not changed
- No gate, guard, budget or verdict logic; no PROTECTED file (`protect.rs`) is touched.

## Not verified
- A task-level `favor-remote` in a project whose own mode is not `favor-remote` does not turn on the s812 fallback for that task's runs (the fallback is read per project, not per task).
- The full workspace suite and the exit scripts were not run by hand here; see the run_check results.
