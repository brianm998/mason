# s332: the monitors keep decoding, file I/O and heavy view work off the main thread

Summary: Both monitors now decode frames and read daemon.json off the UI thread, hold progress bursts to one sidebar publish per frame, and carry a debug main-thread watchdog.

## What changed

- **Swift** (`clients/swift/Sources/MonitorCore`): the receive loop reads and decodes in a nonisolated task
  (`MessageDecoder`, injectable); only the finished message hops to the `@MainActor` model, in order.
  `discover()` (the `daemon.json` read) runs in a detached task. `MonitorModel.apply` holds `StepProgress`
  messages and applies a burst as one batch per frame (`scheduleProgressFlush`, 1/30 s); every other message
  flushes first, so order is kept. The sidebar entries are cached by revision and search.
  `Session.openTerminal`'s file write moved off the main actor.
  `MainThreadWatchdog` (debug builds, or `MASON_WATCHDOG=1`) pings the main queue every 20 ms and logs
  anything more than 50 ms late.
- **Compose**: `MonitorConnection` decodes on the socket thread and posts `apply` to an injected UI executor
  (Swing's event queue in the app). Progress is held to one flush per ~33 ms; `daemon.json` is read on
  `Dispatchers.IO`; the sidebar list is remembered on its inputs. The Kotlin model is now only touched on the UI thread,
  which also closes the unsynchronised-read gap the socket-thread `apply` had.
- The protocol is unchanged (#286).

## Tests

Swift: `testFramesAreDecodedOffTheMainThreadAndAppliedInOrder`, `testAHundredProgressUpdatesWhileBusyPublishTheSidebarOnce`.
Compose: `framesAreDecodedOffTheUiThreadAndAppliedOnIt`, `aHundredProgressUpdatesWhileBusyPublishTheSidebarOnce`,
`aViewArrivingAfterHeldProgressSeesTheProgressFirst`. No clocks; counts only.
