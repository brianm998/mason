# s1124: what runs where, per host

Summary: the daemon keeps a live list of what runs on this Mac, each node and GitHub, shows it in `mason hosts`, a `running on:` line of `mason task show`, `/status`, `/tasks/{id}` and the protocol (`HomeView.hosts`, `TaskDetailView.running_on`), and names the node in `ActiveModel.place`.

## Change

- `running.rs` (new): `Host`, `Kind`, the registry with its drop guard, `runs` (every run in flight), `lines` (every configured host with one line of status) and `arrange` (runs under hosts, with the project filter).
- Sources: node runs register in `node_exec::follow`; local checks in `hostedcheck.rs`; command steps in `jobs.rs`; GitHub runs come from the remote holds, which now also record the suite and project; agent sessions from the `llm:` lease holders; local suites from the step hosts `suites.rs` started.
- `schemas/mason.proto`: `HostRun`, `HostView`, `HomeView.hosts` (16), `TaskDetailView.running_on` (25). `PROTOCOL` stays 2. Swift sources regenerated; Kotlin is generated by its Gradle build.
- `views.rs`: the two new fields; `ActiveModel.place` says `node:<name>` for a check on a node.
- `http.rs`: `hosts` in `/status`, `running_on` in `/tasks/{id}`.
- CLI: `mason hosts [--json]`, `running on:` in `mason task show`, and `mason status` names a node a check waits on.
- `places` and the `where` lines are unchanged: they say why a run was placed where it was.

## Tests

Unit (`running.rs`): the guard, also during unwinding; one task on two hosts; a run moved from a node to this Mac; idle hosts and the project filter; reading host ids; a node's words. `tests/nodes.rs`: a check on a loopback node, given back, ended, then a GitHub hold, read through `mason`. `tests/scheduling.rs`: `ActiveModel.place` and the home view. Protocol round-trip and field numbers. `scripts/exit/s1124.sh` runs them.

## Not verified

- No local compile or test run: this Mac's compile queue was held for heat, so everything was built and tested by `run_check` on GitHub.
- The real daemon with Marmot and real GitHub runs: the node is a second daemon on loopback, and the GitHub run is a hold and run record written as the executor writes them, not a run on GitHub.
- A local suite under a step host and a command step appearing in the list have no test of their own; their id reading and suite-name matching are unit tested.
- The monitor shows none of this yet (a later task). Its summaries treat a `node:<name>` place as they treat `here`.
- The Swift and Kotlin builds were not run by me.

## Status lines (added when the task was finished outside the pipeline)

`running::local_words`, `node_status` and `github_words` build each host's one line, leading with `accepting` or `not accepting` and the reason (decision 1113). Unit tests: this Mac with a heat hold, a limit of 0, remote-only and partly remote-only; a node as `mason node list` words it, including an update that waits for jobs; GitHub with others queued, with the account full, and with macOS full.
