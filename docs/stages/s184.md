# s184: a self-update waits for running landing batches

Summary: A takeover (`mason update`, branch switch) first waits, up to `takeover_wait_s` (default 3600), until no project has a landing batch running, holding new batches back meanwhile, and a re-queued task's window counts from its first submission, so a self-update no longer abandons other projects' batches or restarts their windows.

**Built.**
- `landing.rs`: `Landing::draining` flag (checked by `form_and_start` and again under the lock in `start`, which puts members back), `busy_projects`, `wait_idle_once` (condvar wait, woken by `SlotGuard::drop`). `ready_at` is now the landing clock minus the age since first submission; the clock starts at 2^32 s so it can precede the daemon's start.
- `update.rs`: `drain`/`drain_within`/`drain_and_take_over` (one function used by `POST /update` and `improve::switch_channel`), phase `waiting for landing`, log `waiting for N landing batch(es): <project> #<batch> (<phase>)`, and at the cap a log naming the batches that will be abandoned. `takeover_wait_s` in `update.toml`. `Request.now` / `mason update --now` skips the drain. A failed `take_over` clears the flag.
- `crates/store`: migration 28, `landing_submitted(task, run, at_ms)`, `first_landing_submit`.
- CLI: `--now`; the existing log follower prints the waiting line; its overall patience is now two hours.

**Tests.** `crates/daemon/tests/takeover_drain.rs` (new file, next to #188's update tests): wait + hold + resume (`a_takeover_waits_for_running_landing_batches_and_holds_new_ones`), the cap names the batch, a failed takeover clears the flag. Unit: a requeued task's window. Store: first submission remembered.

**Not verified.**
- The drain tests call `update::drain*` in the test process: no real `POST /update` with a prebuilt runtime, no real exec, no `--now` end to end (the new daemon abandoning the batch is unchanged code), and no two-project case (the held task is in the same project).
- The restart keeps-`ready_at` case is a unit test of the clock arithmetic plus a store test; no restarted daemon was run.
- `scripts/exit/s184.sh` and the real `mason update` printout were not run by me; clippy was not run separately.
- Resuming a batch mid-CI after a restart is out of scope.
