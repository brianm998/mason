# s965: `mason project rename OLD NEW` renames a project and keeps its history

Summary: `mason project rename OLD NEW [--yes]` moves the registration file, appends a new `ProjectRenamed` event, rewrites the store's text `project` columns and name-built keys in one transaction and re-keys the live registry, so the project keeps its id, tasks and history with no restart.

**Event.** `EventKind::ProjectRenamed { project, name }` (core), encoded as `project_renamed` (store codec, same payload as `project_registered`). The reducer refuses an unknown project (`UnknownProject`) and a name another project uses (`NameTaken`), and updates `w.projects[..].name`; the `projects` row is rewritten through `Touched.projects`, so replay and the live projection agree. No migration; the append-only triggers are untouched.

**Store.** `Store::rename_project(old, new)` finds every table with a TEXT `project` column through `sqlite_master` and `PRAGMA table_info` (no hand list), and moves `meta` `def:<name>`, `alerts` `paused:<name>:<mode>` and `schedules.name` `analyst:<name>` in the same transaction.

**Daemon.** `POST /projects/{old}/rename` with `{name, yes}` (`Daemon::rename_project`, `crates/daemon/src/rename.rs`). It refuses an invalid or taken NEW, an existing `NEW.toml`, a project with a task that is not landed or canceled, and a running landing batch, naming each. Without `yes` it returns the plan; with `yes` (owner only) it moves the file (back on failure), appends the event, rewrites the store, re-keys the registry entry, removes `l/OLD-b<N>` landing worktrees with `git worktree remove` and an empty `w/OLD`, and lists the `mason/OLD/*`, `mason/int/OLD/*` and `mason/ci/OLD-*` branches it leaves alone.

**CLI.** `mason project rename OLD NEW [--yes]`; without `--yes` it only prints the plan.

**Trust.** `crates/engine/src/reducer.rs` is PROTECTED; the new arm needs the owner's approval. `event.rs`, `codec.rs` and `migrations.rs` were not found in `PROTECTED` when this was written (not rechecked after the last edit).

**Not verified.** I could not run cargo here (builds are refused in the shell), so everything relies on `run_check`. The exit script `scripts/exit/s965.sh` was written but not run by me. A held step host is not checked separately: a host belongs to a task, and any task not landed or canceled already refuses the rename. The daemon integration test calls `Daemon::rename_project` directly, not the HTTP route or the CLI. Monitors (Swift/Compose) were not examined: the rename arrives as an unknown event kind and I did not check how they handle it or a saved sidebar filter that names the old project.
