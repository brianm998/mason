# s178: MASON's own test step runs suites: a build per suite, an impact map, run_check on the selected suites

Summary: a suite may have its own `build` (holding one `compile` slot, given back before the run), `run_check` on a suites step runs the `development`-bound suites the impact map selects for the worktree's changes, and MASON's own `.mason/mason.toml` now runs `cargo-workspace`, `swift-clients` and `compose-clients` chosen by path.

Task #187. Decision 0173 records the choices, including docs-only changes.

## Built

- **Definition**: `build` is a suite key (`crates/testing/src/model.rs`, `testing_parse.rs`); empty is refused in `validate.rs`. `build` on a step with suites is still refused.
- **Daemon, test step** (`crates/daemon/src/suites.rs`, `jobs.rs`): when a selected suite has a `build`, the step takes no lease up front. Per suite: build under `compile = 1` and give it back, then take the step's `uses` without `compile` plus the suite's and its environment's `uses`, run, release. A suite without `build` holds the step's whole `uses` for its run. A suite already green for the tree builds nothing; suites with one build command share one build per tree. A red build is a red step with the build's output. Gates that run suites hold the whole step's needs.
- **Daemon, `run_check`**: if the test step has suites and one is bound to `development`, `run_check` plans from the worktree's changes (committed, uncommitted and new files against the merge base), runs each selected suite after its build with the same two-phase slots, and reports one line per suite (passed, FAILED with output, or not run and why). Nothing selected is a pass that says so. With no `development` binding it runs the single command as before.
- **`{project_test}`**: in a suite's `command`, `build` or `rerun` it becomes the project file's `test` command (layered with overrides, as the single-command path resolves it). This is how the owner's per-worktree `CARGO_TARGET_DIR` reaches the cargo suite without a path in the repository.
- **`.mason/mason.toml`**: three suites, binding `unit` to `development` and `test_step`, and the impact map from the ticket. Their `build` lines are commented out: the daemon that validates the file when it lands does not know the key yet, so a follow-up uncomments them. Until then each suite holds the step's whole `uses` (as the single command does today). `{project_test}` is understood only by a daemon with this change; the daemon updates from GitHub `develop` after landing.
- **Tests**: definition (build parses, empty and non-string refused, MASON's own impact map by path); `crates/daemon/tests/suite_builds.rs` (holdings read from the broker with gate files, one build shared, run_check runs only the selected suite, no development binding keeps the single command). No timing assertions.
- **Exit**: `scripts/exit/s178.sh`.
