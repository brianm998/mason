# s177: a red that also fails at the merge base is excused on the command path

Summary: A command-path test step whose failing tests (red on every run) all also fail at the merge base is green with the excuse noted in `mason task show`; the base is run once per (base, command, test set), and one "<test> fails on <base>" task is filed per test, deduped against open tasks and tracker issues.

**Built.**
- `crates/daemon/src/basecheck.rs`: `excuse` (called from `command_job` after the last red run), the base run in a throwaway worktree (repository lock, step time limit, `build` first), the cache in the `baselines` table, the fix-task filing and dedupe, `recorded` for the task view.
- `jobs.rs`: the call; `http.rs` and the CLI: `excused` in the task JSON and `excused` lines in `mason task show`.

**Tests.** Unit: all-excused rule, the cache (the second lookup does not run), the fix title. `crates/daemon/tests/e2e.rs`: `a` failing on branch and base is green for two tasks with one fix task; `a` failing only on the branch is red and files nothing. No timing assertions. Exit test: `scripts/exit/s177.sh`.

**Trust.** Verdict logic (decision 0172): a failure is excused only when the same test fails at the merge base. `suites.rs` and `crates/testing/**` are untouched.

**Not verified.**
- A real cargo or xcodebuild project; the filtered base run was exercised with a fake libtest-printing script only.
- A base run is not hosted by a step host, so a daemon restart during it loses the run (it is run again, nothing is cached).
- The tracker-issue dedupe is by test name in the issue's title or body; no real tracker was used.
- The fix task's own landing was not run.
