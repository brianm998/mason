# s219: step-host IPC and process trees on Windows

Summary: On Windows the step host talks over AF_UNIX sockets and its child trees live in named Job Objects, behind `mason_platform::net` and `process::spawn_group`, and the CI windows job now runs the platform, step-host and adapters tests.

What changed
- `mason_platform::net`: Winsock-based `UnixStream` and `UnixListener` on Windows (the `std` types on Unix).
- `mason_platform::process`: `spawn_group` (Job Object per child on Windows), `signal_group` and `signal_process` terminate on Windows, `detached`, `start_time`, `image_path`. All spawn sites that used `group_leader` + `spawn` (step-host, adapters/claude.rs, daemon jobs.rs and basecheck.rs, landing proc.rs, cli resources.rs) call `spawn_group`.
- step-host: the host is launched detached on Windows; the registry's `proc_start`, `proc_command` and `proc_pgid` have Windows versions.
- Tests: `crates/step-host/tests/portable.rs` (connect, reattach through the on-disk record after the controller drops, stop) runs on every platform; Windows-only tests in `net.rs` and `process.rs`.
- `.github/workflows/ci.yml`: the `windows` job runs the `mason-platform`, `mason-step-host` and `mason-adapters` tests. Decision: `docs/decisions/0214-windows-ipc-process-trees.md`.

Not verified
- Nothing was run on Windows. The Windows code (Winsock, Job Objects, `GetProcessTimes`) is only type-checked from macOS. Whether the new `windows` CI step passes is for the owner to check after landing.
- Some adapters tests run `sh -c` (`run_command`, the fake CI host); they are expected to fail in the Windows job until the shell-steps task (W4) lands. I did not gate them.
- Whether a `cmd /C ... ping` child is stopped as a tree (the Windows portable tests) is untested; `host.rs` (Unix-only, scripts `sh`) still covers grandchild kill on Unix.
- Protected files touched (owner approval): `.github/workflows/ci.yml`, `crates/landing/src/proc.rs`, `scripts/exit/s219.sh`.
