# s265: Windows port 3, daemon takeover and the managed loader without exec

Summary: On Windows a daemon update hands over by spawning the new runtime and exiting, and `masond --managed` supervises a child instead of exec'ing, keeping the crash counting and rollback; Unix still execs.

## What changed

- `crates/platform/src/process.rs`: `replace_process` on Windows starts the successor (detached, with `MASON_TAKEOVER_FROM=<pid>`) and exits with `HANDOVER_EXIT` (75); it returns an error only if the successor cannot start or dies at once. New `predecessor()` and `wait_until()` (condition polling, no fixed sleeps).
- `crates/daemon/src/main.rs`: the managed loader is `managed_once` (picks the runtime, rolls back, records the boot). Unix execs as before. Windows `supervise` runs it as a child: exit 0 ends the loader, exit 75 is followed to the successor (found through `daemon.json`), anything else is a crash that the next pick counts. A successor waits for its predecessor to be gone before it takes the port.
- Runtimes: `runtimes/<id>/` is written only by a build into a fresh directory, and `current` is switched by an atomic file write, so nothing writes a running .exe.

## Not verified

- Nothing ran on Windows, and the Windows target check was not run here (cargo is only reachable through run_check). The Windows code is compiled first by CI's `windows` job.
- `ci.yml` is PROTECTED, so the update tests are not yet enabled on the windows job; that needs the owner.
- The port cannot be shared on Windows, so the old daemon must leave before the new one answers; "wait until it answers, then exit" is not possible there. See decision 0260.
- No test drives the handoff end to end; only `wait_until` has a unit test.
- Scoped runs on this branch showed develop failures outside this change: `introspect` digest, `targets` slot-1 glob, and adapter-api `submit_diagnosis is in no step`.
