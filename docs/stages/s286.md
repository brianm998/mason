# s286: a suite's results_file may name a pattern

Summary: A suite's `results_file` may end in a wildcard (`star-desktop/build/test-results/test/*.xml`). MASON reads every matching file as one set of results, and removes them all before a run. Before this, the pattern was opened as a file name, so star's `test-desktop` had never been green.

## Why

On 2026-11-14 six star tasks (#198, #212, #213, #215, #301, #310) were red on `test-desktop` with "the results file `star-desktop/build/test-results/test/*.xml` was not written": Gradle writes one JUnit file per test class, and MASON read `results_file` as a literal path. The store had no green or evidence row for `test-desktop` at all. When tests really failed, the non-zero exit hid it.

## What changed

- `crates/daemon/src/suites.rs`: `results_paths`, `read_results` and `remove_results`. A last path segment with `*` or `?` matches the files in that directory (`mason_testing::glob::matches`), sorted; anything else is the path itself, as before. Judging reads all matches one after another (the parsers find test cases in the text). Every place that cleared the results before a run (five in `suites.rs`, one in `suites/base_red.rs`) removes every match, so stale results from an up-to-date Gradle task are not read.
- Test: `a_wildcard_results_file_reads_every_matching_file_and_a_plain_one_reads_itself` (unit, in `suites.rs`).

## Not verified

A wildcard in an earlier segment (`build/*/results.xml`) is not expanded. A pinned definition takes the new reading as soon as masond runs this build; no repin is needed.
