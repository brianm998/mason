# Stage 296: One-command onboarding

Summary: `mason init` now lands its own setup when the owner answers `--land merge|push|pr` (the default and `--yes` are `no`, so nothing is merged, pushed or opened without a yes), registers the project with a running masond through a new `POST /projects/{name}/register` (no restart), files the proof task, opens the monitor on a Mac you are sitting at (else prints a pairing code), and prints where each choice lives; `s296.sh` takes a scratch repository, fake agent and running daemon from one `mason init` to a landed proof task, and the ten-minute path was not timed on a real machine.

## Built
- `Daemon::register_project` (daemon.rs) and `POST /projects/{name}/register` (http.rs): loads `<config>/projects/<name>.toml`, appends `ProjectRegistered` if the id is new, inserts it into the registry and reads its definition (`load_definition_of`, split out of `load_definitions`). A file that does not load is refused and nothing changes. `reload_registration` is unchanged: it only ever helped edits to projects masond started with (task #172), so it did not remove the restart for a new project.
- `--land no|merge|push|pr` (questions.rs): asked on a terminal, default `no`; without a terminal and with `--yes` it is `no`. `init/land.rs`: `merge` is `--ff-only` and only when the base is checked out and the tree has no uncommitted changes to tracked files; `push` merges then pushes the base (direct, direct-ci, batched) or, in `pr` mode, pushes the setup branch only; `pr` pushes the branch and opens a PR through the GitHub adapter (`GITHUB_TOKEN`; `MASON_GITHUB_API` overrides the API base), else prints the `gh pr create` command. Every refusal or failure prints the exact commands and changes nothing; the exit status is then 1.
- `init::run`: after the setup it lands, registers with a running masond, files the proof task when agreed (`--no-prove` skips), opens the monitor (macOS, a terminal on stdin, the app present, `MASON_NO_OPEN` unset), else prints a pairing code or `mason pair`, then prints where definition, landing, alerts and providers live. `--prove-only` now registers the project itself instead of asking for a restart.
- Tests: `crates/cli/tests/init.rs` (13 new: `--yes` never lands, `--land no` same files, merge with and without a remote, dirty tree, base not checked out, push, push without a remote, pr-mode push, PR without a token, PR against a local fake GitHub API, PR in a non-PR mode, the summary), questions.rs and land.rs unit tests, `crates/daemon/tests/registration.rs`.
- `scripts/exit/s296.sh`; decision 0290.

## Exit test
`bash scripts/exit/s296.sh` ends with `s296: all checks passed`. Part 1: without `--land` nothing moves on a repository with a remote. Part 2: one `mason init --yes --land push` against a running masond that did not know the project merges, pushes, registers, files the proof task, and the task lands (`MASON-WORKS.md` on the bare origin); the elapsed time is printed, not asserted (8 s on this machine, with the fake agent).

## Not run
- The ten-minute target on a real machine with a real agent: not timed. The 8 s above is the fake agent only.
- Answers are given to the exit script as flags, not piped: stdin that is not a terminal has never been read by `init`, so a pipe changes nothing. The terminal question for `--land` was unit-tested for order only, not typed at a real terminal.
- Opening the Mason Monitor app (`open -a`), and a real pairing code: the script runs with `MASON_NO_OPEN` and no LAN pairing; the app path was not run, so as not to put anything on the screen.
- A real GitHub PR: the PR call was tested against a local socket answering one request, not against api.github.com.
- A base branch checked out with no remote: after `--land merge` masond cannot land onto it; init says so, and this was not exercised with a daemon.
- I did not read the whole PROTECTED list; no gate, guard, budget or `scripts/exit` file other than the new `s296.sh` was changed.
