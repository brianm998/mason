# Stage 20: Monitors answer and approve by clicking

## Built
- **Protocol** (`schemas/mason.proto`, additive; see decision 0017): `Hello.actor`, `Welcome.owner`, `Command.approve_hold` (`ApproveHold`), `Approval`, `AttentionItem.approval`, `TaskDetailView.approval`. Rust, Kotlin (Wire) and Swift (regenerated `mason.pb.swift`, `protoc` and `protoc-gen-swift` were installed) all build from it.
- **Daemon**: `views.rs` builds an `Approval` for a proposed task, an approval-step wait and an unapproved self-hold (reasons as lines, the diff hash, the branch, a `git diff` command); the header count and the Home queue include them; a pending hold adds `approve` and `reject` to `allowed_actions`. `ws.rs` maps `approve_hold` to `POST /tasks/{id}/approve` with the diff hash and answers `Welcome.owner`. `http.rs`: an approve with a diff hash other than the hold's is refused (409); reject of a pending hold cancels the task with the reason and is owner-only. `attention.rs`, `selfguard.rs` and `protect.rs` are not edited.
- **Both monitors**: the decision card (options as buttons with the recommended one marked, an Other box with Send, arrow keys and Return, Enter sends and Shift-Enter adds a line in Other, the evidence, the refusal text), a new approval view (what it waits on, the lines, diff hash, branch, diff command with copy, Approve, Reject with a reason box), the top bar's count as a button that opens the first task needing the owner, and no buttons for a connection the daemon says is not the owner. Shared key logic in `MonitorCore/CardInput.swift` and `core/.../CardInput.kt`.
- **Conformance** (`crates/conformance`): `card_item` offers `option:N` and `other` only to the owner; a new `approval:<task>` item (waits-on text, each line, `diff <hash>`, branch, command; actions `approve` and `reject` for the owner only); `visible(views, owner)`; `conformance expected --actor NAME [--now]`. An unexpected `approval:` item fails like an unexpected card. Both clients' `visibleItems` build the same items. `clients/features.toml` lists `decision-card-keyboard`, `approval-view` and `attention-link`, done in both.
- **monitor-tool** (both): `answer --text/--hash`, `approve [--diff]`, `reject [--reason]`, `dump`.
- **Not built: multi-select.** The protocol's question has no multi-select flag (decision 0017).

## Tests
- Rust `crates/daemon/tests/approvals.rs` (a real in-process daemon with a self-hosting hold): the welcome's owner flag for the owner, a stranger and nobody; the hold's approval view, `allowed_actions`, header count and Home queue; Approve with a wrong hash (409), by a non-owner (403), with the shown hash (lands); Reject by a non-owner (403) and by the owner (the task is canceled). The existing `protocol.rs` test covers an answer's stale hash (409) and non-owner (403). A conformance unit test covers owner-only buttons.
- Swift (`MonitorCoreTests`, 25 tests) and Compose core (`MonitorCoreTest`): answer by option, answer with Other text (trimmed, never blank), a stale hash sent as shown and the refusal kept for the card, arrow-key selection and the Enter/Shift-Enter rule, Approve with the hold's hash and plain approve without one, Reject with its reason, owner versus non-owner items, the attention click.

## What testing found
- The first run of `s20-real.sh` was refused by the self-task limit (3 open): the scratch project needs `max_open = 5`, as `s17.sh` has.
- A stale answer was already refused by the daemon (409) and a non-owner already got 403; what was missing was the owner flag in the monitor, so the buttons were drawn for everyone.

## Not done, or not run
- `bash scripts/run-exit-scripts.sh` here: every script passed except `s06.sh`, whose test `the_cli_leaves_quietly_when_its_output_is_cut_off` builds an unquoted `sh -c` line from the path of the `mason` binary. This worktree's path contains a space ("Application Support"), so the line breaks. The same test passes from a checkout of the same base commit in a path without a space, so it is not caused by this stage; it was not changed.
- **The windows themselves were not driven.** Nothing clicked a real SwiftUI or Compose window: the arrow keys, Return, Enter and Shift-Enter are wired in the views (`onKeyPress` in SwiftUI, `onPreviewKeyEvent` in Compose) and the rules they call are unit-tested, but the key handling in a live window, the focus order between the card and the Other box, the Shift-Enter newline in SwiftUI's `TextEditor` and the look of the selection outline were compiled and not seen. `monitor-tool` sends what the buttons send, from the same model code, and the conformance dumps check what is drawn. Screenshots were not regenerated.
- Multi-select: not built (above).
- The detail page's other row buttons are still the daemon's `allowed_actions` for everyone (Cancel and the like); only the card and approval buttons follow the owner flag. The daemon refuses a non-owner's command regardless.
- `s20-real.sh` runs only on a Mac with Swift; on a machine without it the script says it is skipped.
- Changes to protected files: `clients/features.toml` and the new `scripts/exit/s20*.sh` are gate files (new tests; nothing weakened), and `schemas/mason.proto` is the protocol; they wait for the owner's approval.
