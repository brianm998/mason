# s208: a self-update waiting for a landing batch says so and offers Update now

Summary: A built and tested masond update that waits for landing batches is now shown in the monitors as such (batches and latest time), its button reads "Update now" with a daemon-written confirmation of what abandoning the batches means, and `POST /update/now` (or `mason update --now`) stops the wait.

**Built.**
- `update.rs`: `Status.wait` (batches with tasks, window, deadline clock time) set by `drain_within`; `waiting for landing` arm in `daemon_banner`; `button_for`, `waiting_confirm`, `wait_view`; `update_now()` sets `Daemon.update_now`, which `drain_within` checks each pass (logs "the owner chose Update now ... abandons: <batches>" and returns). Abandoned batches then go back to the queue through the existing restart path.
- `http.rs`: `POST /update/now` (409 with a reason if nothing waits); `POST /update` with `now` while waiting does the same and records an `update_now` intervention under the caller's identity; `GET /update` has `waiting`, `daemon_button`, `daemon_confirm`.
- Protocol: `UpdateInfo.daemon_button = 4`, `daemon_confirm = 5` (Swift generated file edited by hand, protoc was not available).
- Clients (Swift, Compose): button label from `daemon_button`, confirmation dialog ("Update now" / "Keep waiting") when `daemon_confirm` is set, commands carry id `update-daemon`, a refusal goes to `updateError`. `clients/features.toml` entry `update-wait-for-landing`.
- CLI: `mason update status` prints the waiting sentence.

**Trust.** `update.rs` and `clients/features.toml` are protected; both are needed to add the waiting state and the parity entry. The takeover rules are unchanged: without the owner's explicit Update now an update still waits up to `takeover_wait_s`.
