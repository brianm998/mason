# s236: a whole-machine request no longer starves behind another project's work

Summary: A request that has waited `order.max_wait_s` (default 30 min) goes ahead of all other pipeline work except a landing, so an `exclusive` request reaches the front and the machine drains for it; progress is compared as a share of each definition's own route, and `mason task priority <id> urgent|high|normal|low` (owner only) re-ranks a task's waiting requests in place.

Task #287. Decision record: `docs/decisions/0231-scheduler-aging-and-comparable-progress.md`. Exit test: `scripts/exit/s236.sh`.

**What changed**

- `crates/scheduler/src/rank.rs`: the rank tuple is now (interactive, band, progress remaining in thousandths of the route, priority, enqueue time, id). Bands: 0 landing, 1 aged, 2 everything else (2 + priority when ordering by priority first). `Rank::with_span`, `aged`, `with_priority` are new; `Rank::new` keeps its signature.
- `crates/scheduler/src/plan.rs`: `World.max_wait` (ms). A request whose age (`now - since`) is at least that is ranked aged for this plan; capacity, the CPU gate, memory, disk, the stall gate and the passing rule are untouched, and a request younger than `max_wait` is planned exactly as before. A wait that is aged says "...; waited 30 min: first in line once the machine is free".
- `crates/scheduler/src/ledger.rs`: `set_max_wait`, `rank_of`, `snapshot_at(now)` (waiting list in the order `plan` takes it, aged first).
- `crates/daemon/src/sched.rs`: `[order] max_wait_s` in resources.toml (whole number, 0 = off, negative refused); `Standing.span`; `Broker::set_task_priority`, `lease_set_task`; `mason resources --json` waiting entries gain `task`, `priority`, `aged` and are listed in aged order.
- `crates/daemon/src/daemon.rs`, `crates/definition/src/graph.rs`: `route_length(def)` (the span), used by `rank_for` and `lease_standing` on the same definition as `steps_remaining`.
- `POST /tasks/{id}/priority`, `mason task priority`: owner only, recorded as the intervention `task_priority`. It emits `TrackerEdited` with the new priority (the store's record), and for a task linked to a tracker issue also stores the new priority in its tracker row and remembers it until the tracker's `priority:*` label is set (`TrackerAdapter::set_priority`, GitHub implements it; the next `mirror_out` sends it), so the sync does not undo it.

**Verified:** see the tests named in the decision record, run through `run_check`. `scripts/exit/s236.sh` was written and run as stated in the decision record.

**Not verified:** the GitHub label calls against the real API (only written against the REST shape; no network here). A priority set on a tracker-linked task is remembered in memory until the label is sent, so a daemon restart in between loses it and the next sync takes the tracker's value back. The monitors have no menu item for it (out of scope).
