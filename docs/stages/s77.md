# s77: an agent's own `mason run` no longer starves a task in its test step

Summary: A `mason run --needs` made by a task's agent is now ranked as that task's pipeline work (its steps remaining and priority) instead of as an interactive caller, so a task already in `test` is granted a `compile` slot ahead of an agent still developing; a `mason run` with no task stays interactive.

## Why

On 2026-11-08 #41 waited over an hour for a `compile` slot and #43 about 30 minutes, both in `test`, while develop agents queued their own `cargo test` runs through `mason run`. `Scheduler::lease_open` built every such request as `Rank::new(true, 0, 0, …)`, and interactive sorts before everything.

## What changed

- `crates/daemon/src/sched.rs`: `lease_open_as(label, uses, Option<Standing>)`. With a `Standing { steps_remaining, priority }` the request is `Rank::new(false, steps, priority, now, seq, false)`. `lease_open` is unchanged (interactive). Arrival time and sequence are the request's own, and the project's priority jump is not applied.
- `crates/daemon/src/daemon.rs`: `lease_standing(task)` reads the task's current step from the world and returns its steps remaining and priority, or `None` for an unknown task or one not in a step.
- `crates/daemon/src/http.rs`: `POST /leases` takes an optional `task`.
- `crates/daemon/src/jobs.rs`: the agent session's environment now carries `MASON_TASK` (before, only script steps and plugins got it, so it never reached `mason run` called by an agent). Set after the project's `agent_env`, replacing any entry of that name.
- `crates/cli/src/resources.rs`: `mason run` sends `MASON_TASK` when it is set to a number, and its default label becomes ``task N `cmd` `` instead of ``interactive `cmd` ``.
- `mason resources` and the monitors need no change: the explanation already says "(interactive)" only for a rank that is interactive, and the snapshot's `interactive` field follows the rank.

## Tests

- `crates/scheduler`: rank ordering for a person, a test step and a linked run; `a_stream_of_task_linked_requests_never_holds_back_a_waiting_test_step`.
- `crates/daemon/tests/scheduling.rs`: a test step outranks a linked run from a task with more steps left (and the run is not shown as interactive); a run with no task still outranks both; a stream of linked requests, with more arriving, cannot hold a waiting test step back.
- `scripts/exit/s77.sh`: a real `masond`, the scripted agent, `compile` limited to 1. One agent queues six `mason run`s; the other task lands after the first run, and `mason resources` shows the queued run as not interactive. A hand-made run is shown as interactive.

## Not verified

- The exit script was not run against the old code to watch it fail; the unit tests encode the old behaviour's ordering instead.
- Coordination with branch `claude/mason-pipeline-performance-737899` (d670ec2, `run_check`): it had not landed on `develop`, and I did not read it beyond confirming that. This change touches only the lease request and does not change `run_check`; if that branch queues through `mason run` it gets the new ranking from `MASON_TASK`, but if it opens leases in another way it must pass a `Standing` itself. Expect a textual merge in `jobs.rs` only if it also edits the agent environment.
- Only the agent adapters that apply `SessionSpec.env` get `MASON_TASK`; I checked the scripted agent, not the real Claude or Codex adapters.
