# s467: the parity gate has an iOS column

Summary: `conformance features` now checks three clients (swift, compose, ios) and reads the `[ipad.*]` and `[phone.*]` deliberate-difference tables, so a feature missing on the iPad or iPhone without a recorded reason fails the gate.

## What changed

- `crates/conformance/src/features.rs`: `CLIENTS` is `["swift", "compose", "ios"]`. `ios` is `done`, `todo`, `n/a` or `difference`. `done` means the feature appears on both the iPad and the iPhone. `difference` needs `ios_ipad` and `ios_iphone`, each `"done"` or the name of an `ipad.*` / `phone.*` entry. Every `[ipad.*]` and `[phone.*]` entry needs a description and a `platform_reason`. An ios status that differs from swift needs a feature `platform_reason`, as before.
- `clients/features.toml`: `ios = "done"` on every feature except `pipeline-editor` (graph editing), `active-sessions-panel` and `health-session-banner` (agent sessions), which are differences. New `[ipad.agent-sessions]` and `[ipad.graph-editing]` tables.
- `crates/conformance/src/main.rs`: the report line names the ios count.
- Android is not a column.

## Trust

Both `features.rs` (CLIENTS is a gate) and `clients/features.toml` (client parity) are protected. The gate change is needed because the old gate could not see the iOS app at all. It tightens the check, and no existing rule was loosened.
