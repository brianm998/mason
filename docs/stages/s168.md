# s168: a retry resumes at the failed step when the failure was not about the code

Summary: A failure is classified when it is recorded (about the code, or outside it: a landing push, fetch or auth error, a lost host), and a retry with no step goes back to the failed step when the failure was outside the code, otherwise to the first developing step as before.

**Cause.** `retry` with no `to` asked `hostloss::retry_step`, which kept the failed step only when the text said "the command was lost". A landing push failure went back to `setup`, so a develop agent, the test step and review ran again on finished work.

**What changed.**
- `FailClass` (`Code`, `Outside`) in `mason-core`. `StepFailed` carries `class: Option<FailClass>`; the reducer stores it on the task as `failure_class` and clears it on a retry. The codec writes it as an optional trailing word, so events recorded before this read back as `None`.
- `FailClass::classify(state, reason)` is called where the step's failure is emitted (`Ctx::conclude`): a landing "landing failed: …" verdict (push, fetch, auth, CI service, services unusable) and a lost command host are `Outside`; everything else (red rounds used up, review red, a weakening, an agent failure, a panic, an owner rejection) is `Code`. A base conflict is not a failure (it is a send-back).
- `hostloss::retry_step(failure, class, step)`: `Outside` goes to the failed step, `Code` to the first developing step, `None` (recorded without a class) keeps the old text rule, so old failures behave as today.
- `GET /tasks/{id}` carries `retry_to` for a failed task (and `failure_class` in the detail). `mason task retry` prints "Task #N will retry from `STEP`" before it sends, and `mason task show` prints a `retry` line under the failure. `--from` and the body's `to` still override.

**Not done.** The monitors' Retry button ("Retry from land") is not changed: it needs a `clients/features.toml` entry, which is protected and waits for the owner. The daemon already sends `retry_to` for them to read.

**Not verified by me.** The shared build queue refused direct cargo commands in this session, so nothing was compiled or run by me except through the `tests` check; `cargo fmt` and `clippy` were not run and the new lines were formatted by hand. The exit script `scripts/exit/s168.sh` runs `crates/daemon/tests/retry_outside.rs`; whether the local pre-receive hook makes landing fail with "landing failed: git push … failed" (and not a retry or a wait) I saw only through that test's result, if it ran.
