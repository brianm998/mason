# s88: alerts and notifications keep working when git or the repository lock is stuck

Summary: Alerts and notifications now run on their own thread that never waits on git or the repository lock, daemon speech runs off it with a per-sentence time limit, and a "git work is stuck" alert names what holds the repository lock.

- Two threads replace the old watcher loop: definitions (watch, fetch, `admit`) and attention (`sync_alerts`, `notify::tick`, every `attention_interval`, 5 s by default).
- `repo_lock` returns a `RepoLock` that records the caller (file:line, from `#[track_caller]`) and start time of its holder. Reading that never takes a repository lock.
- The definitions thread records when each pass ended. `alerts_now` raises `git-stuck` (kind `git_stuck`, sounds as a broken thing) when that is older than `stuck_after` (5 min; `--stuck-after-ms`) plus the reload interval, with the age and the holder if known. It clears when a pass ends.
- Daemon speech runs on a `speech` thread, one sentence at a time; a command that outlives `speech_timeout` (30 s) is killed and logged. While it is at work the next tick leaves further announcements queued.
- `POST /debug/hold-repo-lock?ms=N` (only with `--debug`) holds a project's repository lock, for the exit test.
- Tests: `crates/daemon/tests/notify.rs` (lock held: alerts sync, notification delivered, stuck alert appears and clears; hanging speech is killed and does not delay the tick); `scripts/exit/s88.sh`.

Not verified: a real hung remote (the exit test holds the lock through the debug route instead); a speech command that ignores SIGKILL's children (only the direct child is killed). A stuck `git` that does not hold the lock still raises the alert, without a holder. The existing "in order" speech test now waits for the speech thread instead of reading the file straight after the tick.
