# s868: the owner's self-update build goes ahead of task work and past the heat hold (#923)

Summary: An update the owner starts takes its `compile` slot ahead of all task work and past the CPU and heat holds (never past a die more than 2 °C over `thermal_max_c`); an automatic update rises the same way after `update_wait_max_s` (default 30 min).

**Cause.** `build_leased` asked for `compile` as the lowest pipeline work, so a self-update waited hours behind task work and the heat hold (2026-11-21, 233 commits behind).

**Change.**
- `crates/scheduler`: a request can be `hold_exempt`: the CPU, stall, syspolicyd and pacing holds do not apply to it and the thermal hold applies only above `World::heat_ceiling`.
- `crates/daemon/src/sched.rs`: `Broker::lease_open_update`; the daemon sets the ceiling at `thermal_max_c + 2`; a waiting owner's update says "update waits: die 100 °C over the 99 °C ceiling" or "owner's update: next for compile, the heat hold does not apply to it".
- `crates/daemon/src/update.rs`: `update_wait_max_s` in update.toml; `with_compile_lease` reopens an automatic build ahead of task work after the wait. `mason update` (not `--auto`) is the owner's. The build still holds one `compile` slot and `CARGO_BUILD_JOBS = cpus/8`. The takeover is unchanged.

**Not verified.** No real masond run: `scripts/exit/s868.sh` runs the unit tests only (broker with a fake thermal source and fixed readings). The "ahead of task work" rank is interactive, so the build shows as a non-person holder in the monitor. The monitor-build path (`build_monitor`) is unchanged. Disk and memory gates still apply.
