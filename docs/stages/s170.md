# Stage 170: four flaky daemon tests made deterministic

Summary: The crash-boundary, sweep, hold-across-a-kill and admission tests no longer depend on timing, and `Store::verify` no longer reports a false gap while events are being appended.

**What changed.** See decision 0165. `Store::verify` reads from one snapshot (the sweep test's real cause). The crash test repeats a failed filing and has larger hang limits. The hold test uses a 120 s hold (was 25 s) that is waited out. The admission test, renamed `when_a_step_ends_the_next_task_is_the_next_one_admitted`, asserts log order instead of a duration. `scripts/exit/s170.sh` runs each 10 times; `s60.sh` follows the rename.

**Not verified.** The sandbox refused direct build commands (the build queue hook), so I did not run any test loop, and did not check any test 20 times under two parallel workspace runs. The causes come from the recorded failure logs in MASON's test directory and from reading the code, not from reproduction. I did not reproduce the old failures on current develop. The `git init` timeout seen once in the crash test (a stalled disk) is not addressed. The admission test's `Admitted` assumption (only queue claims emit it) is from reading `daemon.rs`, not a run. Formatting, clippy and `s170.sh` were not run by me; the `tests` check is the only run.
