# Stage 11: Protocol, views and parity tooling

## Built
- **`schemas/mason.proto`** and **`crates/protocol`**: hello, subscribe, typed and raw commands, welcome, snapshot, events, view updates, results; the seven views (`HeaderView`, `SidebarView`, `HomeView`, `TaskDetailView`, `LandingView`, `UsageView`, `EditorView`). Rust through `prost` (compiled by `protox`, so no `protoc` is needed), the **JSON mode** through `pbjson`, Swift through `protoc-gen-swift` (committed, `scripts/gen-clients.sh`). Kotlin through Wire is wired into the script and not generated here.
- **One WebSocket** (`/ws`): a client sends its last sequence number and gets a snapshot, only the events it missed, or nothing; then live events and recomputed views; commands run through the same router as the HTTP API, and typed ones are refused unless in the task's `allowed_actions`. A blocking client in `mason_protocol::client`.
- **Server-computed views** (`daemon/views.rs`): every task row carries `allowed_actions`, its "why waiting" sentence and progress cells; `SidebarView` does the sorting (active oldest first, history newest first and collapsed).
- **The CLI runs over the socket**, so everything a monitor can do it can do; loopback only.
- **`masond --demo`** (and `--demo-manual`, `--demo-step-ms`): an eight-checkpoint scripted scenario of real events.
- **Parity tooling (`crates/conformance`, bin `conformance`)**: `features` (the parity check), `tokens --write|--check` (one design-token file for both clients), `expected` and `check` (the conformance runner), `resume` and `latency` (used by the exit test). `clients/features.toml` (18 features, all todo), `clients/tokens.toml`, CI steps for both checks.
- **Faster hand-offs**, found while measuring: a task holds a session claim only during an agent step; resources are handed back as a step reports; a lost wake-up in the broker is closed.
- `docs/decisions/0008-protocol-readings.md`, `scripts/exit/s11.sh`.

## Exit test
`bash scripts/exit/s11.sh` passes (about 60 s):
```
== 1. a client disconnects and resumes from its last sequence number
it saw 7 event(s), the last is #7; disconnecting
resumed from #7: Events, 9 event(s) arrived, the first is #8, the last #16
only what was missed arrived, in order, with nothing it already had
a client that was up to date was sent nothing
== 2a. a state change reaches a local client in under 250 ms
state change to client over 7 steps: median 18 ms, worst 21 ms (target under 250 ms)
== 2b. when a step ends, the next task is admitted in under 100 ms
a step ends, the next task is admitted: 13 ms
== 3. the command line runs over the same socket
(task list, task show with the decision card, a stale answer refused, an answer accepted)
== 4. the parity tooling
18 features; done in swift 1, in compose 0
  feature.connect-and-resume: swift is "done" and compose is "todo", with no platform_reason. ...
the feature check failed: 1 problem(s)          (the planted imbalance; with a reason it passes)
(a changed token with stale generated files fails the check)
conformance passed at 8 checkpoints               (and a planted extra button is caught)
```
**Targets measured:** a state change reaching a local client in a median of about 20 ms (worst about 25 ms), against the 250 ms target; the next task admitted about 13 to 16 ms after a step ends, against 100 ms (it was about 70 before the fixes above).

### Tests
- **Protocol (4)**: both encodings round-trip, JSON uses the protobuf mapping, an old peer ignores new fields, garbage is an error.
- **Daemon (11)**: a new client gets a snapshot in either encoding; a reconnecting client gets exactly what it missed (and up-to-date and too-far-ahead are handled); live changes arrive as events and fresh views; every entity has its allowed actions, why-waiting and progress cells (filled, hatched, empty); the sidebar sort and section order; a command outside the allowed actions refused, one inside accepted, raw calls and bad input; an answer carrying the card hash (stale, wrong identity, correct); garbage and early commands; both latency targets; the demo script's determinism.
- **Conformance crate (9)**: the feature rules (balanced, imbalanced, reasons, mistakes), the token generation for both languages, the comparison (missing, wrong text, wrong actions, extra rows, order, decoration allowed).
- 371 tests across the workspace; all exit scripts s00 to s11 pass; `cargo deny` is clean.

## What testing found
- **The hand-off was about 70 ms, not the 15 it should be.** Three causes, found from the event timestamps: a task that had moved on to a test step still counted as holding a session for the moment before its test job asked for resources; a step handed its resources back only when its thread ended; and the broker could miss a release that landed between a waiter's check and its wait.
- **A command with no body must not say it is JSON**: the socket gave an empty `application/json` body to `cancel`, which the handler rejected.
- The first resume test dropped the events that arrived while it waited for a command's result; the client now returns them.

## Not done or not run
- **Neither monitor exists yet** (Stages 12 and 13), so the conformance runner has been checked against the server's own views and a planted difference, not against a real SwiftUI or Compose accessibility tree. The item format and `conformance check` are what those clients will target.
- **Kotlin (Wire) code is not generated** here (no Wire compiler); the script and the schema are ready, and CI cannot check the committed Swift is current (no Swift plugin).
- **Thin views**: usage has session counts only (no tokens or windows), landing has debts and a note (no batches), and typical-time estimates need five samples and so are rare for now.
- **LAN access, pairing, mDNS and tokens** are Stage 24; the daemon binds loopback only.
- **The Home view's landing queue, the Health page and the Pipeline editor's editing** are not views yet (the editor view shows the definition, its steps and any problems).
- The latency figures are for this machine on loopback with the demo script and the scripted agent; CI machines will differ, so the tests assert generous bounds (250 ms median, 750 ms worst; 100 ms for the hand-off) while the exit test reports the numbers.
