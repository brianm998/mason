# s205: GitHub CI progress: jobs queued, running, passed and failed per workflow

Summary: While MASON waits on GitHub CI the monitor shows each workflow's jobs told apart (queued, running with names, passed, failed), and every answered poll counts as the step being alive, so a compiling CI is never shown as "no output".

**Cause.** `GitHub::status` returned a bare `Pending` and `ci_verify` never changed the step while it waited, so `updated_at_ms` stood still and a long job read as silent.

**What changed.**
- Adapter API: `CiJobCounts`, `CiWorkflowJobs`, `CheckCounts.jobs`, and `BuildSystemAdapter::status_detail` (default: the state and no detail). `CiState` is unchanged, so `Red` and its `jobs` read as before (#162, #184).
- GitHub: `status` is `status_detail().0`. While a run is unfinished `status_detail` reads `run_jobs` (now with `status` on `ActionsJob`) for each run of the SHA, one entry per workflow run; no logs. A failed jobs read leaves the detail empty and never changes the verdict. `count_checks` gives the same breakdown for PR mode.
- Core: `Progress::heartbeat(at_ms, every_ms)` restarts the quiet clock without faking a figure and keeps `stale_after_ms` at three polls or more. `SubProgress.jobs: Option<JobBreakdown>`. `progress_text::jobs_text` is the one-line form.
- Landing (protected file; reporting only, no verdict, note or ladder step changed): `ci_verify` and the PR wait write one sub per workflow (unit "jobs") and the message "CI on <ref>: 7 jobs: 2 queued, 1 running (name), 3 passed, 1 failed"; `ask` calls `heartbeat` on every answered poll that is not done. Failed polls keep the existing backoff and alert.
- Protocol: `ProgressSub.jobs` (`JobCounts`, field 7). HTTP progress JSON and `mason task progress` show it. Swift and Compose draw "macOS: 4 jobs · 1 queued · 1 running (build) · 2 passed" per workflow, failed in the attention colour; conformance texts include it.

**Not verified by me.** The Swift and Kotlin tests I added were not run (no Xcode or Gradle build here); the Swift protobuf file was regenerated with `protoc`. The breakdown is not stored in the database, so it is empty after a daemon restart until the next poll. I did not add a landing test driving a scripted queued→running→failed sequence through fake-github; `scripts/exit/s205.sh` covers one pending state through a real daemon. `cargo clippy --workspace -D warnings` fails on `introspect.rs` and `ssh_keys.rs`, which this change does not touch.
