# s1158: exit-scripts ubuntu shard 2 red (s914, s1035)

Summary: The analyst's task can be submitted again (it commits nothing, so the change validator no longer runs on it), and a red s914 or s1035 now names the failing sub-script, its exit code and its last 12 lines.

## Causes

Run 45788017032, commit 93e5f2ac0.

- **s914**: `scripts/exit/s777.sh:166`, the grep for `reused.*task=1` in `masond.log`, could not match a coloured log. The reported cause (`<old> <new> refs/heads/main`) is the last line of `pushes.log`, which s777's `fail` prints last. Already fixed on develop by 43f71f6f0; s914 passed on ubuntu-latest in run 45845998111.
- **s1035**: `scripts/exit/s22.sh:270`, `wait_for 60 "the analyst's proposal"`, timed out on ubuntu-latest (run 45845998111) and the same way on macOS. The analyst's task ended `failed`: "the agent ended its turn 3 times without submitting". The analyst is told to commit nothing and to leave `analyst-result.json` uncommitted, and the change validator refused exactly that (no commits beyond the base, dirty tree). Since s877 the daemon closes that task as soon as its file is read, but no test drove the submission.

The cause line the run showed for s1035 (`== 1. a retry loop on a permanent error, ...`) was not where it failed: `cause_of` takes the first line matching `error`, and that is a section header printed by a passing part of s22.

## Change

- `crates/daemon/src/jobs.rs`: no change validator for the analyst's develop step.
- `scripts/exit/s1035.sh`: each sub-script's output goes to a log; a failure prints `FAILED: s1035: <script> exit N`, the first panic/failure/timeout lines, and the last 12 lines. Each has the 1200 s kill limit s914 uses.
- `scripts/exit/s914.sh`: the failure line starts `FAILED:` and carries each exit code.

No wait is widened, no assertion changed, and s22 and s914's six sub-scripts are untouched.
