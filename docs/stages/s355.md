# s355: a run that finished on time is not "timed out" after a daemon restart

Summary: a suite run, or an agent session, counts as timed out only if its command really ran past its limit. That means it was ended by a signal (the deadline's stop), or it ended later than the limit after its host started (`registry::ran_past`). Before this, a daemon that restarted re-attached to the host of a run that had already finished and counted the limit from the host's start. With the limit spent, its timer fired at once, and the run was judged red, "it ran out of time", though it had exited 0.

## Why

On 2026-11-14 star #197 failed after three red test rounds. The last two were `t0-pipeline-static`, which exited 0 with `T0-PIPELINE-OK` after 88 s both times. Each time the step went on to wait for compile and exclusive slots, the daemon took over a new version (`mason update`, 14:02 and 15:47), and the restarted step re-collected the finished run 20–50 minutes after it had started. The host's `exit.kv` said `code=0` and `ended_ms − started_ms` = 87.9 s. The verdict said it ran out of time.

## What changed

- `crates/step-host/src/registry.rs`: `ran_past(limit, dir)`.
- `crates/daemon/src/suites.rs` (`run_hosted_once`): `timed_out` needs the timer to have fired and `ran_past`.
- `crates/adapters/src/hosted.rs`: the same for an agent session's deadline.
- `jobs.rs`'s command-step timer was already safe: it only stops the host, and the verdict comes from the exit record.
- Test: `ran_past_tests::a_command_that_ended_within_its_limit_did_not_run_past_it` (unit, `registry.rs`).

## Not verified

No integration test restarts a daemon across a finished suite run. The unit test covers the decision, and the change is one condition at each of the two sites.
