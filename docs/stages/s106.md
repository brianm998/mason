# s106: daemon bugs, panics and long stalls raise an alert

Summary: Caught panics, job failures, projection drift, a repair the sweep keeps needing for one task, and an event-loop stall of 30 s or more now raise a `daemon_bug` alert (routed like `failed`) instead of only adding to a count.

`attention::bug_alerts(rows, now)` is a pure function from bug rows to alerts: one alert per kind for `thread_panic`, `job_panic`, `job_spawn` and `projection_drift` while a row is under 24 hours old (text: count and latest detail); `missed_job` and `missed_admit` alert per task when the same task appears three or more times within an hour; `orphan_host` and `leftover_branch` stay rows. `stall_alert` raises the alert for an hour after a stall of 30 s or more, naming the length (the daemon keeps the latest such stall). `alerts_now` gains two lines for these. `daemon_bug` is routed like `failed` in `core/notify.rs` and sounds as Broke. `Store::bugs_since` reads only the window. `mason alerts ack` works as for any alert.

`attention.rs` is a trust file: this adds alerts and changes nothing about who may answer.

Tests: `crates/daemon/tests/bug_alerts.rs` (each kind, 24 h window, 3 vs 2 `missed_job`, orphan ignored, stall), the loop-panic test in `panics.rs` now also waits for the alert; exit script `scripts/exit/s106.sh`.

Not verified: a real 30 s stall end to end (only the pure rule is tested); I did not run the whole workspace myself, only the check tool; the alert text in push/speech channels was not listened to.
