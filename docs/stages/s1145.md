# s1145: the pipeline cleans up its worktrees

Summary: the sweep now removes the worktrees of canceled (branch kept) and failed tasks after a keep time, trims idle or low-disk build output, removes unused landing scratch worktrees, and `mason disk` and the monitors show what they take.

## Cause

Only landed tasks and canceled tasks whose branch was deleted lost their worktree. A canceled task with its branch kept (the CLI default) and a failed task kept it for ever, nothing trimmed build output inside a worktree, and landing scratch worktrees were never removed.

## Change

- `crates/daemon/src/worktrees.rs`: the keep rules (pure), the plan, the removal and the report. The sweep calls it every pass.
- Project keys `worktree_keep_canceled_h` (24), `worktree_keep_failed_h` (72), `target_idle_h` (12), `landing_scratch_keep_h` (48), `landing_scratch_max` (2), `build_outputs`.
- A removed worktree comes back from the branch: a step already did that; an owner session, `mason task open` and a diagnosis now do too. The definition's worktree setup runs again before the next step.
- `GET /disk/worktrees`, `POST /disk/clean`, `mason disk [clean [--dry-run]]`, `DiskHistory.worktrees` and the lines under both monitors' Disk section.
- `crates/daemon/src/landing.rs` (protected): one read-only accessor, `Landing::running_slots`, so the sweep leaves a running batch's worktree alone. No landing behaviour changes.

## What counts as "no step running"

A job that only waits (for a compile slot, the disk floor, an account) does not keep its build output: those were the worktrees filling the disk. It does when the definition has worktree setup commands, which would not run again before that job's build. Removing a whole worktree never happens while a task has any job.

## Not verified

- Nothing ran against the live data directory, and the 260 GB reported was not re-measured.
- The `mason` binary was not driven against a running daemon: its text is unit tested, and the two HTTP routes are called in process.
- The Swift and Compose monitors were not built or run locally (the Swift packages cannot be fetched here); no screenshot was rendered.
- How long measuring a few hundred gigabytes takes on the data disk, and how much it slows builds there. It runs only when `mason disk` or a monitor asks (a monitor at most every two hours).
- The exit script drives the scenario through integration tests with a passed-in clock, not a daemon waiting a day.
- A build output under a directory that holds nothing tracked may be reported by git as that parent, and is then not recognised.
- A project's `task_cache` directories keep their own rule (`task_cache_keep_days`); idle trimming covers only directories inside the worktree.
