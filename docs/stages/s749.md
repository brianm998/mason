# s749: live phase of a run on GitHub (#760)

Summary: A run on GitHub now shows what it is doing while it goes ("on GitHub: running, 4 min", "3 of 8 shards done") from the jobs API, instead of 0% until the end.

Part 1 of the ticket only. `GitHub::remote_run_jobs_changed` reads `/actions/runs/{id}/jobs` with its own ETag (a 304 is free) and now keeps each job's steps. `remote::poll` refreshes the jobs on every look at a run that has not completed (the same look that already found out whether a runner had the job, so no new schedule) and `phase_text` turns them into text; `Site::on_phase` hands the text to the step's progress message (`Daemon::progress_message`) only when it changes. Wired for test steps (`suites::run_remote`) and agent checks (`hostedcheck::remote_check`). A run that is not counted has no figure, so no percentage appears.

Rate budget: one run-status look plus one jobs look per `poll_s` = 10 s is at most 720 calls/h per run if every answer were a change, 11,520/h for 16 runs, over the 5,000/h token limit. Both calls are ETag-conditional and a 304 is free; a run's jobs change only a few times (queued, each step start and end, each shard end), so in practice a run costs tens of counted calls per hour. The poller's error backoff is unchanged. I did not measure this on GitHub.

Not done, waiting for the owner (the workflow is protected): part 2, the runner-side counter loop in `.github/workflows/mason-run.yml` and the `mason remote setup` template that publishes `{done, failed, total, phase}` as a commit status (needs `statuses: write`), the daemon reading it into `CheckProgress`, and the counter unit tests on cargo, XCTest and JUnit logs. `suites.rs` (protected) got a small change, the `on_phase` hookup in `run_remote`; it needs approval.

Not verified: the new behaviour has not been seen on a real GitHub run or on the owner's machine; the exit script is only as good as the run_check result.
