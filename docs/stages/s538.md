# s538: the Compose monitor no longer launches processes on its UI thread

Summary: The Compose monitor runs Open session and the update install on a background executor (failure returns to the UI executor), loads the speech voices once off-thread, and caches known task ids, linkified text and section-expanded flags instead of redoing them per recomposition.

- `MonitorModel.background` / `ui` executors (inline by default; the app sets a daemon pool and Swing). `launchSession` returns at once; a failed or throwing launcher copies the command and sets `sessionNotice` on `ui`. `installMonitor` starts its process on `background`.
- `Announcer.loadVoices` runs `sink.voices()` once on an executor into state `voices`; the dialog calls it from a `LaunchedEffect` and shows "System default" alone until it arrives.
- `isKnownTask` uses an id set rebuilt only when the sidebar or task page value changes; `LinkedText` remembers its segments keyed by text, sidebar and task page.
- `isExpanded` reads each preference key once (cached; `setExpanded` updates the cache).

Tests: `UiThreadTest` (latch launcher, failing launcher, counting sink, counting prefs, rebuild counter). Not verified: the real macOS `open`/`say` paths and the dialog composing under Compose (the voice test drives `Announcer.loadVoices` directly, which is what the dialog calls).
