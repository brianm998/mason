# s758: a GitHub section on the monitor's home (#767)

Summary: The home view carries a `github` section (and `mason remote runs`) listing every remote run in flight or ended in the last 10 minutes with its owner, the owner's state, kind, run state, jobs, URL and last update, and both monitors draw it under CPU and Disk.

- `remote_runs.rs` keeps a registry of runs: a step that waits for a pool unit (entered in `jobs::acquire_needs_as` and the debt payment) and a run that is out (entered by `HoldGuard::new`, which now takes a kind; finished when the guard drops, green/red from the record, else cancelled).
- The run's own poll (`remote::poll`) reads the Actions jobs once per changed run (a 304 reads none), with the new `conclusion` and current `step` on `ActionJob`, and puts them in the registry. No second poll loop.
- `HomeView.github` (`RemoteRuns`, proto field 12), `GET /remote/runs`, `mason remote runs [--json]`.
- Monitors: `GitHubSection` (Swift, Compose), `GitHubRuns` (the words, in MonitorCore / core), page `mason://section/github` with every job, feature `home-github-runs`.

Not verified: the Swift and Compose code was not compiled or run here (no network for the Swift packages; the client tests run on GitHub). The daemon test puts jobs in the registry directly, not through a fake GitHub server. Landing lint and batch suites appear once they are out, not while they wait for a pool unit (they take no lease). Live test counts from #760 and other workflows' jobs from #766 are not read: progress is "N of M jobs done, step S". #763's "On GitHub" line is not linked.
