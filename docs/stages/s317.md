# s317: the exit scripts that were red on develop

Summary: six exit scripts (s08, s09, s129, s165, s166, s236) failed on every develop CI run because each checked something that had moved, or depended on the machine; they now check the current behaviour, and no code changed.

## Cause, per script (read against origin/develop)

- **s129**: `views.rs` calls `broker.llm_holders()` (views.rs:857, sched.rs:1630); `llm_held_by` has no caller. Now greps `llm_holders` in views.rs and `fn llm_holders` in sched.rs.
- **s236**: its `alpha` used `exclusive` without declaring `[resource.exclusive]`, so the definition was refused at startup. Already fixed on develop (the declaration, with a comment); reproduced green here after the merge.
- **s165**: flaky rows are keyed by step name, so `mason health` prints `test::alpha`, not `flaky::alpha`. Section 2 then waited for `failed every time: alpha`, which is only in the step's reason; `feedback.txt` says `These tests failed on all 2 runs: alpha`. Both greps follow the code.
- **s166**: the agent runs with a clean environment, so `$OT` was empty and it wrote `run(&, 1);`; the grep for `&|| true` then failed silently under `set -e`. The agent script now builds `OT` itself. Next, `grep -rhs` exits 2 when the daemon deletes a file mid-scan, which killed the script under `pipefail` after the refusal was seen; it is now `|| :` (the wait loop above it is the assertion).
- **s08, s09**: not a race and not a code bug. Decision 0231 and #287 rank by share of the route, and both fresh tasks are 1000, so filing order decides. `two_projects_share_the_pool_and_admission_follows_progress_through_each_route` (crates/daemon/tests/scheduling.rs) asserts exactly that. A tie-break by raw steps left was tried and it contradicts that test, so it was dropped; the scripts now assert the rule: equal share, the one filed first goes first.
- **s08 (second cause)**: `compile_jobs` defaults to 3 and caps the script's `count = 1`, so the "interactive holder" never blocked anyone, and the wait sentence depended on the machine's CPU and settle pause. The script sets `compile_jobs 1`, `compile_cpu_max 100`, `compile_settle_s 0`, and waits for the `Waiting for compile slot` sentence specifically.
- **s09 (second cause)**: `[ "$took" -lt 40 ]` was a wall-clock assertion that failed on a busy machine (landed at 40 s). Removed; `wait_state ... landed 100` already proves the skip stopped the 120 s suite.
- **s50, s127**: s50 passed three times. s127 fails here, three times: it checks that the README status block is current (`gen-status.sh`), and develop's README is behind its stage notes (s312 to s386 missing). MASON regenerates the block when a change lands, and this task must not edit it, so s127 is red wherever the block is stale and is not flaky.

## Why none of it was seen

The pipeline's exit-scripts suite runs only the changed scripts (`.mason/mason.toml`, `run-changed-exit-scripts.sh`), selected by the impact map for `scripts/exit/**`. CI runs all six shards.
