# s102: every alert that means work has stopped reaches the owner

Summary: `disk`, `environment`, `blocked`, `host_lost`, `runtime`, `definition`, `tracker` and the `provider_limit`/`provider_overage`/`provider_budget` alerts are routed like `failed` (monitor, sound, speech, push after 10 minutes), both monitors speak them by default, and a test fails when a raised kind is neither routed nor named monitor-only.

On 2026-11-09 the disk-floor alert was true for over two hours and nothing sounded, because only seven kinds had a route and everything else got the monitor alone.

- `crates/core/src/notify.rs`: ten kinds routed like `failed` and added to `CONDITIONS` (so `mason notify status` lists them and `notify.toml` can change them). New `ALERT_KINDS` (every kind the daemon raises) and `MONITOR_ONLY` (`paused`, `debt`, `provider_hold`: the owner did those, or they stop nothing). A test requires each listed kind to be routed xor monitor-only. A new alert kind must be added to `ALERT_KINDS` by whichever ticket lands it (`numbers`, `stalled`, `long_wait`, `daemon_bug`).
- Monitors (Swift `Speech.swift`, Compose `Speech.kt`): the default kinds include the new ones; a saved `speech.kinds` list gains them once (marker `speech.kinds.added`), after which an untick sticks. Settings pages offer them. The "broke" sound family covers the new stop-work kinds.
- Tests: core (routing, disk sound/speech/push at 10 min), `crates/daemon/tests/notify.rs` (a claim gets one `disk` announcement with sound and speech), Swift and Compose speech tests. Exit test: `scripts/exit/s102.sh`.

Not verified: the Swift and Kotlin tests and the settings pages were written but not run (Swift package resolution needs the network, which this session does not have; I did not run Gradle). `clients/features.toml` was not changed. Push delivery itself is unchanged and was not exercised for the new kinds.
