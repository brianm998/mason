# s326: the monitor updates itself, including a bare `swift build` binary

Summary: a monitor built with `swift build` or `make` now carries the commit it was built from, so it says when a newer one is on the channel; its Update button has the daemon rebuild that checkout's binary in the background (waiting for a `compile` slot, showing fetching, compiling n of m, linking and installing), swap the binary in place only after the build worked, and the monitor then starts the same path and quits.

## What changed

- `clients/swift/Sources/MonitorCore/BuildStamp.swift`: the checked-in file says `""`. The daemon's build writes the commit into it in its own build directory; `clients/swift/Makefile` does the same for `make build` and puts the file back. `MonitorModel.ownVersion` is `MASON_MONITOR_VERSION`, else the stamp, else `dev` (still quiet).
- `schemas/mason.proto`: `MonitorBuild` gains `step`, `done`, `total`, `last_line`, `log` (additive). Swift protocol code regenerated.
- `crates/daemon/src/monitor_inplace.rs` (new): `locate` (a bare binary in `<checkout>/clients/swift/.build` of a checkout of this repository), `check_direction` (never older than the running commit, never the same one), `run` (archive the commit from the daemon's mirror into `runtimes/src/monitor-inplace-swift`, keeping its `.build` so builds are incremental; stamp; `swift build -c release`; parse `[n/m]` lines; cancel; install resource bundles then the binary by rename), and `start`/`cancel` (fetch, resolve the commit, hold a `compile` lease, set the header state).
- `crates/daemon/src/http.rs`: `POST /update/monitor` takes `own_path` and `own_version`; a bare binary goes to the in-place build, anything else to the bundle build as before. `POST /update/monitor/cancel`.
- `crates/daemon/src/update.rs` (protected): `MonitorState` fields, their copy into the header in `info()`, and three `pub(crate)` widenings (`fetch_locked`, `latest_of`, `set_monitor`). Nothing about masond's own update changes.
- Swift monitor: progress text and a Cancel button in the monitor banner; failure text carries the log path; `Session.install` starts the same path again (with the same arguments) and quits when the daemon replaced the running binary.
- Tests: Rust unit tests in `monitor_inplace.rs` (fake `swift`: phases in order, binary replaced only after success, failure and cancel leave it, direction guard, which binaries qualify, line parser) and a Swift test for the progress text.

## Not verified

- The Swift changes were not compiled or tested: this sandbox cannot fetch swift-protobuf, so `swift build` and `swift test` did not run. They need one run on the owner's Mac.
- No real `swift build` ran through the daemon, and nothing was launched or relaunched. The HTTP route and the compile-lease wait are not covered by a test.
- Compose: the update path already stamps through `-Pmason.build`; it has no in-place rebuild and no progress display.
- A running monitor's resource bundles are replaced before the binary; a failure in between leaves new bundles with the old binary.
