# s321: every number on home and in the top bar respects the selected project

Summary: Header, sidebar, home and landing views now carry the project filter they were computed for, and both monitor models drop a view stamped for another project and clear project-scoped values when the picker changes.

**Cause.** The daemon filtered correctly, but its views named no project, so a client could not tell a rebuild computed for the old filter (in flight when the picker changed, or resumed after a reconnect) from one for the new filter. Home's landing queue also preferred a leftover `landing` view, which is only subscribed on the Landing page.

**Change.** New `project` field on `HeaderView`, `SidebarView`, `HomeView` and `LandingView` (`schemas/mason.proto`), filled in `views.rs`. Swift and Compose `MonitorModel` drop any such view whose project differs from the selection, and on a selection change clear counts, attention, status, sidebar, home and landing until the new views arrive. Home's landing queue reads only home's own stage rows. CPU, Compilation and Sessions are labeled "all projects". The `ws.rs` ordering contract of #286 is unchanged.

**Tests.** Daemon: `views_are_stamped_and_none_for_the_old_project_follows_the_new_one` (protocol.rs). Swift `ProjectScopeTests`, Compose `ProjectScopeTest`.

**Not verified.** The Swift and Kotlin tests were not run by the pipeline's cargo checks (no Xcode/Gradle step); the generated `mason.pb.swift` was edited to match the proto. No hand test against a live daemon with two projects.
