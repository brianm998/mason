# s81: every git and shell call has a deadline

Summary: Every git call, build, resolver, status script and `top` now runs in its own process group under a deadline, fetches have a lock of their own so a stalled remote cannot hold up worktrees, merges or cleanup, startup does no network, and a CPU reading over 30 seconds old counts as unknown.

- `mason_landing::proc::output` runs a command in its own process group; at the deadline the whole group is killed and the caller gets `ProcError::TimedOut` (with what it had said). The reaping of the killed child is left to a thread, so a process frozen at launch (the `syspolicyd` stall) does not hold the caller.
- `git::run` uses it: 5 minutes (30 for `clone`), `git::run_for` names its own, `git::set_default_deadline` / `MASON_GIT_TIMEOUT_SECS` shorten it for tests. `GitError.timed_out` tells a deadline from a git failure; its text says "timed out".
- `fetch`, `push`, `clone`, `pull`, `ls-remote` carry `http.lowSpeedLimit=1`, `http.lowSpeedTime=60`, and (unless `GIT_SSH_COMMAND`/`GIT_SSH` is set) an ssh with `BatchMode=yes`, `ConnectTimeout=30` and keep-alives.
- `Daemon::fetch_remote` takes a per-repository fetch lock, separate from `repo_lock`. A fetch that started while a caller waited satisfies that caller. `prepare`, `fetch_project`, the editor's base check and the debt path moved to it. Landing's own fetches (batch, direct, promote, landing.rs) stay under the repository lock, bounded by the deadline.
- `load_definitions` no longer fetches (nor does the startup `reload`); the definition watcher's first pass does.
- `update::shell` (1 hour, `MASON_UPDATE_SHELL_TIMEOUT_SECS`), `Batch::resolve` (1 hour, `MASON_RESOLVER_TIMEOUT_SECS`), `Batch::regenerate_status` (5 minutes), `top` (10 seconds) and the two `git` calls in `plugins.rs` use the runner.
- `Sampler::busy_pct` is `None` when the last reading is over 30 seconds old; `mason resources` says "unknown" in that case.

A call killed by its deadline is an error like any other: the step fails with the reason. Making a failed fetch non-fatal is a separate ticket.

Tests: `landing` (`deadline_tests`, `proc::tests`), `cpu::tests::an_old_reading_is_unknown`, `tests/fetch_deadline.rs`, `tests/fetch_stall.rs` (real masond, TCP listener). Exit script `scripts/exit/s81.sh`.

Not verified: the real `syspolicyd` launch freeze (the kill-after-launch path is reasoned, not reproduced); ssh remotes (the options are set, no ssh server was used); the deadlines against real timings (see decision 0067).
