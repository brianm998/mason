# s733: landing on GitHub

Summary: With the global switch on, landing batch and lint tiers, reruns, bisect runs, baseline runs and debts run on GitHub through the same placement as task runs, a bisect starts both halves of a split at once, and `mason landing` shows where each run went with its link.

What changed (#702):

- `remote::executor_for` takes an optional task: a run no task owns (a landing batch, a bisect half, a baseline at the merge base, a debt) is decided by the global switch and the suite's own rules. Landing's checks (build floor, lint, re-test) have no suite and follow the switch alone (`place::global_place`, `CheckSpec::global`).
- `plan::pin_paired` asks the two halves of a split together; `Runner::pin_red` uses it only when every suite the split can run goes to GitHub, assembling the second half in its own worktree (`<int_wt>-half`). Local runs keep the one-at-a-time order.
- `mason landing` prints each run of a batch with where it ran and the run link (`GET /landing` has `runs`).
- `fake-github` can serve a per-commit run and a red artifact for a commit holding `red.marker` (when `run-artifact-red.zip` exists), for `scripts/exit/s733.sh`.

Not verified: nothing was compiled or run here (the owner skipped testing and builds were refused), so the code, the new tests and `s733.sh` have not been built or executed. Not done: "a baseline whose base SHA is on the remote starts without a push". The run's spec travels in the snapshot's `.mason/run.json`, so a run always pushes one overlay commit (its parent is the base commit, which the remote has, so only that commit is sent); running on the bare base commit needs a workflow trigger that does not exist. Pushes of both bisect halves are not asserted in the fake's request log. Paying a debt and `run_on_base` follow the switch through `run_suite`/`run_hosted`; no separate test was written for a debt.
