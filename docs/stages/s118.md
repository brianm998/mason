# s118: keep reminding while a pipeline-wide stall lasts

Summary: `stalled` and `disk` alerts now repeat their reminder every `[reminder] repeat` (default 2h, `0` off) until acknowledged or cleared; every other kind is still reminded once.

**What changed.** `crates/core/src/notify.rs`: `REPEATING = ["stalled", "disk"]` beside the routing table, `Routing::repeat_ms`, `Routing::reminder_round`, and `due` treats reminder attempts as per-round for those kinds (round k starts at `since + reminder + k*repeat`; a channel is due when it has no delivered reminder in the current round). A repeat goes only to channels that delivered the first notice, waits out quiet hours, and stops on acknowledgement, all as before. `crates/daemon/src/notify.rs`: reads `reminder.repeat`, names a repeat's announcement `reminder<k>` so it is not mistaken for the one already played, and shows `reminder_repeat_s` and `repeating` in the status. Rounds missed (daemon off, quiet hours) collapse into one repeat, not a burst.

**Tests.** Core: `stalled` and `disk` repeat at each interval, `failed` does not, acknowledged does not, quiet hours defer, `repeat = 0` equals the old behaviour, repeats go only where the first notice arrived; `one_reminder_then_silence` is unchanged. Daemon: `repeat` parses. Exit: `scripts/exit/s118.sh` runs a real-daemon test with 1s intervals (claim hands over the reminder and a repeat, each once; acknowledging stops them).

**Not verified.** In this session the shell refused cargo directly, so the tests ran only through the pipeline's `tests` check. Not tried: a push, email or webhook repeat against a real receiver (the core test covers which channels are due); behaviour over real hours.
