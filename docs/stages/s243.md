# s243: the monitor socket no longer queues a new task's view behind other work

Summary: A monitor session now runs commands on their own worker, rebuilds views as one coalesced job per session, sends newly subscribed views (such as TASK_DETAIL) on a job of their own first, and the view pool has 4 threads instead of 2.

Changes in `crates/daemon/src/ws.rs`: commands run one at a time on a per-session task and return through a channel, so pings, subscriptions and pushes carry on; at most one rebuild (events plus views, one pool job) is queued or running per session, and a tick meanwhile marks it dirty; a Subscribe computes new kinds (and TaskDetail when the task changes) first; a view older than one already sent for its kind is dropped. `daemon.rs`: view pool 2 to 4 threads (the broker snapshot, #0229, has landed).

Tests in `crates/daemon/tests/protocol.rs`: a blocked command with ping and TaskDetail still served; ten ticks queue one rebuild.

Not verified: the Swift and Compose clients were not checked for reliance on result ordering relative to views (results stay ordered among themselves); a stub that blocks only Sidebar computation was not written (the test holds two view threads instead); the pool size is fixed, not in `limits.kv`.
