# Stage 8: Scheduler and resources

## Built
- **`crates/scheduler` (`mason-scheduler`, pure)**: the rank tuple (`Rank`: interactive first, fewest steps remaining, tracker priority, enqueue time, task id; a project may opt in to letting priority 0 jump the progress term), `plan` (a request is granted only if its whole set fits and it uses nothing an earlier waiter needs; `exclusive` conflicts with every machine class), the optional free-memory floor (only beside other work), `explain` (the sentence), and `Ledger` (submit, schedule, release, adopt, rerank, live limit changes).
- **`crates/resources` (`mason-resources`)**: machine classes held by kernel `flock`s: one file per slot, a shared/exclusive `machine.lock`, a per-lease marker, and a sidecar saying who holds a slot. Take-all-or-nothing; a dead holder's locks vanish with it.
- **`graph::steps_remaining`** in the definition crate.
- **Daemon `sched.rs` (the broker)**: every step job waits for its resources, all at once, before any timeout starts (agent steps also need an LLM session); admission is ranked across every project and claims nothing until an LLM session is free; limits change live and survive a restart; interactive requests queue ahead of pipeline work; dead interactive holders are reaped through their marker lock.
- **HTTP**: `/resources`, `/resources/limit`, `/leases` (open, poll, release); `task show` carries the live wait.
- **CLI**: `mason run --needs compile[=N],... [--exclusive] [--label L] -- <cmd>`, `mason resources [--json]`, `mason resources limit <resource> <units>`, `mason hook bash` (the optional agent hook; it asks rather than allows).
- A second registered project is exercised in the daemon tests and in `s08.sh`.
- `docs/decisions/0005-scheduler-readings.md`, `scripts/exit/s08.sh`.

## Exit test
`bash scripts/exit/s08.sh` passes. Two projects (alpha explores first, beta does not) share one `compile` slot:
```
== 1. admission follows the rank rule across projects
alpha #0 (4 steps) started at 1793979840241, beta #1 (3 steps) at 1793979837824
== 2. the compile class is never held twice at once
2 test steps held it one at a time
== 3 and 4 and 5. waits explain themselves; interactive goes first; a killed holder frees it
  #2: Waiting for compile slot: 1st in line, held by interactive holder for 0 s
  #3: Waiting for compile slot: 2nd in line, behind #2 (2 steps from landing), held by interactive holder for 0 s
Waiting, in line order
  interactive latecomer Waiting for compile slot: 1st in line, held by interactive holder for 0 s
  #2 Waiting for compile slot: 2nd in line, behind interactive latecomer (interactive), ...
  #3 Waiting for compile slot: 3rd in line, behind interactive latecomer (interactive) and #2 (2 steps from landing), ...
the killed holder's resource was reused after 207 ms
everything landed, nothing is still held
```
`kill -9` of the `mason run` process held a slot; the next waiter (an interactive caller) started 207 ms later, and both pipeline tasks followed, never overlapping.

### Tests
- **Property tests (`proptest`, 300 workloads each)**: over random resources, capacities, needs, ranks, priorities and arrival times, simulated to completion through the real `Ledger`: capacity is never exceeded, an exclusive holder is always alone, **no grant ever passes a conflicting earlier-ranked waiter**, every job runs and is released (no deadlock, no lost lease), every wait explains itself. With one resource, grant order is exactly the rank order. Live limit changes never remove a holder. I checked the properties have teeth: with the passing rule disabled they fail with a minimal counterexample.
- Table tests: the rank terms, the passing rule (a compile passes a waiting test suite; nothing passes an exclusive job), the memory floor, an over-sized request that must not block others, ordinals and durations, the sentence from the design.
- Kernel locks: all-or-nothing, exclusive vs class, marker liveness.
- **Daemon end to end (8)**: a step waits for a held class and says why, then lands; waiting outlasts a 2 s test timeout; an interactive caller goes ahead; a dead holder frees its resource; a new grant gets time to take its locks; LLM sessions adjustable live (no claim, no worktree while none is free; the limit survives a restart); two projects share the pool and admission follows the rank, across projects (and fails if steps-remaining is removed).
- 284 tests across the workspace; all exit scripts s00 to s08 pass. One existing test (`admission_respects_the_concurrency_limit`) changed meaning, deliberately: the limit is on LLM sessions, not tasks in any step.

### CI
Green on Ubuntu and macOS (`cargo test --workspace` and every exit script including `s08.sh`). The macOS job took 5m31s of the 10-minute budget.

## What testing found
- `mason run` did not see `--` when global options came first (`mason --data-dir D run ...`): fixed, and `s08.sh` caught it.
- The first `s08.sh` killed the shell function's subshell rather than `mason`, so the holder survived: a bug in the script, not the product.
- A definition's resources are `[resource.NAME] count = N`, not `[resources]`: the validator refused my first test definition, and the task silently ran the built-in one. That is existing behaviour (the refusal is reported by `mason definition show` and logged), but worth knowing when writing definitions.

## Not done or not run
- **Landing resources** (batch slots, promote lock) in Part 7's table have no consumer until the landing stages.
- **Step-host heartbeats for pool leases**: pools are accounted but nothing uses one until Stage 25. Pipeline steps hold their kernel locks in the daemon, so if the daemon is killed while a step host's command keeps running, the locks free and the command runs beside others until the restarted daemon re-acquires. Moving the lock into the step host closes that; not done.
- **Only one provider account** exists (`claude`); per-account pools work but only one account has an adapter.
- **Tracker priority** is the task's own priority field (urgent, high, normal, low); a tracker feeding it arrives with the tracker stages.
- **The free-memory floor** is tested in the pure planner and its measurement reads this machine's real value, but no end-to-end run set a floor.
- The agent hook is tested as a pure rewrite; I did not install it in a real Claude Code session.

## Differences from the design
None in behaviour. Readings are in decision 0005. One behaviour change to note: `--max-concurrent` now sets the default number of LLM sessions rather than the number of tasks in any step.
