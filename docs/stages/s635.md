# s635: Land now on the landing queue lands past slow testing, and the skipped tests run after the merge

Summary: The landing queue's items and running batches have a Land now button (Swift macOS/iPad/iPhone, Compose desktop/Android) that stops a running batch's remaining local suites and CI wait, keeps the freeze and the build floor, lands every member, and records what it stopped as deferred debts that run on the base after the merge.

**What was wrong.** `land-now` only picked a batch of its own for a queued task; for a task already in a running batch it said it changed nothing. `force` was the only way past slow verification, and it skips everything, including the freeze, and its `landing:force` / `landing:land_now` debts named no suite, so `pay` failed forever ("the debt's suite no longer exists") and the skipped tests never ran.

**Daemon.**
- `land_override` (`http.rs`): for a task in a running batch, Land now sets the landing flag `now_running` (`suites::LAND_NOW_RUNNING`) and adds no blanket debt. A queued task is flagged `now` as before. New `POST /batches/{id}/land-now` flags every member (`land_now_batch` command in `mason.proto`, `BatchRef`).
- `Members::land_now` (`suites.rs`): a member flagged `now_running` stops the batch's suite runs, as a skip by every member does. It is ignored while the project is frozen unless a member is the fix task, so Land now does not pass a freeze. `form_and_start` (`landing.rs`) no longer lets a `now` task past a freeze either (force still does; that is its job).
- `verify` runs the build floor after a stopped run (and after a skipped CI wait), so what lands is still built; a red floor goes down the ordinary red ladder and nothing lands. `ci_verify` stops waiting for CI when Land now is pressed.
- What was stopped (`suite:NAME` for each suite not finished, `ci:<workflow>` for CI) is collected during the run and, when the batch promotes, written as one deferred debt per member and scope before the verdict is delivered. The existing post-land payment (`after_landing`) then runs each on the base tip; red goes through the existing owed-debt alert.
- `debt_suites` takes the batch tier: `landing:force` and `landing:land_now` debts now resolve to the tier's suites (the Test step's suites when the project has no batch tier). `pay` follows `ci:` debts by pushing the base tip under a candidate name and waiting for CI (`pay_ci`).
- Views: `allowed_actions` on `TaskLanding` and `BatchLine`; `land_now` while queued, or in a running batch that is forming, merged or verifying.

**Clients.** `LandNowTarget` (task or batch) with the one-line confirm "Land #N now? Its remaining tests run after the merge; a red result raises an alert.", the pending states ("Landing…" / "Landing requested") kept under a batch key lifted clear of task ids, and a Land now button on landing items and running batches on Home's landing queue and the Landing page. `clients/features.toml`: `landing-land-now`, all done.

**Not verified.** The Swift and Compose clients were built and their pure model tests run only through the project's checks; nothing was rendered or looked at on screen. PR modes (`pr`, merge queue) are not changed: the host's own checks gate the merge there, so Land now does not skip them. The legacy no-suite test command path (`reverify` on a moved base) is stopped by Land now but records no debt. `pay_ci` was not run against a real CI service. Land now on a batch whose suites all finished records no debt (nothing was skipped).
