# s531: a click shows at once that it was taken, and again when masond answers

Summary: Both monitors record a pending entry before a task command is written (the pressed control says "Approving…" with a spinner and the task's other controls are disabled), show masond's error beside that control on failure, say "Approved, waiting for the pipeline…" on success until a view shows the task changed (or three views pass), and draw the sidebar's row at once when a task page opens.

**Cause.** Actions were fire-and-forget: nothing recorded that a command was in flight, so the button looked the same until the next view, and the owner clicked again. Command ids were generic, so a result could not be matched to a control.

**Change (Swift `MonitorCore/PendingCommands.swift`, Compose `core/.../PendingCommands.kt`; same behaviour).**
- `send` gives each task command the id `act:<action>:<task>:<n>` and records a `PendingCommand` (action, task, sent time, the task's state and allowed actions at that moment) *before* calling `sender`. A second command for the same task while one is pending is dropped. Read-only models record nothing.
- A failed result removes the entry and stores the error per task (`actionErrors`), shown beside the action buttons and in the approval view. A successful one moves the entry to *accepted* (label "<Verb>, waiting for the pipeline…"); it ends when a sidebar or task view shows a different state or allowed-action set for the task, or after `viewsToWait` (3) views that do not. If the sidebar already changed before the result arrived, it ends at once.
- `disconnected` marks entries not yet answered "Not sent: reconnecting"; the next welcome clears all entries.
- Wired into: the action buttons on the task page, the approval view (Approve, Defer, Reject), the sidebar row's Approve button (the Swift row is `Equatable`; the label and busy flag are part of its equality, so only that row redraws), and the blockers view (Release/Revive/Retry, Add blocker).
- A task page opened from the sidebar draws that task's row (title, state art, progress, actions) with "Loading details…" until the task view arrives.

**Tests.** `PendingCommandTests` (Swift) and `PendingCommandTest` (Kotlin): entry and label exist inside the fake sender; second click sends nothing; failure; success then a changed view; a view that changed before the result; three unchanged views; disconnect then welcome; read-only. Swift `PendingTaskPageTests` renders the task page offscreen and checks it grows once the sidebar has the task. Three existing tests in each client that sent a second command for a task still pending (skip all then skip one; release, add blocker, revive) now apply masond's answer in between. No timing assertions.

**Not verified / not done.**
- I did not run the Swift or Gradle tests myself (a direct build is refused outside the build queue); they were run only through the pipeline's `run_check`.
- The Compose "opening a task" check is at model level (`sidebarRow`); the Compose module has no UI-test dependency, so the drawn page is not rendered in a test.
- Commands that are not about one task (pause, resume, session and compile steppers, add task, settings and devices pages, which use `raw` commands with fixed ids) are not tracked: their controls show no working label or error yet. Answer cards go through `answer`, so they are tracked in the model, but their controls were not changed to show the label.
- `clients/features.toml` is untouched.
