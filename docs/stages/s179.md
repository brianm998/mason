# s179: never test the same tree twice on the command path

Summary: A green test command is remembered by exact content tree and exact command text, so the command test step reuses a green from `run_check`, an earlier test step or landing's re-test, a repeated `run_check` returns it, and `submit_change` refuses a head whose tree was red on the test step (failing tests named) and is unchanged.

**Built.**
- `crates/daemon/src/cmdreuse.rs`: `content_tree` (the tree `git write-tree` makes from the working files via a temporary `GIT_INDEX_FILE`, so uncommitted work and its later commit share a key), `command_key` (hash of the length-prefixed build and test command text, after layering), and the record/lookup helpers.
- `crates/store`: migration 27, table `command_runs(tree, cmd, green, source, names, at)`, `put_command_run`, `command_run`.
- `jobs.rs`: `command_job` (test step) checks for a green before building and notes the reuse (progress line and `test-r<run>.reused`); records green on a whole-command green and red (with names) on a final exit-status red whose failing tests were read in every run. `TestChecks` (`run_check`) returns a recorded green and records its own. `refuse_known_red` wraps the develop validator.
- `landing.rs`: a green re-test records evidence (it does not skip).

**Exact match.** The key is (SHA-1/SHA-256 git tree of every working file, including untracked non-ignored ones; SHA-256 of build and test text). Equal trees mean equal content and modes; any change to a file or to the resolved command (a runtime or task override) is a different key. Suites keep their own per-suite evidence; `suites.rs` and `crates/testing/**` are untouched.

**Tests.** Unit: key sensitivity, uncommitted work vs its commit (and the real index untouched). `crates/daemon/tests/e2e.rs`: green `run_check` then test step runs the command once and notes the check; a red tree resubmitted is refused naming the failing test, a change is accepted. Exit test: `scripts/exit/s179.sh`.

**Not verified.**
- The "base moves in between" and "runtime override changes the command" cases rely on the key construction (tree, command text) and are not covered by an end-to-end test.
- `scripts/exit/s179.sh` was not run by me, and clippy was not run separately (this session's shell hook blocks cargo test/clippy); the workspace tests passed through `run_check`.
- Two scheduling tests asserted that the command ran twice (check, then test step); they now expect once, which is the specified behaviour.
- A red is recorded only when failing test names were read on every run; a red with no readable names, a timeout or a signal is never recorded, so those resubmissions are not refused.
- Landing's re-test only records; it does not skip when evidence exists.
