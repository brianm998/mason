# s863: `mason init` and `mason adopt` live in a library crate the daemon can call

Summary: The setup logic of `mason init` and `mason adopt` moved from the CLI binary into the new `mason-onboard` crate, with serialisable `plan` and `apply` entry points, so the daemon can serve it; the CLI is a thin front end with unchanged output, prompts, flags and exit codes.

**What moved.** `detect`, `questions`, `suites`, `land`, `setup`, `summary`, `filing_file`, `overlay_path` and the adopt logic (`adopt::adopt`, `adopt::check`) are in `crates/onboard`. It depends on mason-landing, mason-definition, mason-adapters, mason-adapter-api and mason-testing, not on mason-daemon or the CLI. `crates/cli/src/init.rs` keeps the terminal I/O (prompts, "Is that right?", `open_monitor`), registration with masond and the proof task; `adopt.rs` only parses its flags and prints.

**New entry points.** `plan(path, &Flags) -> Plan` resolves every answered question, returns the first unanswered one with its default in `next`, and renders the files (suites proposed, not run). It writes and runs nothing. `apply(path, &Flags, config_dir, progress) -> Result<Applied, String>` does setup and landing (or the adopt) as answered; an unanswered question is an error naming its flag unless `yes` is set. `Flags` is the CLI flag set (serde), plus a `test` field used by adopt that `mason init` does not parse.

**One seam.** `setup` checked the rendered overlay with `mason_daemon::config::parse_project`, which onboard cannot call. The check is now a `Validator` the caller passes (`apply_validated`); the CLI passes the daemon's parser, so its behaviour is unchanged. `apply` alone uses `basic_validate` (TOML, id, `path` and `base` present). The next task should pass the daemon's parser too. Two unit tests that used the daemon's parsers moved to the CLI.

**Not verified.** Nothing was compiled or run locally before the first run_check; `mason init` output was not diffed by hand, only guarded by `crates/cli/tests/init.rs`, which is unchanged.
