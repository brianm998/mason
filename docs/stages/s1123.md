# s1123: projects without `[remote_runs]` can run on nodes (#1150)

Summary: a project with no `[remote_runs]` can be given a placement mode (`[placement] mode`, or `mason remote mode <m> --project P`) and then runs on nodes only; in `remote` mode its runs wait for a node and never run on the coordinator.

## What changed

- `[placement] mode` in a registration file. `[remote_runs] mode` wins over it. `mason remote mode … --project P` and the monitors' Settings write whichever the project has, and every project can now be set.
- `place::decide`: no `[remote_runs]` and a mode of its own is "nodes only". The shared stay rules (`remote = false`, a device, `exclusive`) still keep a suite here. With a node that has room: the node. With none: `remote` waits (a node placement marked `wait:`), `favor-remote` and `favor-local` run here and say "no node had room; this project has no GitHub setup".
- `node_exec::execute`: a marked run is not handed back. No room, a refusal or a lost node is waited out (the pause doubles up to 64 polls) until the run is stopped or the daemon stops.
- A nodes-only run on a node holds no `compile`, `test-suite` or `test-small` slot of the coordinator and no node unit; one that comes back (balancing modes) takes its slots then, by the existing fallback lease. Its `run_check` wait is credited to the agent's deadline like any node run.
- The coverage map of a nodes-only project is made on a node (in `remote` mode a pass with no room is skipped).
- `mason remote status`: `<mode> (nodes only: no GitHub setup)`; JSON has `nodes_only`. `mason task show` says "a node". Swift and Compose Settings show the same and let such a project be set.
- Toolchains: the existing node matching (`nodes::covers_run`, from the suite's name and the Xcode its command names). No `needs_tools` key was added.
- `crates/daemon/src/suites.rs` and `site_for_run` are unchanged: a nodes-only run never takes the GitHub path, so the refusal there is not reached.

## Gates touched

- `scripts/exit/s816.sh` asserted that a project with no `[remote_runs]` refuses a mode. This task asks for the opposite, so that one line now checks that a bad mode is refused for such a project.
- `clients/features.toml`: the `settings-placement` description said the choice is disabled for such a project.
- The Swift and Compose tests that asserted the disabled choice now assert the new text.

## Still runs on the coordinator

A landing lint or build check sent to a node still holds this machine's slots while it is out, as it did before (`landing.rs` is not changed). As for projects with GitHub: baselines and negative runs of a suite, landing's lint tier and build floor unless the definition sends them away (`where = "github"`, `floor_where = "github"`, which for a nodes-only project means a node), and all git work.

## Not verified

- No real second Mac: the node in the tests and the exit script is a second daemon on loopback.
- The five projects named in the task were not tried; whether Marmot has their toolchains was not checked. Node matching asks for Rust for any suite not named `swift*` or `compose*`.
- Daemon restarts while a nodes-only run is waiting or running were not tested.
- The Settings page was not looked at on screen.
