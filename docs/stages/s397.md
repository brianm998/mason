# s397: a retry diagnosis is applied by itself for every project when the failure was not the code

Summary: a `retry` diagnosis is applied by itself, once per task per day, for any project when the failure was outside the code (unless the retry loop already has one coming), or when the diagnosis sets `no_code_change`; every other verdict stays a card, and an alert names what was applied.

## Why

On 2026-11-14, 20 diagnoses waited for the owner, some for a day, and most said "run it again from test, no code change". Only MASON's own project applied a retry by itself (`diagnose::decide`).

## What changed

- `crates/daemon/src/diagnose.rs`: `decide(Facts)` takes the failure class, `no_code_change`, the daily limit and `autoretry::pending`. Outside class: apply unless a loop retry is pending. Code class: apply for MASON's own project, or when the diagnosis says `no_code_change`, once a day. `record_verdict` is the public entry; `applied_alerts` names, for an hour, what was applied.
- `crates/adapter-api/src/contract.rs`: `submit_diagnosis` has an optional boolean `no_code_change`; the prompt tells the agent when to set it.
- Tests: unit tests of `decide`; `crates/daemon/tests/diagnose_retry.rs`; exit script `scripts/exit/s397.sh`.

## Not verified

- Diagnoses are still started only for code-class failures (`diagnose()`), so the outside-class path is reached today only through `record_verdict`; the outside retries themselves are the retry loop's.
- The applied alert also appears for a diagnosis the owner applied by hand, for an hour.
- No real agent set `no_code_change`.
