# s250: a diagnosis session for a task that failed on its own code

Summary: when a task fails with class `code`, one read-only agent session (tier `light`, at most two per task) looks at it and ends with `submit_diagnosis` (retry with a note, back to explore, close, or ask the owner); the self project's retry is applied by itself once a day, every other verdict waits for the owner to apply or dismiss it, and `mason task retry --message` carries a note to the next round's prompt once.

Decision 0245 records the choices.

**What changed.**
- `crates/adapter-api/src/contract.rs` (protected): `StepKind::Diagnose`, the tool `submit_diagnosis` (verdict `retry`, `explore`, `close` or `ask`, with the fields each needs) and its validation. The diagnosis session has only `submit_diagnosis` and `report_progress`, and is read-only.
- `crates/daemon/src/jobs.rs`: `acquire_llm`, the session slot (`llm:<provider>` of the account, no `compile` or `test-suite`) that a diagnosis takes through the broker, waits for like any request, and gives back when it ends.
- `crates/daemon/src/diagnose.rs`: the trigger (called where a task fails with class `code`), the prompt (title, body, plan, failure reason, every round's feedback, the tails of the newest logs, `git diff --stat` against the base), the session (the same adapter, a `light` model), the cap of two sessions per task (counted in the store before the session starts), `decide` (the rule above), `apply`/`dismiss`, the card text and the alerts for pending diagnoses.
- `crates/store`: migration 34, `diagnoses` (task, time, verdict, arguments, status), and `add_diagnosis`, `diagnoses`, `set_diagnosis_status`.
- `crates/daemon/src/http.rs`: `retry` takes `message`; `retry_task` writes it to `retry-note.txt` in the task directory before the retry starts; `GET /tasks/{id}/diagnoses` and `POST /tasks/{id}/diagnoses/{n}/apply|dismiss`.
- `crates/daemon/src/jobs.rs`: an agent step reads the retry note once and deletes it (`take_retry_note`, `with_retry_note`); a failure with class `code` calls `diagnose::on_failed`.
- `crates/daemon/src/config.rs`: the project key `diagnose = false` turns it off (default on).
- `crates/cli/src/main.rs`: `mason task retry --message TEXT` and `mason task diagnosis <id> [apply|dismiss N]`.
- `scripts/exit/s250.sh` (protected).

**The card.** A failed task cannot hold a question in the engine (a question needs a step), so a pending diagnosis is shown as an alert of kind `needs_you` that says what is suggested (the recommendation first for an `ask`), with Apply and Dismiss as `mason task diagnosis <id> apply|dismiss N` and the two endpoints. It is not a `QuestionAsked` event. Applying `close` retries the task into a step and closes it with no change, because a failed task cannot be closed directly.

**Not run, and known gaps.** Nothing was run: no unit test, no fake-claude test, no exit script (the owner asked for building and linting only). The fake-claude integration tests the brief names (auto-applied retry once a day, a card for the other verdicts, the cap) were not written. The retry note is not cleared when a retry is never started.
