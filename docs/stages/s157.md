# s157: masond logs a deliberate stop, does not count it as a crash, and reloads registration files

Summary: masond logs `masond stopping: SIGTERM|SIGINT` and exits 0 after a bounded graceful shutdown with `stopped` in boots.log (which `crashes_in` no longer counts as a crash), and `mason project reload` applies an edited registration file without a restart, refusing fixed fields by name.

**Stop.** A task in `main.rs` waits for SIGTERM or SIGINT, logs at INFO, and the HTTP server shuts down gracefully (`http::serve_until`), bounded to 3 s so launchd's 5 s timeout holds. Step hosts are separate processes and keep running. `stopped` is recorded for the running sha and the process exits 0. The log line has no sender pid: tokio's signal API does not expose `si_pid`, and reading it needs a raw `sigaction`, which I did not add. The unified log (`sent by launchd[1]`) still says who.

**Crash count.** `crashes_in` treats `stopped` like `healthy`. This touches `update.rs` (PROTECTED): without it a SIGTERM before `healthy` (a restart in the first 30 s) is a `start` with no ending, and three in five minutes roll back a good build.

**Reload.** `Daemon::reload_registration` re-reads `projects/<P>.toml`, diffs it by top-level key against the one in force, and swaps in the new `ProjectCfg` for tasks admitted from then on (running tasks keep what they started with). It logs `registration reloaded` with the changed keys. `path`, `base`, `remote` and `[self]` are refused, naming them, and so is a file that does not parse; the current registration stays. A project masond did not start with needs a restart. `Daemon.projects` became `projects()` (a snapshot) over a leaked-entry registry, so existing `&ProjectCfg` borrows stay valid across a swap; each reload leaks one `ProjectCfg` (a few KB). CLI: `mason project reload [--project P]`; HTTP `POST /projects/{name}/registration/reload`.

**Not verified.** I could not run the build tool directly (the build queue refuses it); everything was compiled and run only by the `tests` check. I did not run `scripts/exit/s157.sh` or `run-exit-scripts.sh` by hand, nor try SIGTERM under a real launchd. Fields other than the four fixed ones are assumed safe to change live; I did not audit each reader (for example `task_cache` is read for disk paths only at start, so a change there is applied to tasks but not to the disk probe until restart).
