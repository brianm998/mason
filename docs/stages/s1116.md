# s1116: answer a failed task's diagnosis like any decision card (#1045)

Summary: a failed task holds its diagnosis as its decision card, answered on the task page or with `mason task answer` (an option runs its action, other words retry the task with them), and every answer may carry the owner's context.

## What changed

- `crates/daemon/src/attention.rs` (protected): `card_of` gives a Failed task the card of its pending diagnosis. `answer_with` (`answer` is it without context) accepts that card with the same owner check and stale-hash check as a question, writes the question and answer to `decisions.txt`, records an `answer` intervention, and takes the `decisions.txt` lines back if the action is refused. `context` (trimmed, at most 2,000 characters, else 400) makes the stored answer `<label>\nOwner's context: <context>`, for questions too. An option is picked from `answer` alone.
- `crates/daemon/src/diagnose.rs`: `pending_card` (the newest pending diagnosis of the failure the task is in now), `row_card` (the stored card; the hash covers the diagnosis id), `answer_card` (an option: its action through `apply_args`, the context appended to the retry note, explore reason or close evidence, row `applied`; other words: retry from the default step with them as the note, row `answered`). Answer, apply and dismiss run under one gate and re-read the row. The notice for a pending card says to answer it on the task page or with `mason task answer`; an older row with no card keeps `apply|dismiss`. "Applied by itself" is now said only of diagnoses the daemon applied, not ones the owner did.
- `crates/daemon/src/views.rs`: a Failed task's actions are `answer` (with a card), `retry`, `cancel`, `open_session`, and `diagnose` when none is pending or running and the budget allows.
- `crates/daemon/src/http.rs`: `POST /tasks/{id}/answer` takes an optional string `context`.
- `crates/daemon/src/jobs.rs`: the built-in explore prompt now ends with the retry note. It dropped it before, so an `explore` option's reason (s1048) and a `retry --message` to exploring never reached the exploring agent (a prompt pack already showed it).
- CLI: `mason task answer <id> <answer> [--context TEXT]`.

## Agent prompts

`prompts.rs` is unchanged. The context reaches an agent only where an owner's words already go: the answered-questions block (`decisions.txt`) and, for a failed task, the retry note (kept in the owner notes too), each time after the label `Owner's context:`. It is not put through `fenced`: that function is private to `prompts.rs` and marks task text as data not to be followed, while this is the owner's instruction, accepted only from an owner identity. An option's note or reason is the diagnosis agent's text and reaches the next agent as it did when a diagnosis was applied (s1048).

## Not verified

- No real model and no real monitor were used.
- The monitor has no handler for the `diagnose` action, so until the monitor task that follows this one it shows a button that does nothing. The websocket `AnswerTask` command has no `context` field (the HTTP route, also through a raw command, does).
- A `close` option retries the task and then closes it (as s1048 did); a step may start in between and is stopped by the close.
- Two answers sent at the same moment are serialised by a lock; no test races them.
