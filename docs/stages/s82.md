# s82: landing re-verifies outside the repository lock

Summary: When the base moves while a batch lands, the re-verification now runs with the repository lock released and holds the broker leases the test step or suites use, which also removes a self-deadlock when a landing suite is red on both runs.

`Batch::finish` used to fold a moved base in and re-verify under the repository lock. That stopped every other step in the repository for a whole test run, and a red landing suite whose failure survived the rerun reached `baseline`, which takes the same non-re-entrant lock from the landing thread: a hang with the lock held (read from the code, not reproduced; MASON's own configuration has no landing suites).

`Batch::finish_with(a, lock, reverify, point)` takes the lock only for the fold (fetch, compare, `catch_up`, status block) and for the promote (fetch, compare, push). `reverify` runs between them with the lock released. A tree is promoted only if the base, fetched under the lock, is still the tip the tree was last verified on; otherwise it folds and re-verifies again, up to `max_fold`. `finish` remains, with no lock. The crash points are unchanged.

In the daemon, the first verify, the red-ladder reruns, bisect, the re-test (the test step's `uses`) and `post_land` acquire what the test step or the suites use through the broker, ranked as the batch's first task. The wait is outside every timeout; a batch stops waiting if all its tasks left the landing step (post_land does not watch: its tasks have landed).

Tests: `crates/landing/tests/batch.rs` (lock not held in `reverify`; base moving during `reverify` folds and verifies again; a base that keeps moving is never promoted unverified); `crates/daemon/tests/landing.rs` (red re-verification with no baseline ends and frees the lock; the re-test holds a `compile` lease and not the repository lock); `scripts/exit/s82.sh`.

Not verified: I did not run the new daemon deadlock test against the old code to watch it hang, so it shows the new code ends, not that the old code hung. A wait that is cancelled because every task left landing ends the batch through the service-error path. The waiting lease does not show a wait text on the tasks.
