# s1127: s724 expects the current `mason doctor` wording

Summary: Exit script s724 now expects the workflow line `mason doctor` prints today, and the causes of the s723 and s727 failures are recorded as races in those scripts.

## s724

Its last check looked for wording that `remote_run_findings` (`crates/cli/src/doctor.rs`) no longer prints, so it failed on every run. It now matches the current line as a fixed string (`grep -F`). Steps 1 and 2 are unchanged. It passes on its own on this Mac. See decision 1116.

## s723 (not changed, still fails)

Run on this Mac without edits: 4 of 4 runs failed with `FAILED: the run was not pushed and looked up`. The script waits for a holder of the `gha` pool and then greps the fake's `requests.log` at once. The daemon takes the lease before it dispatches the run and looks it up, so the file did not exist yet. A temporary copy that waited up to 120 s for the `head_sha=` request saw it within a second and passed 2 of 2 runs. This is a timing race in the script; no code regression was found.

## s727 (not changed, passes here)

Run on this Mac without edits: 4 of 4 runs passed. For the failure on node marmot (run t1129r6759) only the tail of the output was kept, and the `FAILED` line is not in it. The push log in that tail shows a `mason/run/**` push for task 2 and then task 2 landing, which fails the check `a task set to local pushed a run`. So this cause is inferred, not read. The script calls task 2 "held", but it is filed with `--after 1` after task 1 has already landed, so it starts at once. If its test step starts before `mason task run-on 2 local` arrives, it runs on GitHub as first chosen. The same output shows an event-loop stall of 1523 ms just after that push.

## Follow-up

Fixing the two races edits two more gate scripts, so it was filed as a separate task.
