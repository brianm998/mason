# s99: the self-update test lost its agent's host because the test let the agent finish

Summary: The self-update test no longer fails because its fake agent finishes on its own: the agent now waits for a release file instead of sleeping 90 s, and a failure of the host assertion reports every host's state, exit record, pids, heartbeat and journal tail.

**Cause: a fault in the test, not in the takeover.** The fake agent slept a fixed 90 s (`slow_script(90_000)`) and then submitted its change. The update takes as long as the build plus the new build's self-test; on a loaded machine (other cargo builds, other test binaries starting daemons) that is more than 90 s. The host then finished its work normally and wrote `exit.kv` with `code=0`, so `status_of` reported `Exited` and `running_hosts` came back empty. The takeover did not touch the host. (The earlier reading in the ticket, that the absence of cargo's "running for over 60 seconds" line meant the agent had not finished, was wrong: that line is printed at 60 s of the test, and says nothing about 90 s.)

**How it was shown.** First, 43 runs of the test on its own (3 in sequence, 40 as 5 parallel loops of 8) were all green: with only the test's own load the self-test is fast and the update lands inside 90 s, so the fault does not show. Then the whole `update` binary was run 15 times (5 at once x 3), which puts about 35 daemons on the machine. The target test failed in 4 of those 15 (3 of the failures kept the ids below). The new failure message shows, for each:

```
host t0r0-1 state=Exited(ExitRecord { code: 0, signal: 0, output_len: 2414, ... })
  host_pid=61450 alive=true child_pid=61652 alive=false
  exit.kv: code=0 signal=0 ...
  journal tail: ... "result":"done" ... "subtype":"success" ...
```

The journal ends with the agent's `result: done`, and the daemon log of the same run shows the self-test starting at 21:41:51 and finishing at 21:42:54, with the takeover at 21:42:54, more than 90 s after the agent started. No stop, reap or lost-host line appears in the daemon log for the host (the added `warn!` lines in `stop_hosts` and before `reap_dir` did not fire). Exit code 0 with no signal rules out a kill of the host. This matches the production logs: 10 of 12 failures are this assertion, and the ones in loaded test steps.

**Fix.** The agent runs `sh` that waits until `<gate>/release` exists (or the gate directory is gone, so a failed test leaves nothing running), and the test writes `release` only after the host assertion. The agent ends when the test says so, not when time runs out; nothing was lengthened, retried or removed, and the assertion is the same (same id, same pid). `running_hosts` no longer hides a registry error (`expect` instead of `unwrap_or_default`). `MASON_TEST_LOG=/abs/path` appends the daemon's stderr to that file (any other value still inherits it), and `host_report` quotes the tail on failure.

No change to `update.rs`, `selftest.rs` or any file in `PROTECTED`. `daemon.rs` and `jobs.rs` only gained two `tracing::warn!` lines, no behaviour change.

**Result after the fix.** Under the same 5-at-once load that failed the target test 4 times in 15, it passed 15 of 15. `scripts/exit/s99.sh` (20 runs of the whole `update` binary in a row, load average about 40 from other builds) printed `s99: 20 green out of 20 attempted` on its second full run. Its first full run, made before the script kept the failing output, was 13 green out of 20, runs 1-7 red; which test failed there was not captured, so it is not explained (the script now prints the failed test names and panic lines). In the 35-daemon load, `the_self_test_runs_on_a_copy_and_a_bad_database_fails_it` failed in all 15 runs and `a_build_that_crashes_is_rolled_back_by_itself_with_an_alert` in 3, both before and after the fix, so those are load limits of other tests.

**Not verified.** That all 10 production failures had this cause (only the 3 kept reproductions were read; the production logs carry no host output). That the takeover never stops a host under some other order of events: no such order was seen in 58+ runs. The separate failure seen only in the 35-daemon load, `the_self_test_runs_on_a_copy_and_a_bad_database_fails_it` ("did not land in 300 s"), is a load timeout of a different test and was not investigated. #59's resume path was not exercised.
