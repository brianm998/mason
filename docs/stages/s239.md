# s239: the compile pacing pause applies only while a compile is running

Summary: The 30 s pause between compile starts now applies only while a compile is running, so an idle compile queue no longer waits out the pause, and a request behind a paused one says what it is behind.

**Problem.** `mason resources` showed `compile 0/5` with 20 requests waiting on "letting the last compile show in CPU use". The pause exists for a running compile whose load the CPU reading has not caught up with; with none running there is nothing to wait for.

**Change.** `plan` (`crates/scheduler/src/plan.rs`) computes `settling` only when `compile_running`, as `hot` and `stalled` already do. Within one pass the first grant counts as running, so the second compile is still paced. `Ahead` carries the cause each earlier waiter waits on; when a compile waits behind such a waiter and no slot is held, `explain` says "Waiting for compile slot: 4th in line, behind #289 (letting the last compile show in CPU use, 7 s)" instead of implying a full slot. Reasons named: pacing, CPU, disk stall, disk floor, memory.

**Tests.** `crates/scheduler/tests/properties.rs` (four planner/ledger cases), `explain.rs` (wait text), `crates/daemon/tests/limits.rs` (broker with `compile_settle_s = 600`). Exit: `scripts/exit/s239.sh`.

**Not verified.** The exit script drives the broker with a fake CPU source, not a running `masond` through `mason run` and `mason resources --json`; the live queue effect was not observed.
