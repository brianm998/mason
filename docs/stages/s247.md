# s247: the daemon retries failures outside the code by itself

Summary: a task that failed with class `outside` (a lost step host, a fetch that timed out, a refused push, a CLI that ended with no result) is retried from the failed step after 10 minutes and again after 60, a third such failure within 24 hours stays failed, and failures about the code are never retried.

Decision 0242 records the choices.

**What changed.**
- `crates/core/src/task.rs`: `FailClass::classify` marks as outside the reasons the event log records for failures that say nothing about the code: lost step host, step host that never started, fetch that failed or timed out, a CLI that exited with no result, a refused push of a `mason/ci/` ref. Unit tests carry each real reason text.
- `crates/core/src/event.rs`, `crates/store/src/codec.rs`, `crates/engine`: `Retried` has `auto: bool`, written as a trailing word, so an old log decodes as a manual retry.
- `crates/daemon/src/http.rs`: the retry endpoint's check-and-emit became `retry_task`, used by the endpoint and by the automatic retry, with the same `seen` guard. The task JSON shows `auto_retries` and `next_auto_retry_ms`.
- `crates/daemon/src/autoretry.rs`: the loop (every 30 s), `due` (the schedule), `bursts` (three or more tasks with one normalised reason within ten minutes), `status`.
- `crates/store`: migration 30, `auto_retries` (task, time, reason), so a restart neither forgets nor repeats a retry.
- `crates/daemon/src/attention.rs`: the failed alert waits while a retry is coming; a burst raises one `environment` alert; a failed-fetch burst holds its retries until a fetch works.
- `crates/daemon/src/config.rs`: project key `auto_retry = false` turns it off; delays, window, tick and burst size are daemon settings so tests use zero delays.
- `crates/cli/src/main.rs`: `mason task show` prints the automatic retries and the next one.
- `crates/daemon/tests/auto_retry.rs`, `scripts/exit/s247.sh`.

**Not verified.** The restart case rests on the retries being counted in the store, not on a killed daemon. Only the fetch-failure burst has a probe; other bursts are held by the delay alone. The tests call one pass of the loop themselves; the loop's own timer was not exercised. `mason task show` output was not run against a real daemon.
