# s1232: the settings catalogue behind the Project page (daemon half)

Summary: `GET /projects/{name}/settings` now also returns a `catalogue` of every per-project setting (value as written, effective value, source, writability, sensitivity, when it applies, the real model of each agent step, the tier grid), and `POST` on the same route sets or unsets any catalogued key; the monitors' Project page is not built.

Task #1243, decision 1222.

## What is done

- `crates/daemon/src/projsettings.rs`: the catalogue (`KEYS`, about 150 key patterns from `parse_project`, `parse_agent`, `parse_self`, `parse_services`, `introspect::parse_cfg`, `schedule::parse`, and the step and tier-mapping tables), drawn as seven sections: project, models, limits, testing, runs, services, proposals. A key in the file the catalogue does not know is listed under `unrecognised`, read-only, with secret-looking names hidden.
- `models`: one row per agent step (tier, level, real model and effort, the source of each, from `launchview::inspect`), the diagnosis session, the escalation model and ladder, the six-cell tier grid with each cell's source (built-in, provider file, project file), and the providers.toml accounts.
- Writing: `{"set": {key: value|null}}` (null unsets), `"preview": true` (diff only), `"confirm": true` (needed for program and guard keys). `toml_edit` edit, `parse_project` + `parse_overlay` + mapping-table check, atomic write, `reload_registration`, old text back if it refuses. `provider = "codex"` becomes `[provider] use = "codex"` when a mapping table is written. A literal token, an out-of-range value, an unknown key and a fixed key (`path`, `base`, `remote`, `[self]`) are refused with the file unchanged.
- Who may write: viewers and non-owners are refused. Requests through a paired device carry `x-mason-paired: 1` (set by the LAN guard in `lan.rs` and by the WebSocket command path in `ws.rs`, never read from the client); those are refused the keys that run a program or weaken a guard, an owner device included.
- Timing: `Daemon::reload_registration`'s comment, the `mason project reload` message and docs/self-hosting.md said a reload reaches "tasks admitted from now on". `jobs::ctx` reads the current registration whenever a step run starts, so it reaches the next step run of every task. Reworded. Each catalogue entry says `next_step_run`, `next_use` or `after_restart`.
