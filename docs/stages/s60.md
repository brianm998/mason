# s60: The pipeline gets unstuck: conflicts go to the agent, run_check runs the overridden command, tests stop failing for want of a CPU

Summary: A base conflict no longer fails a task: the develop agent is told to merge and resolve it. `run_check` and landing run the test command as layered (runtime overrides included), and a develop step's tool timeout covers a whole test run. The tests that failed only on a busy machine now check what they mean.

Done by hand on the owner's request, outside the pipeline, while it could not land anything: on 2026-11-07, tasks #12, #14, #15 and #16 ran out of test rounds on tests that went red only under load, and #17 and #20 failed outright on conflicts with `develop`.

## What was wrong

- **A conflict with the base failed every step.** `prepare` in `crates/daemon/src/jobs.rs` brings a task's branch up to date with the base before each agent step. On a conflict it aborted the merge and failed the step ("folding in the base conflicts in: …"). A retry ran the same merge and failed the same way, so no agent ever saw the conflict. #20 and #17 were stuck like this behind #18, which had changed the same lines of `selfguard.rs`.
- **The owner's test command reached only the test step.** `run_check` (the develop agent's tool) and landing's legacy suite called `layers::resolve` with no runtime overrides, so `mason config set step.test.command …` did not reach them. `run_check` was also cut off by the agent's 600 s tool timeout, while the command itself may run for `test_timeout_s` (3000 s for MASON). Agents then ran the suite again by hand, which doubled the load.
- **Tests that measured the machine, not the code.** Each test binary started every test at once, one thread per CPU (36 here), and `definitions.rs` alone ran 21 daemons. With up to ten tasks testing at once, load reached 40 to 95, and a different set of daemon tests went red on each run:
  - the 100 ms hand-off bound in `protocol.rs`;
  - an e2e check that counted test and landing steps as holding a session, although by design they hold none;
  - the scheduling test that read a task's activity before its `WaitStarted` event had been written;
  - "step host did not start" at a 10 s deadline (the first exec of a freshly built binary waits for the system to scan it);
  - the update self-test, which ended `Failed` and did not say why.

## What changed

- `prepare` returns the conflicting files instead of failing. A develop step gets a note first in its feedback: run `git merge <base>`, resolve keeping both changes, build, and commit with `-s`, followed by the list of files. Explore and review are read-only and go on with the branch as it is. Landing still refuses a branch that does not merge (unchanged), and that sends it back to develop, where the agent now sees the conflict.
- `jobs::test_command` is the one place that resolves the test step's command: definition, local overlay, runtime overrides and the task's own overrides. `run_check` and landing's `legacy_cmd` both use it.
- `jobs::tool_timeout_for`: a develop step's tool timeout is at least `test_timeout + 60 s`. Other steps keep `tool_timeout_s`.
- Step host start deadline: 10 s to 60 s. The loop still returns the moment the host is up, or when it exits. The text is identical to task #15's commit, so the two merge cleanly.
- Self-test: up to 300 s for the scripted task (was 150 s), and a failure says why ("ended Failed: <the task's failure>") or what state the task was left in.
- Tests:
  - `support::Scratch` holds one of N slots for as long as it lives. N is CPUs / 4, clamped to 2 to 8, and `MASON_TEST_WORLDS` overrides it. A test waits for its slot before its world exists, so the wait is outside its deadlines. After 600 s it goes ahead anyway, so a test that makes two worlds cannot deadlock.
  - The hand-off test sets every periodic admission path (the definition watcher; the sweep already was) an hour away, and asserts the hand-off within 5 s, which only the event can do. It prints the number; `scripts/exit/s11.sh` still holds that number to the 100 ms DESIGN target.
  - The e2e concurrency check counts only agent steps without a lease, as `Daemon::llm_free` does.
  - The scheduling test waits for the activity before reading it; it still checks that it names the compile slot.
  - `landing_crash.rs` deadlines tripled, identical to task #17's commit `d302d84`.
- New tests in `e2e.rs`:
  - `a_branch_that_conflicts_with_the_base_goes_to_the_agent_to_merge_and_lands`. The base gets a conflicting `conflict.txt` while the task is in develop. The red test sends it back; the second develop turn must find the note and the file name in its prompt, merges, and the task lands with the merged file and no failure counted.
  - `run_check_runs_the_test_command_the_owner_overrode_at_runtime`. The project's command fails and prints FROM-THE-PROJECT; a runtime override prints FROM-THE-OVERRIDE. The agent's `run_check` output must show the override's text and never the project's.

## Exit test

`scripts/exit/s60.sh` runs the two new e2e tests and the reworked ones (the hand-off, the concurrency check, the held-class wait, the update self-test).

## Not done, not verified

- The other half of the load is owner configuration, not code, and is not in this change: `compile = 2`, and a runtime override (until 2026-11-14) that runs the test step through `~/.config/mason/bin/mason-queued compile …`. Once GitHub #30 (the compile CPU gate) lands, that override can go.
