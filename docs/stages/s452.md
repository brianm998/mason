# s452: the exit scripts still red on CI after #333

Summary: s09, s19, s54 and s130 (scripts) and s393 and s396 (their daemon tests) are pointed at what the code does now, and s09, s19, s40 and s130 say why they fail; the code needed no change.

## Causes, found by running each against a scratch daemon

- **s54**: its start step is also the work step, and since s312 a start `command` step is run as worktree setup in MASON's own checkouts (the landing worktree) with no task. The step waited for a gate file named for a task title that was empty, so the batch sat in `forming` until the 600 s setup timeout. The command now exits 0 when `MASON_TITLE` is empty. The script also unsets the task variables it inherits, which a daemon started from inside a task would pass on.
- **s19**: parsers are supported since s292 (protocol 3). The fixture's manifest says protocol 1, so it is refused with "needs protocol 3" rather than "not yet supported"; the check looks for that text. The refusal is still what is tested.
- **s130**: the check "names no queued command" matched `xxxxxxxxxx`, the padding of the *holder's* own command, which the wait text shows cut short. It now looks for a long run of it. The script also unsets `MASON_TASK`, otherwise `mason run` registers as that task ("held by task N") when the script is run from a task. The script's `fail` printed its message here; why the CI log shows none was not found.
- **s09**: the known-red ledger (decision 0225) files a fix task for the failure section 4 excuses. It takes the next task number, which the scripted agent and suite read their mode from, so every later task was off by one and section 5 timed out. The script waits for that task, cancels it and counts it.
- **s393** (`a_debt_closes_by_itself_...`): since s426 landing pays every open debt at once, so the proof is "green when run on <base> at <sha>" as often as "checks green on ...", and the debt may already be paid right after landing. The test accepts either proof and no longer asserts "open" there. `a_debt_whose_suite_is_still_red_...` had the same race (the base went red after the landing); the base is now red before the task lands, and the test waits for the first try.
- **s396**: the narrowed command ran three times (the step, plus runs at the merge base to tell the task's red from the base's). The assertion is about which crates ran, so it now compares the set of command lines.
- **s40**: passes here. Its `cargo test ... | grep` pipelines exited silently when a test run printed no result; they now show the whole output and name the command. The runner's failure was not reproduced.

s09, s19, s40 and s130 get an `ERR` trap so any failing command names its line (s54 already has `fail`).

## Not verified

- On a 4-core runner. Locally every script was run with `MASON_CPU_FILE` set as run-exit-scripts.sh does, but not under `taskpolicy` or fewer cores.
- s40 could not be made to fail locally; the change to it is for the message only. #445 (Deferred state) was not checked.
- s130's "no message" on CI was not reproduced as such; its real failure (above) does print one here.
- No verdict logic, gate or scheduler rule was changed.
