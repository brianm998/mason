# s395: the review step settles base lines a task replaced on purpose

Summary: a base line the task's merge replaced in place is no longer sent back by the landing audit unseen; the review step is shown each (base line, replacement) pair and an approval declares them as `removes` with the reviewer's reason.

## Why

22 send-backs in the 2026-11-10..14 review were "conflict resolution dropped landed lines". Star #216 failed after three landing rounds with correct code: it rewrote two source-pin test lines another task had just landed, and the agent declared only one under `removes`.

## What changed

- `crates/landing/src/audit.rs`: `replacements` pairs each dropped line with the changed region of the merge that replaced it; `review_block` words them for the reviewer.
- `crates/daemon/src/landing.rs`: `dropped_in_merges` is shared by `check_dropped` and the new `replaced_for_review`.
- `crates/daemon/src/jobs.rs`: the review prompt gets that block; an approval's `removes` are added to the task's `change.json` (`add_removals`), which the landing audit already reads. A `changes` verdict sends the task back as before.
- `crates/adapter-api/src/contract.rs`: the review submission accepts `removes`.
- A line dropped with no replacement nearby is not paired and is still sent back.

## Not verified

- No live review agent was run end to end; the daemon path (prompt block, `add_removals`) is not covered by a full pipeline run, only by the pairing tests in `crates/landing` and contract validation.
- Whether a reviewer model reliably copies the pairs into `removes`.
- Projects with no review step get no owner card; not implemented.
