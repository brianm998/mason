# s394: a red batch is split to find the task that breaks it

Summary: A red batch whose red blame cannot pin on one task is split by halves, so only the task (or the tasks that break it together) goes back and the rest land; a red every task reproduces is a base red and blames nobody.

**Problem.** The whole batch went back whenever blame named no single task (20 star tasks in four days).

**Change.** `crates/landing/src/plan.rs`: `pin`/`Pin`. `crates/daemon/src/landing.rs`: `pin_red`, `settle_pin`, replacing the two park-everyone paths; progress and closing note show the split. Decision 0387.

**Trust.** `landing.rs` and `crates/landing/**` are protected; the change is red-ladder verdict logic and needs the owner's approval.

**Tests.** `plan.rs` unit tests; `crates/daemon/tests/landing_split.rs` (three tasks, one culprit; two tasks only together). `scripts/exit/s394.sh` runs them against the real daemon test world.

**Not verified.** Nothing ran against star's real suites or real CI. The exit test uses the test world's masond in-process, not an installed `masond`. The base-red branch is tested only in the pure search, not through a running landing. A batch whose red is CI-judged real still goes back whole, as before. I could not run cargo directly (build queue), so only run_check results count.
