# s126: banner icons

Summary: Every banner under the top bar now starts with a decorative 20 pt mascot icon (scaled with the text zoom) in both monitors, chosen only by the banner's own kind, and the daemon emits a `landing_frozen` banner while landing is frozen.

## What changed

- `crates/daemon/src/views.rs`: the header adds one `landing_frozen` banner per in-scope freeze. Before, a frozen landing showed only on the landing page, though DESIGN Part 17 lists it as a banner.
- Swift: `MasonMascot/BannerIcons.swift` holds the mapping (and the kinds deliberately without an icon); `BannersView` shows the icon with `.accessibilityHidden(true)`; `Theme.mascotBannerIcon` reads the existing `mascot_banner_icon` token.
- Compose: `BannerIcons` in `Mascot.kt`, `BannerImage` in `TopBar.kt` with `contentDescription = null`, `Theme.mascotBannerIcon`.
- Mapping: connection → connection_lost, daemon-down → daemon_down, read-only → read_only, monitor-update → update; paused, definition, landing_frozen as themselves; provider_outage/overage/budget/hold/limit → provider. `provider_extra_billing` and `provider_warning` are informational and deliberately have no icon; an unknown kind has none and never crashes.
- `clients/features.toml`: added `mascot-banner-icons`, done in both. No check weakened.
- Tests: each client's mascot test covers every daemon kind and an unknown one; the daemon's landing freeze test asserts the banner.

## Not verified

- I could not build or run anything myself (the shell sends builds to the shared queue); only `run_check` ran the tests. The Swift and Kotlin UI changes were not compiled or looked at on screen, on either theme, by me.
- The conformance run was not run separately. It compares item text, which is unchanged; the new daemon banner appears only while a freeze exists.
- The daemon-update row (`daemon-update`) has no icon, as the ticket names only the monitor-update banner.
