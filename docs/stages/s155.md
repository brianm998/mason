# s155: outside pipelines queue in masond

Summary: Another pipeline can queue with masond: `mason run --pipeline` ranks its work with MASON's tasks (behind a person's), `mason hold` holds resources for a process's life and prints `granted`, an outside `llm:claude` hold counts against the same `[llm] claude` limit, and `mason resources` and `mason status` list outside holders and waiters by pipeline name.

**Built.**
- `crates/daemon/src/outside.rs` (pure): request parsing (priority names, progress 0 to 6 as `6 - progress` steps), the display label, the waiter wording.
- `sched.rs` (protected): `Meta::External` gains `pipeline`; `lease_open_outside`; snapshot holders and waiting gain `pipeline`; an outside waiter's explain is `waiting for R (N ahead)`; an outside lease is not counted as a person's in the compilation view.
- `POST /leases` reads `pipeline`, `priority`, `progress` (ignoring `task` when `pipeline` is present).
- CLI: `mason run --pipeline/--priority/--progress`, `mason hold`, outside lines in `mason resources` and `mason status`. `crates/cli` gains `nix` (signal) for the `--pid` check.
- Docs: `docs/self-hosting.md` section, decision 0150.

**Ordering against a MASON task.** Same existing rule: fewer steps remaining first, then priority, then arrival. At equal steps: outside urgent before every MASON priority; high before MASON normal and low, after MASON urgent; normal after MASON high, before MASON low; low after all. By default a MASON step with fewer steps remaining goes first whatever the outside priority, so the ticket's "waits behind a high step" is tested at equal steps (and with `priority_first`). A person's `mason run` always goes first.

**Tests.** `crates/daemon/tests/outside.rs` (ordering table, steps vs priority, person first, explain, `llm:claude` with limit 2 and used 2), unit tests in `outside.rs` and `cli/resources.rs`. Waits are bounded polls; no timing assertions.

**Exit test.** `scripts/exit/s155.sh`: real masond, `[llm] claude = 1`, fake agent. Output:
```
== 1. a hold is granted once and holds the slot
   granted
== 2. a MASON task's agent step waits for it, and the holder is listed with its pipeline
   task is queued
     other first: holding llm:claude for 3 s
   waiting
== 3. stdin closes: the hold ends, the agent starts and the task lands
   landed
== 4. SIGTERM, SIGKILL and the exit of --pid each free the slot
   SIGTERM freed it
   SIGKILL freed it
   --pid exit freed it
```

**What testing found.** MASON admission (`llm_free`) already counts the hold, so a task whose agent step would wait is not claimed at all ("queued") rather than waiting inside the broker. A first version of the CLI prefixed the label twice.
