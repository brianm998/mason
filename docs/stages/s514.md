# s514: show the syspolicyd gate in the monitors and alert when it holds long

Summary: the broker publishes `syspolicyd`'s CPU reading and limit in the Compilation view and the resources snapshot, both monitors show "syspolicyd 640% — holding compiles over 300%", and an owner alert is raised after 30 unbroken minutes of holding.

## What changed

- `crates/daemon/src/sched.rs`: the broker keeps the latest reading and when it first went to the limit (`policy_since`, reset the moment it falls under). `compilation()` fills new `syspolicyd_pct` / `syspolicyd_max_pct`; `snapshot()["cpu"]` carries the same; `policy_hold()` reads it afresh for the alert.
- `schemas/mason.proto`: `Compilation.syspolicyd_pct` (11, -1 without a reading) and `syspolicyd_max_pct` (12, 0 without a gate). Additive. Swift regenerated with protoc.
- `crates/daemon/src/attention.rs`: `policy_hold_alert` (key `syspolicyd`, kind `environment`) after `POLICY_HOLD_ALERT_MS` (30 min). One alert: it exists while true.
- Swift and Compose: `policyLine` on the Compilation view and on the Health page's CPU section, shown in both UIs and in the item list; `clients/features.toml` entry `syspolicyd-gate` (Android todo, as for the Compilation section).
- Tests: `the_views_carry_the_syspolicyd_reading_and_limit` (FakePolicy), `a_syspolicyd_hold_alerts_once_it_lasts_the_threshold` (no clock: `now` is passed in), client line tests in both suites. Exit script `scripts/exit/s514.sh`.

## Not verified

- The Swift and Kotlin client tests and the UI changes were not built or run here; only the Rust side was.
- "Held" means the reading is at or over the limit, whether or not a compile is waiting at that moment.
- The alert is not delivered to a real notification channel in any test.
