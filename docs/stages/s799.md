# s799: landing places builds by the suite's own rules (#815)

Summary: Landing's build floor, base floor and fast tier now place each suite by its own `runs_on`, `remote = false` and device rules, so a batch touching `clients/swift` builds Swift on macOS instead of failing as "develop does not build".

## Problem
Batch #511 failed with "develop does not build (swift-clients ...)" because `build_floor` sent every
build through `executor_global`, which uses only the project's `[remote_runs] runs_on`
(ubuntu-latest). Swift's `SwiftUI` module exists only on macOS.

## Change
- `hostedcheck::CheckSpec.place` now carries `Option<TaskId>`: `Some((None, suite))` is a landing
  check no task owns. `executor_for` → `place_of` then applies the suite's `runs_on`,
  `remote = false`, device/exclusive rules and the global switch.
- `landing.rs` `build_suites` (floor and base floor, which shares it) and the fast tier pass
  `place: Some((None, suite))`, `global: false`.
- Checks left global because they name no suite: the legacy no-suite test/rebuild specs
  (landing.rs ~2368). The lint tier stays as #811 made it.

## Not verified
- No new automated test was added: the landing test world has no fake-GitHub fixture, and none
  could be run here (tests run on GitHub via run_check only).
- No real masond + fake GitHub end-to-end run, and no real GitHub floor run of swift-clients on
  `macos-latest` (no URL to record). `scripts/exit/s799.sh` checks the wiring structurally only.
- The extra note for a red from a runner the suite does not allow was not added: with placement
  fixed the floor no longer runs on such a runner.
- The floor still takes a local compile slot before a remote run, as before.
