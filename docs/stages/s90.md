# s90: a busy worker pool must not blank the monitors

Summary: View computation and event reads now run on their own small pool, a monitor that cannot be served is retried or closed instead of getting an empty snapshot or a silently lost update, and `mason status` shows each pool's queue depth.

`Daemon::view_pool` (2 threads, 64 queued) serves `compute` and `records` for the WebSocket and the `/status` route; the 4-thread `pool` keeps the HTTP handlers and git work. In `ws.rs`:

- the snapshot, the resume events and the welcome's `last_seq` wait up to 5 s for room on the view pool; if they cannot run the socket is closed, so the client reconnects and says so. An empty `Snapshot` is no longer ever sent (the old `unwrap_or((last, vec![]))` is gone);
- `push_views` reports `Busy`; the session then holds a "views are owed" flag and retries every 100 ms (`catch_up`: events since `sent`, then the views) until it succeeds, with no new event needed. A tick whose event read failed no longer drops the events: `sent` only moves past events that went out;
- `Pool` counts queued work; `mason status` prints `pool NAME: Q queued of CAP (T threads)` and `status --json` has `pools`.

Debug-only routes `POST /debug/wait-repo` (waits on a repository lock, new) and the existing `/debug/hold-repo-lock?ms=` (404 without `--debug`) hold or wait on a repository lock, for the exit test.

Tests: four in `crates/daemon/tests/protocol.rs` (main pool full: full snapshot and updates; view pool busy: owed update arrives with no further event; snapshot waits for the pool; unservable snapshot closes the socket, never goes out empty), `scripts/exit/s90.sh` with `crates/daemon/examples/snapshot_probe.rs`.

Not verified: a real git stall (the exit test uses a held repository lock, the same wait); behaviour on the LAN/TLS listener, which shares `session`; the real clients' reconnect UI on the new close. Other HTTP handlers are still on the main pool and still answer 503 when it is full; only `/status` moved.
