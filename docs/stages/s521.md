# s521: every landing batch is linted before it lands

Summary: a `lint` tier in `.mason/landing.toml` runs the format check and clippy (`-D warnings`) on every batch, including batches whose testing was skipped, and parks a red one with the files and lines in its note.

## Why

In two days six lint errors landed on develop and five files were not formatted. A landing batch runs the batch tier's suites, or only a rebuild when every task's testing was skipped (s429); neither runs the linter, and a task's own test step does not either.

## What changed

- `.mason/landing.toml` declares `[[tier]] name = "lint"` naming the suite `lint`; `.mason/mason.toml` defines that suite's command (the format check and clippy with `-D warnings`). Another project declares its own command the same way; landing has nothing special to mason.
- `landing.rs`: `lint_checks` runs the command of each suite of the lint tier in the batch's integration worktree (its build directory is reused). It runs in `verify` after the batch suites are green, and again when the base moves (the re-verification path), whether or not testing was skipped. Only the owner's force stops it. A red is red for the suite `lint`, with the places (`file:line`) read from clippy's and rustfmt's output, then the end of the output.
- It is not a `batch` tier: that would replace the build floor and the s429 rebuild-only rule for skipped tests, which are kept as they were.

## Not verified

- The command was not run against a real batch on the live daemon; the tests use a stub command.
- A lint red that comes from the base itself is not told apart from the batch's (the base-build check looks at builds only), so a base that is already lint red parks batches until it is fixed.
- The lint suite's `parser` and `min_tests` keys are required by the definition but unused: only the exit status counts.
