# s66: A lost step host is recorded, run again once, and never a verdict

Summary: a step host that disappears is now explained (pids, whether they still exist, the signal, how the journal ended, the time) in the step's failure text and `mason task show`, a lost test/command/suite run is re-run once on a fresh host without counting as a failed attempt, two or more hosts lost together raise one alert, and tests and exit scripts only kill hosts they can verify they started.

Task #40. Decision 0047.

## Built
- **step-host**: `LostReport` / `lost_report(dir)`; `host.kv` carries `host_start` and `child_start`; `launcher::exit_signal` (the signal the host's parent saw); `reap_dir` / `reap_verified` and `step-host-ctl reap ROOT`.
- **Safe kills**: `kill_hosts` (daemon tests), `selftest.rs`, the step-host tests and every `scripts/exit` cleanup that read pids from a registry go through `reap`.
- **Store**: migration 20, `step_host_losses`; `record_host_loss`, `host_losses_for_task`, `host_losses_since`.
- **Daemon**: `hostloss.rs`; the single re-run in `jobs.rs` (`run_command_once`) and `suites.rs` (`run_hosted`); alerts in `attention.rs` (`host_loss_alerts`); `host_losses` in `GET /tasks/{id}`; `mason task show` prints them.
- **Owner sign-off pending**: the automatic re-run (its own commit). See 0047.

## Not done / not verified
- The protobuf `TaskDetailView` has no host-loss field; monitors see the failure text only.
- The cause of the 2026-11-07 loss is unknown; nothing here proves what killed those hosts.
- The pid-reuse case is covered by a unit test with a mismatched start string, not by forcing the OS to reuse a pid.
