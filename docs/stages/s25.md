# Stage 25: Device test environments

Summary: Projects can declare iOS simulator, Android emulator, iPhone and Android phone environments; each suite leases one device by capability from a pool sized by a device provider (the scheduler's own wait when none is connected, rewritten as "environment problem, not the task's fault: waiting for an iPhone ..." with an `environment` alert), sees it as `MASON_DEVICE`, goes through setup, health, suite and teardown, and expired certificates and offline devices are classified environmental; `s25.sh` checks all of this on a fake provider, and no real simulator, emulator or phone was used.

## Built
- `crates/adapter-api/src/device.rs`, `device_kit.rs`: `DeviceProvider` (`list`, `prepare`, `health`, `teardown`), `Device`, `DeviceKind`, `ProviderError` (transient or permanent), and a conformance kit (sorted stable listing, health repeatable, teardown idempotent, unknown device is permanent, a vanished device leaves the listing).
- `crates/adapters/src/devices/`: the system provider (`xcrun simctl`, `adb devices -l`, `xcrun devicectl`) with pure parsers, tested on **hand-written** fixtures in `crates/adapters/tests/fixtures/devices/`.
- `crates/devices`: inventory counts and diffs, lowest-free pick, per-device `flock` lease, the wait sentence, and the fixture-file fake provider (which passes the kit and logs `setup`, `health`, `teardown`).
- `crates/testing`: `EnvKind::Device(DeviceType)`, `os` on an environment, `with_device` (`export MASON_DEVICE='id'; cmd`), and `signatures.rs` (`no-device`, `device-offline-or-locked`, `expired-certificate`).
- `crates/definition/src/testing_parse.rs`: the four device `type` values and `os`; built-in signatures are added only to a definition with a device environment.
- `crates/daemon`: `targets.rs` (reads the provider on a thread with a 10 s limit every `poll_ms`, sizes the pools, leases a device), `Broker::set_pool_units`, `[targets]` in `daemon.toml`, `suites.rs` (lease, prepare, health, suite, teardown on every exit; the rerun, baseline and negative control use the leased device), `jobs.rs` (device pools are never defaulted to one unit; the wait is worded for a person), `GET /targets`.
- CLI: `mason targets list [--json]`.
- `scripts/exit/s25.sh`, `s25-real.sh`, `s25-manual.sh`, fixtures `scripts/exit/fixtures/s25/`; the sample app `docs/examples/device-sample/`; decision 0052.

## What testing found
- A red suite that fails the same way at the merge base is excused as a baseline failure, so a "failing suite" fixture that always fails lands the task. The fixture now fails only if the change adds `android/red.txt`.
- The log for a red suite shows the rerun and the baseline check also prepare and tear down the device, so there are more `setup`/`teardown` pairs than one; the check is that the first calls are setup, health, suite, that the last is teardown, and that setups equal teardowns.
- Task numbers start at 0, so scripted agents that choose a suite by task number must count from 0.
- A pool declared with zero units and a request for one is a `TooBig` wait in the scheduler; its text is replaced in `jobs.rs` by the device sentence only for device pools with no units, so a busy pool still shows its place in line.

## Changed expectation
One existing test's expectation changed: `every_reference_must_exist_and_every_mistake_is_named` in `crates/definition/tests/testing_tables.rs` expected `must be "local" or "compose"` for an unknown environment type; the message now lists the device types, so it expects the start `must be "local", "compose", "ios-simulator"`. The type `simulator` is still refused. Nothing else was weakened or removed.

The real `System` provider's boot, health and shutdown commands (`simctl boot`/`bootstatus`/`shutdown`, `adb shell getprop sys.boot_completed`) were never executed. Android OS versions are not read (`os` is empty for Android devices, so an `os` prefix matches no Android device).

- **Teardown on a skip before the suite starts** is not applicable (no device is leased yet); a skip mid-run is tested.
- Named pools beyond the four kinds, reserving a device by id, and reading Android OS versions are not built.
