# s292: plugins can provide adapters, parsers and environments

Summary: Protocol 3 lets a plugin provide a tracker, git host or CI adapter, a results parser or a test environment (named `plugin:<name>` in the project file and suites), adds `step.cancel`, and `mason definition check --project P` knows P's approved plugin step types; every plugin is built only from an approved hash.

## What changed

- `crates/plugins`: protocol 3 (`PROTOCOL`, `SUPPORTED`), the manifest parses the new `provides` kinds (refused under protocol 1 and 2), `adapters.rs` (tracker, host, CI wrappers), `step.cancel` in `host.rs`, the kit passes a plugin with no step type.
- `crates/daemon`: `kind = "plugin:<name>"` for `[host]`, `[ci]`, `[tracker]` (`config.rs`), `services.rs` builds the wrappers via `plugins::approved_provider`, `suites.rs` reads a suite with its parser plugin and runs an environment plugin's setup, health and teardown, `plugin_job` passes the cancel check.
- `crates/testing` (protected): `Suite::plugin_parser`, `Environment::plugin`, `parse::from_plugin`. `crates/definition`: `parser = "plugin:x"` and `type = "plugin:x"` parse.
- `crates/cli`: `mason definition check --project P`.
- Fixtures: `crates/plugins/tests/fixtures/{adapters,parser,canceler}` (Python, no binaries).
- Docs: `docs/plugin-protocol.md` (version 3), decision 0286.

## Tests

`crates/plugins/tests/adapters.rs` (tracker_kit, host_kit, build_kit against the wrappers; parser and environment methods; cancel reaches a running step), `crates/daemon/tests/plugin_adapters.rs` (unapproved or changed plugin builds nothing; approved plugins pass the kits; parser and environment calls; approved step types), `crates/testing/tests/plugin_results.rs`, config tests in `config.rs`, the `definition check` test in `crates/cli/src/definition.rs`, the manifest tests. None asserts on time.

## Not done

- **The agent adapter surface** (`adapter:agent:<name>`): a manifest may name it; nothing loads it. Provider accounts' adapter wiring was not read or changed.
- **Definition validation of a plugin's name**: a suite naming `parser = "plugin:x"` that no approved extension provides fails when it runs ("no extension ... provides"), not when the definition is validated. Likewise `type = "plugin:x"` in an environment.
- **`mason definition dry-run`** does not take `--project`.
- A plugin adapter's process is started per use and each wrapper has its own process; `services::tracker(p)` scans the base commit on each call (no cache).
- Cancel: the daemon's plugin step does not conclude a canceled task's step. Whether the task's state is `Canceled` before the step ends in every cancel path was not read or tested end to end; only the host-level cancel (`cancel_reaches_a_running_step`) is tested.
- The exit script `scripts/exit/s292.sh` imports through a plugin tracker and runs the kits and a parser plugin through the daemon library's own tests, not a running `masond`.
- Nothing here has been run against a real third-party plugin or with a real project registered in a running daemon.
- The protected paths (`crates/testing/**`, `suites.rs`, `scripts/exit/s292.sh`) wait for the owner's approval.
