# s213: a red that a local suite reproduces is searched for locally, not with more CI runs

Summary: `[ci.local]` in landing.toml maps CI job names to local suites; a batch red only in mapped jobs has its culprit found by running those suites on each half locally, with one more CI dispatch on the union without the culprit.

**Problem.** When CI went red, the red ladder bisected by dispatching CI for each half, whatever job failed (batches #107 and #112 took 10 and 11 `pr-gate` runs). Most of those reds were in `static checks`, which star's `t0-pipeline-static` runs locally in seconds.

**Change.**
- `crates/landing/src/config.rs`: `[ci.local] "<job>" = ["<suite>", ...]` (`LandingConfig::ci_local`); malformed entries are refused.
- `crates/daemon/src/landing.rs`: before the ladder, if every failed CI job is mapped to suites the project defines (and CI did not judge a real failure), then
  1. the base branch's latest CI result for those jobs is read (`ci_watch::base_red_jobs`); red there too: the batch is held with no bisection;
  2. the mapped suites run on the whole union locally; green: "CI red in J, but S is green here: environment difference", an alert is raised and the batch waits for the owner;
  3. otherwise the halves are bisected with those suites locally (`run_local`, the code `verify` already used, under the batch's rank); the culprit is parked and the next round verifies the remaining union, through CI, once. If the red is local but pinned on no single task the batch is sent back by the ask rung, with no CI runs.
  Any unmapped failed job leaves the ladder as it was.
- `docs/migrations/star/.mason/landing.toml`: `"static checks" = ["t0-pipeline-static"]`, for the owner to install.

**Trust.** `landing.rs` (the red ladder) and `.mason/**` wait for the owner. CI still has the last word on the final union; only the search for the culprit moves local.

**Tests.** `landing_modes.rs`: (a) 4 tasks, one culprit, mapped job: culprit parked, exactly 2 CI dispatches; (b) unmapped job: bisects through CI (3+ dispatches); (c) mapped suite green locally while CI red: alert "environment difference", 1 dispatch, nothing landed or sent back. `red_base.rs`: `base_red_jobs`. `config.rs`: parsing.

**Not verified.** (d) "base red in the same job holds the batch" is tested only at the `Source` seam (`base_red_jobs`), not through a running landing: the landing's base lookup needs a github-actions `[ci]`, and the landing test world uses the command CI, so the lookup finds no source there and excuses nothing. The base lookup matches jobs by name in the 10 newest finished base runs, not by workflow. Nothing was run against real GitHub or star's real suites. The star `landing.toml` was not installed.
