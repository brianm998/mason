# s345: a test step's build suites run side by side

Summary: when a test step selects two or more suites whose run needs nothing but `compile` (and that have no `build` of their own), they run side by side before the step's other suites. Each runs in its own thread on its own lease, so the broker decides how many run at once: as many as there are free `compile` slots. The step's loop then takes their results in order, so reds, base-red checks, skip debts and the closing note work as before. Such a step also queues suite by suite (as with s340), so it holds nothing step-wide.

## Why

On 2026-11-14 a star test step (#293) ran `build-StarCpp`, `build-StarCore`, `build-cli`, `build-daemon` and `build-gui` one after another for about ten minutes. Each holds one `compile` slot, three were configured, and each builds its own package directory. Without a selected exclusive suite, star's step also held a single step-wide lease of everything, since none of its suites has a `build` key.

## What changed

- `crates/daemon/src/suites.rs`:
  - `compile_only` and `run_side_by_side` (in `std::thread::scope`).
  - `queues_per_suite` now also counts two or more compile-only suites, and `builds_per_suite` and `run` use it.
  - In `run`, a suite that already ran beside the others is not leased or run again.
- `crates/daemon/src/sched.rs`: `Broker::acquire_beside`. A step's extra concurrent requests are recorded in `lease_tasks`, as a `mason run` command's are, so they never take the step's own place in `by_task`. `acquire` is unchanged.
- `crates/daemon/src/jobs.rs`: `acquire_needs_beside`.
- Test: `a_steps_build_suites_run_side_by_side` (`crates/daemon/tests/scheduling.rs`). Each suite passes only if it sees the other start in the same attempt. Without the change it fails with `a:alone`.

## Not verified

On star's live queue. Two builds of packages that share a dependency each build it in their own `.build`, as they did one after another. Gradle and SwiftPM take their own locks if two suites ever build the same directory. Wait notices from suites waiting at the same time can end early: one suite's wait ending clears the task's wait note while another still waits.
