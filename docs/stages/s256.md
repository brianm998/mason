# s256: fewer develop tasks start while a project's check queue is long

Summary: admission does not start a project's next queued task while more than its limit of `run_check` and test-suite requests of that project are waiting (default twice the test-suite resource's count, or `[admission] max_check_queue`; 0 turns it off); tasks already running are unaffected, an urgent task is never held, and a held task's activity reads "held: N checks are waiting (limit M)".

Decision 0251 records the choices.

**What changed.**
- `crates/definition/src/model.rs`, `parse.rs`: the definition key `[admission] max_check_queue` (whole number, 0 = off; unset = the default).
- `crates/daemon/src/daemon.rs`: `check_hold` counts the waits of class `test-suite` or `test-small` of the project's tasks (a test step and a `run_check` both record their wait with that class), compares with the limit, and `next_admission` skips a held task. `check_hold_decision` is the pure rule. Admission runs after every event, so a task starts as soon as the count drops. The change stays in admission: `crates/scheduler/**` and `sched.rs` are untouched.
- `crates/daemon/src/http.rs`: the task view's activity for a held queued task.
- `scripts/exit/s256.sh` (protected).

**Not run.** Nothing was run: the unit tests (the decision, the definition key), the integration test the brief names (a queued task waits while the limit is exceeded and starts when it drops) and the exit script. The integration test was not written.
