# s1245: acceptance criteria name a check; develop reports and review grades per criterion

Summary: plan criteria are `{criterion, check}`; `submit_change` carries `criteria` (`met | not_met | partly` plus evidence, `notes` required for `not_met`); `submit_review` carries `criteria` (`agree | disagree` plus why). A `disagree` on a criterion develop marked `met` becomes a blocking finding and turns an approval into `changes`.

## Change

- `crates/adapter-api/src/contract.rs`: schemas and shape checks; 1 to 8 criteria; empty or copied check rejected.
- `crates/daemon/src/criteria.rs` (new): reading both plan shapes, count checks, the prompt table, folding review grades into findings.
- `crates/daemon/src/jobs.rs`: count checks on `submit_change` and `submit_review`, the table in the review prompt, grades applied before the verdict is recorded.
- `crates/daemon/src/diagnose.rs`, `plan_view.rs`, `views.rs`, `suites.rs`: the table in the diagnosis prompt and the plan view; the acceptance gate reads both shapes.

## Not done / not verified

- Plain-string criteria are still accepted by `submit_plan`, and develop is asked to report only when the plan's criteria are objects, so the scripted fixtures and exit scripts that submit string plans keep working. The schema offers objects only.
- `criteria` is not in `submit_change`'s schema `required` list for the same reason; the daemon requires it for object plans.
- Monitors: the table reaches them as plan-view text; no `clients/features.toml` change. A follow-up if a real table is wanted.
- Only `cargo check` was run locally; tests run on GitHub via `run_check`.
