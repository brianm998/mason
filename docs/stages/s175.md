# s175: Scheduled CI runs: dispatch a slow workflow when it matters, rerun failures once, file red and flaky tasks

Summary: a `kind = "ci"` schedule (off unless a project's overlay configures one) dispatches a workflow on the base branch at a time of day or every so often when the path rule says it matters, follows the run, reruns its failed jobs once and files one `Normal` task per red group and one `Low` task per flaky group (reds first, capped, deduped against open tasks and issues like the base-branch CI watch), so MASON can take over starpipe's nightly Gherkin dispatch.

Task #163. Decision 0170 records the keys and the choices the ticket left open.

## Built

- **Rules** (`crates/core/src/ci_schedule.rs`, no I/O, no clock): `decide` (in flight, same tip, never green, changed files against globs), `relevant_globs` (the `on.pull_request.paths` block list; empty or missing is an error), `path_matches` (GitHub semantics), `GroupBy` (`<group>/<leg>`), `classify` (red, flaky, infrastructure, unfinished), `group`, `select` (cap, reds first, covered groups free), the follow state machine `step` with the 3-day give-up, `due_at` for a daily local time.
- **Adapter** (`crates/adapters/src/github.rs`): `dispatch_workflow(file, ref, inputs)`, `workflow_file_runs(file, branch)` (all statuses, with event, run-name and attempt, in the new `WorkflowRun`), `rerun_failed(run)`. `base_runs`/`ActionsRun` are unchanged.
- **Store**: migration 26, `schedules.follow`; `ScheduleRow.follow`.
- **Daemon**: `schedule.rs` parses the `ci` kind (workflow, ref, inputs, run_name, at/every, paths/paths_from, group_by, max_tickets; unknown keys refused). `ci_schedule.rs` is the only I/O: git (fetch, tip, `show`, `diff`), the host (`Host` trait; GitHub, or a fake in tests), the filing. `ci_watch.rs`: `named_keys` and `emit_task` were extracted from `who_names` and `file_task` with no change in behaviour (the watch's tests are untouched and pass), and `source` takes the name of what needs the `[ci]` section. `introspect.rs` routes the kind: due by `at` or `every`, a followed run is looked at every tick without counting as the schedule running.
- **Status**: `mason schedule list` shows the kind and `[following run N]`; `mason status` prints `scheduled CI run in flight: <schedule> run N (waiting for ...)` (`ci_runs` in `/status`); `/schedules` carries `follow`.
- **fake-github**: serves `wf-runs.json`, `POST .../dispatches` (logs the body and adds `dispatch-run.json` to the runs), `POST .../rerun-failed-jobs` (logs it, swaps in `jobs-N-2.json`, sets `run_attempt` 2).
- **Tests**: 8 rule tests (core): decide for every case in the ticket plus cancelled, other run-names and no path rule; globs read from a workflow; glob semantics; `at` and the daily due rule across time zones; job-name splitting; classification and grouping; the cap; the follow steps and the give-up on an injected clock. 1 schedule parse test, 1 store test (the follow round trip), 1 adapter test over recorded responses (dispatch with and without inputs, runs newest first with event/title/attempt, rerun, a refused rerun), 9 daemon tests in `crates/daemon/tests/ci_schedule.rs` over a fake host: red twice files one task per group with legs grouped, red then green one `Low` flaky task, cancelled rerun and filed nothing, an all-green run is not rerun, the cap keeps reds first, a job an open task already names (as the watch files it) is not filed again and does not use the cap, a run that never completes is dropped after the limit (injected clock), a refused rerun is retried and a run rerun by hand is not classified, dispatch plus the follow state round trip through the store plus finding the new run on a later tick, globs from the workflow at the tip and an empty list refused, and a tick with no `ci` schedule makes no row. No timing assertions.
- **Exit**: `scripts/exit/s175.sh`.

## What testing found

- The fake host swaps in the second attempt's jobs on a rerun, which is what the real API does for `filter=latest`; the first attempt's failures must therefore be read before the rerun. The test with a refused rerun checks that the state stays at the first attempt.
- Clippy asked for `matches!` in `group`; fixed.

## The owner's cutover for star (not run; nothing in MASON touches star or `~/.config`)

Until these are done nothing here runs for star, and starpipe keeps dispatching.

1. Add to `~/.config/mason/projects/star.toml` (the project's `[ci]` must be `github-actions`):

   ```toml
   [schedule.gherkin-nightly]
   kind = "ci"
   workflow = "gherkin.yml"
   inputs = { features = "" }
   run_name = "Gherkin: full"
   at = "23:00"
   paths_from = ".github/workflows/gherkin-smoke.yml"
   group_by = "<group>/<leg>"
   max_tickets = 6
   ```

   `features = ""` is starpipe's dispatch (it sends `{"features": ""}`); drop `inputs` if the workflow's default is already empty. star's job names are `<feature>/<leg>` as the ticket says; starpipe's own code split `<leg> · <label>`, so check a recent run's job names and use `group_by = "<leg> · <group>"` if they are still the old form.
2. Set `gherkin_nightly_enabled = false` in `~/.star-pipeline/config.toml`.
3. Restart both daemons:
   ```
   launchctl kickstart -k gui/$(id -u)/com.brianm998.mason
   launchctl kickstart -k gui/$(id -u)/com.brianm998.starpiped
   ```

   Do 2 and 3 in one go with 1, so the two are never both on. `mason schedule list` should then show `star/gherkin-nightly`; `mason schedule run star/gherkin-nightly` starts it at once (a decision that says "not dispatched" is the rule working: nothing new since the last green full run).
