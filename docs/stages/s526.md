# s526: running steps read test_timeout_s and the other limits live

Summary: a step already running now reads `test_timeout_s`, `test_reruns`, `step_timeout_s` and `tool_timeout_s` from the live registry each time it uses them, so a registration reload reaches it without a restart.

## What changed

- `crates/daemon/src/jobs.rs`: `Ctx::live()` returns the project as registered now (falling back to the step's copy if the project is gone). The test timeout of a check, the test reruns, the agent's tool timeout and step budget, and the limit of a hosted command are read through it. `Ctx.project` stays the copy made at start and is still used for path, base and remote. The first time a live limit differs from the start value, one `info` line says so (was, now).
- `crates/daemon/tests/stop.rs`: `a_running_step_reads_limits_changed_by_a_registration_reload` builds a step's `Ctx`, changes `test_timeout_s` through `reload_registration`, and checks `live()` has the new limit while the copy keeps the old one. No timing assertions.
- `scripts/exit/s526.sh` runs that test.

## Not verified

- A host already spawned keeps the deadline it was started with: `step_timeout_s` is read live when an agent host starts (and again if it is restarted), not changed in a process already running.
- No real running step was observed picking up a reload; only the `Ctx` accessor is tested.
