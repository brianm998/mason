# s1088: a CI run MASON stops waiting on is cancelled

Summary: A landing or debt CI run that MASON stops waiting on without a verdict (timeout, error, Land now, an abandoned batch, a superseded or red pull request) is now cancelled before its branch is deleted, and the batch's note says how many runs were cancelled.

- `BuildSystemAdapter::cancel(run, git_ref)` is new; its default does nothing, so Jenkins, generic and plugin CIs are unchanged.
- GitHub lists the runs by `head_sha` (or by `branch` when no commit is known) and cancels only the unfinished ones whose `head_branch` is that ref. `mason/ci/**` keeps the rules of `may_cancel` (no pull-request runs, through `cancel_own_run`); `mason/pr/**`, MASON's own pull-request branches, includes the pull request's checks. Every other ref is left alone.
- The command CI takes an optional `[ci] cancel` command (`MASON_RUN`, possibly empty, and `MASON_REF`; it may print the number cancelled). It is also how the tests record cancels.
- `landing.rs`: `ci_verify`, the pull-request path and `remove_refs` cancel before deleting. The ref of a pull request that merged is not cancelled.
- `suites.rs` (protected): the debt CI run is cancelled when its wait ends in an error. No verdict changes.
- A failed cancel is logged and changes neither verdict nor error.

Tests: `crates/daemon/tests/it/ci_cancel.rs`, three tests at the end of `crates/adapters/tests/github.rs`, and `scripts/exit/s1088.sh`.

Not verified: anything against the real GitHub API (the adapter is tested with recorded responses). A run GitHub has not yet created when MASON gives up (Land now seconds after the push) is not found, so not cancelled. The pull-request modes cancel only when the project has a `[ci]` section of a kind that can cancel. A debt run left by a daemon that died mid-wait has no ref row and is still not cancelled.
