# s72: CI green again, and the queue counts slots held outside it

Summary: CI on `develop` was red from s60 on: tests that merged without a git identity, a demo banner whose clock text differed between two demo runs, an exit script that ended itself on `wait`, and rustls versions with advisories. The broker now counts machine slots held by processes it has no lease for, so it no longer grants them again.

Done by hand on the owner's request, outside the pipeline. The numbers 72 and 0058 were reserved in the store under task 900072 (standing in for the owner) after checking that no task's open question names them.

## Why

GitHub Actions on `develop` was red from `1fc5826` (s60) on, and every job failed from `94b66cc` on:

- **`test`:** `a_branch_that_conflicts_with_the_base_goes_to_the_agent_to_merge_and_lands` (s60) and s69's conflict tests ran `git merge` in the fake agent without a committer identity. A developer's machine has one; a CI runner does not ("Committer identity unknown"), so the agent never submitted and the task failed.
- **`monitor-swift`, `monitor-compose`, and s49 in `test (macos)`:** s67 (account holds) made the demo hold `claude-full` until `now + 2 h 10 m`, and the header banner says "resets Sun 16:35 UTC (in 2 h 10 m)". The exit scripts record the expected views and the client's capture from two separate demo runs, minutes apart, so the two banners named different times.
- **s49 itself:** `stop_demo` killed the demo with SIGKILL and then ran `wait`, which returns 137. Under `set -e` that ended the script right after step 1's capture, before its checks ran, with no message. The line was rewritten on 2026-11-07 to drop a `|| true`.
- **`lint`:** Stage 24 added rustls 0.23.43 and rustls-webpki 0.103.15, which have five RustSec advisories (RUSTSEC-2026-0285, -0346, -0348, -0349, -0382); `cargo deny` fails on them.
- **On the owner's machine, not in CI:** after the daemon updated itself, a `mason run` started by the old daemon (a develop agent's `run_check`, whose test had hung) kept its compile slot. The new broker had no lease for it and counted the slot free, so it granted it again and again. Every grantee failed with "a slot is held by another process": task #27's test step spent its whole timeout this way.

## What changed

- `crates/daemon/tests/e2e.rs`: the fake agent's `git merge` passes `-c user.name=t -c user.email=t@t`, as its commits already did. Checked by running the e2e tests with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1`.
- `crates/conformance`: `steady` takes the clock out of a banner (the time of day, the weekday before it, and an `(in …)` countdown), and `compare` uses it for `banner:*` items only. Every other item still compares its text exactly, and a banner must still say the same thing about the same account.
- `scripts/exit/s49.sh`: `stop_demo` accepts exactly 137 from `wait` (the SIGKILL it just sent), nothing else.
- `Cargo.lock`: rustls 0.23.46, rustls-webpki 0.103.16.
- `crates/daemon/src/jobs.rs`: the uncommitted-work check `prepare` gained in s69 (`6673885`) runs `git --no-optional-locks status`. A plain `git status` takes `index.lock` to refresh the index, and an agent still winding down in the same worktree (its step just superseded by explore-anyway) failed its own commit on it. `explore_anyway_before_a_task_starts_and_after_it_skipped_exploring` failed this way in CI on macOS. Eight copies at once, three rounds: 10 of 24 failed with `index.lock` before the change, 0 of 24 after.
- `crates/daemon/src/sched.rs`: each scheduling pass compares, for every machine class, the slots the kernel says are held with the leases that hold their locks, and adopts the difference as holders "held outside the queue" (named by the slot's holder label in `mason resources`). They count against the class until the kernel says the slot is free.

## Tests

- `conformance`: `a_banner_is_compared_without_its_clock`.
- `sched`: `a_slot_held_outside_the_broker_is_not_granted_again`: a slot taken by another `Locks` (as a process from before a restart would) is counted, a second lease waits, and it is granted once the outside holder lets go.

## Exit test

`scripts/exit/s72.sh` runs the two tests, the conflict e2e tests without a git identity, and `cargo deny check advisories` when cargo-deny is installed.

## Not done, not verified

- A develop agent's `run_check` runs its command as a child of `masond`, outside any step host. When the daemon replaces itself (a self-update), the thread that would time it out is gone, and a hung command runs on. That is how the stale slot came about. This change keeps it from blocking the queue, but does not stop or collect such a command; running `run_check` under a step host would.
- The owner's `mason-queued` wrapper still treats "could not take the granted resources" as the daemon being unreachable and queues again. With the broker fixed, the error should no longer come up.
- CI was not run before pushing; the jobs were reproduced locally where they could be (s12 and s13 locally run the Swift and Compose halves; Linux was not available).
