# s379: the LAN listener names extra hosts and can bind chosen addresses

Summary: `[lan] hosts` adds names (a Tailscale name) to the pairing URL as `alt=` and to `GET /lan`, `[lan] bind` picks the addresses to listen on (default `0.0.0.0`), `mason lan status` shows both, and the Swift and Compose cores parse `alt=` and order addresses with `Reach.order`.

## What changed

- `crates/daemon/src/config.rs`: `LanCfg` gains `hosts` (letters, digits, `.`, `-` only, duplicates dropped) and `bind` (non-empty list of IP addresses); both strictly parsed. `LanCfg` is no longer `Copy`.
- `crates/daemon/src/lan.rs`: one listener per bind address, the same router and TLS (with port 0 the first picks the port and the rest reuse it); `reach_hosts` and `pair_url`; `POST /pair/codes` and `GET /lan` return `hosts` (and `/lan` returns `bind`).
- `crates/cli/src/main.rs`: `mason lan status` prints hosts and listening addresses.
- `clients/swift` and `clients/compose/core`: `PairURL`/`PairUrl` read `alt=`; `PairedDaemon` keeps `alternates`; pure `Reach.order(paired:, bonjour:)`.
- `docs/install.md`: reaching the daemon through Tailscale.
- `scripts/exit/s379.sh` (new; s24.sh is untouched): two bind addresses (127.0.0.1 and 127.0.0.2, else ::1), a fake phone pairs through the second.

## Not verified

- The Swift and Kotlin tests were written but not run here (no run of `swift test` or Gradle). The Swift `PinningDelegate` answers the server-trust challenge itself and never falls back to default host name validation, so a name that is not in the certificate still connects when the pin matches. That was read, not exercised.
- No real Tailscale network, phone or interface other than loopback was used. The certificate still names only `<host>.local` and `<host>`; pinning makes that irrelevant.
- The mDNS record is unchanged and advertises on all interfaces regardless of `bind`.
