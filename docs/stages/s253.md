# s253: a test that flakes in three tasks is quarantined by MASON, with one task to fix it

Summary: a test with flaky records from three or more distinct tasks within seven days, that is not quarantined and that its suite has been seen to pass, is quarantined for 14 days (owner `mason`, reason `auto: flaky in N tasks since <date>`) and one task, "flaky: <suite> <test>", is filed at normal priority; the quarantine is lifted when that task lands.

Decision 0248 records the choices.

**What changed.**
- `crates/daemon/src/autoquarantine.rs`: the rule. `consider` runs right after flakes are recorded, in the suites path and in the command path; it counts distinct tasks in the window, checks the seen-passing guard and the quarantine already in force, validates the quarantine with the gate's own `check_quarantine`, files the task (not again while one with that title is open) and writes the quarantine. `to_lift` and `lift_landed` remove an automatic quarantine whose task has landed; the sweep calls it.
- `crates/store`: migration 32, `seen_passing` (suite, test), filled with the names of every green suite run; `seen_passing` also counts a name that a base run listed and did not fail. `flaky_tasks_since` reads the flake log with its task.
- `crates/daemon/src/suites.rs` (protected): a green run notes its test names as passing; a flaky class calls `consider`. No verdict changes.
- `crates/daemon/src/jobs.rs`: the command path's `record_flaky` calls `consider`.
- `crates/daemon/tests/auto_quarantine.rs`, `scripts/exit/s253.sh` (protected).

A quarantined test still runs and is reported; it stops deciding the step through the existing `RedClass::Quarantined`.

**Not verified.** The lift on a landed task is tested on its selection, not by landing a real task. The quarantine reason carries the task as a suffix (`; task #N`) after the required text so the lift can find it. The command path (no suites) never notes passing names, so a test there is not auto-quarantined until a suite run has seen it pass.
