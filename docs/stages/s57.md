# s57: Deep and light tiers with effort levels, mapped by each provider's config

Summary: pipelines say `deep` or `light` and `low`, `medium` or `high`; each provider's built-in table, `providers/<provider>.toml` and the project file's `[provider.<provider>]` say which real model and effort that is, for Claude and Codex alike (`fast` still means `light`).

Task #26.

## Built
- `crates/definition/src/tiers.rs` (pure): `Tier`, `Level`, `Entry`, `Mapping` with a source per entry, built-in tables, `parse_table`, `launch` (requested tier/level plus explicit model/effort to the real model and effort) and `describe` (the reverse lookup for display).
- `layers::resolve` yields the requested tier and level (with sources) and only explicit real model/effort; `builtin_profile` is gone. Validation: `Capabilities::with_efforts`, effort errors, `validate::warnings`.
- Daemon `providers.rs` reads the files; `jobs.rs` no longer special-cases Codex. `mason doctor` prints the effective mapping per provider with sources, file problems and definition warnings. `mason config show` shows tier and level. Adapters export `EFFORT_LEVELS`; `fake-claude` records its argv like `fake-codex`.
- Decision record: `docs/decisions/0035-tiers-readings.md`. `docs/DESIGN.md` updated.

## Trust files touched (owner approval)
Definition validation (`crates/definition/src/validate.rs`: effort check, tier check, warnings) and the configuration layers (`layers.rs`: requested tier/level, explicit-model precedence). Both are needed because the abstract levels and the tier names have to be accepted and checked where definitions are, and because `resolve` is where precedence lives. `.mason/mason.toml` is untouched.

## What testing found

- The scripted agents keep a turn count and argv log beside their script, so the exit test removes them between phases.
- `cargo test --workspace` under load (other sessions share this machine) failed wall-clock tests that pass alone: `when_a_step_ends_the_next_task_is_admitted_within_100_ms` (also over 100 ms on the base commit in another worktree, and failed again here once at 202 ms), `admission_respects_the_concurrency_limit`, `an_update_while_an_agent_session_runs_does_not_interrupt_it`, `a_schema_mismatch_is_named` (2 s limit). Each was rerun alone; all but the first passed; the first passes about two times in three.
