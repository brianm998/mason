# Task dependencies (s42): Task dependencies (GitHub issue #7)

The base is Stage 20 (3847064). The engine already had blockers (`TaskFiled { blockers }`, `Activity::Held`, release on landing); nothing could create them. Now every filing path can, GitHub's "blocked by" is read, and both monitors show it.

## Built
- **Body parser** (`crates/definition/src/filing.rs`): `dependencies(body, own_repo)`. `Depends on #3, #4`, `Blocked by #5`, own-repository URLs; other repositories, fenced blocks and inline code are skipped. `mason help filing` explains `--after` and the body lines.
- **Engine**: `EventKind::BlockerRemoved` (proposed or queued only), `ReduceError::BlockerCycle(path)`; the store codec, the state-by-event matrix and the event text in the views know it.
- **Store**: migration 10, `tracker_deps(project, number, blocker_number)`.
- **Tracker adapter API**: `TrackerCaps.dependencies`, `Blocker { number, open }`, `TrackerAdapter::blocked_by` (default: none). GitHub reads `/issues/{n}/dependencies/blocked_by`, dropping other repositories' issues. `tracker_kit` checks it; recorded in `fixtures/github/tracker_kit.json`.
- **Tracker import** (`crates/daemon/src/tracker.rs`, `sync_with_deps`): native and body blockers, import in dependency order (repeated passes), cycle and outside-blocker alerts, `BlockerAdded` / `BlockerRemoved` for changes on GitHub, drift alert for a started task, canceled-blocker alert. Dependencies are re-read on a timer and on refresh even when the listing's ETag is unchanged. Imports are serialised.
- **Filing**: `mason task add --after 3,4`, `AddTask.after`, `"after": [..]` in `POST /tasks`; unknown, canceled or failed ids are refused naming the id. `mason task show` lists `blocked by` and `blocks`; `--json` has `blocked_by` and `blocks`.
- **Views and monitors**: `TaskRow.blocks`; the task page of both monitors shows `waiting for #N` and `blocks #M`; the conformance items and `features.toml` (`task-dependencies`) match. `mason.pb.swift` regenerated.
- **Fake GitHub** (`crates/adapters/src/bin/fake-github.rs`): a loopback HTTP server over a directory of JSON (issue listing with a content ETag; dependencies, which can change without the ETag changing; comments; closing).
- `scripts/exit/s42.sh`, `scripts/exit/fixtures/s42/`, `docs/decisions/0020-task-dependencies-readings.md`.

## What testing found
- **A real race.** The first run of section 3 imported each issue twice: the poll thread and `mason task refresh` both ran a poll and both saw the issue as new. This existed before (the window was a few milliseconds); the dependency lookups widened it. Polls are now serialised.
- Task ids follow dependency order, not listing order, even among issues that are not related to each other in the same listing (a blocker is imported in the first pass, its dependent in the second). The script looks tasks up by title for that reason.

## Tests
Unit tests: the body parser (lists, other repositories, own URLs, fenced and inline code, CRLF); the engine (removal releases and wakes; a started task is not pulled back; the cycle path); the codec round trip; the state-by-event matrix; GitHub's `blocked_by` on recorded responses; and daemon tests of the import (order whatever the listing order, an open blocker that is not a task, closed blockers, cycles, add/remove/started, canceled blocker).

## Not done, and not verified
- **Nothing was run against real GitHub.** The dependencies endpoint and its response shape (`number`, `state`, `repository_url`) are from GitHub's documentation as remembered, not from a capture. The recorded responses and the fake server are written in that shape; if the real API differs, only `GitHub::blocked_by` changes.
- **The Compose monitor was not built** and its UI test was not run (no Android or Gradle build was attempted here); the Kotlin change mirrors the Swift one and the Kotlin item builder. Swift compiled (`swift build`); the SwiftUI page was not looked at and its UI tests were not run. The conformance check of the two item lists (`mason-conformance features`) passes, which is a text parity check, not a rendered one.
- **Dependency lookups cost one request per relevant open issue per changed listing.** Fine for a stage chain; not for hundreds of issues.
- **A body line naming an old issue the listing has paged out is treated as satisfied** (see decision 0020).
- **`--after` is only at filing.** There is no command to add or remove a blocker afterwards (`BlockerAdded` is reachable only from the tracker sync).
- **Release on landing was timed only to the second** (the script says 0s); the engine test shows the wake effect in the same transaction.
