# s242: the broker runs one scheduling pass per tick and probes lock files outside its lock

Summary: Waiting jobs now share one scheduling pass per tick instead of each running its own, and the lock-file probes (`Locks::alive`, `Locks::slots`) run with the broker's mutex released.

**Cause.** Each waiter in `Broker::acquire` ran the whole `pass`, with file I/O, under `self.st` ten times a second, so W waiters meant about 10·W identical serialized passes, and every grant's `notify_all` made each of them run another.

**Change** (`crates/daemon/src/sched.rs` only). A waiter skips the pass when one has run since its last wake-up; releases and submits still pass at once. The probes are read with the lock released (ids and classes copied out, probed, the lock re-taken, results applied, ids that have gone ignored). `acquire` keeps the `holds(id)` check and `wait_timeout` under one hold. Ranking and grant order are unchanged. The wait snapshot from #0229 is published at the end of each pass.

**Tests.** `one_pass_serves_every_waiter_per_tick` counts passes with 30 waiters; `readers_and_release_do_not_wait_for_a_blocked_lock_file_probe` blocks a probe and checks the readers and release, with bounded joins that only report failure. Existing broker tests are unchanged. Exit: `scripts/exit/s242.sh`.

**Not verified.** The live 30-job case on `/Volumes/sp`. The previous full-workspace run ran out of time while tests were still passing; it showed no failure.
