# s819: set the placement mode from the monitors

Summary: both monitors show the placement mode and its source for MASON (home), a project and a task, and the owner sets or clears each from a "Runs on" control; the protocol is version 2 and masond carries the mode in the header, home and task views and takes a typed `SetPlacement` command.

Task #834. Decision 0812.

## Built
- `schemas/mason.proto`: `SetPlacement` (command 23: scope `global|project|task`, project, task, mode or `default`), `Placement` (mode, source, own, settable), `ProjectPlacement`; `HeaderView.project_placements`, `HomeView.placement` and `.project_placement`, `TaskDetailView.placement`, `TaskRow.run_on_override`. All additive. `PROTOCOL` is 2; `MIN_PROTOCOL` stays 1, so a version-1 monitor still connects, shows no control and cannot send the command.
- `place.rs`: `task_placement`, `project_placement`, `global_placement`; `clear_project_mode` (removes `[remote_runs] mode` and the old `fallback`). `POST /remote` with `"mode": "default"` and a project clears it. The store has `task_overrides_for_key`, so a view build reads every task's `run_on` once.
- `ws.rs`: `SetPlacement` maps to `POST /remote` (global or project) and `POST /tasks/N/run_on`, so the owner-only rule is the CLI's.
- Swift (`MonitorCore/Placement.swift`, `PlacementControl` in `MonitorUI/Pages.swift`) and Compose (`core/.../Placement.kt`, `PlacementControl` in `app/.../Pages.kt`): home (global, plus the project when one is selected), task page; each shows "favor-remote, from the project", the four modes, "Follow MASON" / "Follow project" (only while the level has its own choice), a one-line confirm and the pending label. Shown only when `canAct`. The task row shows "runs on <mode>" when the task overrides its project. The Android phone shows the global mode as a line, with no control (`clients/features.toml`: `placement-control`, android todo).

## Tests
- `placement_monitors` (daemon, `it`): the views carry mode and source at each level; a non-owner's three sets are refused and write nothing; the owner's project set is written and shows source `project`; `default` clears.
- `PlacementTests` (Swift MonitorCore), `PlacementTest` (Compose core), `PlacementControlTest` (Compose, offscreen).
- Exit test `scripts/exit/s819.sh`.

## Not verified
- Nothing in Swift or Compose was compiled or run locally (no network for the Swift package fetch, and the shell refuses tests); the pipeline's checks are the first build of those files. `mason.pb.swift` was regenerated with the installed `protoc-gen-swift`.
- The exit script sends the HTTP calls `masond` maps the typed command to; it does not drive a WebSocket client. The `call_for` mapping itself has no test of its own.
- The views tests are integration tests (`it`), not unit tests in `views.rs`: building a view needs a `Daemon`.
- The Swift confirm is an `.alert`, the Compose one an `AlertDialog`; neither was rendered. No project list page exists in either monitor, so the project control is on home when that project is selected.
- The "Runs on" marker is not on the iPhone's `PhoneTaskRow`.
