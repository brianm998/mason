# Stage 14: Landing engine, direct and local-only

## Built
- **`crates/landing`**: `config` (`.mason/landing.toml`: mode, base, window, `max_size`, `parallel`, tiers, red ladder, resolver, `max_fold`; every mistake named; a tier that names `ci` is refused under `direct` and `local-only` with a pointer to the CI mode; later modes parse but are refused with "arrives in Stage 15"), `plan` (pure: batch formation, footprint overlap, blame by impact, bisection, whether a moved base needs re-verifying; property-tested), `batch` (the integration branch: assemble, resolver hook, union diff, fold in a moved base and promote), `promote` (fast-forward the base by push or compare-and-swap, shared with the single-task lander).
- **`crates/daemon/src/landing.rs`**: a coordinator per project that forms batches from the landing queue, runs disjoint ones in parallel, walks the red ladder, promotes under the repository lock, runs the post-land tier, freezes landing on a red and files a top-priority fix task, and acts on land-now and force. Landing jobs now wait on it instead of landing one by one.
- **Store migration 7** (`batches`, `freezes`, `landing_flags`), `GET /landing`, `mason landing`, the queue-idle metric, and `LandingView` extended with modes, batches (phase, landed, parked), freezes and idle time. The **Landing page** of both monitors shows them.
- `docs/decisions/0011-landing-readings.md`, `scripts/exit/s14.sh`.

## Exit test
`bash scripts/exit/s14.sh` passes:
```
== 1. a batch of five: three land, the conflict and the culprit are sent back
== 2. disjoint batches run in parallel, overlapping ones wait
== 3. kill -9 at every landing phase of a batch with a culprit
== 4. the rest of the engine
```
Five tasks form one batch: `t1` and `t2` add files, `t3` and `t4` edit the same line (`t4` is ejected for the conflict), `t5` makes the integration suite red. The suite goes red once over the union; the ladder reruns it, blames by impact (every task impacts it, so no one is blamed yet), bisects, and names `t5`. `t1`, `t2`, `t3` land in one fast-forward; `t4` and `t5` are sent back, each with its own reason; the integration branch is gone and the owner's checkout was never touched. For the crash run, the real `masond` is killed at `batch_formed`, `batch_merged`, `batch_red`, `batch_verified`, `batch_before_promote`, `batch_after_promote` and `land_before_event`, restarted, and in every case the clean task is on the remote exactly once, the culprit never is, the log and projections agree, and no integration branch is left behind.

## What testing found
- **Land now and force order matters.** My first land-now/force test put both marks on at once; when the forced red landed first, the verification of the land-now task rightly failed on a red base. The test now marks them one after the other.
- **A suite host's id names one run.** The bisection ran the suite over several subsets with the same id prefix, so later runs got the first run's result and the culprit was never found. Each run now has its own id.
- **A crashed batch left its integration branch behind**, caught by the crash test's cleanup check. Recovery now sweeps `mason/int/<project>/*` when a project's coordinator starts.
- **`ls a b` fails if either is missing**: the first test suite script looked for marker files that way and never saw them; the culprit landed. It was the test script, not the engine, and the batch's recorded notes (`integration: green, 1 tests ran`) made it visible at once, so the notes of a green run are now kept on the batch.
