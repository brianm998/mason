# 0008: Readings made while building the protocol, views and parity tooling (Stage 11)

Where the plan or design left room, Stage 11 chose the following. Any can be overruled.

- **The schema is compiled by `protox`, a protobuf compiler written in Rust.** So
  building MASON needs no `protoc`, on CI or on a contributor's machine. `prost`
  generates the Rust types and `pbjson` the proto3 JSON mapping from the same
  descriptors. Swift is generated by `scripts/gen-clients.sh` with `protoc` and
  `protoc-gen-swift` where they are installed (the result is checked in under
  `clients/swift/Sources/MasonProtocol`); Kotlin needs the Wire compiler
  (`WIRE_COMPILER_JAR`) and is generated only where that exists. The script says
  which it could not do. CI cannot check that the committed Swift is current, since
  it has no Swift plugin; the Swift client's own build (Stage 12) will.
- **Commands are typed for what a monitor offers, and `Raw` reaches the rest.** The
  typed ones are the actions in `allowed_actions` plus add task, pause, resume and
  limits. `Raw` (an HTTP-style method, path and JSON body) is what the command line
  uses for everything else. Both run through the **same router as the HTTP API**
  (the socket calls it in process), so there is exactly one implementation of every
  operation, the intervention record sees every command, and nothing a monitor can do
  is out of the command line's reach. Typed commands that act on a task are refused
  unless the action is in the task's current `allowed_actions`.
- **The command line speaks the protocol.** It connects, says hello with
  `commands_only` (no snapshot, no pushes), sends one `Raw` command in the JSON
  encoding, reads its result and goes. The HTTP API is still served, for `curl` and
  debugging, but nothing in MASON depends on it.
- **Resume rules.** A client says hello with the last sequence number it saw.
  `0`, a number the daemon has never reached (its data was reset), or more than 2000
  events behind: a **snapshot** of the subscribed views. Exactly up to date: nothing.
  Otherwise: **only the events after its number**, followed by the views as they now
  stand (a client cannot rebuild a view from event summaries). Views carry the
  sequence number they were computed at. The event log is append-only and kept, so
  "events" is always possible within the limit.
- **Encoding is decided by the first frame**: binary is protobuf, text is the proto3
  JSON mapping, and the daemon answers in kind.
- **Pushes.** An in-process bus carries every appended sequence number (and a poke
  for changes that are not events: a pause, a limit). The socket coalesces a burst
  into one update, then sends the new events and recomputed views.
- **`allowed_actions` is one function** (`views::Ctx::allowed_actions`) of the task's
  state, whether it waits on an approval, and whether it skipped exploring. Every view
  uses it and the socket enforces it.
- **Progress cells come from the task's pinned definition.** Filled: a succeeded run
  of that step. Part: the current step, running. Hatched: the current step waiting,
  labelled with the wait's own sentence. Empty: not started. There are no
  percentages. "Usually 15 to 20 min" and the amber "slow" flag appear only with at
  least five samples from the project's own history; durations are approximated by
  the gap to the task's next step start, so they will be rare until step ends are
  recorded directly.
- **Sidebar order is the protocol's, not the client's.** Needs-you first, then queued,
  exploring, developing, testing, review, landing, proposed, then failed, landed and
  canceled (history). Active states sort oldest first by enqueue time (ties by id);
  history sorts newest first and starts collapsed.
- **Views that are thin today say so** instead of faking data: the landing view has
  debts and a note that batching arrives in Stage 14; the usage view has session
  counts and a note that token windows come with usage tracking.
- **`masond --demo` plays a script of real events** (the same kinds the pipeline
  appends) into a scratch store: no projects, agents or git, so the views, protocol and
  commands are the real ones. The script has eight checkpoints (an empty daemon, five
  tasks filed, three admitted, a question asked, a wait on a compile slot, a failure,
  a landing). By default it advances on a timer; `--demo-manual` advances only on
  `POST /demo/next`, so a test can stop at each checkpoint.
- **The conformance runner reads views into items** (`tile:testing`, `row:queued:7`,
  `card:2`): the texts a person can read in each and the actions it offers. A client's
  accessibility tree is read into the same JSON; `conformance check` requires every
  expected text to be shown, the actions to match exactly, the order of sections and
  rows to be the server's, and no row or card the server did not say is there.
  Decoration is allowed. A collapsed section shows no rows.
- **Feature parity.** `clients/features.toml` gives each feature a status per client
  (`done`, `todo`, `n/a`). Uneven statuses fail unless there is a `platform_reason`,
  and `n/a` always needs one. It starts with the eighteen features of Part 17, all
  `todo`; the clients flip them as they build.
- **One token file** (`clients/tokens.toml`: light and dark colours, sizes, motion)
  generates `MasonTokens` constants for Swift and Kotlin; CI regenerates and fails on
  a difference.
- **Loopback only, for now.** The daemon binds 127.0.0.1. LAN access, pairing and
  tokens wait for Stage 24; the hello's `token` field is reserved and ignored.
- **Two fixes the latency target forced** (decision 0005's session rule, adjusted):
  a task counts against LLM sessions only while its current step is an *agent* step,
  so a task that has moved on to testing no longer holds a queued task back for the
  moment before its test step asks for resources; and a step's resources are handed
  back as it reports its result, not when its thread winds down. A lost wake-up in
  the broker (a release landing between a waiter's check and its wait) cost up to a
  tenth of a second and is closed. Handing a session to the next task now takes
  about 15 ms, down from about 70.
