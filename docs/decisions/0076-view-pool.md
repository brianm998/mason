# 0076: Screens get their own worker pool; an unservable monitor is retried or closed, never blanked

The one blocking pool also runs handlers that wait on git and repository locks, so four stuck handlers made `Pool::spawn` return `Busy` for the view computation too, and the monitor got an empty snapshot or lost updates. View computation, event reads and `/status` now run on a separate two-thread pool. If that is also busy, a session keeps a "views owed" flag and retries every 100 ms; a connecting client waits 5 s and is then disconnected rather than sent an empty snapshot, because a closed socket is something the client already handles and reports, and an empty screen is not. Alternative rejected: making the one pool bigger, which only moves the threshold. Pool queue depth is in `mason status` so a stuck pool is visible. No gate, guard, budget or trust file changed.
