# 0011: Readings made while building the landing engine (Stage 14)

Where the plan or design left room, Stage 14 chose the following. Any can be overruled.

- **Batch state lives in the store's own tables, not in the event log** (migration 7: `batches`, `freezes`, `landing_flags`), like debts, pauses and alerts. The plan sketched `BatchPhase` events; but a batch describes the pipeline, not a task's progress, no reducer rule depends on it, and every landing step is idempotent, so replaying a log of phases would add nothing recovery does not already do by itself. A task's own outcome (sent back, landed) is still an event, as before.
- **One coordinator thread per project, one thread per batch.** Landing jobs (one per task in the landing step, as before) join a per-project queue and wait for their verdict; the coordinator forms batches (`plan::form_batch`: by rank, the window running from the oldest waiting task, a full batch going at once) and starts each on its own thread in the lowest free integration slot. A daemon restart re-queues every task still in the landing step, and batches a dead daemon left unfinished are marked `abandoned` and their integration branches swept.
- **The integration branch is `mason/int/<project>/b<id>` in a persistent worktree per slot** (`<landing dir>/<project>-b<slot>`), reset to the base tip on every assembly. `clean -fd` runs without `-x`, so ignored build caches stay and builds are incremental.
- **A batch's footprint is the paths it changes plus the suites the impact map selects for them.** Two batches may run together only if neither shares a file or a suite with the other, up to `parallel`. A task whose paths the impact map does not know impacts every suite (as elsewhere), so it overlaps with everything.
- **The suites run once over the union, through the existing suite machinery** (parsers, proof, environments, evidence by tree, broker leases), as runs that belong to no task, so nothing can skip them. A tree that was green is not run twice, whoever asks.
- **The red ladder walks the configured rungs in order.** `rerun-failed` runs the red suites once more (green: noted as flaky, the batch goes on). `blame-by-impact` points at the tasks whose changes impact a red suite; it is used only when that is a strict subset of the batch (or a batch of one). `bisect` tries the first half, then the second, each as its own assembly and run; if each half is green alone but the whole is red (an interaction), it stops without a culprit. `ask` is the end: the batch's tasks go back with the evidence, nothing lands, and the owner is told by the same task state and an alert as any other failure. A task is only parked for a red it can be shown to have caused, except at that last rung.
- **A conflict inside a batch ejects only that task** (merged in rank order, so the earlier of two conflicting tasks lands and the later goes back). A `resolver` command in `landing.toml` may resolve it in the integration worktree first; it succeeds only if it exits 0, leaves no conflict markers, and the merge commits. The resolving *agent* plugs in there; the engine does not start one itself in this stage.
- **Promotion is under the repository lock, by fast-forward only** (`promote::promote`, shared with the single-task lander). If the base moved, it is folded into the integration branch; the suites run again only if a moved path is one the batch touches or impacts a suite the batch selected (`plan::needs_reverify`). A red after the fold, or a conflict with the moved base, makes the batch assemble again on the new base, where the conflict shows up as an ejection and the red is blamed properly. At most `max_fold` (default 3) moves are followed.
- **Without a batch tier in `landing.toml`, landing re-verifies a moved base with the test step's command, as before**, so a project that has not written a `landing.toml` lands as it did in Stage 7, one task at a time per look at the queue.
- **`local-only` stops at the local base branch** (no fetch, no push) and refuses if the base is checked out; modes that use CI, and `pr-each`, `pr-batch` and `host-queue`, parse and validate but are refused with an error naming Stage 15. A tier that names `ci` under `direct` or `local-only` is refused with a pointer to `direct-ci` or `local-only-ci`.
- **The post-land tier runs on the base after it moves**, in a throwaway worktree. Red with `on_red = "freeze"` freezes the project: only its fix task (filed at the same moment, top priority) is batched until a post-land run is green, which lifts the freeze. A forced landing passes a freeze.
- **Land now and force are marks the task carries** (`landing_flags`) plus the debt the endpoints already recorded. Land now makes its own batch at once (still verified); force skips verification and the freeze. A mark is cleared when the task lands.
- **Queue idle time** is the time tasks waited with no batch running (window waits and freezes included), per project, in `mason metrics`, `mason landing` and the Landing page.
- **The Landing page** (both monitors) shows the modes, any freeze, the queue, the last batches with phase, who landed and who was parked, the idle time, and debts. It is not part of the conformance items yet: those cover the pages the demo script drives.
