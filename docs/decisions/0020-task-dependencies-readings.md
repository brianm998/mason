# 0020: Readings made while building task dependencies (Task dependencies (s42))

Where GitHub issue #7 or the design left room, Task dependencies (s42) chose the following. Any can be overruled.

- **Two sources, joined.** An issue's blockers are GitHub's native "blocked by" relationship (`GET /issues/{n}/dependencies/blocked_by`) **and** `Depends on #N` / `Blocked by #N` lines in its body, as a union. The body is a fallback, not a second opinion: it is not consulted only when the native list is empty. Reading the body means both can be wrong the same way, but a chain written either way works, and removing a blocker means removing it from both.
- **What a body line is.** Case-insensitive `depends on` or `blocked by`, followed by a list of references (`#3, #4`, `#3 and #4`, `#3 & #4`, an optional colon). A reference is `#N`, `owner/repo#N` or a URL. Only this project's repository counts (`#N`, a `github.com/<repo>/issues/N` URL, or `<repo>#N`); another repository's reference is read and skipped, because there is no task to wait for. Fenced blocks (``` and ~~~) and inline code spans are removed first: text quoted as code is not a statement. The parser is `definition::filing::dependencies`, with unit tests.
- **Where a blocker stands.** A blocker number resolves to: a **task** (an imported tracker row: held until it lands), an **open issue that is not a task yet** (the dependent is not imported and is looked at again next poll, so import order follows dependency order, within one listing too: the import repeats until a pass imports nothing), or **nothing to wait for** (closed before it was ever a task, or not visible in the listing and not open according to GitHub). A closed issue that was never imported is treated as satisfied: there is no work of ours to wait for. An open blocker that cannot be imported (an unlabeled outsider's issue, another repository's) leaves the dependent unimported and raises an alert naming both, rather than quietly starting it.
- **Closed as completed counts as landed only if its task landed.** A closure on the tracker already cancels a live task (Stage 15), so a blocker closed there without landing is a **canceled** task. A canceled blocker never lands, so the dependent **stays held and an alert says which task is held by which canceled one** and that the dependency must be removed to release it. It is not released automatically and not canceled with it: that is the owner's call.
- **`--after` and the filing API refuse a canceled or failed blocker, naming its id**, and an unknown id. A `failed` task can be retried, but a task filed to wait for one would be held for an unbounded time with no one told; refusing is the safer reading. A **landed** blocker is accepted and already satisfied. Duplicate ids are folded.
- **A cycle cannot be filed, only imported or edited into.** A freshly filed task has no dependents, so `TaskFiled` cannot close a cycle. A cycle is reachable two ways: issues that depend on each other on the tracker (neither is imported, and one alert names the path, e.g. `#104 -> #105 -> #104`), and a `BlockerAdded` between existing tasks (refused by the reducer; `ReduceError::BlockerCycle` now carries the path and the HTTP error prints it).
- **A change on GitHub reaches a queued task, never a started one.** `BlockerAdded` and the new `BlockerRemoved` are accepted only in `proposed` and `queued`. For a task past `queued` the change is **not applied**, and an alert says so (`the dependencies of issue #N changed ... task #T is already developing, so it is not pulled back`). It stays until the GitHub side agrees with the task again. Pulling a running task back to `queued` would throw away work the owner can see; holding is for work that has not started. The tracker's edges are remembered in `tracker_deps` (migration 10), so a tracker change is told from an `--after` edge, which is never removed by a sync.
- **Landing a blocker releases its dependents at once.** The release is in the reducer: the landing event removes the blocker from each dependent and emits `WakeScheduler` in the same transaction, and `emit` admits straight after. It does not wait for a poll. `scripts/exit/s42.sh` uses a five-minute poll interval so the only thing that can start the next task is the landing.
- **The ETag does not cover dependencies, so dependencies are asked on a timer too.** On GitHub a dependency edit may not change the issue listing's ETag. The listing is still conditional (an unchanged repository costs one request). When it is unchanged, the dependency lookups for the last listing's relevant issues are repeated every **five poll intervals**, and at once on a manual refresh (`mason task refresh`, a webhook, opening a task). After a changed listing they are looked up for every open issue that is the owner's or carries the label (the ones that can be imported), one request each. That is N requests per changed listing; a repository with hundreds of labeled open issues would want GitHub's GraphQL or a cached per-issue `updated_at`. Not done.
- **One look at a time.** The poll thread and a person's refresh could both run `poll_once` and import the same issue twice; the exit test found it (the same issue became two tasks). A lock now serialises them. The window existed before, and the dependency lookups made it wide.
- **A failed dependency lookup changes nothing.** An issue whose lookup failed is left as it was this poll; it is not read as "no blockers" (which would release it).
- **Body lines only: blockers on issues the listing paged away.** The listing is the newest 100 issues. A body reference to an older issue that is not a task is treated as satisfied (it is not visible and GitHub did not say it is open). Native links say whether the blocker is open, so those are right.
- **Proto and monitors.** `AddTask.after = 7` and `TaskRow.blocks = 18`, additive. The task page shows `waiting for #N` and `blocks #M` (links), in both monitors; the conformance item for the detail carries the same two texts; `features.toml` has `task-dependencies`. The Swift monitor was built (`swift build`); the Compose one was not built here.
- **Gates touched.** This stage adds `scripts/exit/s42.sh` and its fixtures (new gate files under the protected `scripts/exit/**`) and a `task-dependencies` entry in `clients/features.toml` (protected). `crates/engine/tests/matrix.rs` (the state-by-event matrix) gained a `BlockerRemoved` row and its count went from 11 x 20 to 11 x 21: the number of events checked rose, no check was removed. No gate, guard, budget, verdict or trust rule was weakened or changed.
