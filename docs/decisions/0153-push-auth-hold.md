# 0153: a refused push holds landing; the owner chooses the SSH key

On 2026-11-11 tasks #159 and #171 failed at landing with sound work: `Permission to <repo> denied to brian-preffect.` masond's login ssh-agent held only the work key. The owner's fix (`core.sshCommand` in the repository) was ignored, because masond set `GIT_SSH_COMMAND`, which git ranks above `core.sshCommand`.

**Honour the repository's ssh command.** For a network subcommand with neither `GIT_SSH_COMMAND` nor `GIT_SSH` set, `git::run` reads `core.sshCommand` in the working directory and uses it as the base, appending `-o BatchMode=yes -o ConnectTimeout=30 -o ServerAliveInterval=15 -o ServerAliveCountMax=4`. ssh takes the first value of an option, so the owner's key or option wins.

**An auth failure is not the change's fault.** `git::auth_failure` recognises `denied to <user>`, `Permission denied (publickey)`, an https 403 and `Authentication failed`; a timeout or a non-fast-forward rejection is not one. The batch's end (the one place every push path, the candidate push, the PR branch update and the fold's promote, ends in) checks its failure text: on a refusal it holds the project's landing (a `landing` pause owned by `masond:push-auth`, seven days unless lifted) and delivers `Verdict::Held` instead of `Failed`. `land_job` waits out the pause and submits again, so the task stays in landing and no failure is charged. The alert `push-auth:<project>` is derived from the pause row, so it lives exactly as long as the hold and survives a restart; a fetch that fails the same way raises the same key. The pause store has no reason column: the owner string carries it.

**Choosing a key.** `GET /projects/{p}/ssh-keys` lists each `~/.ssh/*.pub` with a private key beside it and each key in masond's agent: fingerprint, comment, `in_agent`, `encrypted` (`ssh-keygen -y -P ''` fails only on a passphrase), `on_owner_account` (the fingerprint is on `https://github.com/<owner>.keys`; base URL overridable for tests by `MASON_GITHUB_URL`), `seen_as` (`ssh -T`, only for a key that can sign without asking). `POST /projects/{p}/ssh-key {"path"}` accepts only a key the list offered, writes `core.sshCommand`, unlocks if needed, probes with `git ls-remote <remote> HEAD`, and lifts the hold only if the probe gets through; otherwise the hold stays and git's words come back. Owner only (`x-mason-as`).

**The passphrase never passes through MASON.** `ssh-add --apple-use-keychain <key>` runs with `SSH_ASKPASS=mason-askpass.sh` and `SSH_ASKPASS_REQUIRE=force`; the script is an `osascript` dialog with a hidden answer on the daemon's own Mac. The passphrase goes dialog, ssh-add, Keychain. It is not a request field, a log line or a store row. Off macOS the request says to run `ssh-add` by hand. The monitors say "Enter the passphrase in the dialog on <host>". The script is `packaging/mason-askpass.sh`, installed beside `masond` (`MASON_ASKPASS` overrides the place).

**Open choices.** (1) The monitors get the action from a `push_auth` banner for a hold, not for a fetch-only refusal (a banner needs a hold to stand on); the alert and the CLI cover that case. (2) The banner's project is the text before the first colon, since `Banner` has no project field and the generated Swift schema is not regenerated here. (3) https remotes get the hold and the alert but the picker cannot help: the fix is a token. (4) `mason doctor` runs a BatchMode `git ls-remote` per project with a remote and FAILs a refusal naming the account.
