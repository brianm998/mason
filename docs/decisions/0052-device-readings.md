# 0052: Device test environments: readings (s25)

Parts 7 and 8 left these open.

- **Naming.** The capability a task leases is `device:<kind>`, with kind one of `ios-simulator`, `android-emulator`, `ios-device`, `android-device`. A suite whose environment has one of those types needs one unit of it; nobody writes it in `uses`. The command is `mason targets list` and the route `GET /targets`, because `mason devices` and `GET /devices` already mean LAN pairing (Stage 24). An environment may add `os = "17"`: the device chosen must have an OS version starting with it. The pool still counts devices of the kind, so an `os` that matches nothing free becomes an environmental wait inside the suite, not a pool wait.
- **Providers are built in, not plugins.** A provider is a trait in `adapter-api` (`DeviceProvider`: `list`, `prepare`, `health`, `teardown`) with a conformance kit (`device_kit::conformance`). The system provider (`xcrun simctl`, `adb devices -l`, `xcrun devicectl`) and the fixture-file fake are the only two. A tool that is not installed has no devices; it is not an error. `prepare` boots only a simulator that is shut down; `teardown` shuts down only what `prepare` booted. Emulators and phones are never started or stopped by MASON.
- **Two layers of lifecycle.** The provider readies and releases the device. The environment's own `setup`, `health` and `teardown` commands run on top of it, with `MASON_DEVICE` set (as `export MASON_DEVICE='<id>'; <command>`, quoted). Order: provider prepare, setup, provider health, health command, the suite, teardown command, provider teardown. The fake provider logs `setup`, `health` and `teardown` per device, and the s25 suites log `suite <id>` to the same file, so the order is checked from one list.
- **Capacity.** The daemon reads the inventory every `poll_ms` (default 2000; the tests use 500), on its own thread with a 10 s limit, and sets each pool's units to the count of ready devices. Zero units gives the scheduler's existing "can never fit" wait, which does not block anyone else; the daemon rewrites its sentence (see below). A new `Broker::set_pool_units` sets the size without writing `limits.kv` and without becoming the owner's fixed limit; an owner's `mason resources limit` still wins. A failed read keeps the last good inventory: a flaky tool is not an unplug. The system provider is read only while some loaded project declares a device environment.
- **A device is a kernel lock.** After the scheduler grants a pool unit the step picks the lowest-id free ready device of the kind and takes a `flock` on `device-<id>.lock` in the locks directory. A holder that dies frees it, as machine classes do. If no device can be taken (it vanished between the grant and the pick, or the `os` prefix matches none free) the suite waits as environmental and tries again.
- **"Immediately".** Plugging a device in is noticed at the next inventory read, so a waiting task resumes within one `poll_ms`. The read ends in `set_pool_units`, which runs the scheduler pass and wakes waiters; nothing else waits for a timer. `s25.sh` allows 5 s at `poll_ms = 500`.
- **Lowering never kills.** If a leased device is unplugged the pool shrinks but the holder keeps its grant. The suite then fails with the tool's own output ("device offline", "no devices/emulators found"), which the built-in signatures classify as environmental: a wait and an alert, never the task's failure.
- **The wait sentence.** `environment problem, not the task's fault: waiting for an iPhone (device:ios-device): none is connected. Plug one in and unlock it; the task resumes when it appears`. It starts with `environment problem` on purpose: `attention.rs` already turns an activity starting that way into an `environment` alert. A wait on busy devices keeps the scheduler's own sentence, which gives the place in line ("Waiting for device:android-emulator: 1st in line, held by #0 ...") and is not an alert.
- **Signatures.** `no-device`, `device-offline-or-locked` and `expired-certificate` are built in (`mason_testing::signatures`, hand-written regexes) and are added at parse time only to a definition with a device environment. A signature of the project's with the same name wins. The ones in the file were written from the documented messages of xcodebuild, adb and codesign, not captured from real runs.
- **Fixtures are hand-written.** The simctl, adb and devicectl fixtures follow the tools' documented output and were not recorded from a real machine. The parsers ignore keys they do not know. A real run (`s25-real.sh`) is the check.
- **Where the code is.** `DeviceType` (in `mason-testing`, which has no dependency on the adapter crate) and `DeviceKind` (in `adapter-api`) are the same four names; the daemon converts by name. This duplication was chosen over making the pure testing crate depend on the adapter API.
- **Left out.** Named pools beyond the four kinds (for example "the lab iPhones") are not built: capability is the kind. Reserving a particular device by id, parallel use of one simulator by two suites, and installing apps are the project's setup command, not MASON's.
- **Changes to existing checks.** The test `every_reference_must_exist_and_every_mistake_is_named` expected the refusal text `must be "local" or "compose"` for an unknown environment type. Types such as `ios-simulator` are now valid, so it expects `must be "local", "compose", "ios-simulator"` (the start of the new message). An unknown type is still refused.
- **Owner approval.** Self-hosting marks `crates/testing/src/model.rs`, `crates/testing/src/env.rs`, `crates/daemon/src/suites.rs`, `crates/daemon/src/sched.rs` and `crates/definition/src/testing_parse.rs` as areas that wait for approval. Each is changed here because the stage cannot be built without it: the environment kinds, the per-device lifecycle, the device pool setter, and the new `type` values. `jobs.rs` (the wait sentence and not defaulting a device pool to one unit) is changed for the same reason. No gate, budget or verdict rule is weakened.
