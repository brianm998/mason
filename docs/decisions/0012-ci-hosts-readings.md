# 0012: Readings made while building GitHub, CI and PR landing (Stage 15)

Where the plan or design left room, Stage 15 chose the following. Any can be overruled.

- **Three small traits, defined here** (`adapter-api::service`): `GitHostAdapter` (open, status, merge, enqueue, close a PR), `TrackerAdapter` (conditional list, mirror, close) and `BuildSystemAdapter` (trigger on a ref, status, `doctor`), each with declared capabilities. Stage 3's traits were only for the agent; the plan's "using the traits" had nothing to use, so these are new. Errors are classified once (`classify`): 404, 422 and other refusals, and 401/403-that-is-not-a-rate-limit are permanent; 429, 403 with a rate-limit header and 5xx or no answer are not.
- **One HTTP seam, `Http`**, with `Curl` for production (the system's `curl`; the request's headers, token included, go to it as a config on stdin, so nothing secret is in the process list; in test mode the network guard refuses anything but loopback) and `Recorded` for tests, which replays a script and fails on any request it was not given. No HTTP crate was added.
- **The recorded responses are written by hand to GitHub's documented shapes, not captured from a live repository** (I have no approved repository to capture from). They are checked against the adapters; they are not evidence about GitHub itself. `s15-real.sh` is where that evidence would come from.
- **Credentials are references** (`env:NAME`, `file:/path`) and the project file refuses a raw token. A missing token is a permanent `Auth` error found before any request is made.
- **GitHub Actions** runs are found by commit (`head_sha`), so the run id is the commit; a push to `mason/ci/**` starts the workflow by itself, and a configured `workflow` is also dispatched. Failed *jobs* are the names the red ladder works with. Only the first page of issues and of check runs is read (100 each).
- **The generic command CI** (`[ci] kind = "command"`: a trigger command and a status command) is Part 11's "no code needed" adapter, and is also the fake CI of the exit test. Jenkins, GitLab CI and the others are not built.
- **A fake git host** (`FakeHost`: a bare repository and a directory of JSON files; checks are a command over the PR head's tree; the merge queue merges at the next look; a reviewer is a file) runs inside the real daemon, so the exit script exercises the real landing code. It is configured in a project file like any host (`[host] kind = "fake"`).
- **`[host]`, `[ci]` and `[tracker]` live in the project file** (the owner's, outside the repository), not in `.mason/landing.toml`: they name accounts and credential references, and a landed change must not be able to point the pipeline at another host. `landing.toml` says only which mode; `service_problems` says what a mode lacks (a remote, a `[ci]`, a `[host]`) and the task is failed with that sentence.
- **Verification is one function.** After the local suites (if the batch tier names any), `direct-ci` and `local-only-ci` push `mason/ci/<project>-b<batch>-<n>`, run CI on it and delete it; the PR modes push `mason/pr/<project>-b<batch>-<n>`, open a PR and wait for its checks. Every place the engine verified before (the first run, the rerun, each half of a bisection, the re-run after a moved base) goes through it, so a CI red really does reach the same ladder, and a moved base really does run CI again. A bisection over CI or pull requests costs a candidate ref or a PR per probe.
- **Candidate refs and PRs are never forced, are unique per probe, and are recorded in the store (`landing_refs`) the moment they are pushed**, so a crash cannot leave one unseen: on restart the project's coordinator closes every PR and deletes every ref of a dead daemon's batches, then sweeps integration branches as before.
- **`local-only-ci` fetches nothing and pushes only the candidate**; it needs a remote (the validator says so) but its base is the local branch.
- **Promotion in the PR modes is the host's merge.** `pr-each` is a batch of one (a PR per task). `pr-batch` merges the batch's PR once checks are green and any required review is given: a review not yet given is waited for and shown as an alert ("waiting for an approval"); *changes requested* (or a PR closed by someone) parks the batch's tasks with that reason. If the host refuses to merge because the base moved, the new tip is folded into the batch's branch and pushed (a plain push), so checks run again, up to `max_fold`. `host-queue` enqueues the PR and waits for the host to merge it; a PR dropped from the queue parks the batch. **Force** lands by the direct fast-forward whatever the mode, since it skips verification by definition.
- **A parked task goes back to development at once**, not when its batch ends: a batch may wait hours for a review, and the culprit has nothing to wait for. (Found by a test: the culprit's verdict sat behind the approval.)
- **A service that cannot answer is not red.** A transient failure backs off (the `Poller`: doubling, capped, a rate limit waiting at least as long as it said) and raises an alert while it lasts; a permanent one raises attention at once and ends the batch with that reason, with no task blamed.
- **The tracker.** One thread polls each tracker project conditionally (ETag; an unchanged answer costs nothing); a webhook (`POST /hooks/github`, HMAC-SHA-256 over the raw body with a secret held by reference, checked in constant time, unknown repository or bad signature indistinguishable) or `mason task refresh` asks at once; a stopped poll gets one more try when asked. **Outside issues and PRs are ignored until the owner labels them**: an owner's issue is imported; anyone else's only with the project's label (default `mason`); PRs are never tasks. Someone else's issue is filed with `Outside` trust, so prompts fence it, even once labeled. **The tracker owns title, body, priority and closure**: an edit there becomes a new event, `TrackerEdited`, applied in any live state; a closure cancels the task. **State goes back out as a comment, or a close when the work landed, best effort**: a failure is logged, nothing waits on it, and it is tried again next look because what was mirrored is only remembered when it worked.
- **`mason doctor`** reads `.mason/landing.toml` on the base, says what the mode lacks, and for GitHub Actions with a CI mode checks that some workflow runs on `mason/ci/**` or `workflow_dispatch` (comments do not count); the check reads the base branch's commit, not the checkout. Stage 26 can reuse `workflow_problems_at`.
