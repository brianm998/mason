# 0049: Account holds, resets and warnings (s67)

Choices the ticket left open. The owner may change any of them.

- **Reset texts.** `mason_core::reset_text` turns a provider's text into an epoch only when the text pins it down: `epoch N` (milliseconds are taken for seconds), or a clock time followed by `UTC`/`GMT`/`Z` (the next such time). A clock time with a **named zone** ("3pm (America/Los_Angeles)") or **no zone** ("try again at 3:00 PM") is *unknown*, because no time-zone database is a dependency and a wrong guess would either hold for hours too long or release too early. Unknown means the backoff probe below. The clock and its zone are still parsed (`reset_text::clock`) so a later change can resolve them.
- **Backoff.** With no usable reset, or for an outage: the first try is `hold_retry` after the hold began, then each refused probe doubles the wait, capped at 30 minutes (or `hold_retry` if that is larger). `hold_retry` stays 60 s by default.
- **One probe.** A held account without a known reset lets exactly one task start a session when a try is due; the claim is in memory, released when that session ends in a refusal (the wait doubles) or in anything else (the hold ends), when the task's job ends, or after 1 hour as a safety net. The probe is the task's real next session (a resume with the hold note), not a synthetic call. The cost: while a probe session that was accepted keeps working, other tasks on the account wait until that step ends. A step that was accepted by the provider lasts at most the step timeout.
- **A known reset** needs no probe: when it passes, the first gate that notices clears the hold and everyone may start. If the provider still refuses, the refusal holds again with the new reset (or the backoff).
- **Merging.** Two sessions that report the same limit extend one hold; a known reset is never replaced by an unknown one; the later of two known resets wins. A `manual` or `budget` hold is never replaced by a provider event.
- **Overage.** Claude reports no block while extra billing is in use, so under `overage = "hold"` (the default) a window that is blocked or at 100% while overage is `in use` holds the account (kind `overage`) until the latest such window resets. Under `allow` nothing is held; an "extra billing" item and banner show while the latest snapshot says overage is in use, with the cost when the snapshot has one. The snapshot is only as fresh as the last session's report, so the item clears at the next report that no longer says "in use".
- **Warnings.** One per account, window and reset, remembered in the store (so a restart does not repeat it). The item exists while that window is still the account's reported one and its reset is in the future. The projection uses the last two readings of the same window and reset: with fewer than two there is none; otherwise "reaches the limit in X, before the reset" or "will not reach the limit before the reset" or "not rising". It is the reported rate only. Readings are thinned to one per 5 minutes (decision 0045), so a projection needs two reports at least 5 minutes apart or a changed state.
- **Budget.** An api account's spend this month (cost the stream reported, since 00:00 UTC on the 1st) is checked after each attempt's tokens. Past `warn_at` of the budget: one warning per month. At 100%: `budget` hold with no end. `mason account release` lifts it and records a waiver for the month, so the spend still being over does not hold it again; the next month starts clean. Raising `monthly_budget_usd` takes effect when the daemon next reads `providers.toml`.
- **Who.** `mason account hold|release` and `POST /account/hold|release` take the actor's name (`MASON_AS`, else `$USER`, else the first owner name) and record it as an intervention (`account_hold`, `account_release`). These count as interventions in the metric, like other owner actions. The pipeline's own holds are not interventions.
- **One item, one banner.** Provider events join the alerts (`account-hold:<account>`, `extra-billing:<account>`, `usage-warn:<account>:<window>:<reset>`) and the header banners come from the same list, so there is one of each however many tasks wait. Kinds: `provider_limit`, `provider_outage`, `provider_overage`, `provider_budget`, `provider_hold`, `provider_extra_billing`, `provider_warning`.
- **Waiting text.** "waiting for claude: usage limit, resets Tue 09:00 UTC (in 2 d 3 h)". It is fixed when the wait begins (a task's wait is an event); the usage page and the alert recompute it every time they are read. Times are UTC (decision 0045).
- **Where the gate sits.** Before a lease is taken for any agent step, and again after it is granted (a hold that began while queued sends the task back to waiting without a lease). A session held in a limit gives its slot back while the account waits and takes one again to resume. Tasks that are not agent steps are not held. Running sessions are never stopped.
- **A snapshot that says blocked** with a reset already past is not a block, in the hold and in the usage page's status.
- **Protocol.** `ProviderStatus.status` gains the value `outage` (besides `ok` and `blocked`); `doing` says what is in force. No field was added. Monitors that only style `blocked` show an outage as plain text; the monitor buttons for release and hold are not built.
