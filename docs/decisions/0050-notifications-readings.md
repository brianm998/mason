# 0050: Notifications, sound and speech: readings (s23)

Part 19 left these open.

- **One reading of "one alert, one reminder, no loops".** An alert is a row in `alerts` (migration 6) for as long as its condition is true. Each channel in the condition's rule gets its first notice once the rule's delay has passed, and the whole alert gets one reminder, `reminder.after` after it began (default 30 min, settable). The reminder goes to the channels that carried the first notice and whose delay was not later than the reminder's: an escalation that only just went out (the hour-mark email, with a 30-minute reminder) is its own nudge and is not reminded. Nothing is sent after the condition clears or the alert is acknowledged. A condition that clears and returns is a new alert (`INSERT OR REPLACE` resets `since`, `acked_at` and `reminded_at`), so it gets a new first notice.
- **Acknowledging stops noise, not visibility.** `acked_at` suppresses every later delivery and drops announcements not yet heard. The alert is still listed (marked acknowledged) while its condition holds, because a failed task cannot clear itself. Acknowledging is owner-only (`POST /alerts/{key}/ack` or `/alerts/ack`, `mason alerts ack KEY`); the identity is the request's `as`, defaulting to the daemon's first owner, as for the other loopback commands.
- **Failed deliveries are retried a few times, then dropped.** Up to `reminder.attempts` (3) tries, `reminder.retry` (1 min) apart; a refusal the channel calls permanent (bad credentials, unknown topic, a channel not configured) is not retried. Every try is a row in `deliveries`, so a restart does not send twice.
- **Quiet hours** are a daily window per channel (`[quiet] push = "22:00-07:00"`), local time. A notice due inside the window waits for the window to end and is then sent if the alert is still true. The monitor is never quiet and never muted. Local time comes from `date +%H:%M` because the standard library has no time zone; `MASON_TEST_MINUTE_OF_DAY` replaces it in tests.
- **The routing table is data with Part 19's defaults** (`mason_core::notify::Routing::defaults`). "Landing" (a frozen base branch or a stuck landing) is routed like a failed task. Daemon down, credentials failing and provider outage are routed to everything including email and the webhook. A kind the table does not name is shown on the monitor only. Overrides are `[routing.<kind>]` tables of `channel = delay` in `<config dir>/notify.toml`, read on every pass, so a change applies without a restart. A table always keeps the monitor.
- **Sound and speech are one announcement.** The first notice on `sound` and `speech` together is one queued announcement (a sound, then one sentence), keyed by alert, run, delivery and channel set, so however often the dispatcher looks it exists once. "Landed" is an event, not a condition: it queues one short speech line per task, and nothing for tasks that had landed before the daemon started looking.
- **Which device speaks: the monitors ask.** A monitor posts `POST /announce/claim {client, muted}` about every 3 s over the command channel it already has (a raw command; no new protobuf message, no regenerated client code). The daemon keeps each unmuted client's latest claim and elects one with `elect`: the current speaker keeps the job while it claims, the owner's `speech.preferred_client` wins when nobody holds it, otherwise the most recently active. Only the speaker is handed the queue, oldest first. A speaker that has not claimed for 30 s loses the job to the most recently active other client. Announcements are handed out once, and anything older than `speech.stale` (10 min) is dropped, as is anything about an alert that cleared or was acknowledged before it was heard. A muted monitor sends `muted: true`: it never speaks, but it counts as present, so the daemon does not speak over someone who muted on purpose.
- **Daemon speech** is off unless `[speech] daemon = true` and a `command` is set (`say`, `espeak-ng`, `spd-say`, or any program that speaks its last argument). It runs only when no monitor has claimed for 30 s, one sentence at a time, waiting for the command to finish.
- **Clients keep their own queue behind a sink.** Announcements play one at a time: the next sound does not start until the previous sentence has ended (the sink calls back). Muting stops what is playing and empties the queue; nothing about banners or the attention count depends on the announcer. States, sounds per family (`decision`, `broke`, `info`) and the voice are stored per device; voices are listed from the OS (`AVSpeechSynthesisVoice`, or `say -v ?`, `espeak --voices`, PowerShell on the desktop).
- **The monitor's old chime stays for an older daemon.** Until a daemon has answered a claim, a newly waiting task still plays the one sound it did before; after that the daemon's announcement is the sound, and playing both would double it.
- **"Daemon down" is raised by the monitor.** The first failed reconnect starts a clock; 15 s later the monitor shows a banner (muted or not) and queues its own announcement; the connection returning clears it and a later loss is a new alert.
- **Channels.** Email goes through `curl smtp://`, with the settings and password in a curl config on standard input and the message in a private (0600) temporary file that holds no secret; `tls = "starttls"` (default) makes curl refuse an unencrypted session, `"tls"` uses `smtps://`, `"none"` is for a trusted local relay. ntfy is `POST <server>/<topic>` with `Title`, `Priority` and `Tags` headers and an optional bearer token; the webhook is a JSON body signed `X-Mason-Signature: sha256=<HMAC-SHA-256 of the raw body>`, which the existing `webhook::verify` checks. A secret can be given inline, as `<name>_env`, or as `<name>_file`; error text has it removed. Each channel passes `notify_kit::conformance`: an accepted message and its reminder succeed, a server error and an unreachable server are transient, a refusal is permanent, and no error contains the secret.
- **Sends run on the definition watcher's thread**, one after another, with curl's 30 s limit. A slow server delays the next watcher pass (definition reloads, pause expiry), not the alerts themselves. Moving sends to a worker pool is a change to make if that shows up in use.
- **Provider outage and credential failures have routes but no new source.** The table names them, but this stage does not add an alert source for them: the daemon already shows a provider outage as a banner and a held task, and raising alerts from those paths touches the provider code that other stages own. They will be notified when something raises an alert with kind `provider_outage` or `credentials`.
