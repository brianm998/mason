# 0775: The full test keeps a record and runs at 01:00 and after 30 quiet minutes, only for a tip not yet fully tested

The owner wants the full test suites to run much less often than once per landing, without leaving changes untested for long. Task #782 gives the existing `ci` schedule kind (decision 0170) a record of its own and a second trigger. It adds no new kind: a `ci` schedule is the full test of a project that has a CI workflow, and the `suites` kind for projects without one comes in a later ticket and will use the same record and the same rule.

**The record** is the `full_tests` table: project, schedule, base commit tested, trigger (`nightly`, `quiet`, `manual`), start, finish, verdict (`green`, `red`, `cut off`) and a link (the CI run). A row with no finish time is running. It is written when the dispatch succeeds, finished when the followed run ends, and read by the one decision below. Because `ci` followed its run by reading GitHub back and kept nothing, nothing before this showed when the full test last ran.

**The tip is fully tested** when the last finished full test with a verdict of green or red (a cut-off one says nothing) is of the tip, or when every file changed since it is one no suite reads (`affected::reads_none`: docs, `*.md`, `scripts/exit/`, the smoke file). That is the README status-block commit after each landing. A running full test counts for its commit, and while one runs no second starts, for any commit.

**One rule.** `mason_core::full_test::decide` (no I/O, no clock) takes the record, the tip, what changed since and returns start or skip with a reason (`the tip abc123 was fully tested at 01:00 (green)`, `a full test of abc123 is running`). The nightly trigger, the quiet trigger and `mason schedule run <name>` all reach it through `ci_schedule::dispatch_as`. The CI host's own check (a run in flight, the globs of `paths`/`paths_from`) still runs after it, so a schedule that had a path rule keeps it. `mason schedule run <name> --force` skips both checks and starts anyway; the row says it was forced.

**Triggers.** `at = "01:00"` as before. New `when_quiet = "30m"` (at least a minute, the same duration words as `every`). A schedule needs `at`, `every` or `when_quiet`; with only `when_quiet` it has no clock. Quiet means no task of the project in `queued`, `exploring`, `developing`, `testing`, `review` or `landing`. A landing batch is tasks in `landing`, and a newly admitted task is `queued`, so neither needs a check of its own. Tasks waiting for the owner (`proposed`, `deferred`, `needs attention`, `failed`) do not count. `QuietTimer` starts when the project goes quiet, restarts when it stops, fires once at the duration and not again until the project has been busy and then quiet again. The timer is in memory (a restart starts the wait again, which at worst delays a run the tip check would allow); the record is in the store.

**Shown.** `mason schedule list` (a line under each full-test schedule), `mason status` (one line per full-test schedule) and the `/schedules` and `/status` JSON (`full`, `full_tests`) carry: the last full test (commit, time, verdict, trigger, link), how many commits and landed tasks since it, a running one, and the next trigger (`nightly at 01:00; quiet for 12 of 30 min`). Tasks landed are counted from the merge subjects of the range (`Merge branch 'mason/<project>/t<N>'`).

**Red.** A red full test files tickets as before (groups, one rerun of failed jobs, cap, dedupe against open tasks and the CI watch). Each ticket now ends with the range since the last green full test: commit count, the range, the tasks landed in it whose changes select suites, and the ones that touched only paths no suite reads. A cut-off verdict is given to a run that was dropped, rerun by hand, or ended with only infrastructure failures.

**Not protected.** Nothing here is verdict logic: a full test files tickets and gates nothing. No file in `PROTECTED` is touched (`suites.rs` and `crates/testing/**` are not).
