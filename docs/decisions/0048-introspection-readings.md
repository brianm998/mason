# 0048: Introspection and recurring jobs: readings (s22)

Part 14 left these open.

- **The history the detectors read is a table, `step_attempts` (migration 16).** The event log says a step failed but not why in a comparable form, and the in-memory world forgets. One row is written when each attempt ends (`Ctx::conclude` in `jobs.rs`): task, project, step, outcome (`green`, `red`, `fail`), the reason, a signature, the attempt number (`retry_n`, 1 for the first try) and the time. Detectors, the verdicts and the digest read tables and the event log, never live state. Also new in migration 16: `findings` (a proposal's metric, its "before" values and its verdict), `schedules` (when each job last ran, and a base-health baseline) and `triage_samples`.
- **Signature:** the reason in lower case with digit runs, hex strings and paths replaced by `#` and `<path>`, so "unknown model fable-9 (request 41)" and "(request 42)" are the same failure.
- **Permanent or transient:** a reason is permanent if it contains one of a fixed list of phrases (`not found`, `permission denied`, `unknown model`, `invalid`, ...) and none of the transient list (`timed out`, `rate limit`, `429`, `503`, `try again`, ...). A reason with both counts as transient, because a missed finding is cheaper than calling a passing error permanent.
- **Thresholds** (all settable under `[introspect]`): a retry loop is 3 retries of one permanent signature in one task, or 5 across a project in the window; the same signature 3 times; no-result rate above 30% of at least 5 attempts; waiting above 60% of active time; 3 force-skips of one suite; landing queue idle 10 minutes with a task ready; the window is 24 hours. These are readings, not facts from the design, and are expected to be tuned.
- **Metrics are rates with their counts** (`num / den` over `n` records), so a window's length does not matter: `retry_loop_rate` (permanent retries per attempt), `no_result_rate`, `repeat_failure_rate`, `wait_share`, `force_skip_rate`, `interventions_per_landed`. `landing_idle_ms` and `expired_switches` are snapshots with no window; a finding may name them, but its fix gets the verdict `unmeasured` and the digest says to check it by hand.
- **Verdict rule:** with at least `min_samples` (5) records since the fix landed, the fix worked if the rate fell to half or less of what it was when found, and did not help otherwise; a metric that was zero cannot have been helped. Fewer samples: no verdict yet, checked again next cycle. A proposal that was cancelled or failed is closed as `abandoned`. A fix that did not help is not filed again by the detector; reverting it is the owner's call from the digest. A fix that worked and later regresses is filed again, judged only on history since the fix.
- **Findings are proposals.** They go through `proposals::file`, so the duplicate, evidence and per-day rules apply and the policy decides `proposed` or `queued` (agent source, so the default is that the owner looks first). A finding with no evidence or an unknown metric is refused before that. Each rule's evidence names the recorded rows and a file to look at (`crates/daemon/src/jobs.rs` for retry loops), which is what routes it to MASON's repository when that is registered.
- **Schedules live in the local overlay**, `[schedule.<name>]` of the project file, not the definition: they are a machine's choice, like paths and accounts. `every` is `hourly`, `daily`, `weekly` or a number with `s`, `m`, `h`, `d`. A job seen for the first time waits one interval, so starting the daemon never fires everything. Kinds: `task` (files a Low-priority task, not again while the last is open), `base-health`, `mutants` and `live` (run a command on a clean checkout of the base branch and compare the failures with the baseline stored in `schedules`; the first run only records the baseline). The comparison uses the schedule's own baseline column and not the testing system's `baselines` table, which is keyed by commit and suite and serves a different question. Base-health runs its command directly on a worker thread, not through the resource scheduler; the tasks it files do go through it.
- **The detector cycle and the analyst are built-in schedules** (`introspect` daily, `analyst:<project>` weekly; `--introspect-ms`, `--analyst-ms`, `--schedule-ms` for tests). `[introspect] enabled` and `analyst` turn them off per project.
- **The analyst is an agent task with a JSON result file.** It is filed at Low priority with the 7-day digest in its body. The agent writes `analyst-result.json` in its worktree (uncommitted); when its step ends the daemon reads it, checks every entry with the rules above and files the good ones. Refusals are written to `analyst-refused.txt` beside the step's logs. This needs no change to the contract or its tools.
- **Digest:** computed on request from the event log (replayed, with time charged to the state each task was in and to its wait reason), `step_attempts`, `debts`, `flaky`, `interventions` and `findings`. Nothing is stored or estimated; a figure with no data is `null`, and `trace` gives the row and event counts it came from. Tokens per landed task are shown as "not recorded" because the daemon does not record tokens per task. Exploring skips are counted by route (`flag`, `clarity`, `classifier`), with how many of those tasks later asked to go back to exploring. Forced landings are the `landing:force` and `landing:land_now` debts, with their reasons.
- **Triage never answers.** The optional command (`[triage] enabled`, `command`, `sample_percent`; off by default) is run on each question and its suggestion (`answer`, `close` or `escalate`, with evidence) is stored. The question still goes to the owner. A fixed share of suggestions, chosen by a hash, plus every one that cites no evidence, is queued for the owner's review (`mason triage review`); the digest reports "questions answered by triage" as 0 and counts suggestions and their reviews. This is a deliberate reading: the design allows triage to answer with evidence, but a wrong answer given on the owner's behalf is worse than an unneeded question, and nothing in this stage can yet show that triage judges well.
- **The Health page reuses the raw GET path** the page already uses for resources (`GET /health`, decoded as JSON in both clients) and adds no protobuf view. A new `HealthView` message would only repeat a JSON body that nothing else needs typed, and would have meant regenerating both clients' protocol code.
