# 0047: Lost step hosts: record why, re-run once, keep tests from killing other tasks' hosts

Task #40, stage s66. Each is the reading taken; change one and the others stand.

- **A lost host never produces a pass, only a re-run.** A host that disappears without an exit record means the command did not finish, so nothing was judged. The step is run again on a fresh host (id ends `-host1`, new log, the old log kept) and is judged only by a completed run: green only if that run is green, red only if it is red. The loss itself is never a red verdict, never a green one, and never counts as evidence. Gates, guards, the verdict logic and the trust files are untouched.
- **AWAITING OWNER SIGN-OFF: the automatic re-run.** It changes how a verdict is reached (a step can now run twice without a failed attempt), so it is its own commit ("Re-run a command step once when its host is lost") and should be approved, or reverted on its own, by the owner. Everything else (the report, the table, the alerts, the safe kill) stands without it: without the re-run a lost host fails the step as before, now with the report in the failure text.
- **Infrastructure retry, not a failed attempt.** The re-run does not change `attempt`, `failures`, the sent-back count (`max_rounds`) or `explore_returns`. It is not the `test_reruns` of 0041 either (that one re-runs a *red* run to tell a flake apart; this one re-runs a run that never ended). Each of those reruns, if it too loses a host, gets its own one re-run.
- **Once.** A second loss in a row fails the step (`fail`, as today) and the text names both reports. The retry index is read from the registry (does `<id>-host1` exist), so a daemon restart in the middle resumes it and does not grant a third host. For the hosted suite runs (`run_hosted`, which the landing batches and test suites use) the same single re-run applies; a second loss there keeps the existing outcome ("could not run") and names both. A landing step runs no step host of its own in this code, only those suite runs.
- **Agent steps keep their resume behaviour.** An agent's host is reattached after a daemon restart and a lost one is retried on the ladder (`max_retries`), which counts as a retry with the same limits as before; none of that changes. Only `test`, `command`, `script` and suite hosts get this re-run.
- **What is recorded.** `LostReport` (step-host registry, read-only; `ClientError::HostLost` is unchanged): host and child pids, whether each is still the recorded process, the signal the host's parent saw, journal length and whether it ends mid-line, last heartbeat, the time. The signal is known only to the process that started the host (a process-global map in `launcher.rs`): after a daemon restart it reads "signal unknown". The time is when the parent saw the host end, or when the loss was noticed. `host.kv` gains `host_start` and `child_start` (`ps` start strings); old entries without them are never signalled.
- **Where it shows.** The step's failure text, `step_host_losses` (store migration 20, written by the daemon, not rebuilt from events, like `step_launches`), `mason task show` (`host lost `test` (re-run once on a fresh host): host pid 1234 gone at 16:16:53, killed by signal 9, no exit record; ...`) and `--json` `host_losses`. The protobuf `TaskDetailView` is not extended (the Swift and Kotlin clients are not regenerated here): the monitors show the failure text, which carries the report. No event kind was added; the history of a re-run is the table, the log line written into the old log, and the `-host1` log.
- **Alerts** come from the table, like the other conditions. Two or more hosts of different tasks lost within 5 seconds of each other (chained: each within 5 s of the one before) raise one alert, "N step hosts were lost at the same time (tasks #12, #15): something killed them", listing each report. A task whose re-run host was lost too has its own alert. A single loss that the re-run answered is only in the task's history, not an alert. Alerts last one hour after the loss.
- **Tests kill only what they started.** `reap_dir`/`reap_verified` (and `step-host-ctl reap ROOT`) signal a host only if its pid still has the recorded start string and a command line naming `step-host` and its directory, and a child group only if the pid has the recorded start string and leads its own group. Pids 0 and 1, our own pid and group, and entries without start strings are never signalled. `kill_hosts` (daemon tests), the daemon's selftest, the step-host tests and the `scripts/exit` cleanups use it. `s04.sh`, `s06.sh` and `s17-real.sh` only read `host.kv` and kill nothing.
- **Start strings have one-second resolution**, so a pid recycled within the same second of the same command line would pass; the command line check (which names the directory) and the process group check keep that to a host the same test started, in the same second, in the same directory. Not proven impossible, only not practical.
- **The cause of the original loss is still not known.** This change makes the next one explain itself and stops tests from being a suspect; it does not claim to have found it.
