# 1111: "Update masond" updates every node too

On 2026-11-25 the first node (Marmot, arm64) was set up by a hand cross-build, a copy and a hand install, and the owner expected to repeat that after every update. Part of the automation existed (the coordinator pushed its runtime to each node after it had taken over), but a protocol bump stranded every node, nodes lagged each update by a whole cross-build, the monitor showed nothing, and there was no way to push again short of waiting out ten minutes.

- **The push does not look at `node_proto`.** `needs_runtime` asks only whether the node runs or holds the commit and whether there is a build for its architecture. `PUT /node/runtime` and the status keys it relies on (`node_proto`, `arch`, `runtime_sha`, `runtimes`) are named constants in `node_serve.rs` and pinned by a test; a protocol bump may change anything else, but not those. The alternative, versioning the endpoint separately, would need a second contract for a node to find out which to speak; one stable route is simpler.
- **Cross-builds start with the coordinator's build, sends wait for its self-test.** The nodes' packages are built beside the coordinator's own (same compile lease, same build-jobs cap, one build at a time), so the nodes no longer start a cross-build only after the takeover. Nothing is sent until the coordinator's build has passed, so a build that fails cannot leave the nodes on a commit the coordinator does not run. This is the only protected-file change (`update.rs`: two calls in `run`, nothing in rollback, the self-test, the no-downgrade rule or the landing drain).
- **A node that is off is not built for, and not waited for.** It is "will update when it returns": the first poll that finds it sends the runtime (a finished cross-build is reused). The wait for builds and sends is capped at `update_wait_max_s`, and a failure never fails the update.
- **Per-node state is computed, not stored.** From what the node reports (running and installed runtimes, a pending takeover) and this coordinator's last try, so it is right after the coordinator's own takeover, when everything in memory is gone. A failed send is an alert (`node:<nid>:update`) while it is failed, not only a log line.
- **`mason node update NAME|--all` starts the sends and answers.** Building takes minutes; the answer lists which nodes started, and `mason node list` shows how each goes. It bypasses the ten-minute retry wait, not the rule that one send per node runs at a time.
- **The `release` channel is left out.** It has no source mirror to cross-build from; a node on that channel is still updated by hand.
