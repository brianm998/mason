# 0018: Readings made while letting the monitors answer and approve (Monitor answers (s40))

Where the task or the design left room, Monitor answers (s40) chose the following. Any can be overruled.

- **Multi-select is not built.** The task says to allow multi-select questions "if the protocol's question type has them". It does not: `DecisionCard` and the agent's `ask` tool carry options and a recommended one, with no "several may be chosen" flag, and the daemon's `pick` takes one option or free text. So the card has option buttons (one click answers) and the Other box, and no check boxes. Adding multi-select means a protocol change (a flag on the card, an answer that names several) and a change to the `ask` tool's schema; neither is made here.
- **The protocol change is additive.** `Hello.actor = 7`, `Welcome.owner = 8`, `Command.approve_hold = 15` (`ApproveHold {task, diff_hash}`), `message Approval`, `AttentionItem.approval = 3`, `TaskDetailView.approval = 17`. No field is renamed or renumbered, and the protocol version stays 1: an older monitor ignores the new fields (it sees no approval view, and its answers still work), and an older daemon leaves `owner` false, so a newer monitor shows the card without buttons and says why.
- **Whether the connection is the owner comes from the welcome.** The monitor says who it is in `Hello.actor` (the same identity it already puts on commands: `MASON_AS`, else the operating-system user) and the daemon answers `Welcome.owner` using the one rule that decides who may answer (`attention::is_owner`, unedited). The clients draw the answer, approve and reject buttons only when it is true. This is a courtesy, not the check: the daemon still refuses a non-owner's command (403), so a client that ignores the flag gains nothing. Until a welcome arrives the flag is false, so buttons appear a moment after connecting rather than disappearing.
- **Rows keep the daemon's list of actions.** `allowed_actions` is the daemon's one list and stays the same for every viewer; only the card and approval buttons are owner-filtered. The detail page's generic Approve/Reject buttons are hidden for a non-owner, and hidden for everyone when the approval view is there (so Approve is never drawn twice, and a hold is never approved without its diff hash).
- **Approving a hold sends the diff hash shown.** `approve_hold` goes to the existing `POST /tasks/{id}/approve` with `{diff_hash}`. If a hold exists and its hash differs, the daemon answers 409 ("not the diff you were shown"); a plain approve with no hash keeps working for the command line, which has no screen to be stale against. The comparison runs before the owner check, so the refusal says the diff moved even to a stranger; it reveals nothing the monitor does not already show.
- **Rejecting a hold cancels the task.** A pending self-hold used to have no reject at all (the daemon refused anything but proposed and approval-step tasks). The hold loop already treats a task whose run is gone as finished, so reject now emits the same `Canceled` event the cancel button does (branch kept), records an intervention (`self_reject`, with the reason), and is the owner's action (403 otherwise). No new state was added; the reason is recorded, not turned into a retry.
- **The diff is shown as a command, with its hash.** The approval view lists the reasons the hold gives (one per touched gate or trust file and per broadened skip: the hold's reasons split on "; "), the diff hash, the branch, and a `git -C <repo> diff <base>...<branch>` line with a copy button. A diff embedded in a view would grow it without a bound and would have to be kept in step with the hash. Opening it is one paste.
- **What needs the owner.** The header count and the Home queue now include proposed tasks, tasks waiting on an approval step, and tasks with an unapproved self-hold, as well as questions (and, in the header count only, failed tasks, as before). A task in both lists is counted once. Clicking the count opens the first task in the Home queue (oldest first); with an empty queue (only failed tasks) it goes Home. No notification is involved.
- **Keys.** Arrow keys move a highlight over the options (it starts on the recommended one; nothing is sent until Return), Return sends the highlighted option, and in the Other box Enter sends and Shift-Enter adds a line. The key logic is plain code (`OptionSelection`, `otherBoxKey`) so both clients and their tests share one rule; the views only wire it to the toolkit.
- **A refusal is shown on the card.** The last failed command's text (for a stale card, "stale: that card has changed ...") appears on the card and on the approval view. It is the model's `lastResult`, which clears on the next successful command, so an old refusal can linger on another card until then; that is judged better than a refusal nobody sees.
- **`monitor-tool` can name what the button would send.** `answer --text`, `answer --hash` (a hash the owner was not shown), `approve --diff`, `reject --reason` and `dump` exist so the exit test can drive the same code the buttons run. `conformance expected --actor NAME --now` plays a non-owner, or reads a real daemon once.
