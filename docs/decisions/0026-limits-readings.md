# 0026: Readings made while limiting only the machine (s48)

This changes `crates/daemon/src/selfguard.rs`, `crates/daemon/src/sched.rs` and `crates/scheduler/**`, all trust files; it loosens a guard and waits for the owner. It also edits `scripts/exit/s44.sh`, a gate file, because its step 5 asserted the old `max_open` rule.

- **The principle.** Limits are for the machine's resources and for work MASON starts for itself. They are never for how many tasks the owner files, holds, queues or spends. Two limits are strict: concurrent LLM sessions (`llm:claude`) and local compile CPU.
- **Why it is safe.** What remains protects the machine (sessions and compile CPU cannot exceed what the machine has, however many tasks are queued) and bounds the loops MASON starts itself: `max_open`, `per_week`, `max_steps` and the cooldown still refuse agent proposals (`OwnerAgent`) and outside issues (`Outside`) exactly as before. An owner-filed task waits in the queue; it does not run faster, spend faster or land without its holds. A person filing tasks is not a loop; a flood from them costs queue rows, not sessions.
- **Plainly: an owner can now file without any count limit.** This also holds for every client that reaches the HTTP API (`POST /tasks` files as Owner) and for a tracker issue by an owner name. Accepted by this change. Not changed: the cooldown after a rollback, which stops every filing and is not a count; holds on protected files; the ad-hoc exit number room in `numbers.rs`, which can refuse owner tasks (flagged for the owner, needs a gate change).
- **`selfguard.rs`.** `check_as` applies `max_open` and `max_steps` only when trust is not `Owner`; `usage` counts open tasks and agent steps of non-owner tasks only. `Usage` gains `yours_open`; `GET /self` keeps its fields and adds `yours_open`. `check` and `check_filing` (strict) still refuse on every count. Tickets #25 (held tasks do not count) and #29 (`max_steps`) are not undone: whichever lands second must keep the owner exemption and the non-owner counts.
- **`--max-concurrent`** no longer limits running jobs; nothing in admission reads it. It remains only as the default of the `llm:claude` limit, now 10, because tests and the exit scripts set it. `resources.toml` `[llm] claude` and a live `mason resources limit` still override it. The limit survives a restart (`limits.kv`), tested by building a second Broker on the same file. Not done: a per-project-definition setting; the limit is machine-wide, so `resources.toml` is where it is configured.
- **The compile CPU gate.** `World` carries an optional `CpuGate { busy_pct, max_pct }`. A request that needs `compile` waits (`WaitCause::Cpu`, "compile waiting: CPU 71% > 50%") while busy >= max, even with nothing else running, and starts on the first pass after it falls. It is checked only when a compile would start; a granted one is never revoked. It is not a count of compiles. Waiters are re-passed every 100 ms, which is the recheck. The scheduler stays pure: the daemon's `cpu.rs` holds the `CpuSource` trait, a sampler thread (one reading a second, average of the last three) and `MASON_CPU_FILE`, a file holding the percentage, used by the exit script. Tests inject `FakeCpu` and never read the machine. `compile_cpu_max` is `[cpu] compile_cpu_max` in `resources.toml`, 1 to 100, default 50.
- **Sources.** Linux: two `/proc/stat` readings 250 ms apart. macOS: `top -l 2 -n 0 -s 1`, the last "CPU usage" line. Unreadable: no gate (the CPU line says so).
- **Not verified.** The macOS source against a real busy machine beyond the parser on fixed text and a run of the sampler here; the Linux source (no Linux host); Kotlin build and tests if Gradle could not be run.
