# 0016: Readings made while building plugins and extensions (Stage 19)

Where the plan or design left room, Stage 19 chose the following. Any can be overruled.

- **Only step types run.** The plan says a plugin can provide a step type, parser, environment or adapter. A parser, environment or adapter changes how the testing system, the scheduler and the services are wired, and none of them has a place to plug in yet. A manifest that provides one is refused with "not yet supported", and the rest of the project loads. The protocol and the manifest already name the kinds, so adding one later changes no plugin.
- **A step type is a variant plus a name.** `StepType::Plugin` is added (not to `StepType::ALL`, which stays the built-in list); a step carries the plugin's type name (`Step::plugin`) and its settings (`Step::config`, JSON). `parse` still knows only the built-in types, so every existing test is unchanged; `parse_with` takes the type names plugins provide. A stored definition (a task is pinned to one) is read with any name allowed, since it was validated when it was stored.
- **Settings are the step's own keys.** A plugin step is written `type = "migration-check"`, `directory = "migrations"`, so the editor's set-field operation and form work on it unchanged. Keys the built-in steps use (`next`, `on_red`, `max_rounds`, `uses`, `budget`, `category`) keep their meaning; a plugin cannot use those names for settings.
- **Validation checks settings against the plugin's schema** (a small subset of JSON Schema, in `mason_plugins::schema`; no schema crate), the category against the manifest's list, and again before running. Without a plugin providing the type, the definition says "no extension provides the step type".
- **The base commit is the only source.** Extensions are read with `git ls-tree` and `git cat-file` from the project's base ref, never from a worktree or a task branch, the same rule that keeps a task's edit of `mason.toml` from changing the checks it faces. The folder's name must equal the manifest's name, symbolic links are refused, and size is capped (500 files, 16 MiB).
- **Approval is by hash, outside the repo.** SHA-256 (written in the crate, with the standard test vectors, so no new dependency) over sorted path, executable bit and bytes. The owner's identity approves (the rule that decides who may answer), the file records who and when, and each approval names a name and a hash: another hash, name or project is not approved. A failing step says `needs approval: mason extension approve <name>` and, if the name was approved before, that it changed. The task **fails** (not waits): the owner approves and files the task again, as with any red result. A waiting state would hide a decision behind a quiet task.
- **No gap between check and run.** The bytes hashed are the bytes written to `<config dir>/extensions/<hash>/`; that copy runs. An existing copy is re-hashed first and replaced if it differs.
- **Palette and forms need no approval.** What the editor offers comes from the manifests and schemas on the base commit; nothing is run to get it. Running needs the approval.
- **Script steps (level 2).** A command step gets `MASON_TASK`, `MASON_TITLE`, `MASON_PROJECT`, `MASON_WORKTREE`, `MASON_BRANCH`, `MASON_BASE`, `MASON_STEP`, `MASON_ATTEMPT` and `MASON_RESULT_FILE`. If the script writes `{"passed": bool, "summary": text}` there, `passed` overrides the exit status (false is red; true is green despite a non-zero exit, which lets a script report a result it computed), and an unreadable result file fails the step. Without `passed`, the exit status decides.
- **Prompt packs (level 4)** replace the default prompt for `explore`, `develop` or `review` from `.mason/prompts/<kind>.md` on the base commit. `{task}` is the task text *fenced as data*; a pack that omits it still gets it, so a pack cannot take the fence off outside text. `{feedback}` is likewise appended when absent, so a retry still learns why it failed. Also `{project}`, `{number}`, `{base}` and `{plan}`. Placeholders inside the task text are not expanded.
- **Timeouts.** `initialize` and `shutdown` get 30 s; `step.run` gets the step's `budget` (default 10 min). A plugin that does not answer is killed. A daemon restart in the middle of a plugin step runs it again.
