# 0009: Readings made while building the SwiftUI monitor (Stage 12)

Where the plan or design left room, Stage 12 chose the following. Any can be overruled, and the layout is the owner's to judge at the checkpoint.

- **A Swift package, not an Xcode project.** `clients/swift/Package.swift` (Swift 6 tools in Swift 5 language mode, macOS 14+) builds with `swift build` and tests with `swift test`, so CI and a contributor need no Xcode project. Targets: `MasonProtocol` (the generated messages, swift-protobuf), `MasonTokens` (generated), `MonitorCore` (connection, state, navigation, search, items), `MonitorUI` (the SwiftUI views), `MasonMonitor` (the app) and `monitor-tool` (conformance dump, screenshots, an answer command). `scripts/bundle-monitor.sh` wraps the app in a `MASON.app` with an Info.plist declaring the `mason://` scheme, which is what makes deep links open it.
- **The client speaks the protocol's JSON encoding** with the generated types, over one `URLSessionWebSocketTask`, reconnecting with a growing pause and saying hello with the last sequence number it saw. A dropped connection shows a banner and turns the tiles to dashes.
- **Everything shown comes from the daemon.** Counts, sort order, allowed actions, waiting text and progress cells arrive in the views; the client has no rule of its own except presentation (which sections the user opened, the search filter, text scale). The one addition to the views was `TaskRow.body` (for search) and `TaskDetailView.route`, `started_at` and `explore_returns` (why exploring was skipped).
- **Search** filters on the client over the rows it has, by name (project and key), title and body, each with its own checkbox. The count in a section header shows the filtered count while a search is active.
- **Collapse choices are per device** (UserDefaults); the server's default (history collapsed) applies until the user chooses. Clicking a count tile expands its section and scrolls to it.
- **Text scale** (⌘+, ⌘−, ⌘0; 80 to 240 percent) scales real text and the spacing and tile sizes from the tokens, so everything reflows; nothing is a zoomed image. The sidebar width grows with the scale up to a limit.
- **Identity.** The monitor sends who it is (`MASON_AS`, else the macOS user name) with every command, since only the owner's identity counts as an answer.
- **The conformance items are built from the same state the views draw**, and each view carries its item id as an accessibility identifier. So `monitor-tool conformance` proves the model shows what the daemon requires at each checkpoint, and a harness reading the real accessibility tree will find the same ids. It does not itself walk the accessibility tree: that needs UI-scripting permission on the machine and a built app bundle, which CI does not have.
- **Screenshots are rendered by the real views** hosted in an off-screen window (`monitor-tool snapshot`), against `masond --demo-manual` at fixed checkpoints, so they need no screen-recording permission and are reproducible. They are not captures of a live window.
- **The Pipeline page is a placeholder** that shows the definition, its steps and any problem, as the plan says; the editor is Stage 18. The Health page shows the daemon's resources, who is waiting and the event-log position.
- **CI.** The Swift client has a job of its own (`monitor-swift`, macOS, 25 minutes) so the 10-minute Rust job keeps its budget; the Rust job's exit scripts skip `s12.sh` (`MASON_SKIP_SWIFT`).
- **Parity file.** The features the monitor now has are marked done in `clients/features.toml` with a `platform_reason` saying the Compose monitor is Stage 13; Stage 13 removes those lines as it catches up. The pipeline editor stays todo in both.
