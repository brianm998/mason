# 0024: A fixed loopback port, and monitors that find the daemon again

Task #23. Each is the reading taken; change one and the others stand.

- **Why a fixed port is safe.** MASON is for one person on one machine. The daemon listens on `127.0.0.1` only, nothing is bound to another interface, and the port was never a secret: any local process could read it from `daemon.json`. A fixed number adds no way in and takes none away. No gate, guard or trust file changes; who may act is decided by the identity on the connection, as before.
- **The default is 7423, not 7421.** The ticket proposed 7421 and asked that it not be in `/etc/services`; it is (`mtportmon`, Matisse Port Monitor). 7423 is not listed there on this machine. `DEFAULT_PORT` in `crates/daemon/src/config.rs` is the one place to change it.
- **Only the binary applies the default.** `DaemonConfig::new` still says port 0, so every test that builds a config gets a free port and parallel test daemons never meet. `masond` resolves the port with `resolve_port`: `--port`, then `[daemon] port` in `<config dir>/daemon.toml`, then 7423; a `--demo` run with neither takes 0, so a demo can run beside the real daemon. The test helper that starts a real `masond` passes `--port 0`, and so do the exit scripts that start one.
- **`daemon.toml` is strict.** Only `[daemon] port` (0 to 65535) is known; anything else, or a file that does not parse, stops the daemon from starting and names the file (the way `resources.toml` is read).
- **A taken port is an error, never a quiet move.** `AddrInUse` becomes exit 1 with the port, the holder (`lsof`, when it can say: pid and program, else "another process") and how to change it. Another daemon on the same data directory is refused earlier by the unchanged single-instance check. A restart does not trip this: the listener sets `SO_REUSEADDR`, and the exit script proves the same port comes back after a kill.
- **Updates keep the port.** `take_over` still passes the port it was on; the self-test (`masond selftest`) binds no port at all.
- **Re-discovery on the client side.** Both monitors take a function that reads `daemon.json` (a port given by `--port` is a fixed answer). After any failure they read it again and retry after 1, 2, 4, 8 s, then every 10 s (a welcome starts the schedule over); while connected they read it every 2 s and reconnect on a changed port, pid or `started_ms`, saying hello with their last sequence number so the daemon sends only what was missed (or a snapshot). They ping every 5 s; 15 s with no message or Pong is a stall and reconnects. All of these show "Daemon restarting, reconnecting…", not an error. The command line reads `daemon.json` again once, after 200 ms, when a connection is refused.
- **mDNS is not added.** Discovery is on the same machine; a stable port solves it with nothing to run. If a remote monitor is ever added, advertise `_mason._tcp` then, in its own ticket.
