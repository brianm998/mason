# 0023: Live step progress, the choices the ticket left open

Task #13 (GitHub #18). Each is the reading taken; change one and the others stand.

- **Throttle: one a second, with an urgent bypass.** A run's output-only change is pushed at most once every 1000 ms (`THROTTLE_MS`, `mason_core::progress::Throttle`). A change of `done`, `total`, `message`, the sub-counts or the state is pushed at once. A burst is one update: the first output after a send schedules the send for `last_send + 1000`, later output only folds in (10,000 lines at one instant give one scheduled send, none immediate).
- **A 250 ms ticker flushes the due sends.** There is no timer per run: one `progress-ticker` thread wakes every 250 ms, sends what has come due and writes the records that are old. So the gap between two output pushes is at least 1000 ms and at most about 1250 ms. The ticker does not run in `--demo` (no work runs there).
- **Persistence every 3 s.** A record is written to `step_progress` when it has changed and the last write is 3000 ms old (`PERSIST_MS`), and once when the run begins and when its job ends while the run is still open (a daemon stopping). Columns, not JSON. A write is on the daemon's own thread, never on the output path.
- **`done` of a step with no reported count is the line count, source `counted`, unit `lines`.** It is replaced for good by the first reported `done`. `total` is empty until something reports one or the history rule offers one.
- **History total = the high end of the middle half** of the `done` figures of this project's successful runs of the step (`middle_half`, the rule `typical()` uses for times, now shared; at least five samples). A total of 0 is not offered (a silent step has nothing to be typical about). It is offered only where there is no real (reported or counted) total, and its source is `history`, so a monitor never draws it as a real total. `step_history` holds successful runs only; it is keyed by run, project and step name.
- **Streams, not one offset.** An agent step has a step host per invocation (`key-1`, `key-2`, …, and `keyuN-…` after a stronger-model retry); a suite step has one per suite. Output is counted per stream (the host's id) by absolute journal offset, and the record keeps a high-water mark per stream. A journal read again (an agent re-followed after a restart, a log re-read) adds nothing. The marks are stored with the record (`marks`, text `stream=offset;…`).
- **Restart rule.** A command or suite step that is found again after a restart first counts the bytes of its log beyond the stored mark (the stored record is up to 3 s old), with the log's modification time as the time of that output, then follows the host from the log's length. The count carries on, nothing is counted twice, and a silent step's `updated_at` is not moved by the restart. An agent's journal is replayed from 0 and deduped by the marks.
- **The record is dropped when its run ends.** Success writes the final counts to `step_history` first. Any other outcome drops it. A run that is still open when the job thread ends keeps its stored row; at daemon start the rows of runs that are not open are removed. The last push for a run says `FILLED` (succeeded) or `EMPTY` (otherwise) with the final counts.
- **The label stays "running".** `ProgressCell.label` is the word it always was; the monitors build "1,240 lines, 3 s ago" from the new fields. The text is theirs to write (ticket #21).
- **Protocol stays at 1.** Only new field numbers: `ProgressCell` 6 to 15, enum `ProgressSource`, `ServerMessage.step_progress = 8`, `Welcome.now_ms = 9`. An older client skips what it does not know.
- **Who hears a push.** `StepProgress` goes to a client whose subscription names the task, or that has a Sidebar or Home view of the task's project (or of all projects). A client with no views (a command-only connection such as the CLI) gets none. A lagging receiver skips ahead: every push carries the whole record. `StepProgress.seq` is the last event sequence number the session has sent, so it never runs ahead of the events the client holds.
- **Times are absolute.** `started_ms`, `last_output_ms` and `updated_at_ms` are instants on the daemon's clock; `Welcome.now_ms` and `StepProgress.now_ms` give the daemon's clock, so a client counts "updated 4 s ago" as `daemon_now + (local elapsed) - updated_at`.
- **`GET /tasks/{id}/progress`** returns the live records of the task's open runs (and so does the `Raw` command). `mason task progress <id> [--watch] [--json]` prints them; `--watch` polls once a second and prints a line only when something moved.
- **Not in this ticket:** real counts for agent steps (#19), for test, command, script, plugin, CI, PR and landing steps (#20), and what the monitors draw (#21). `Daemon::progress_report` and `progress_subs` are the entry points those tickets use.
