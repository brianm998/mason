# 0032: Readings made while changing what counts as an open self-task (s54)

This changes `crates/daemon/src/selfguard.rs`, a trust file; it loosens a guard (what counts toward `max_open`) and waits for the owner's approval.

- **What counts.** `open` is the project's tasks whose activity is neither idle nor held: running, queued and claimable (waiting for a slot, a resource or a not-before time), paused, or waiting on the owner. `held` (shown, not counted) is the tasks blocked by unlanded tasks.
- **Why a held task cannot spend anything.** It has no step run: no agent step starts, no LLM session or resource is leased, no worktree is made, and no slot is taken. `max_steps` counts step runs, so a held task adds nothing to it either. The slot limit exists to bound concurrent work and spend (DESIGN.md Part 13); a held task does neither. Counting it only starved the one task that could run (the chain of #9, #10, #11).
- **Why `max_open` still bounds the work.** A task joins the count the moment its blockers land, which is the moment it can be claimed. So `max_open` still bounds how many self-tasks can be running or claimable at once. What actually runs is bounded further by the scheduler (`--max-concurrent`, resources); a test releases five held tasks at the same instant and checks never more than `max_concurrent` agent steps run.
- **Proposed is not counted. Decided, not incidental.** A proposed task waits for the owner's approval to start and spends nothing, like a held one. This loosens the old reading (every task not landed, failed or canceled). The flood of proposals is still bounded by `per_week`.
- **Released tasks are never refused.** A task leaving `Held` that takes the count over the limit was admitted already; it waits in the queue like any queued task. No claim path consults `selfguard`; only filing does (`POST /tasks`, the tracker import). A new filing is refused only if the counted tasks have reached `max_open`.
- **Unchanged.** `max_steps`, `per_week`, the cooldown after a rollback, the holds on protected files. A flood of held tasks is bounded by `per_week` (for agent and outside tasks); the owner's own held tasks are bounded by what the owner files.
- **Paused** overrides held in the derived activity, so a paused blocked task counts (as the ticket lists "paused"). A cancelled blocker never lands, so its dependents stay held and uncounted until the owner deals with them.
- **Display.** `Status` gains `held`; `GET /self` gains `held`; `mason self` reads "2/3 open (4 held behind others, not counted)" when any are held. The refusal says what was counted and how many held were not.
- **Tests that changed.** Three tests in `crates/daemon/tests/selfguard.rs` filed the tasks they meant to be open as *proposed*; they now file them as queued, since proposed tasks are no longer open. No assertion or limit was relaxed.
- **Not verified.** Monitors (nothing in this repository reads `/self`); real GitHub tracker import against a chain (the s54 exit test uses `--after` through the command line); behaviour with `NotBefore` waits beyond the unit-level count.
