# 0231: waiting requests age, progress is compared as a share of each route, and the owner can set a task's priority

On 2026-11-13 all 19 star tasks in their test step (each needs `compile` + `exclusive`) sat at the back of the resource queue behind 20 mason requests; mason holders kept `test-suite` slots 20-40 minutes and new mason requests kept arriving ahead. An exclusive request only blocks requests ranked after it, so it needs everything ranked before it to drain, and that never happens while another project has work.

**Aging.** `order.max_wait_s` in resources.toml (default 1800; 0 turns it off; a negative or non-integer value is refused). In `plan`, a request with `now - since >= max_wait` is ranked as aged: band 1, between a landing (0) and everything else (2, or 2 + priority when the machine orders by priority first), with progress and priority ignored so the oldest goes first. Once an aged exclusive request is first, `machine_all` stops every later machine-class grant and the machine drains for it. A landing and an interactive caller keep their place (`aged` does nothing to them). `since` is the request's own arrival, so a task step that moves on starts a new wait. Time is `World.now`, so the scheduler stays pure and tests inject it. Requests younger than `max_wait` are planned exactly as before; no limit, gate, capacity or passing rule changed. The wait text of an aged request ends "; waited 30 min: first in line once the machine is free". Aged requests do not weigh priority, so changing the priority of a task whose request is already aged does nothing for it.

**Comparable progress.** Chosen: steps remaining as a share of the shortest start-to-landed path of the task's own definition (`graph::route_length` = `steps_remaining(def, def.start)`), in thousandths, computed with the same `def` that `steps_remaining` uses in `rank_for` and `lease_standing`. Why: it keeps one number, uses the definition's own graph (no new keys, nothing to maintain per step type), is 1000 at the start and falls to 1000/span at the landing step, and so ranks "how far has it come" the same for a 3-step and a 5-step route. Counting only `test` and `landing` steps was rejected: it makes every project's agent steps free, and a definition with no test step (beta in the exit test) would rank as if already landed. The rule stays a plain tuple in `rank.rs`: `(not interactive, band, remaining, priority, enqueued, id)`. `steps()` is still the raw count, which `mason resources` and the explain text show. Without a span the share is steps x 1000, which orders the same as raw steps, so every caller that does not know a span (outside pipelines, tests) is unchanged.

star's test step has `review` after it: 3 of 5 steps left (600) against mason's develop, 3 of 4 (750); star is no longer behind mason's develop work, and still behind mason's own test step (2 of 4, 500) which is further along. (Open question in the task, why mason develop requests count 2: they are `run_check` calls, which `jobs.rs` ranks as the task's test step (`as_step = test_step`), by design, so a develop agent's check queues like the test step it stands in for. Not changed.)

**Priority.** `mason task priority <id> urgent|high|normal|low`, `POST /tasks/{id}/priority`, owner only (`owner_only`; the identity is `x-mason-as`), refused for a finished task. It emits `TrackerEdited` with the task's own title and body and the new priority (the store's record; the reducer already accepts it in any live state), then `Broker::set_task_priority` re-ranks every waiting request of the task (its step lease and its `mason run` leases, noted by `lease_set_task`) with `Rank::with_priority`, which rebuilds the rank from its inputs and keeps arrival time, span, landing and by-priority ordering. Requests of other tasks are untouched. It is recorded as the owner intervention `task_priority`. For a tracker-linked task the row's priority is set and remembered as owed to the tracker; `mirror_out` calls the new `TrackerAdapter::set_priority` (default no-op; GitHub deletes the other `priority:*` labels and adds the new one), and until then a listing with the old label does not take the priority back.

**Why trust files change.** `crates/scheduler/**` and `crates/daemon/src/sched.rs` decide who goes first, and `http.rs` gains an owner-only route; the owner approves. No limit, gate or test was weakened: capacity, the CPU gate, memory, disk and the passing rule for requests younger than `max_wait_s` are as before.

**Tests.** `crates/scheduler/src/rank.rs` (progress share, aged order, with_priority), `explain.rs` (aged text), `crates/scheduler/tests/properties.rs` (exclusive at the back before and after `max_wait`, no machine-class grant ahead of it, granted once holders release; two projects' routes; aging off without `max_wait`; property: every request is granted with aging on and no later request takes the machine from an aged exclusive one), `crates/daemon/tests/task_priority.rs` (re-rank keeps arrival, other tasks unchanged, non-owner refused, `max_wait_s` parsing), `scripts/exit/s236.sh`.

**Not verified:** the GitHub label calls; behaviour across a daemon restart between the command and the label going out (the owed priority is in memory); a live run on the real star/mason queue.
