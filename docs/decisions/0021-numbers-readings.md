# 0021: Readings made while building the numbers MASON hands out (s43)

Where the task text left room, s43 chose the following. Any can be overruled.

- **Two counters, per task, in the store.** Migration 11 adds `number_reservations(task, kind, number, released, at)` with `PRIMARY KEY (task, kind)` and `UNIQUE (kind, number)`. Kind `decision` is a four-digit decision number; kind `exit` is the two-digit number shared by the stage note (`docs/stages/sNN.md`) and the exit scripts (`sNN.sh`, `sNN-real.sh`, `sNN-manual.sh`). Taken in one writer-thread transaction: the next number is `max(floor, every reserved number of the kind) + 1`, where the floor is the highest such number on the base branch (`git ls-tree` of `docs/stages`, `docs/decisions`, `scripts/exit`). A task that asks again gets its row back. A cancelled task's rows are marked released and kept, so the counter never goes down and a number is never reused (gaps are fine).
- **When.** Numbers are reserved when the task is first claimed (`Daemon::admit`, just before `Admitted`). They are also (re)checked at the start of every explore and develop step, so a task claimed before this upgrade gets numbers on its next agent step. Filing and tracker import reserve nothing.
- **Ad-hoc range.** Tasks that do not name a stage draw their exit number from `max(adhoc start, base highest, reservations) + 1`; the start is `MASON_ADHOC_EXIT_START` (default 40). The ceiling is 99, because `scripts/run-exit-scripts.sh` globs `s[0-9][0-9].sh`. Filing a non-stage task refuses (HTTP 409, "used up") when no number is left, counting existing reservations and the base; it does not widen to three digits. Tracker import is not refused; if the range is gone the task fails at its first agent step with the same words.
- **What "names its stage" means.** `Stage NN` (one or two digits, as a word, any case) in the title, or at the start of the body's first line. A passing mention in a body ("task #1, which really was Stage 20") does not count. Such a task keeps NN for its stage note and exit script and reserves only a decision number. Its stage number is not stored and not counted by the ad-hoc counter; if two live tasks name the same stage, or the stage is already on the base, the landing check refuses the later file (see below) rather than a counter resolving it. That is a person's mistake to fix, and the message says which number is taken.
- **The prompt.** `numbers::prompt_block` is appended to the explore and develop prompts (default text and prompt packs alike; a pack cannot leave it out). It states the three paths, says not to look for or take another number, and says not to edit the README status block. The review prompt is unchanged. `prompts.rs` itself is not touched.
- **The landing check.** `landing::check_numbers`, at the start of `submit_and_wait` (before the task joins the queue, so before any fold): the files the branch adds against the merge base (`git diff --diff-filter=A base...branch`) under the three numbered names must carry the task's number, and not a number the base tip already uses in that family. A violation is a `SentBack` verdict (the task goes to the step the landing step's `on_red` names) whose reason and feedback name the file and the file name to use (`docs/stages/s45.md`). Only added files are judged: editing an existing note is not touched. A task with no reservations at all (a demo, or numbers never handed out) is not held to anything.
- **README status line: a generated list, not prose.** The single `Status:` paragraph that every task rewrote is now a block between `<!-- status:begin -->` and `<!-- status:end -->`, one bullet per stage note in number order: the note's `Summary:` line, or its heading when it has none. The long prose that used to follow `Status:` stays as a normal paragraph (it was prose written by hand, not generated); tasks are told not to edit it either. A list is chosen over keeping prose because a prose sentence cannot be built from notes without losing meaning, and because any two tasks now add different files and never the same line.
- **Who writes the block.** `scripts/gen-status.sh` rewrites it; `scripts/check-status.sh` fails when it is stale. MASON runs the generator on the integration branch after a batch is assembled (and again after a moved base is folded in, having first dropped its own earlier regeneration commit so the fold cannot conflict in the block), as a commit "Regenerate the README status block". So the union that is verified is the union that lands. Repositories without `scripts/gen-status.sh` are untouched. `check-status.sh` is not added to CI: a task branch on its own holds a stale block until it lands.
- **A restarted or retried task keeps its numbers**, because they are rows in the store, not in the prompt. A fold conflict's retry, a send-back, a daemon restart and a `retry` all read the same rows.
- **Monitors and CLI.** `TaskDetailView.numbers` (`NumberLine`: kind, number, released, path, source) additive in the proto; `mason task show` prints a `number` line per kind and `--json` has `numbers`; both monitors show them on the task detail (`clients/features.toml` entry `reserved-numbers`).
- **Not done.** A task whose branch was cut before this change and already holds a numbered file under a number that is not its reservation is sent back at landing (it gets numbers at its next agent step or at admission). Nothing renames its files for it. Reservations for projects other than MASON's own are made too (the counters read whatever numbered files the base holds; a project without them starts at the range start), which is harmless but unused.
- **Protected paths this touches** (owner approval): `crates/daemon/src/landing.rs` and `crates/landing/src/batch.rs` (the landing path: the new check and the status regeneration), `scripts/gen-status.sh` and `scripts/check-status.sh` (a gate script that makes the README's status line fail when stale), `scripts/exit/s43.sh` (a new gate script), `clients/features.toml` (a new entry). The prompt text is built in `numbers.rs` and appended in `jobs.rs`; `prompts.rs` is unchanged. No existing check, test or limit was weakened or skipped.
