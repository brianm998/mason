# 0014: Readings made while building self-hosting and gate protection (Stage 17)

Where the plan or design left room, Stage 17 chose the following. Any can be overruled.

- **MASON's own repository is an ordinary project with a `[self]` section** in its project file (the owner's, outside the repository). The section is the only thing that turns protection and limits on, so registering the repository is an act of the owner and nothing in the repository can do it. Its `.mason/mason.toml` is the built-in graph written out, so that changing it is changing a gate; `.mason/landing.toml` lands a batch at a time, direct, after the project's test command (`cargo test --workspace`).
- **The rules are compiled into the running daemon** (`protect::PROTECTED`: path globs with the reason for each, in five groups: gates, verdict logic, guards, budgets, trust, plus the self-change rules). The check never reads the candidate: a branch that rewrites `protect.rs` and adds a file saying nothing is protected is held anyway, and the two files that decide are on the list. The owner can *add* globs (`[self] protect`); no change can remove one. The list is conservative and was written by me from the design's categories; it is the first thing to correct if it holds too much or too little.
- **Where the check runs: before the landing queue, not in the definition.** The landing job asks the daemon about the diff (`base...branch`, paths and `-U0`) before the task may join a batch. This is not an approval *step* in the pipeline definition, because a change to the definition could remove it. A held task waits (with a `WaitStarted` that says why, and an alert that names the command) and nothing else of its batch is affected.
- **An approval is for one diff.** The hold stores the SHA-256 of the diff it was raised for; an approval for another diff does not release it, and the same diff, retried after a restart, keeps its approval. Only the owner's identity approves (as for an answer): anyone else is refused with 403 and the attempt is recorded as an intervention. `mason task approve` sends the caller's identity (`--as` to change it).
- **The weakening scan is line-based over the unified diff, and deliberately blunt.** Per file: assertions removed in excess of added, tests removed in excess of added, a deleted test file, any added ignore/disable (`#[ignore]`, `@Ignore`, `@Disabled`, `.skip(`), any added broadened skip (`|| true`, `exit 0` in a shell file, `continue-on-error: true`, `skip = true`), and a number that went *up* under a name containing limit/max/timeout/budget/cap/threshold/quota/retries/attempts/rounds/ceiling, or *down* under min/floor/required/coverage, matched by name between a removed and an added line. It will hold some harmless changes (renaming a test that is both removed and added is fine; raising a `timeout` for a good reason is held) and will miss anything cleverer. Its purpose is to make the owner look, not to prove anything.
- **Limits** (`[self]`: `max_open` 3, `per_week` 10, `max_steps` 40, `period_h` 24, `cooldown_h` 24): open self-tasks, tasks filed in a week, and agent steps started per period. **Spend is counted in agent steps, not money**, because token cost is not recorded anywhere yet; this is the honest stand-in, and a cost cap belongs with usage tracking. Filing past a limit is refused with the number and the limit by the API (HTTP 429), and the tracker import leaves the item for the next look. The urgent fix task of the landing freeze is not counted.
- **A rollback starts a cooldown and files one proposal.** The loader records the rollback (`runtimes/rollback`); self-tasks are refused for `cooldown_h` from then, and at the next start the daemon files one *proposed* task per self project (waiting for the owner, high priority) with the failed build and its recent starts, then marks it filed.
- **Nothing is published.** The proposal is a task in the local database; this stage adds no tracker publishing of self-tasks (the privacy rule in Part 13 is kept by there being none).
