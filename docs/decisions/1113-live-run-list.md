# 1113: what runs where is read from live state, with a registry only where there is none

`place::seen` records placement decisions: an entry outlives its run, and a run a node gave back stays "node". The owner wants to see what runs on each host now.

- **A new list, not a change to `SEEN`.** The decisions explain why a run went somewhere and are still shown as the `where` lines. The list of runs in flight is `running.rs`.
- **Derive where the truth already exists.** GitHub runs are the remote holds (which survive a restart, so adopted runs show); agent sessions are the `llm:` lease holders; each is removed by the code that ends the run. Registering them a second time would give two answers that can differ.
- **Register where nothing else knows.** A node run is known to the coordinator only while it follows it, so `node_exec::follow`, the one place every node job passes (suites and checks), holds a drop guard. A job a node gives back leaves the node when `follow` returns and the next host enters it. Local checks and command steps do the same.
- **Local suites are read from their step hosts, so no protected file changes.** `suites.rs` decides verdicts. The hosts it starts are the ones with a `run.key` file and, while running, no `exit.kv`; the suite's name is the longest of the project's suite names that ends the host id. The cost is two file checks per host directory each time the list is read. The alternative, a guard in `suites.rs`, would be simpler code and a change to a gate for a display. `sched.rs` needed nothing: `llm_holders` and `load_reading` were public.
- **An agent that waits on its own check shows twice** (the session here, the check where it runs), because both are true. `ActiveModel.state` is as before: `working` while the session is held.
- **Hosts are listed whether or not they run anything.** This Mac, every paired node, and GitHub when a project has `[remote_runs]` or a run is out there. A project filter drops runs, never hosts.
- **Every host's line says whether it takes new work, and why not.** A node's words are the ones `mason node list` gives (`not accepting (updating to runtime 57cb926816: waiting for 3 jobs to end)`), plus `not accepting (full: 2 of 2 jobs)`. This Mac says `not accepting:` with the heat hold or a limit of 0 (`place::cannot_run_here`), or a placement of `remote` with no fallback for every project, and `accepting, but not for <project>` when only some are. GitHub's line comes from the broker's `gha` view, the one `mason resources` prints (read through the public `snapshot`, so `sched.rs` is unchanged): `accepting: 14 of 20 runners in use (MASON 6, other workflows 8 running, 20 queued: ...); macOS 5 of 5`, or `not accepting: the account is full` / `macOS runners full` when a MASON request waits and the account or the macOS pool has no unit left. A request that waits while there is room is not a refusal; it is granted at the next pass.
