# 0051: LAN access, pairing and phones: readings (s24)

Parts 16 and 20 left these open.

- **A second listener, not a wider first one.** Loopback is unchanged (same port, same trust, no token). With `[lan] enabled = true` in `daemon.toml` (or `masond --lan`; `--lan-port N` and `[lan] port`, default 7424, 0 for any), a separate listener binds `0.0.0.0` and serves the same routes over TLS. Off is the default and nothing listens beyond `127.0.0.1` then. `daemon.toml` is parsed strictly: a bad `[lan]` value stops `masond` with `daemon.toml: lan.enabled must be true or false` and the config directory named.
- **Every route needs a token on the LAN listener; the only open route is `POST /pair`.** Tokens are 32 random bytes from `/dev/urandom`, `mt_` + 64 hex, shown once, stored only as SHA-256 (migration 19, `devices`). A copy of the database holds no working token. The token goes in `Authorization: Bearer` on every request, including the WebSocket upgrade. `Hello.token` stays reserved: the upgrade is refused with 401 before a Hello can be sent, so an unpaired client reads nothing and no Hello is needed to check. A token is looked up on every request, so revoking is immediate.
- **Roles come from the token, never from a header.** `x-mason-as` is removed and replaced: an owner token acts as the daemon's first owner identity (`--owner`, else the user), a viewer as `viewer:<id>`, which is not an owner. A viewer passes `GET`/`HEAD` and subscribe, and gets 403 on everything else, on `/devices`, `/pair/codes` and `/lan`, and on any typed WebSocket command (checked against the command's method and path in `run_command_as`). The rule is a pure function, `mason_core::access::decide`. An owner token may do everything the loopback CLI can, including issuing codes and revoking devices; that is a wide grant, and the reason to pair a viewer instead for a device that only needs to look.
- **Pairing codes.** Eight digits, uniform, from `/dev/urandom`; single use; valid 120 s; issued by `POST /pair/codes` (loopback, or an owner token), role `owner` (default) or `viewer`. The code state machine is pure (`access::Pairing`). One failure count covers all codes, since a guesser does not know which it is hitting: after 5 wrong tries every outstanding code is voided and `POST /pair` answers 429 until a new code is issued. Eight digits and five tries is about 5 in 10^8 for a guess. The cost is that a hostile LAN client can burn the owner's code by guessing; the owner just issues another. Status codes: 400 malformed/wrong, 410 expired, 429 locked.
- **TLS and the pin.** A self-signed certificate and key are made once with `rcgen` into `<data dir>/lan/` (key `0600`) and reused, so the fingerprint is stable across restarts. The fingerprint is the SHA-256 of the DER certificate, 64 lowercase hex characters. It travels in three places: the `mason://pair?host=H&port=P&fp=F&code=C` string (the QR payload), the mDNS TXT `fp`, and `GET /lan`. Clients pin it and ignore the certificate chain and host name (a phone cannot validate a self-signed LAN cert any other way). A client that pairs stores its token keyed by the fingerprint, so a daemon whose certificate was replaced finds no token and must be paired again; that is the "changed certificate is rejected" rule.
- **mDNS.** `mdns-sd` advertises `_mason._tcp.local.`, instance `MASON on <hostname>`, TXT `proto` (protocol version), `fp`, `version`. It uses the system's interfaces, so it is noisy in the log on a machine with many virtual interfaces; a failure to advertise is a warning, not a stop. `GET /lan` returns the record that was handed to the advertiser, which is what `s24.sh` checks; whether another device on a network actually sees it is not testable here.
- **Crates.** `tokio-rustls`/`rustls` (the `ring` provider, no C build), `rcgen`, `mdns-sd`, `sha2`, `hyper-util` (to serve the router over the TLS stream with upgrades). Hand-rolled cryptography stays out. The older hand-rolled SHA-256 in `adapter-api` is left alone.
- **Welcome gets `role`** (field 10, additive): `owner`/`viewer` on the LAN, empty on loopback. `owner` is set from the role on the LAN and from `Hello.actor` on loopback as before.
- **Phone apps.** The Swift side adds `Pairing.swift`, `PhoneLayout.swift`, a Bonjour browser in `Discovery.swift`, and a `MonitorPhone` target (SwiftUI with no AppKit) for the iOS app, whose Info.plist declares `NSLocalNetworkUsageDescription` and `NSBonjourServices`. The Compose side adds `Pairing.kt` and `PhoneLayout.kt` to the core and an `android` module with NSD. The phone layout is one list: tiles that scroll sideways, then the Home row, then sections, Landing and Usage; choosing a row pushes its detail (`PhoneNav`).
- **Deliberate differences** (graph editing, log deep-dives, agent sessions) are recorded in `clients/features.toml` as `[phone.*]` tables the parity gate does not read. Adding `ios`/`android` columns to `CLIENTS` in `features.rs` would change a gate and waits for the owner.
- **Background alerts** use the existing ntfy channel (Stage 23): a phone subscribes to the owner's topic with the ntfy app. No push service of ours is built.
