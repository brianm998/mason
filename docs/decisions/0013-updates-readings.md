# 0013: Readings made while building self-reload and updates (Stage 16)

Where the plan or design left room, Stage 16 chose the following. Any can be overruled.

- **Configuration of the source is `<config dir>/update.toml`**, outside the repository (like `[host]` and `[ci]`): `repo` (a path or URL `git` can clone), `channel` (`stable`, `main` or `branch:<name>`), `build` (default `cargo build --release --bins`, run in a clean copy of the commit), `out_dir` and `bins`. Without it there is nothing to update from, and the command says so.
- **Channels.** `stable` is the newest `v*` tag (version-sorted), `main` is the tip of `main`, `branch:<name>` the tip of that branch. They resolve against a bare mirror of the source kept in `runtimes/source.git`, fetched at every update. `--sha` names an exact commit instead.
- **Runtimes are immutable and complete or absent.** `runtimes/<sha>/` holds the binaries and a `READY` file written last; the build happens in `runtimes/src/<sha>/`, a copy made with `git archive` (so never a checkout that can move, and no `.git`), and is renamed into place only when everything was copied. A failing build leaves nothing that looks complete, and building what is built is a no-op. `runtimes/current` and `previous` name the runtimes; a runtime that crashed and was rolled back from goes in `runtimes/bad`.
- **The new build tests itself, not the old one testing it.** `masond selftest --db COPY` runs in the *new* binary: (1) its migrations on a copy of the real database (a `VACUUM INTO` copy), which must open and verify; (2) the five golden event logs from earlier builds, compiled in, which must replay to landed; (3) a scripted task in a sandbox of its own (a scratch repository, the stand-in agent, a throwaway data directory) from filed to landed. It needs `step-host`, `mason-mcp` and `fake-claude` next to it, so a build without them cannot pass. The real database is only ever read, and the daemon takes a backup (`runtimes/backups/store-<ms>-<sha>.db`) before taking over.
- **Takeover is `exec`, keeping the pid.** The daemon records the new runtime as current, lets an event in flight finish, and replaces itself with `runtimes/<sha>/masond` and the same arguments (data and config directories made explicit, and the *same port*, so monitors that reconnect find it where it was). Step hosts are separate processes and do not notice; the new daemon reattaches to them as after any restart. Nothing waits for sessions to end.
- **Rollback by a loader.** `masond --managed` is what a service manager runs. It picks `runtimes/current`, and counts crashes before exec'ing it: a start is a *crash* if the build was not called healthy (alive 30 s by default, `--healthy-after-ms`) before the next start; **three crashes in five minutes** switch to `previous`, mark the build bad, and leave an alert that stands until `mason update ack`. Starts are recorded by the loader and by the takeover, not by the daemon, because a build that dies at once would never record itself. With no earlier runtime it runs the build anyway and says so.
- **No accidental downgrades.** An update to a commit that is a strict ancestor of the running one is refused, saying how many commits it would drop, unless `--rollback` is given. A running version the source has never heard of cannot be compared, which is refused too. Another branch's commit (neither ancestor nor descendant) is allowed. A build in the bad list needs `--rollback` to be tried again.
- **The command is asynchronous.** `POST /update` starts the work on its own thread and `GET /update` reports the phase (`fetching`, `building`, `testing`, `taking over`, `failed`, `idle`) and a log; `mason update` follows it, and finishes when the new runtime answers. A failure at any step leaves the running daemon exactly as it was, and says so. `--check` builds and self-tests but does not take over.
- **Step hosts and clients accept current and previous protocol versions.** Step hosts already did (`protocol::negotiate`, `[CURRENT, PREVIOUS]`, from Stage 5). The monitor protocol now has `MIN_PROTOCOL` (current minus one, never below 1), and the daemon serves any client in the range. Today both are 1, so the range is one version; the rule is in place and tested, not yet exercised by a real bump.
- **A client that is too old is told why.** Outside the range the daemon sends a `Welcome` first (so the client can read `min_protocol` and `version`), then an `Error`, and no views. A monitor whose own protocol is below the `min_protocol` it is told stays read-only (nothing is sent; the banner says why) in both clients.
- **The update banner.** `Hello` carries the monitor's build (`MASON_MONITOR_VERSION`, else `dev`) and `Welcome` the daemon's (the runtime's commit, else `dev`). A banner and an Update button show only when both are real and differ, so development builds never nag. The button's plan: with `MASON_SOURCE_DIR` set to a checkout, build from it (`scripts/bundle-monitor.sh`, or Gradle's `installDist`), launch the result and close this one; with `MASON_INSTALL_URL` (https only), open that page; otherwise say what to set. **Fetching a signed build is not built**: there is no signing or publishing yet.
