# 0061: Releasing, adding and reviving blockers: the readings taken

Task #29, stage s75. Each is the reading taken; change one and the others stand.

- **Only the owner identity may change a blocker.** `unblock`, `block` and `revive` check `attention::is_owner` (the same identity `approve` and `relink` take) over HTTP, the websocket command path and the CLI, and answer 403 to anyone else. A blocker can encode an ordering the owner wanted, so neither an agent nor a viewer device may drop one. The commands change the event set and the holds; they touch no gate, no limit, no verdict and no budget, and `selfguard.rs` is unchanged.
- **`retry` does not revive a cancelled task; `revive` is new.** The reducer refuses `Retried` from `Canceled` (a matrix row and a test pin it). `Revived` takes a task from `Canceled` to `Queued`, only when it was cancelled with its branch kept (`cancel_keeps_branch`), clears nothing else, and asks for the same catch-up with the base as `Retried`. Its worktree, branch and links are untouched. A task rejected while proposed also reads as cancelled-with-branch-kept, so the owner can revive it too; that is the owner's own reversal of their own rejection. `revive` refuses a task whose tracker issue is closed, because the next poll would cancel it again.
- **A failed blocker is retried, not revived.** `task show`, the alert and the monitors name `mason task retry <id>` for a failed blocker and `mason task revive <id>` for a cancelled one. `revive` on a failed task says so.
- **One additive event, `BlockersChanged { task, released, added }`.** Releases are applied first, then each addition is checked for a cycle on the updated world; a refusal leaves the world untouched. Only a proposed or queued task takes it (409 otherwise); releasing a task that is not a blocker is refused (`NotABlocker`); a cycle is refused naming the path (422). Replay applies the same events and gives the same world. The older `BlockerAdded` and `BlockerRemoved` stay as they are (the tracker sync uses them).
- **`block` refuses a cancelled or failed task**, as `--after` does (decision 0020): it would hold the task forever.
- **Tracker interplay.** For an imported task GitHub's relationship and body lines stay the source of truth, with two owner overrides kept in new tables (store migration 21, not in the event log, like `tracker_deps`): a *release* (`tracker_overrides`, kind `release`) and an *addition* (kind `add`).
  - A release removes the blocker and the poll does not put it back: the desired set is GitHub's minus the released tasks. It lapses when what GitHub lists for that issue changes at all (a new blocker, one removed, one removed and later re-added): `tracker_relationship` keeps the last list the poll saw, and a poll that sees a different one deletes that issue's releases first. A change that happens and is undone between two polls is not seen. The lapse is seen only on a poll that asked about dependencies (the sync skips an issue it did not ask about, as it did before).
  - An addition is never removed by a GitHub edit; if GitHub also lists it and later drops it, the owner's blocker stays.
  - The commands take the tracker's poll lock, so a poll cannot read the old overrides and put a blocker back in the middle of a release.
  - Each blocker is marked "from GitHub" (listed in `tracker_deps` for the issue) or "set by you" (everything else, including every blocker of a task that was not imported).
- **The alert for a blocker that can no longer land** is made from the world in `attention::alerts_now` (kind `blocked`, one per held task, key `held-blocker:<task>`), not raised at poll time. It names the commands once, and clears by itself when the task is released or the blocker is revived or retried. It no longer depends on the tracker poll, so it also covers tasks that were not imported. The old text inside the `tracker-deps` alert is gone.
- **Monitors.** `TaskRow.blocker_links = 24` carries each blocker's state, origin and actions; `Command` gains `unblock = 16`, `block = 17`, `revive = 18`. Both monitors draw Release per blocker, Revive for a cancelled one, Retry for a failed one, and an Add blocker field with a task picker built from the sidebar's live tasks (not itself, not already a blocker, not landed, cancelled or failed); a non-owner sees the list and no controls. Conformance items `blocker:<task>:<blocker>` and `add-blocker:<task>` are compared in both.

## What was not verified

- The monitors were built and their core tests run (`swift test`, Gradle `:core:test` and `:app:compileKotlin`); neither app was launched, so the Release, Revive and picker controls were not seen on screen, and the Compose dropdown picker in particular was never clicked.
- The exit test uses command steps standing in for the agent and a fake GitHub (recorded JSON shapes), not a real model or GitHub.
- A real GitHub relationship edit (the dependencies endpoint) was not exercised.
- The conformance expected/check comparison between the daemon and the two apps was not run end to end against live apps; the item lists are built by the same rule in Rust, Swift and Kotlin and each side's tests assert them.
