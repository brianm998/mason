# 0055: Readings made while giving test, script and plugin steps live counts (s70)

- **Only line formats get a live count.** TAP, nextest, pytest, xctest, Swift Testing, Gradle and regex are lines, so passed, failed and skipped can be counted as they arrive. JUnit, Playwright and Cucumber are whole documents (an XML file, a JSON report) that only mean something at the end, so they show lines. The ticket listed Playwright and Cucumber with the line formats; their parsers read a JSON document, so they are left out.
- **One function per line, shared with the full parse.** Each line parser was split into a per-line function that the full parse and the live counter both call (`crates/testing/src/parse.rs`, `live.rs`). The live count at the end equals the full parse by construction, and a unit test feeds every fixture whole, a byte at a time, and split at every position. The nextest and pytest rule that a failure beats a pass for a repeated name is kept in the counter. The verdict is still the full parse and is not touched.
- **`done` is the passed count.** A failed test is shown in the message ("N failed, M skipped"), not in `done`, so `done` against the expected total reads as "passed of 40".
- **Two new sources, `expected` and `minimum`.** The last green run's count and the suite's `min_tests` are real totals (they count toward a percentage) but not the same claim as a step's own `total`, so a monitor can say which it is. Additive in the protocol (`SOURCE_EXPECTED = 4`, `SOURCE_MINIMUM = 5`); the Swift file was regenerated.
- **The last green count is its own table.** `suite_green(project, suite, base, executed)`, written when a suite goes green, read when the test step starts. `evidence` is keyed by tree and a new commit never matches it, so it cannot say what the base's run had. The row for the same base wins; failing that the most recent green of the suite on any base is used, since a landing moves the base (and the exit test's second run would otherwise never find the first's). A suite with `min_tests = 0` and no green run has no total.
- **No history total for a test step.** The typical figure counts a step's `done`, whose unit is lines or a step-reported count; a test step's unit is tests. Mixing them would have shown a wrong total.
- **A step's count is the sum of its suites.** One sub-count per selected suite, created when the step starts. The step's total is shown only when every suite has one. A suite that is reused (green for this exact tree) shows its recorded count as done and total.
- **A progress file reports into its suite.** `done` and `total` it gives become the suite's reported figures and stop the live test count for that suite; its message is prefixed by the suite's name. The file is deleted before each attempt and read four times a second, whole lines only; a last line without a newline counts when the command ends.
- **A script's progress goes to the step.** `MASON_PROGRESS_FILE` uses the same format and applies to the step's own record: a count alone is output-grade (throttled), a total or message is sent at once.
- **After a restart the log is read again.** The live counter is rebuilt from the suite's log from offset 0, then fed what follows, so counts are exact and not doubled. Suites finished before the restart keep their stored sub-counts.
- **Protocol 2 is negotiated by the manifest.** The host speaks the version the manifest names (1 or 2) and the plugin must answer with that number. A `step.progress` from a protocol 1 plugin is ignored at run time and fails the conformance kit. Malformed notifications are ignored at run time and flagged by the kit. Notifications do not extend the call's timeout.
- **Approval says what it waits on.** The approval run's message is "waiting for the owner"; the monitor counts the time from the run's start. Gate steps have no job and so nothing was added.
- **Check counts ride on `PrStatus`.** `PrStatus.counts: Option<CheckCounts>` is filled from the answer the host already gave (GitHub's check runs), so no extra request is made. A host without a list gives `None`. A trait method of its own was weighed and left out for that reason.
- **Landing counts phases, not suites.** A batch's landing run has `unit` "phases", done of 4, and `rollup` leaves a run in that unit alone, so the suites and checks are sub-counts beside it. The suites report into the first member's run and are copied to the others every 250 ms.
- **CI waits have no count.** No build-system adapter lists runs' jobs; they show the waiting message and its start.
