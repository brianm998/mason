# 0019: Readings made while narrowing the self-hold scan (s41)

Where the task left room, s41 chose the following. Any can be overruled. protect.rs and selfguard.rs are trust files, so the change waits for the owner; for each rule that got narrower the reason it is safe and the test that shows it still catches its case are below.

## Which diff is read

- **The scan diffs against the freshest base.** `selfguard::scan_base` picks the local base (`develop`) when the remote-tracking ref (`origin/develop`) is an ancestor of it, else the remote-tracking ref. A stale `origin/develop` made work that had already landed on the local base look like the task's own change (`git diff origin/develop...branch` lists everything the branch merged in from a newer base). Nothing is fetched. *Safe because* the range is still `<base>...<branch>`: only what the branch added since the merge-base, against a base that is never older than before. *Test:* `a_stale_remote_ref_does_not_make_landed_work_the_tasks_own`.
- **A merged-in sibling's unlanded change is still listed.** I rejected "skip the second parent of merges": a sibling's gate change that has not landed would ride through unseen. The three-dot range only drops what the base already holds. *Test:* `a_siblings_unlanded_protected_change_merged_in_is_still_listed`; and `a_base_merged_into_the_branch_does_not_count_as_the_tasks_change` for the other side.
- **Not reproduced on `mason/mason/t2`.** That branch is not in this checkout, so I could not run the three commands on it (see docs/stages/s41.md). The two failure modes are both handled; which one hit #2 is not established here.

## A new file is judged as new

- **Adding a file under `scripts/exit/**` is not held by its path; editing one is, and so is `scripts/run-exit-scripts.sh`.** A new exit script has no earlier version to weaken, and it does nothing until the runner lists it, which is a held change. Only `scripts/exit/**` is exempt (`ADDED_OK`); other gates (`check-*.sh`, workflows, `.mason/`, ...) stay held when added. The new file's content is still scanned: a real `cargo test || true` in it is held. *Safe because* the wiring is held, and the runner here globs `scripts/exit/s[0-9][0-9].sh`, so **a new script there is picked up with no runner change**: such a script that is not weak by the scan (for example one that just `exit 0`s) would pass. That is the trade-off; the owner reads new gate files in review. If it is not wanted, delete `ADDED_OK` and the new-file rule goes away (one line). *Tests:* `a_new_exit_script_is_not_held_by_its_path_but_edits_and_the_runner_are`, and scripts/exit/s41.sh.
- **A bare `exit 0` is flagged only in an existing file.** In a new script it is a first line, not an early exit that cuts a test short. *Safe because* in an existing file it is flagged as before. *Test:* `a_bare_exit_zero_is_flagged_in_an_old_file_and_not_in_a_new_one`.

## `broadened skip` for `|| true`

A `|| true` is not flagged when every operand before it ends in a cleanup or probe command (`kill pkill killall rm rmdir unlink wait trap command which type test [ [[ pgrep`), looking at the last simple command after `;`, `&&`, `|`, `do`, `then`, `else`; or when the same line goes on to `exit N` with N not zero. Anything else is flagged exactly as before (`cargo test || true`, `grep -c x || true`, a pipeline ending in anything else). *Safe because* the words are ones whose failure is not a test result; a check cannot hide behind them without being named by them. *One test per idiom* (each with a sibling in the same diff showing a real `|| true` still gives exactly one finding): `a_kill_cleanup_...`, `an_rm_cleanup_...`, `a_wait_cleanup_...`, `a_trap_is_not_...`, `a_command_probe_...`, `a_kill_chain_...`, `a_diagnostic_then_a_failing_exit_...`. A probe word used as a wrapper (`test -f x && cargo test || true`) ends in `cargo test` and is still flagged.
- `2>/dev/null` was never a finding, so nothing changes for it. `#[ignore]`, `@Ignore`, `.skip(`, `xit(`, `continue-on-error: true`, `skip = true`, `skip: true`, lowered floors, raised limits, removed assertions, removed tests and deleted test files are unchanged. `xfail` and allowlist entries are **not detected today and are not added here**; the issue's wording suggests they should be, which is a separate change.
