# 0015: Readings made while building the graphical editor (Stage 18)

Where the plan or design left room, Stage 18 chose the following. Any can be overruled.

- **The daemon owns the editor; the clients draw and send operations.** `mason_definition::editor` applies small operations (insert a step after another, remove, connect an edge, set a field, rename, set the start, bind a level, set a suite's level, move a node) to the *text* of the pipeline with `toml_edit`, so comments, blank lines, key alignment and ordering survive and a one-field edit is a one-line diff. The daemon keeps a **draft** per project (the pipeline, `landing.toml` and the layout sidecar, with a history for undo and redo), builds the model a canvas draws as an `EditorView`, and applies it. The monitors send operations as `raw` commands to `/projects/<p>/editor/...`; so does `mason editor`, which is how the exit test drives it without a screen.
- **A refused edit changes nothing, and "worse" is defined.** An operation is refused if the result does not parse or has a problem the text did not already have (compared as path and message). So a definition that already has problems can be edited toward a fix, and an edit never adds one. Inserting a step is therefore one operation that **splices** it into the graph (it takes over what the step before led to) rather than "add, then connect": a step nobody can reach is itself a problem. Removing a step reconnects what led to it. A step created with some settings (`command` for a command step) carries them in the same operation, and the palette says what each type needs.
- **`extends` is real.** The plan said "create a step with `extends`", but the definition format had no such key. A step may now `extends = "<step>"`: it takes every key that step (and the one it extends) has and it does not set itself; a missing parent or a loop is a problem on the `extends` key. It is inheritance of settings at read time, one name deep at a time, resolved before the step is checked.
- **Layout is computed by the daemon; hand placement goes in `.mason/layout.toml`.** A node's lane is its category, its column its order along the graph from the start (loops back do not count), so two steps in one lane sit side by side. A node dragged by hand is written to the sidecar (`[node.<name>] x = .. y = ..`) and never touches the pipeline; the sidecar follows a rename and loses a removed step. It is committed with the pipeline.
- **Forms come from JSON Schema.** For the selected step the daemon sends a schema for its type (with the real choices filled in: this pipeline's suites, agent profiles, resources, the categories that type may have; an `x-order` for the order fields appear in, since a JSON object has none) and the values the text sets. The clients render strings (with choices), whole numbers, switches, lists of choices or text, and tables of whole numbers from the schema alone; a plugin's step type, when there are plugins, gets its form by sending a schema. Edges are not form fields: they are drawn and picked.
- **The test grid is bindings made visible.** Rows are suites (with their level, changeable), columns the points where a level can run (development, test step, batch, after landing, schedule); a tick binds *the suite's level* there, so every suite of that level runs there too (the page says so). With no bindings at all the engine runs every suite in the test step, and the grid shows that.
- **The landing editor edits `landing.toml` the same way** (`mason_landing::edit`): mode (with the seven choices), window, batch size, parallel batches, the fold limit, a conflict resolver, tiers (suites, `on_red`, `ci`) and the red ladder's rungs and order, refused if the file would not be a valid configuration (a CI tier under a mode without CI says to use the CI mode).
- **Simulate** walks scripted tasks through the draft with the real reducer (the dry run of Stage 4): the standard scenarios, or one the person writes (`test: red, red`).
- **Preview says what an apply does**: the unified diff of the three files, the changes in words (steps added, removed or changed; suites; what runs where; "changes how the project lands"), and which running tasks are in a step the change touches ("2 task(s) in `test` will finish on the old version": each task stays pinned to the definition it started under). On MASON's own repository the editor says `.mason/` is protected.
- **Apply is the owner's act and goes to the base branch.** Only the owner's identity applies (the same rule as an answer). It refuses a draft with problems, an empty one, and one whose files changed on the base since it began (discard and start again: a three-way merge of a pipeline is not attempted). In a direct landing mode it writes the files in a throwaway worktree on the base tip, commits (as the person, with a note that it was edited in the monitor) and promotes by fast-forward (a push, or the local branch in `local-only`), then the daemon reloads. Where the landing mode uses pull requests it pushes `mason/edit/<project>-<ms>` and opens a PR, and nothing changes until it merges. A clean draft follows the base as it moves. The apply is recorded as an intervention. On MASON's own repository, applying edits to `.mason/` is the owner's own act and is not held (the hold is for tasks).
- **The environment-failure edge is not drawn.** Environment failures are not an edge in the definition (a suite that cannot get its environment waits and retries, charged to no task), so the canvas has success edges and red edges only; an edge for it would need the definition to have one.
- **Conformance** is machine-checked for the editor too: `conformance editor-expected` makes the list of what the editor shows (lanes, each node with its problems, edges, grid rows, problems, what may be done to the draft) from the daemon's view, and both monitors' tools (`monitor-tool editor`) dump the same list from their own state; they match, with and without a step selected. It needs a real daemon, because the demo has no repositories.
