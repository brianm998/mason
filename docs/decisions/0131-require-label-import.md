# 0131: `require_label`: the label alone decides on a shared tracker

MASON imported an issue when `by_owner || labeled`; the project's `label` mattered only for an outsider. A tracker shared with another pipeline (star, stage 27: starpipe keeps `pipeline`, MASON claims `mason`, the owner files both) needs the label to decide for everyone. On 2026-11-11 the first poll of star imported all 34 of the owner's open issues, none labelled `mason`.

**`[tracker] require_label`**, a bool, default `false` (today's rule, unchanged). When true an issue is imported only if it carries `label`, whoever filed it. Trust does not change: the owner's issue is filed with `Owner` trust, anyone else's with `Outside`. One function (`admitted`) decides, and the three places that asked (the native blocked-by read in `poll_once`, the adoption of `(GitHub #N)` tasks, the new-import candidates) call it. The pending list and the "blocked by open ... which MASON has not imported" alert read the same state, so they follow without a change: with the key on, a labelled issue blocked by an unlabelled open one waits and says so; an unlabelled issue is not MASON's, so being blocked by a labelled one raises nothing. A non-boolean value is refused at load, naming `[tracker] require_label`.

**Canceled tasks of unlabelled issues are not listed.** The "link a live task with relink" waiting entry is skipped when the key is on and the issue lacks the label: it is another pipeline's issue.

**Labelled after the cancel: import it as a new task** (the recommended option; relink stays available). With the key on, an issue whose task is canceled and which now carries the label is filed again, through the normal import path (limits, dependencies, proposed/queued, trust all apply). To tell "labelled after the cancel" from "labelled at import, then canceled", the store keeps a `labelled` column on each tracker item (migration 24, append-only, NULL until the first look after the upgrade), written at import and on every look. The rule re-files only when the row says `labelled = false` (it was seen without the label), the issue is open and labelled now, and the task is Canceled. A row that was labelled at import and was canceled stays tied to the canceled task and is listed with the relink reason, as today: the owner canceled work the label asked for, and putting the label back changes nothing. If the new import is refused (a limit) or waits (a blocker), the old row stays, still `labelled = false`, and the next look tries again. A row with NULL is never re-filed: the first look after the upgrade only records the state.

**Why a column and not "unlabelled now, labelled later" from the last listing.** The poll keeps no history across restarts, and a cancel can come between two looks; the row is the only thing that survives.

**Not done:** removing the label from an issue does not cancel its task; the task is the owner's by then. With the key off the column is still recorded, but nothing re-files.
